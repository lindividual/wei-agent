# 用本地模型压缩 tool call 返回：一个跑过的测量

这个目录不是为了做功能，是为了**在写代码之前把账算清**。它回答一个问题：

> 用本地模型压缩工具输出（再顺带优化上下文压缩），值不值得做？收益从哪来，代价在哪？

结论是**收益的方向和直觉相反**，而且最大的一笔账跟模型无关。下面是证据。

目录里没有一行是 app 的一部分，删掉整个目录不影响任何东西。所有脚本都只读
`~/.wei/sessions`，从不写入。

---

## 0. 环境先说清楚：这台机器上 Apple Foundation Models 不能用

`afm/` 是给 Apple 端侧模型写的测量工具，`swift build` 通过、逻辑跑通，但**一次推理都没成功**：

```
model: unavailable(deviceNotEligible)
contextSize: 4096
→ GenerationError.assetsUnavailable: "This device does not support Apple Intelligence."
```

机器是 Mac14,2（M2、8GB）、macOS 26.5.1、region 中国。`eligibilityd` 数据库里说得更直白：

```
OS_ELIGIBILITY_DOMAIN_FOUNDATION_MODELS  →  DEVICE_REGION_CODE = 2（不通过）
```

**所以下面关于模型的数字全是「算术 + 已建好但跑不起来的工具」，不是实测。**
承认这一点比含糊过去重要：模型质量（摘要能不能保住路径、延迟多少毫秒）在这台机器上
**没有数据**，而这恰好是决定成败的那个数。工具已经验证到「能编译、能读语料、能优雅地报告
设备不支持、能写出评分脚本要的 JSONL」，换一台符合条件的机器直接跑即可。

## 1. 语料与工具链

| 文件 | 做什么 |
|---|---|
| `corpus.py` | 从会话日志里取出**模型真正见过的消息流**，写成 `data/messages.jsonl`；另写 `data/candidates.jsonl`（>1KB 的工具结果，即压缩候选） |
| `surface.py` | 工具输出在哪、瘦身已经免费拿走多少、剩下多少 |
| `rig/`（MoonBit） | 用 driver 自己的编码器复演每次请求，按前缀缓存计费，对比各种压缩策略 |
| `scenario.py` | 瘦身够不着的那部分有多大、暴露面有多大 |
| `afm/`（Swift） | 给端侧模型跑 digest，写 `data/digests-*.jsonl` |
| `score.py` | 给 digest 打分：压缩比、**事实召回率**、延迟 |
| `regret.py` | **§5.5**：窗口该开多大。切边界多花的钱 vs 逼出来的重读，纯日志，无模型 |
| `trace.py` | **§5.6**：把「边界一动，后面全按新价重算」逐请求打出来（讲解用） |
| `esc/`（MoonBit） | 一个测量前提的检查：`Json::stringify` 会不会转义非 ASCII（**不会**，所以按线上字节计数是可用的） |

语料：**37 个会话、27,882 条模型可见消息、13,370 次请求、22.3 MB 工具输出**
（14,242 条结果）。注意这台机器上有个 app 实例在**实时写** `~/.wei/sessions`，所以每次跑的
计数会漂 1% 以内，不影响结论。

复跑（全部从仓库根目录，`data/` 与 `afm/.build/` 已 gitignore）：

```bash
export PATH="$HOME/.moon/bin:$PATH"
cd spikelocalsum
python3 corpus.py                       # -> data/messages.jsonl, data/candidates.jsonl
python3 surface.py                      # 质量与瘦身前后
python3 scenario.py                     # 剩多少、工作量、暴露面
python3 regret.py                       # §5.5 边界能有多小（约 60 秒）
python3 trace.py ~/.wei/sessions/*/*.jsonl | head -40   # §5.6 逐请求看机制
python3 baseline.py && python3 score.py data/candidates.jsonl data/digests-trim.jsonl
python3 score.py data/candidates.jsonl data/digests-marker.jsonl
cd rig && moon run . --target native --release -- ~/.wei/sessions --all   # 经济账（约 2 分钟）
cd ../afm && swift build && swift run afmdigest --candidates ../data/candidates.jsonl \
    --out ../data/digests-afm.jsonl --limit 50 --repeat 10 --verbose
python3 score.py data/candidates.jsonl data/digests-afm.jsonl --examples 5
```

`corpus.py` 里有一处容易错、错了会**凭空发明模型没见过的消息**：会话日志是树，
模型看到的是「从最后一条沿着 parent 走出来的链」（`core/session_context.mbt::Session::path`），
不是文件顺序。被编辑掉的分支、回退过的路径都在文件里，但从来不在请求里。第一版按文件顺序读，
重复消息因此虚高到 12.9%（按链读只有 1.1%）。

## 2. 上下文长什么样

```
1. mass before trimming
   toolResult      14242 msgs    22.31 MB   54.4%
   thinking         6941 msgs    18.19 MB   44.4%
   assistant        6443 msgs     0.45 MB    1.1%
   user              256 msgs     0.05 MB    0.1%
   total                          41.00 MB
```

工具输出占 **54.4%**（README 说的「一半」成立；`read` 单独约 30%），思考占 44.4%。
瘦身（`core/trim.mbt`，免费）之后：

```
   thinking         18.19 MB ->    0.43 MB   (-98%)
   toolResult       22.31 MB ->   16.28 MB   (-27%)
   total            41.69 MB ->   17.91 MB   (-57%)
```

**瘦身之后，剩下的 prompt 里 90.9% 是工具输出。** 这时候直觉会说：那就压工具输出。
下面两节说为什么这个直觉只对了一半。

按大小拆开，工具输出的字节**正好两半分属两种命运**：

| 在哪里 | 结果数 | 字节 | 占工具输出 | 谁能动它 |
|---|---|---|---|---|
| 4KB 阈值以下 | 12,574 | 10.84 MB | **48.6%** | **只有模型**（瘦身连碰都不碰；<1KB 的 2.6MB 连候选都算不上） |
| 瘦身保留的头尾（>4KB） | 1,254 | 11.07 MB | **49.6%** | 瘦身已经在里面了；digest 只能**替换**它，不是净省 |
| 窗口内（recent_window） | 415 | 0.42 MB | 1.8% | 只有缩小窗口，而那是在拿正确性换钱 |

注意上面是**全体**工具结果，所以两行加起来不是 100%。压缩候选（>1KB）是 5,227 个结果 / 19.7 MB：
其中 3,959 个（8.5 MB）落在第一行（纯新增），1,268 个（11.2 MB）落在第二行（只是在换掉瘦身已留的头尾）。
外面那一列是本研究里最反直觉的一条：**模型唯一真正开得出的新地，是那些小结果；
而「大的地方」正是规则已经站着的地方。**

另一个负结果：**完全重复的工具结果只占存活的 1.1%**（1,201/14,242 命中过同样的文本）。
也就是说「同工具同参数、文件没变」这类纯规则能抓的冗余比想象的小得多——1.1%，
不足以支撑任何东西。

## 3. 最大的一笔账：边界在哪里，而不是裁什么

`rig/` 复演每次请求：按 driver 的编码器算线上字节，按前缀缓存计费（命中的按 cache read、
其余按 fresh input），并且用日志里记的 `usage` 校准。整语料（价格取 `deepseek-v4-flash`：
input 0.14、cache read 0.0028 USD/M）：

**下面每一行的裁剪动作完全相同**（同样 4KB 阈值、同样 40 行头 + 20 行尾、同样清空旧思考），
只有 `recent_window`/`advance_step` 这两个数字不同。`wN-sM` = 最近 N 条消息保持原样、边界每 M 条消息才允许前移：

| 策略 | prompt tokens | cache-read | fresh in | USD | 改写% |
|---|---|---|---|---|---|
| raw（完全不瘦身） | 4,303,963,934 | 4,289,399,105 | 14,564,829 | 14.049 | 0% |
| **`shipped-20/8`（现状）** | 2,416,137,347 | 2,365,826,232 | **50,311,115** | **13.667** | 22.6% |
| `shipped-20/1`（同样窗口，边界每步动） | 2,406,242,801 | 2,316,353,041 | 89,889,760 | 19.070 | 51.7% |
| `w1-s1`（最新 1 条保持原样） | 2,350,526,087 | 2,340,127,583 | 10,398,504 | **8.008** | 6.7% |
| **`w2-s1`（最新 2 条）** | 2,354,571,569 | 2,336,597,862 | 17,973,707 | **9.059** | 48.3% |
| `w4-s1`（最新 4 条） | 2,360,282,388 | 2,333,800,295 | 26,482,093 | 10.242 | 52.2% |
| `w8-s1`（最新 8 条） | 2,371,727,423 | 2,328,956,195 | 42,771,228 | 12.509 | 52.0% |
| `w2-s2` | 2,355,445,778 | 2,336,040,654 | 19,405,124 | 9.258 | 50.4% |
| `w4-s2` | 2,361,154,189 | 2,333,442,184 | 27,712,005 | 10.413 | 51.9% |
| `w4-s4` | 2,364,061,342 | 2,337,606,564 | 26,454,778 | 10.248 | 38.5% |
| `w4-s8` | 2,369,897,581 | 2,345,260,974 | 24,636,607 | 10.015 | 23.1% |
| `w2-s1-5+5`（更狠的裁剪） | 1,589,355,829 | 1,572,432,761 | 16,923,068 | 6.772 | 62.6% |
| `w2-s1-marker`（天花板） | 1,327,596,410 | 1,311,581,303 | 16,015,107 | **5.915** | 63.2% |

四条结论：

**① 账单差异几乎全来自「边界放在哪」，而不是「裁什么」。** 裁剪动作一模一样的四行——
`w1-s1` / `w2-s1` / `w8-s1` / `shipped-20/8`——是 $8.01 / $9.06 / $12.51 / $13.67，**差 1.7 倍**。
机削是唯一的机削：供应商的缓存是**字节前缀**，所以一条消息第一次与上一次请求不同，
公共前缀就从那黑断掉，它后面的一切按新输入重算。现状把一条结果**留到 20 条消息之后**才裁，
裁的那一刻它后面正站着整个 recent window，于是被重算一遍。

**② 现状买的是「更晚的裁剪时点」，而它不值这些钱（★ 理由在 §5.5 被改过）。**
从 $13.667 降到 `w2-s1` 的 $9.059，**省 $4.61（34%）**——而这是一次**只改两个数字**的改动
（`recent_window: 20 → 2`、`advance_step: 8 → 1`），`core/trim.mbt` 的架构、可逆性、
`prepared_context` 全都不用动。

这一条原来写的是「一条工具结果的有用寿命是一次请求，而现状买了十次」。**实测不支持这句话**：
不变重读的间隔中位数是 **48 条消息**，一半发生在今天已经裁掉的位置之后（§5.5 C）。
站得住的理由换成**价钱比**：留着的字节每个请求按 cache read 重发一次，
回去重读一次按 fresh input 收一次，**差 50 倍**——所以「之后还想再看一眼」不构成保留的理由，
「会不会被需要 50 次以上」才是。

**③ 保真度的开价是 $1.05，不是 $5.66。** `w1-s1`（最新 1 条保持原样）是 $8.008，
`w2-s1`（最新 2 条）是 $9.059：**多留一条消息多花 $1.05**。而 $8.008 → $0 的极端（完全不投影）是 $14.049。
即：从「从不保持原样」到「最新 2 条保持原样」要多花 $1.05，从那里再到现状的 $13.667 要多花 $4.61——
**多花的这 $4.61 买的不是更长的保真，而是更晚的裁剪时点。**

**④ `advance_step` 在小窗口下几乎不再值钱。** `w4-s8`（$10.015）只比 `w4-s1`（$10.242）好 2%，
而窗口从 20 降到 4 值 25%。`shipped-20/1` 的 $19.070 则说明：**窗口大的时候**量化是必需的
（上一版就是拿这个当 `advance_step` 的理由），但一旦窗口小了，它就退化成细节。

另有一条校准证据：7,250 组「边界没动、只有新消息追加」的相邻请求上，
provider 实际计费 ÷ bytes/4 估计 = **p10 0.80、中位 1.01、p90 1.16**——
`core/context_pressure.mbt` 依赖的那个估计，在增量上基本无偏（±20%）。
另外 `shipped-20/8` 行的 printed/billed = 1.108，说明这套复演确实在描述被计费的那些请求；
`raw` 行 0.622 则说明「不瘦身的推导是实际账单的 1.6 倍」，和 README 里 1.45× 的结论一致。

## 4. 模型能碰到多少？

`w2-s1-marker` 是**任何模型的理论上限**——把每个 >1KB 的结果换成一个什么都不含的标记，
还保持最新 2 条原样，也只要 $5.915。这是「压缩」这个词能兑现的全部。

现实一点：模型不会输出空标记，它会输出摘要 + 要逐字保留的行区间（`afm/Prompt.swift` 里的
`Digest` 结构就是按这个设计的：判别式，不是复述）。所以：

| | USD | 占账单 |
|---|---|---|
| raw | 14.049 | 100% |
| `shipped-20/8`（现状） | 13.667 | 97% |
| `w2-s1`（**不用模型**，只改两个数字） | 9.059 | 64% |
| `w2-s1-5+5`（更狠的确定性裁剪） | 6.772 | 48% |
| `w2-s1-marker`（**完美模型**的天花板） | 5.915 | 42% |

**模型整个可争取的空间是 $0.86（占总账单 6%）**——从 $6.772（一行确定性代码就能到的地方）
到 $5.915 的绝对天花板。这不是「模型没价值」，而是说：**在这套上下文管线里，
最贵的那个变量是边界，不是摘要质量。** 连完全错到 0% 召回的 `marker`，也只比 5+5 规则
多出 $0.86。

**它要处理的群体是「小结果」。** 48.6% 的工具字节在 4KB 阈值以下，瘦身碰都不碰它们——
这是模型唯一能开出新地的地方。而 49.6% 的字节正在瘦身已经保留的头 40 + 尾 20 行里，
对这部分 digest 只是**替换**，不是净省。这跟「先压大的」的直觉相反：
大的地方，规则已经站在那儿了。

工作量与代价（`score.py` 会给实测值，这里只有算术）：

- 候选 **5,227 个结果、15.2 MB 输入**（1KB 门槛、单次输入上限 6KB——端侧 4096 token 的窗口装不下更多）。
- **延迟**：每个候选一次本地推理，且它在**工具路径上**。`afm/` 记录每次调用的毫秒数，
  `score.py` 报中位数和 p90。回合延迟等于 `k × 单次延迟`。
- **暴露面**：`w2-s1-marker` 级别会丢掉 **11.1 MB** 的原始字节（`recent_window` 只护最近 2 条消息）。
  一个被压掉的中间行如果后面又要用，就得重新 `read`——那一次按 **fresh input**（0.14/M）计价，
  而被它替代的字节本来按 **cache read**（0.0028/M）计价，**差 50 倍**。但一个结果留在 prompt 里
  是**每次请求都要重发一遍**的，所以只要它还能活过 0.5 次请求，压掉就是赚的。
  这不是反对压缩的理由，恰恰相反——**但它意味着「宁漏不误」的取舍要偏向「多留」**，
  也就是判别式保留行区间这个设计比自由摘要更稳，以及 §3 的 `w2` 比 `w0` 值 $1.05。

## 5. 事实召回率：怎么判断 digest 好不好

不量「读起来怎么样」，量**该逐字保留的东西还在不在**（`score.py`）。抽取是机械的、
不可自证的，所以只取无歧义的：

- 路径类 token：绝对路径、带斜杠和扩展名的相对路径、`file.ext:line`
- 结果自己标为出错的行（`error` / `failed` / `Traceback` / `panic` / `warning` …）
- 数字串

一个把路径和错误行全留下、其余全丢的 digest 就是合格的；一个读起来通顺但把
`src/agent/loop.ts` 说成「那个 agent 循环文件」的 digest 不合格。这是 `core/facts.mbt`
的同一套思路——**事实用规则保，摘要才是模型的话**，而这也正是 `afm/Prompt.swift` 让模型
「用行区间引用」而不是「复述路径」的原因。

## 5.5 边界能有多小：`regret.py` 量了那个「日志给不出」的数

§8 说「『一条工具结果只需要被完整看一次』是建模断言，不是测量」，`scenario.py` 也把
regret 概率做成参数、并注明「日志给不出」。**失败**确实给不出，但**需要**给得出：
日志里每一次「模型回头去拿它已经看过的东西」都在。`regret.py` 从三个角度量它，
结论是 §3 那个 $4.61 站得住——但站得住的**理由**和原来的说法不一样。

### A. 这笔暴露有多大

`recent_window: 20 → 2` 额外提前裁掉的中间字节（按「每个曾经逐字携带它的请求」计）：

| 量 | 值 |
|---|---|
| 整语料 prompt 字节 × 请求 | 30.8 G |
| 现状策略裁掉的中间字节 | 188.8 M（0.6%） |
| 其中 **#0 提前裁掉的** | **172.6 M（0.6%）** |
| 落在 #0 这条带里的结果数 | **1,482** |

也就是：**今天已经在裁的中间字节，91% 会因为两个数字而提前裁掉**——不是新增一种裁剪，
而是把同一种裁剪提前 ~18 条消息。

### B. 被裁的行还会回来吗？（和「留下的头尾」配对比）

同一批结果、同一时刻，把它**丢掉的中间行**和它**保留的头/尾行**放一起比：

| 总体 | 结果数 | 行数(丢/留) | 行命中%(丢/留) | 结果级命中%(丢/留，行/长 token) |
|---|---|---|---|---|
| 现状已经在裁 | 1,456 | 113,234/61,515 | **37.4 / 13.5** | 50.9/51.2 · 93.8/97.7 |
| #0 提前裁 | 1,482 | 114,428/62,624 | **37.8 / 14.4** | 52.8/55.1 · 95.6/99.0 |

两条读法，都要说清楚：

- **中间行回来的频率是头尾的 ~2.8 倍**（37.4% vs 13.5%）。所以「中间是死重」不成立——
  被丢的那部分**至少**和故意留下的部分一样活。这是**反对**「随便裁」的证据。
- 但在**结果级**上两者几乎相同（50.9% vs 51.2%）：所以「丢掉中间」相对「留下头尾」
  并没有额外的损失形状。而「留下头尾」是**今天已经在做**的事。换句话说：
  **#0 不是引入一种新的丢失，而是把今天已经接受的那种丢失提前 18 条消息。**

（两个数都是下界：改写、记忆里的复述都不算命中。）

### C. 模型回头拿旧字节的频率——以及它花多少钱

`read` 调用 2,065 次，其中 **801 次（38.8%）** 读的是一个**读过、且之后没有被 edit/write 改过**的路径：

| | 次数 | 两次读之间的消息间隔 |
|---|---|---|
| 早先的字节**已经在 w20 窗口之外** | **399** | 中位 **48**，p90 211，max 1485 |
| 仍在 w20 内、且仍在 2 条消息内（#0 下也是逐字） | 217 | 2 |
| 仍在 w20 内、但已超出 2 条（#0 会「逼」它） | **185** | 中位 **8**，p90 20，max 26 |

把「承载这次重读的那次调用」整笔记在重读头上（**上界**，那次调用做了别的事也算进去）：

| | 花费 |
|---|---|
| 全部 801 次不变重读 | $1.253 |
| **其中 #0 这条带里的 185 次** | **$0.259** |

`bash` 侧的同一测量（文件工作在 shell 里，所以覆盖面更宽）：13,155 次调用里 **131 次（1.0%）**
是同一会话里原样重跑的命令——和文档里那条 1.1% 对得上——**间隔中位数 44 条消息，只有 2% 在 2 条以内**。

### D. 所以 §3 站得住，但理由要改

把两边放在一起：

| | 值 | 出处 |
|---|---|---|
| #0 省下的账单 | **$5.62**（$16.296 → $10.673） | `rig` |
| #0 逼出来的重读，记整笔调用 | **≤ $0.259** | `regret.py` C |
| 净 | **≈ +$5.36，21× 余量** | |

而且这 $0.259 还是个**上界**，理由在 C 那一行本身：那 185 次重读**发生在字节还在窗口里的时候**——
它们不是「因为看不见才去拿」，是本来就会发生的重读。真正的新成本是
「w20 下不会重读、w2 下才会重读」的那些，而那从日志里看不到（反事实）。

**要改的那句话**（原文：「一条工具结果的有用寿命是一次请求，而现状买了十次」）：

- 实测**不支持**「有用寿命是一次请求」。不变重读的中位间隔是 **48 条消息**，
  一半（399/801）发生在**今天已经裁掉**的位置之后——也就是说模型经常回去拿窗口早就不给的字节。
  这条断言该删掉。
- 真正支撑 #0 的是**价钱比**：一条结果留在 prompt 里，是**每个请求按 cache read 重发一次**；
  回去重读一次，是按 **fresh input 收一次**。两者差 50 倍（`deepseek_v4_flash_pricing`：
  0.0028 vs 0.14）。所以**「20 条消息之后还想再看一眼」根本不构成保留的理由**——
  留 50 个请求的价钱，等于重读一次的价钱。
- 推论（比原来那句话更有用）：**窗口该由「留 vs 重读」的价钱比定，不是由对「有用寿命」的猜测定。**
  在这个价钱比下，正确的问题不是「它会不会被需要」，而是「它会不会被需要 50 次以上」。

### E. 这一步仍然量不到什么

`regret.py` 是**纯日志**，没有模型、没有反事实。它给不出的是**质量**那一侧：
一个被提前裁掉的中间行如果后面再也没有被拿回来，日志里没有任何痕迹——
这正是 §8 那条「最大的洞」，**没有被这一步补上**。补它只有一条路：
在真实会话上跑 `w20` vs `w2` 的**端到端任务成功率**。经济账和暴露面现在都量完了，
放行条件只剩这一个，而它需要真实的 API 调用。

## 5.6 逐请求地看机制：`trace.py`

`§3` 是整语料的账，`§5.5` 是暴露面。这个脚本回答的是**机制**：为什么「边界放在哪」值钱。
它把每个请求打一行——cutoff、这次要发的字节、能复用的字节、按新价收的 token——
并且用 `rig` 同一套 `trim_text` 和同一个 `cutoff` 公式，所以两边的方向一致
（输出用简化的编码器，绝对值比 `rig` 略低，看**形状**不看小数）。

拿一个真实会话（`2026-09-19T07-12-52 dc420b33`，36 条消息、14 次请求、122 KB 工具输出）：

**现状（`recent_window: 20, advance_step: 8`）**

| req | cutoff | body KB | reused KB | fresh tok | 边界动了 |
|---|---|---|---|---|---|
| 2 | 0 | 3.4 | 0.2 | 836 | no |
| 3 | 0 | 65.2 | 3.4 | 15,803 | no |
| 4 | 0 | 71.4 | 65.2 | 1,589 | no |
| **11** | **8** | **66.9** | **6.8** | **15,377** | **yes** |
| 13 | 8 | 71.2 | 69.6 | 408 | no |
| 14 | 8 | 71.3 | 71.2 | 26 | no |

**#0（`recent_window: 2, advance_step: 1`）**

| req | cutoff | body KB | reused KB | fresh tok | 边界动了 |
|---|---|---|---|---|---|
| 2 | 2 | 3.4 | 0.2 | 836 | yes |
| 3 | 5 | 65.2 | 3.4 | 15,803 | yes |
| **4** | **8** | **16.3** | **6.8** | **2,436** | **yes** |
| 5 | 11 | 30.7 | 13.6 | 4,370 | yes |
| 13 | 31 | 50.8 | 49.2 | 408 | yes |
| 14 | 33 | 50.9 | 50.8 | 26 | yes |

| | 现状 | #0 |
|---|---|---|
| body/请求 | **75.6 KB** | **35.9 KB** |
| fresh/请求 | 3,371 tok | 2,512 tok |
| 边界动了几次 | **1** | 13 |
| **这个会话的账单** | **$0.0072** | **$0.0052（-28%）** |

三行就能读完全部机制：

1. **req 11（现状）**：`cutoff` 从 0 跳到 8——攒够了 `advance_step`。这一刻 body 从 119.9 KB 掉到 66.9 KB，
   但 `reused` 只剩 6.8 KB：**从第 8 条往后的一切都按新价重算**，这一次 15,377 fresh token，
   是整个会话最贵的一次请求。这就是 `§3` 说的「裁的那一刻它后面正站着整个 recent window」。
2. **req 4（#0）**：**断点落在同一个地方**（`cutoff` 从 5 走到 8，`reused` 同样是 6.8 KB——
   所以「被打破的位置」两列一样），但新 body 只有 **16.3 KB** 而不是 66.9 KB：
   **窗口只有 2 条，所以断点之后几乎没有东西**，fresh 只有 2,436。
   代价是边界每次请求都在动（13 次 vs 1 次），可是每次动只重算两三条消息——**总账仍然是省 28%。**
3. **req 13/14（两列）**：`reused` ≈ body，`fresh` 只有几百——稳态。现状的稳态是 **75.6 KB/请求**，
   #0 是 **35.9 KB/请求**。**日常账单就是这个数的比拼**，而边界那一下只是它的入场费。

顺便一个反直觉的例子（同一个会话 `rig` 的输出）：`raw`（完全不裁）=$0.0065，比现状的 $0.0090 **还便宜**——
因为**短会话里，裁剪打破前缀的钱可能超过它省下的字节**。这也解释了为什么 `advance_step` 在大窗口下是必需的
（`shipped-20/1` = $0.0261，是现状的 2.9 倍），以及为什么整语料上（长会话占多数）结论才反过来。

## 6. 模型要跨过的那条线

`baseline.py` 把**已经存在的两种确定性压缩**走同一套 `score.py`，于是「模型比规则好多少」
是一个可以比较的数字，而不是一句话：

| 策略 | n | 输入 | 输出 | 压缩比 | 事实召回 | 延迟 |
|---|---|---|---|---|---|---|
| `trim`（现有 40+20 行规则，应用到全部） | 5,227 | 19.68 MB | 12.83 MB | **1.53×** | **95.0%** | 0 ms |
| `marker`（>1KB 全换标记） | 5,227 | 19.68 MB | 0.26 MB | **76.2×** | **0.0%** | 0 ms |

按工具拆：`bash` 1.31× / 95.6%，`read` 2.16× / **89.5%**。

三件事从这张表里直接读出来：

**① 模型要跨的线是「1.53× 且 ≥95% 召回」。** 低于这个数，它不如一行不花时间、可重现的代码。

**② 召回这个指标不是废的。** `marker` 把字节压到 1/76，召回 **0%**——它完美地演示了
「压缩比很高的坏 digest 长什么样」。而 `trim` 作为**按定义逐字保留头 40 行 + 尾 20 行**的规则，
召回也只有 95.0%（`read` 更低，89.5%：代码的关键行在中间）。**连确定性规则都会丢 5% 的事实**——
而它丢掉的那些，正是模型可以赢的地方，也是模型可能输得更惨的地方。

**③ 5,227 个候选里只有 3,787 个进入召回评分**，其余 1,440 个抽不出任何可机检的事实
（纯数字/日志行），只能评压缩比。这个比例说明「事实召回」作为主指标是对的但覆盖不全。

一个合理的期待是：4B 级模型在这批语料上拿到 3–5× 压缩比、~95% 召回，也就是**比规则好 2–3 倍**。
但这 2–3 倍只作用在 §4 那 **$0.86** 上（$6.772 的确定性 5+5 规则 → $5.915 的绝对天花板）。
**换向：同一个 `case` 里真正值钱的东西，是一个不用模型的窗口参数。**
注意这一切在本机都是算术：`afm/` 一次推理都没跑成。

## 7. 建议

按这个顺序做，前面的便宜且已经可做：

1. **把 `recent_window` 从 20 降到 2（并把 `advance_step` 从 8 降到 1）。**
   两次改数字，值 **$4.61/13.67（34%）**，而 `core/trim.mbt` 的架构、可逆性、`prepared_context` 全不用动——
   它仍然是一个投影。
   但**验收不能靠美元**：能省钱恰恰是因为模型看一条结果的时间变短了，而这一点在这个语料里
   **没被量过**。必须用能跑完整回合的评测（`agent/driver_test.mbt` 的 `with_fake_model`）
   对比 `w20` 与 `w2` 的任务成功率。
   *不要一次降到 1*：日志里 92% 的回合追加 2 条消息、8% 追加 3 条，所以 `w2` 是「每条消息都被
   带过至少一次」的最小值，`w3` 覆盖全部。
2. **把 `TrimPolicy::default()` 里的两个数字做成可配置的**，并把 `verify` 里那个
   「tokens 13,427,710 → 7,574,571」的统计加上「按前缀缓存计费后是多少」——
   现在那个数只报体积，不报钱，而这两者已经被证明会反向。
3. **换更狠的确定性裁剪**（不用模型）。$9.06 → $6.77（15+15 → 5+5）。
   这一步要在真实会话上验「少留的行里没有后面要用的东西」——`score.py` 的召回口径可以直接用
   （把裁剪出的文本当成 digest 打分），而且它免费、确定性、可回归。
4. **然后才是模型**，而且只做「规则读不懂的那一块」：48.6% 的小结果，**并且要在第 3 步之后**——
   因为模型只能从 $6.77 走到 $5.92，而第 1 步能拿 $4.61。
   先在一台能跑端侧模型的机器上把 `afm/` 跑起来，拿到**延迟**和**召回率**两个数；
   召回率必须接近 100%（错一个路径就是丢掉一次工具调用），延迟决定它能不能待在工具路径上
   （大概率不能——候选 5,227 次推理，适合后台队列 + 下一轮之前补上）。
5. **上下文压缩（compaction）不要用本地模型**，理由在 `docs/local-model-context.md` 第 3 节 C：
   要总结的就是装不进本地窗口的那一大段，而端侧窗口只有 4096 token。

## 8. 这份分析自己不可靠的地方

- **模型质量没有数据**：设备不支持，§4 的分配是算术，`afm/` 只证明到「能跑通流程、能报告设备不支持」。
- **「压掉之后模型会不会做错」仍然没有数据，但洞的两边被 §5.5 各补了一半。**
  需要那一侧量到了：中间行的回头率是头尾的 ~2.8 倍，重读成本 ≤ $0.259——**方向对**。
  仍然量不到的是反事实：一个被提前裁掉、之后再也没被拿回来的行，日志里不留痕迹。
  原来那条「重复调用只有 1.1%」的旁证是**错的**（它测的是命令字符串重复，不是回头率）——
  真正的回头率是 **38.8% 的 `read`**（§5.5 C）。
- **前缀缓存被简化成字节前缀**：真实实现按块（常见 64–128 token）匹配，改写点附近可能多失效一点。
  方向不变，数值有误差。
- **`freeze-*` 行用的是 `trim_text`（头/尾/标记），不是模型输出**：确定性是为了先把经济账算清楚。
  它高估了「随便留几行」的可行性（模型会挑对行），也低估了模型出错的下行（挑错了就是丢一次工具调用）。
- **价格取的是 fixtures 计费的那档**（0.14 / 0.0028）。现用 id 是 0.3 / 0.006，比值同样是 50×，
  所以结论按比例放大，但绝对金额会更高。
- **bytes/4 对中文是低估的**（一个汉字约 1 token 但占 3 字节）。所有策略用同一个估计量，
  所以**对比**不受影响，绝对 token 数偏低。
- **`billed/derived` 那一列只能当粗检**：它带着系统提示和工具 schema（推导里没有），
  也带着日志写下来时生效的裁剪策略（未必是正在模拟的那个）。干净的校准是 §3 的增量口径。
