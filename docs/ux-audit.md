# UX 走查：pi-web-shell 的 Web UI

- **日期**：2026-09-13
- **方法**：在真实浏览器里按目标走一遍，**测量而不是目测**（截图 + `innerText` + computed style + 几何）
- **仪器**：`harness/ux-walkthrough.mjs`（走查，产出 `_build/ux/*.png|txt`）、`harness/ux-measure.mjs`（量布局/层级/对比度/行宽）
- **判断顺序**：结果对 → 理解对 → 感受对。做成不了，理解得再顺也没用。

## 走查的场景

> **谁**：一个刚打开这个页面的人。
> **情境**：`moon run ui` 起来，浏览器打开 `127.0.0.1:8790`。空 store，或一个用了一阵的 store。
> **要达成什么**：问一个问题，并看懂答案；知道还能做什么；出错了能收回来。
> **从哪进来**：地址栏，直接落在页面上。

走查了 8 个状态：空 store 首屏、turn 进行中、turn 结束、turn 中被拒绝的操作、无交互时页面提供什么、设置面板展开、13 个会话的回归、30 轮长会话打开。

## 一个前提说明

我**没有**子 Agent 工具（只有 bash/read/write/edit/glob/grep），所以「用子 Agent 模拟用户视角」这一步是我自己按「先写清目标、再不带解释地走一遍」的纪律做的，不是我之外的第二双眼睛。这一条会影响结论的可信度：**结构性的问题（下面 P0）证据够硬，因为它有数字；「感觉对不对」的部分只代表一个人。** 建议后续补一次真正的外部走查。

## P0 — 结果不对 / 理解不对

### P0-1 表格渲染不出来，而且没有任何提示

**症状**：模型输出的 markdown 表格变成一串竖线原文。

**证据**（三种独立来源一致）：
- cmark 的 `Block` 枚举里**没有表格**，只有 heading / list / quote / code / thematic break；`render` 也没有扩展参数。这是 CommonMark，不含 GFM 表格。
- 直接调用渲染器：`render("| a | b |\n|---|---|\n| 1 | 2 |\n")` → `<p>| a | b |`。
- 浏览器里量一个含表格的回答：**没有任何 `<table>/<th>/<td>` 元素**，pipe 文本进了 `<p>`。

**为什么是 P0**：coding agent 的回答**经常**用表格（对比、参数、文件/行号清单）。读者拿到的是读不下去的一坨，而且**看不出是渲染失败还是模型本来就这么写的**。这是「结果对」层面的失败。

**建议**（按代价排序）：
1. 在 `html/render.mbt` 加一个**表格预扫描**：识别 GFM 表格块，自己渲染 `<table>`，其余交给 cmark。约 60–100 行，纯函数，可单测。
2. 换一个支持 GFM 的渲染器（代价最大，且 cmark 的 `safe` 与转义行为要重新验证）。
3. 至少：检测到疑似表格时**明确降级提示**（但这是「靠解释补救」，不如 1）。

**验收**：`html/` 里有一个测试，输入上述 markdown，断言输出含 `<table>` 且单元格数量正确；浏览器走查里有一个含表格的回答，量到 `table` 元素存在。

### P0-2 三条命令完全不可发现

**症状**：`/name`、`/skill:<name>`、`/model` 在页面上**一次都没出现过**。

**证据**：量「页面上任何提示性元素」→ 0 个。唯一提到操作的是输入框 placeholder：「Ask something… (Cmd+Enter to send)」。侧栏里会话名就是第一句提问（例如 `Use the bash tool to run exactly: /bin/sleep 25`），没有任何改名入口。

**为什么是 P0**：会话命名和 skill 显式调用是**做得到但没人知道做得到**。这是「理解对」的失败 —— 按定义就是「不知道能做什么」。README 有写，但**需要说明才能懂就是设计问题**。

**建议**：
- 命名：侧栏会话行加一个重命名入口（双击标题 / 一个铅笔图标），而不是只留命令。
- skill：输入框支持 `/` 触发一个轻量列表（服务端渲染可用 `<datalist>`，零 JS），或在空会话时给一行提示。
- 命令本身保留，但**不作为唯一入口**。

**验收**：一个没读过 README 的人，在不看文档的情况下能改名一个会话、能发现 skill 的存在。

### P0-3 正文的层级和页面自己的排版系统打架

**症状**：答案里的标题、引用、列表用的是浏览器默认样式，不是这套设计 token。

**证据**（浏览器 computed style，一个含结构 markdown 的回答）：

| 元素 | 实测 | 问题 |
|---|---|---|
| `h2` | **22.8px / 700**，上下 margin 18.9px | 页面的 type scale 上限是 15.2px（`--text-base`），正文里冒出一个系统外的字号，比页面自己的 UI 标签还醒目 |
| `ol` / `ul` | `padding-left: 40px` | 不在 `--space-*` 刻度上 |
| `blockquote` | **`border-left: 0px`** | 和普通段落**完全无法区分**，而它承载「这句是引用/强调」的语义 |
| `table` | 见 P0-1 | — |
| `pre` / `code` / `a` / `summary` | 已样式化 | ✅ |

**为什么是 P0**：这三样是答案**结构**的载体。标题不分级、引用看不出是引用、列表缩进是随机值 = 读者拿不准哪句是结论、哪句是引用。属于「理解对」。

**建议**：在 `html/theme.mbt` 里给正文块补一组样式，**全部取自现有 token**（标题用 `--text-base`+600 而不是 1.5em；列表缩进用 `--space-5`；`blockquote` 给左侧 `--line-strong` 竖线 + `--muted`）。原则是**内容的层级由内容决定，但尺子必须是同一把**。

**验收**：`html/` 断言行内样式；走查量到 `h2 ≤ --text-base`、`blockquote.borderLeftWidth > 0`、列表缩进等于某个 `--space-*`。

## P1 — 感受不对 / 构图问题

### P1-1 正文行宽 125 字符

**证据**：`#transcript` 的正文列实测 **952px @ 15.2px ≈ 125 字符/行**。舒适阅读区间是 45–90。
**原则**：构图——「字体层级、间距、卡片全部为内容层级服务」；行宽是内容层级的核心参数。
**建议**：给 `.text`/段落一个 `max-width: 68ch`（≈ 78 字符）并居中。这是**一处 CSS**，收益最大。
**验收**：量到的 chars/line 落在 60–80。

### P1-2 页面上最密的元素是元数据，而且一半在显示 0

**证据**：全新会话的顶栏实测 **6 个 chip**：`session ddc86e60` / `model deepseek-v4-flash` / `tokens 0 in / 0 out` / `cache 0` / `cost $0.000000` / `context 1.9k / 1M`。
**原则**：构图——「每一页都要有重点」「如果所有东西权重一样，页面就没有焦点」；UX writing——「每个词都要有存在的价值」。
**问题**：一个刚打开的页面，最显眼的横条上 **4 个 chip 在说「还没有」**；`session ddc86e60` 是读者没选过也控制不了的随机 id；`model` 是默认值。真正的重点（空对话 + 输入框）反而没有视觉权重。
**建议**：没有用量的会话**不画用量 chip**（有数据才出现）；`session` chip 无名时不显示，或显示可点击的「未命名」。
**验收**：空会话顶栏 chip 数 ≤ 2。

### P1-3 状态行和 turn footer 是同一句话，逐字重复

**证据**：同屏同时可见

```
1 model call, 0 tool calls · 1.7k in / 90 out · $0.000269 · 27% cached   ← 回答下面的 footer
1 model call, 0 tool calls · 156 in / 2 out · $0.000028                  ← 状态行（再下面）
```

而 `cost` 这个数字在同一屏出现 **3 次**（顶栏 chip、footer、状态行）。
**原则**：UX writing——「避免重复，economy of language」。
**建议**：分工——**状态行只说「正在发生什么」**（working… / failed: … / cannot change…），**结果只留在 footer**。状态行在 turn 结束后应回到空或一句环境描述。
**验收**：turn 结束后，同一串数字在屏上只出现一次。

### P1-4 Stop 按钮在没事可停的时候可以按

**证据**：三个状态（空会话 / turn 中 / turn 后）实测 `#stop` 都是 `disabled: false`，且可见。
**原则**：Familiarity——「看起来一样的东西应该行为一样」；Agency——「不要挡路，也不要假装」。
**问题**：一个不撒谎的按钮应该在自己无用的时候是灰的。现在它可点、点了没反应（我验证过不会误杀下一个 turn，所以是**无害的谎言**，但仍是谎言）。
**建议**：无 turn 时 `disabled`，随任务面板一起刷新（`picker` 已经这么做了，可以照抄）。

### P1-5 会话的默认身份是一串随机 id

**证据**：顶栏 `session aa82ec73`；侧栏行显示第一句提问（可能是 `/bin/sleep 25` 这种机器话）。
**原则**：Simplicity——「用平实语言」；Familiarity——「建立在已知之上」。
**建议**：未命名时用「新会话」或首句的**截断可读版**；命名入口见 P0-2。

### P1-6 状态行把长路径当反馈

**证据**：打开一个会话后状态行是 `opened 48 messages in /var/folders/m4/…/uxm-store-m0aqWF-project`。
**原则**：UX writing——「去掉填充词」；「先给 why/benefit，再给动作」。
**问题**：读者关心的「48 条消息」被一个临时目录路径淹了。
**建议**：`opened 48 messages`；路径进 tooltip。

## 已经很好的（别动）

这些是**量出来的**，不是感觉：

- **对比度**：逐个测了每个含文字元素的对比度，**0 处低于 4.5:1**。
- **点击目标**：**0 处小于 24px**。
- **折叠**：原生 `<details>`，0 行 JS 记得状态。
- **流式反馈**：turn 中状态行确实在动（`working… 1 model call(s), 0 tool call(s)`），并且我逐帧追踪确认它**会正确地收尾**成结果行，不会卡在 working…（我一度以为有 bug，追踪后确认是我的探针时序问题，**不是**产品问题）。
- **拒绝是准确的**：我验证过拒绝真的出现在状态行，且措辞说明了原因和条件。
- **键盘**：`Cmd/Ctrl+Enter` 发送，且 placeholder 里写了。

## 建议的执行顺序

按你给的三层顺序，以及「越往后改越贵」：

1. **P0-3 正文排版**（一处 CSS，改完立刻能看到）+ **P1-1 行宽**（一处 CSS）
   → 这两条是**同一段工作**（都在 `html/theme.mbt`），加起来不到 30 行，却决定「读起来对不对」。**先做这个。**
2. **P0-1 表格**（`html/render.mbt`，可单测的纯函数）
3. **P0-2 发现性**（改名入口 + skill 触发）
4. **P1-2 / P1-3 / P1-4**（顶栏减法、状态行分工、Stop 置灰）—— 同一段「减法」工作
5. P2 按需

## 怎么知道它在变好（可量的验收）

把这次的仪器当尺子，每轮走查跑一次，看这几个数：

| 指标 | 现在 | 目标 |
|---|---|---|
| 正文 chars/line | **125** | 60–80 |
| 空会话顶栏 chip 数 | **6** | ≤ 2 |
| 同屏重复的用量句 | **2 处** | 1 处 |
| 正文 `h2` 字号 | **22.8px** | ≤ 15.2px（`--text-base`） |
| 表格渲染 | **0 个 `<table>`** | 有 |
| 页面上的命令提示 | **0** | ≥ 1 |
| 对比度 < 4.5:1 | **0** | 0（别退步） |
| 点击目标 < 24px | **0** | 0（别退步） |

最后两行是**回归底线**：这两项现在是对的，任何 UI 改动都不许把它们弄坏。建议把它们加进 `harness/ui-browser-check.mjs`，这样每次改动都有机器盯着。

## 附：这次的仪器怎么用

```bash
node harness/ux-walkthrough.mjs     # 走一遍，产出 _build/ux/*.png + *.txt（8 个状态）
node harness/ux-walkthrough.mjs --fast   # 跳过真实模型调用，只走静态状态
node harness/ux-measure.mjs         # 量一个含长会话的页面，输出 JSON
node harness/ux-measure.mjs --empty # 量空 store
```

走查脚本的设计原则是**不设断言**：它只记录「屏幕上有什么、能点什么、字号多大」，这样下一轮加一个状态（比如「新功能做完了长什么样」）比改一个断言便宜。
