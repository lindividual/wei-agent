# 用本地小模型做「工具输出压缩 + 上下文压缩」——方案调研

> **2026-09-19 更新：已经跑过一轮测量，结论要改。**
> 见 `docs/native-compression-spike.md`（spike 目录本身已删，脚本不再可复跑）。三条实测结果推翻了下面第 2 条的排序：
>
> 1. **账单差异几乎全来自「裁剪边界放在哪」，而不是「裁什么」。** 裁剪动作完全相同的四行，
>    只是 `recent_window` 不同，是 $8.01 / $9.06 / $12.51 / $13.67（现状），**差 1.7 倍**。
>    机制仍是前缀缓存，但杠杆不是「投影 vs 落盘」，而是**一条结果在被改写前还能活多久**。
> 2. **一行不用模型的改动值 $4.61（占总账单 34%）：`recent_window: 20 → 2`。**
>    它仍然是投影（可逆性、`prepared_context` 都不用动），只是把边界提到
>    「一条结果被读过的下一次请求」——而校验不能靠美元，因为模型看结果的时间变短了，
>    这一点在本语料里没被量过。
> 3. **模型的全部空间只有 $0.86（6%）**：从 $6.77（确定性 5+5 规则）到 $5.92（>1KB 全换标记的天花板）。
>    「压缩」这个词在这套管线里能兜现的上限就是这个数。
>
> 另一个要记的负结果：**完全重复的工具结果只占 1.1%**，所以「同工具同参数」这类纯规则无可拓。
> 本机（Mac14,2 / M2 / 8GB / region 中国）的 Apple Foundation Models 不可用
> （`deviceNotEligible`，`OS_ELIGIBILITY_DOMAIN_FOUNDATION_MODELS` 因 `DEVICE_REGION_CODE` 不通过），
> 所以当年的 `afm/` 工具只验证到「流程跑通、能干净地报告设备不支持」，
> **模型质量与延迟在本机没有数据**——而那正是决定成败的那个数。

**结论先行。**

1. 这两个目标里，**只有一半适合本地模型**。工具输出的语义压缩适合；整段历史压缩（compaction）
   不适合——因为要压缩的输入本身就装不进本地模型的窗口，而输出又是整段会话唯一的记忆，错了没有回退。
2. 这个仓库里**最贵的一课是前缀缓存**：任何在「投影期」重写已发送内容的方案，都会把前缀缓存打掉，
   省下的 token 可能不够还重发的那部分（瘦身实测净赚只有 $0.35）。所以本地模型要么**写在落盘时**
   （内容第一次进对话前压缩一次、冻结、之后字节不变），要么**只做选择不做重写**。
3. 本地模型相对云端模型的真实优势是**隐私和零边际成本**，不是「更快」或「更省」。对 1M 窗口的
   DeepSeek 做 compaction，本地模型在延迟和质量上都是劣势。
4. 先别接模型。这个仓库已经有一条**确定性**的压缩链（截断 → 瘦身 → 代码 digest），其中
   `script` 实测 10.5×。本地模型应该只补规则读不懂的那部分（非结构化自然语言输出），
   并且要先在离线语料上证明净收益。

## 1. 现状：已经有三层，别重复造

| 层 | 文件 | 做什么 | 代价 | 可逆 | 已实测 |
|---|---|---|---|---|---|
| 截断 | `core/truncate.mbt` | 工具输出硬上限：2000 行 / 50KB / 单行 500 字符；文件读留头，命令输出留尾 | 免费 | 是 | — |
| 瘦身 | `core/trim.mbt` | 投影期：旧工具输出超 4KB 留头 40 + 尾 20 行；清空旧 thinking；边界按 `advance_step=8` 量化 | 免费 | 是（原文仍在日志） | 净赚 **$0.35**（省 $0.95 cache-read，多付 $0.60 重发，**7%** 的调用被改写） |
| 压缩 | `core/compaction.mbt` + `driver.mbt::compact_if_needed` | 超阈值时把旧历史交给**云端模型**总结，写 `compaction` entry | 一次 API 调用 | 否（但原文留在文件里） | 1M 窗口阈值 98 万，日常不触发；用 40k 窗口在测试里验证 |
| 代码 digest | `core/script.mbt` / `builtin` | 用程序产出 digest，只回打印的东西 | 编译一次 | — | `moon check` 40 个错误 **21,336B → 2,028B（10.5×）** |

几条已经量出来、直接改变方案的事实：

- **工具输出约占全部上下文的一半，`read` 一项占 30%**；reasoning 占 1/5（`core/trim.mbt` 开头）。
  这是本地模型唯一值得动的靶子。
- **瘦身的净收益只有 $0.35**，因为「裁剪省下的 cache-read」要跟「改写已发送内容造成的重发」比过。
  教训在 README 里写得很直白：**「不要改写已发送的内容」这条设计意图本身不是结论。**
- **上下文占用是锚定出来的**：用 provider 实报的 `prompt_tokens` 做锚点，平均相对误差 17% → 0.2%
  （`core/context_pressure.mbt`）。做任何压缩方案的效果评估都该复用这个数，不要用字符 ÷4 估。
- **`context_pressure` 里的固定开销**（系统提示 + 7 个工具 schema）约 **1,314 token/请求**。

## 2. 唯一的硬约束：前缀缓存

DeepSeek 的前缀缓存按**请求 messages 数组的字节前缀**命中。这意味着：

- 对**已经发过**的消息做任何重写（哪怕只是把一段工具输出换成一个更短的摘要），从被改的那条起，
  到数组末尾，全部按新输入计价。而「被改的位置」通常落在对话中段——后半段全是新的和大块的，
  正好是最贵的部分。
- 所以瘦身才要把边界量化（`advance_step`）：让裁剪发生在固定位置，上一轮请求是新请求的字节前缀，
  连续 7 轮几乎不重发。
- **对本地模型更危险**：模型输出带采样随机性，同一条工具输出两次总结会得到两个不同字符串。
  只要在投影期跑模型，**每一轮的前缀都会变**，缓存命中率直接归零。这比确定性瘦身的代价大得多。

**推论（几乎决定了整个架构）：本地模型的压缩必须发生在内容「第一次进入对话」之前，
落盘、冻结、之后字节不变。** 一旦某条消息被发出过，就不要再碰它——除非愿意付重发钱。

## 3. 方案矩阵：本地模型可以放在四个位置

下面每个格子都标：本地模型的适配度、接入点、主要风险。

### A. 工具结果压缩（**写时**，推荐主战场）

**机制**：一次工具调用返回后、结果写进日志之前，本地模型把 >N KB 的非结构化输出（grep 命中、
构建日志、大文件片段、命令输出）压成一份摘要。摘要与原文一起落盘；`trim` 投影时优先用摘要。
摘要**一次生成、永久冻结**，所以缓存安全。

**任务形态要收窄**，否则会踩幻觉的坑。建议本地模型只做**抽取式 / 选择式**，不做自由改写：

```
输入：工具名 + 参数 + 原始输出（截到 N KB）
输出（固定 schema）：{
  "digest": "≤ K 字的结构化摘要",
  "keep_ranges": [[起, 止], ...],   // 原文里必须逐字保留的行区间
  "drop_reason": "..."
}
```

确定性引擎按 `keep_ranges` 剪，digest 只作为「省略段的说明」。这样路径、错误码、命令行这些
**必须精确**的东西由原文区间保证，模型负责的只是「哪一段可以省」——一个判别任务，小模型做得好、
编造空间也小。这和 `core/facts.mbt` 的思路一致：事实用规则抽，摘要才是模型的话。

**收益来源**：`trim` 现在的省略段是「… N of M lines omitted …」，模型可以把它换成有信息的摘要。
注意靶子大小由实测决定：`trim` 的 4KB 阈值以下不动，以上留头 40 + 尾 20；模型真正能改的是中段。

**风险**：
- **歧义丢失**：工具输出里的关键行常在中间（比如一段日志里唯一那行 warning）。判别式保留区间
  能缓解，但要靠评测验证。
- **回归**：压缩后的上下文让主模型（DeepSeek）做错原本能做的事。必须用能端到端跑 turn 的
  假模型/真模型评测，而不只是量 token。
- **热路径延迟**：每此工具调用加一次本地推理。可只对 >N KB 触发，或放进后台队列、
  下一轮之前补上（当前 `run_tools` 是串行执行的，见 `agent/driver.mbt`）。

**接入点**：`agent/driver.mbt::run_tools` 里结果提交前后；摘要作为 `custom` entry 落盘
（`customType: "tool-digest"`，带 tool call id），`core/trim.mbt` 的投影读它。这跟
`core/facts.mbt::agent_notes` 用 `Custom` entry 存 note 是同一个套路。

### B. 历史瘦身的策略选择（**投影期，但只选不改**）

**机制**：本地模型对每条旧消息打一个标签 `keep / drop / shrink`，纯判别，不生成文本。
规则的输出（drop thinking、裁中段）不变，模型只是把规则读不懂的「这条还有用吗」补上。

**为什么可能成立**：判别输出是短、离散、可审计的；如果标签在落盘时算一次并冻结，
它就等价于一个确定性策略，**不违反缓存约束**。

**值不值得**：仓库自己的测量说，瘦身里**尺寸阈值比窗口重要得多**（8KB→4KB 多省 4.4 个点，
窗口 20→0 只多省 1.6）——意思是空间分散在「大但不巨大」的结果里，规则已经能抓。
模型能补的多半是「这条已被后续结果取代」这类语义判断，而这类判断很大一部分**能被规则抓到**
（同一工具、同一参数、文件 hash 没变 = 重复读）。所以这一步的**优先级低于 A**，
除非离线评测显示规则漏掉的量可观。

### C. 整段历史压缩（compaction）——**不适合本地模型**

**理由，按重要性排**：

1. **装不下**。要总结的是「被丢掉的那段」，而它本来就很大。当前参数：1M 窗口下
   `keep_recent_tokens=100000`，即一次 compaction 要总结 **~90 万 token**；即使 40k 窗口的测试路径，
   keep=10000，要总结的也有 ~3 万 token。本地小模型窗口常见 4k–32k（Apple 端侧模型约 4k），
   要总结必须先 map-reduce 分块——多了一层流水线，也多了一层质量风险。
2. **错了没得退**。compaction 摘要是整段会话**唯一的记忆**，之后所有轮都建立在它上面。
   它还是低频高价值的操作：花一次云端调用换正确性，是划算的；用本地模型省这一次调用，
   省的钱可以忽略（1M 窗口日常不触发压缩）。
3. **延迟**。本地 4B 模型 prefill 大致几百 token/s 量级，9 万 token 要几分钟；云端 1M 上下文的
   模型在这件事上又快又准。本地模型在这里是三项全输。

**唯一可能成立的形态**：compaction **之前**用本地模型做一次「预修剪」——把送进摘要的输入变小，
给云端 summarizer 更好的信噪比。但这本质上是 B，不是 C。

### D. 把旧工具输出挪出上下文，按需取回（**替代内联，收益最大也最伤筋动骨**）

**机制**：老的工具输出不再内联进请求，而是进本地索引；给模型一个检索工具，
需要时再取回来。压缩比可以是「全删」，且不破坏缓存（因为老内容本就在前缀之外）。

**成本**：要新增工具（当前 8 个 + code mode 2 个）、要决定「什么时候该取回」（模型未必知道
自己缺什么），而且它把「上下文」从一个确定的东西变成了一个检索系统——这跟这个仓库
「每一轮都是确定的派生」的哲学冲突。

**本地模型的角色**：只做 embedding / 重排。值得记一笔，但不该是第一版。

## 4. 本地推理怎么托管

仓库现在是 native macOS 主端，MoonBit 侧在 `macos/appffi/`，通过 C FFI 跟 Swift 通信
（`ffi.mbt`：MoonBit→host 用 `wei_emit`，host→MoonBit 用轮询式 `wei_recv` inbox）。
四种托管方式，按接入成本排：

| 方式 | 接入成本 | 上下文/能力 | 备注 |
|---|---|---|---|
| **① 本地 OpenAI 兼容 server**（Ollama / llama.cpp `llama-server` / LM Studio） | **最低**。`DEEPSEEK_BASE_URL` 已存在（环境变量，默认 `https://api.deepseek.com`；原先的 `--base-url` 随 `ui/` 一起删了），复用 `platform/http.mbt` + `request_model` | 取决于模型，可到 32k+ | 用户自己装 server；对测试极友好——`agent/driver_test.mbt` 的 `with_fake_model` 就是同一套 |
| **② Apple Foundation Models**（Swift 侧） | 中。要新加一条 MoonBit↔Swift 的请求/响应 FFI | 端侧 ~3B，**约 4k token 的 session 窗口**，要求 macOS 26 + Apple Intelligence | 零下载、免费、不出机器；**只够做 A/B 里的短任务**，做不了 compaction |
| **③ MLX Swift / CoreML 在进程内** | 高。要自己做模型下载/安装/内存管理 | 可自选 0.6B–8B | 仓库已有先例：`VoiceCapture.swift` 的 `AssetInventory` 下载安装流程可以照搬 |
| **④ llama.cpp 静态链进 native 二进制** | 最高。跨架构构建、FFI、内存 | 自选 | 单文件自包含，但会把这套本就复杂的 `macos/build-moonbit.sh` 再推高一层 |

**建议从 ① 开始**：它不需要改架构，能立刻验证「本地模型压出来的东西到底有没有用」这个核心问题；
等结论是「有用」再考虑 ②/③ 去掉外部依赖。

## 5. 模型与任务匹配

- 这个任务**不需要强推理，需要稳定的指令遵循和长一点的有效输入**。候选（按体积）：
  Qwen3 的 0.6B/1.7B/4B/8B、Llama 3.2 1B/3B、Gemma 3 4B、Phi-4-mini ≈3.8B。
  4B 级是甜点：够懂结构化输出，权重 ~2.5GB（q4），Apple Silicon 上解码几十 token/s。
- **判别式 > 生成式**（第 3 节 A）：输出固定 schema、可校验、可回退到规则。生成式摘要
  只用来描述「省略段是什么」。
- 相关但不同的一条路：**LLMLingua 一类的 token 级 prompt 压缩**（用小模型算困惑度剪 token，
  2–20×）。它压出来的是非自然 token 串，**只对同一个小模型有效**，而这里下游是 DeepSeek——
  跨模型注入被剪过的 token 风险很高，不建议。
- 端侧 4k 窗口这个限制要正面认下：**别指望一次喂进去整个工具输出**。可行的做法是
  只让模型看「被规则省掉的那段」的一个有界窗口（例如前 8KB），或者 map-reduce。

## 6. 怎么知道它在变好（这是这个仓库的强项，别浪费）

仓库已有的量尺可以直接复用，加一根新尺：

| 指标 | 来源 | 说明 |
|---|---|---|
| 每调用 input / cache_read / cache_write / output | 日志 `usage` | 成本口径的唯一事实 |
| **cache 命中率**（本轮 + 累计） | README「用量与上下文」 | 本地模型方案最该盯的数字；投影期跑模型会把它打穿 |
| **请求前缀共同长度** | `request_drift` | 直接回答「这次改动有没有打掉前缀」 |
| 上下文占用（measured / estimated） | `context_pressure` | 压缩效果的权威分母 |
| **压缩比 / 事实召回** | 新增 | 每个工具类型压掉多少字节；原文里的路径/命令/错误行是否 100% 还在 |
| 任务成功率 | 端到端 eval | 压完之后主模型还能不能把活干完 |

**离线回放优先**：`verify` 手上就有 172 个会话文件、55,931 条 entry。先在这些真实记录上跑
「候选压缩策略」，把 token 节省、cache 影响、事实召回三个数算出来——**不接进实时路径**。
这和 README 里「优化都从测量开始」是同一套做法，也是唯一能在便宜的地方试错的位置。

## 7. 推荐路线（分阶段，每阶段有验收标准）

**阶段 0（不接模型）**
- 基线已经量完 (见 `docs/native-compression-spike.md`)：工具输出占 54.4%、思考 44.4%；瘦身免费拿走 57%，
  剩下 90.9% 是工具输出；其中 48.6% 在 4KB 阈值以下（模型唯一纯新增的部分）。
- 「同工具同参数、文件 hash 未变」这类可证明已死的冗余**只占 1.1%**——这条不用再图了。
- 真正值得做的第一件免费事：**`recent_window: 20 → 2`（`advance_step: 8 → 1`），值 $4.61/13.67。**
  它把「一条工具结果在被改写前还能活多久」从 ~10 轮降到「被读过的那一次请求」。
  仍然是投影，可逆性不动；但**验收不能靠美元**，必须用能跑完整回合的评测对比 w20/w2 的成功率。
- 第二件：更狠的确定性阈值（$9.06 → $6.77），用 `score.py` 的召回口径验收。

**阶段 1（离线，本地模型只读语料）**
- **阻塞点：先要有一台能跑模型的机器。** 本机 Apple Foundation Models 不可用
  （`deviceNotEligible`，region 不通过），所以现在是「工具建好了、数据没有」。
  两条路：换一台符合条件的 Mac（macOS 26.4+、Apple Intelligence 已开）跑那套 `afm/` 工具（已删，见 git 历史），
  或者先用方式 ①（本地 OpenAI 兼容 server）把同样的问题答一遍——`score.py` 对两者一视同仁。
- 在回放语料上量三个数：**压缩比、事实召回、延迟**（外加同一输入重跑是否逐字一致——
  稳定是能否落盘冻结的前提，`afm/Harness.swift` 已内置 `--repeat`）。
- 验收：事实召回 100%（路径/命令/错误行）；延迟低到能进工具路径，否则就是后台队列。

**阶段 2（实时，写时压缩）**
- 顺序按那次 spike 的实测调整：**先**做阶段 0 那两件不用模型的事（$4.61 + $2.29），
  **然后**才让模型接手 4KB 以下那 48.6%——因为模型只能从 $6.77 走到 $5.92，而一个窗口参数就值 $4.61。
- 触发条件：只在结果 > 1KB 时触发（4KB 以下才是模型纯新增的部分）；摘要 + keep_ranges 作为
  `custom` entry 落盘，`trim` 优先用；设置面板加开关，默认关。
- 验收：cache 命中率不下降、成本下降、端到端任务不回归；**事实召回率接近 100%**
  （错一个路径就是丢掉一次工具调用）。

**阶段 3（按需）**
- 小窗口 / 短会话的 compaction 可以试本地 + map-reduce；大窗口继续云端。
- B（判别式瘦身）在阶段 0 的测量支持下，如果规则确实漏掉可观部分，再上。

## 8. 需要你拍板的几个问题

1. **动机排序**：省钱、隐私、延迟、还是质量？四者导向不同的方案——
   为隐私，②/③ 在进程内是必要的；为省钱，先看阶段 0，本地模型很可能不划算。
2. **能不能接受用户另装一个本地 server**？能，就走 ①；不能，成本跳到 ③/④。
3. **端侧 4k 窗口**够不够你要做的事？如果核心诉求是整段历史压缩，答案是**不够**，方案要换。
4. 是否愿意为此新增**一条会读日志、会写 `custom` entry 的新管线**（也就是可逆性要重新设计）？
