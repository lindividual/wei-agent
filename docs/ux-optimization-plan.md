# UX 优化清单：pi-web-shell 的 Web UI

- **日期**：2026-09-13（第二轮）
- **方法**：与 `docs/ux-audit.md` 同一套仪器 —— 真实 Chrome（CDP）量 computed style 与几何，叠加**字节级 HTML 检查**和**针对本项目实际依赖版本（cmark 0.4.8）的单元探针**。
- **判断顺序**：结果对 → 理解对 → 感受对。
- **本文与上一轮的关系**：不推翻结论，但**修正了一处代价误判**（表格是 1 行 flag，不是 60–100 行），并补上了上一轮没量到的两项（代码块不可复制、无响应式）。凡是上一轮已经量清楚的问题，这里只给结论与新数字，不重复论证。

## 怎么读这份清单

每条包含：**症状 → 证据（可复现）→ 为什么在这个层级 → 改法（具体到文件）→ 验收**。

层级按**改错的代价**排，不按工作量排：

- **P0**：结果不对或理解不对。答案读不出来（表格）、该做的事做不了（复制代码）、不知道能做什么（发现性）。
- **P1**：感受不对。读起来累（行宽）、注意力被噪声占（顶栏/状态行）、按钮撒谎（Stop）。
- **P2**：打磨与防护。响应式、无障碍、性能、仪器本身。

## 一、现状

### 一句话

**结构是对的，内容是残的。** 这套 UI 的骨架（服务器渲染 + 原生 `<details>` + 4 操作 patch + 语义 token + 明暗双色）是干净的，设置面板和会话管理的完成度也高。问题**几乎全部集中在「正文」这一层**：模型输出的 markdown 有近一半的结构没被渲染或没被这套设计系统接管 —— 而正文正是这个页面存在的理由。

### 硬数据（本轮实测）

| 指标 | 实测 | 目标 |
|---|---|---|
| 表格渲染 | **0 个 `<table>`**，pipe 进 `<p>` | 有 |
| 代码块复制入口 | **0 / 112 个 `<pre>`** | 每个都有 |
| 代码语言标识 | `language-*` 存在但**无人使用** | 显示或高亮 |
| 正文 `h3` 字号 | **17.784px** | ≤ 15.2px（`--text-base`） |
| `blockquote` 左边线 | **0px**（只有 UA 缩进） | > 0，且用 `--line-strong` |
| 有序列表缩进 | **40px**（UA 默认，不在刻度上） | 某个 `--space-*` |
| 正文行宽 @1280 | 920px ≈ **121 字符** | 60–80 |
| 空会话顶栏 chip | **6 个，其中 4 个是 0** | ≤ 2 |
| `Stop` 空闲态 | `disabled:false` | `true` |
| 窄屏（≤690px）输入框宽 | **26px** | 可用 |
| 地标（main/nav/header） | **0** | ≥ 2 |
| `aria-live` | **0** | status 有 |
| 长会话页面 | 3.7MB / 23547 节点 / **首屏 5.3s** | 可控 |
| 对比度 < 4.5:1 | **0**（144 个元素逐个测，回归底线） | 0 |
| 折叠行 `summary` 高度 | **21px**（94 个里 88 个 < 24px） | ≥ 24px |

### 已经很好的（别动）

量出来的，不是感觉：**对比度 0 处不合格**（本轮在含内容的长会话上重测 144 个元素，仍为 0）；原生 `<details>` 折叠、0 行 JS 记状态；流式状态行会动的确会收尾；设置面板的信息架构（事实 / 可改 / 来源）清晰；暗色模式与语义 token 齐备；拒绝措辞准确且说明了条件。

> **对上一轮的一处更正**：`docs/ux-audit.md` 说「点击目标 0 处小于 24px」。这**只在空页面上成立** —— 该轮是在空 store 首屏量的，那里没有正文。本轮在含内容的会话上量到 **94 个折叠行里 88 个只有 21px 高**（见 P2-2）。教训是仪器本身：**baseline 必须在最复杂的状态上量，否则它守不住任何东西。**

## 二、优化清单

### P0-1 表格渲染不出来 —— 而且只是**一行 flag**

**症状**：模型输出的 markdown 表格变成一串竖线原文。见本轮截图：`| Option | Cost | Note | …` 直接进了段落。

**证据**（四个独立来源一致）：
1. 浏览器端到端：夹具会话含 3×3 表格，`document.querySelectorAll('#transcript table').length === 0`，且能找到一个 `textContent` 含 `"| Option"` 的 `<p>`。
2. 字节级：对夹具会话取原始 HTML，`/<table/i` 不匹配。
3. 单元探针（实际依赖 cmark 0.4.8）：`@cmark_html.render(src, safe=true)` → `<p>| a | b |`；`safe=true, strict=false` → `<div role="region"><table>…`。
4. 依赖源码：`cmark_html.render` 的默认是 `strict? = true`；`@cmark.Parser` 里 `exts: !strict`。**表格是扩展，默认关着。**

**为什么是 P0**：coding agent 的回答**经常**用表格（对比、参数、文件清单）。读者拿到的是读不下去的一坨，而且**看不出是渲染失败还是模型本来就这么写的**。

**改法**（按代价，取第 1 条）：

1. **把 `strict=false` 打开**：`html/render.mbt:26` 与 `html/content.mbt:59` 两处 `render(source, safe=true)` 加 `strict=false`。**这是一行。**
   已实测副作用，都可接受：
   - 额外开启删除线、任务列表（任务列表产生 `<div class="task"><input type="checkbox" disabled>`；与面板的 `.panel .task` **只是同名、作用域不冲突**，但因为选择器是后代选择器，值得加一条注释钉住）。
   - `safe=true` 下原始 HTML 仍被丢弃（已实测 `<script>` 被替换为注释），安全性不变。
   - 输出带 `role="region"` 包裹，可访问性反而更好。
2. 给表格补 CSS（见 P0-3 同一段工作）。
3. **不要**手写表格预扫描（上一轮的建议 1）—— 依赖已经提供了这个能力，重写等于自己维护一个和上游不一致的解析器。

**验收**：`html/` 加一个测试：输入上表 markdown，断言输出含 `<table>` 且 `<td>` 数为 6；浏览器走查量到 `<table>` 存在。

### P0-2 代码块不能复制（112 个里 0 个有入口）

**症状**：每个回答里的命令、代码、配置都无法一键复制，只能手工划选；代码块也不显示语言。

**证据**：长会话页面上 `#transcript pre`（含 `pre.args`）共 **112** 个，`button.copy / [data-copy]` **0** 个，`.lang` 徽章 **0** 个，`class*="token"` 高亮 **0** 个。同时 `class="language-moonbit"` **确实被 cmark 输出了**（探针确认），只是没有任何东西消费它。

**为什么是 P0**：在一个 **coding agent** 的界面上，「把这段代码拿走」是这个页面的**头号动作**。没有它，读者要把答案重新敲一遍。这属于「结果对」——不是好不好看的问题。

**改法**：
- 服务端渲染的 markdown 是 `Raw` 字符串，DOM 里没有可挂钩的节点，所以这一步**在客户端做最便宜**：`ui/assets.mbt` 的脚本里加约 15 行 —— 找到 `#transcript pre`，包一层容器，插入语言标签（读 `code.className` 的 `language-*`）和一个 Copy 按钮，点击写剪贴板并把文案短暂改为 `Copied`。已有 `apply(patch)` 之后调一次、以及 `appendtext` 流式期间不动即可（流式块完成后会被 `replace` 成渲染后的 markdown，正好重建）。
- 若要语法高亮：这是另一个量级（引一个 highlight 库或自己写），**建议先不做**——语言标签 + 复制已经拿走 90% 的收益。等有真实反馈再说。
- 顺手修 `pre` 的断词策略：现在是 `word-break: break-word`，会把代码在 token 中间拆断。改成 `overflow-wrap: normal` + `overflow-x: auto`（横向滚动优于拆断）。

**验收**：浏览器走查断言每个 `#transcript pre` 内有一个可点复制按钮；点击后 `navigator.clipboard.readText()` 等于代码原文（CDP 可授权剪贴板读）。语言标签在 ``` 带语言时出现、不带时不出现。

### P0-3 正文排版不在设计系统里

**症状**：答案里的标题、引用、列表用的是浏览器默认样式，不是这套 token。

**证据**（浏览器 computed style）：

| 元素 | 实测 | 问题 |
|---|---|---|
| `h1–h6` | `h3` = **17.784px / 700**，margin-top 17.784px | 页面 type scale 上限是 15.2px，正文里冒出系统外字号 |
| `ul` / `ol` | `padding-left: 40px` | 不在 `--space-*` 刻度上 |
| `blockquote` | `border-left: 0px`，颜色与正文相同 | 只有 UA 的 40px 缩进，**没有竖线、没有降级色** |
| `table` | 见 P0-1 | — |
| `pre` / `code` / `a` / `summary` | 已样式化 | ✅ |

**为什么是 P0**：这三样是答案**结构**的载体。标题不分级（h3 和 h4 一样大）、引用看不出是引用 = 读者拿不准哪句是结论、哪句是引用。属于「理解对」。

**改法**（`html/theme.mbt`，与 P0-1 的表格样式同一段工作，约 25 行）：给正文块补一组样式，**全部取自现有 token**：
- 标题：`--text-base` + 600（`h3` 可再低一档到 `--text-sm`），行内 margin 用 `--space-2/3`；**不要**用 `1.5em` 之类的相对字号。
- 列表：`padding-left: var(--space-5)`，`li` 下间距 `--space-1`。
- 引用：`border-left: 2px solid var(--line-strong)`，文字 `--muted`，`padding-left: var(--space-3)`。
- 表格：`border-collapse: collapse`、单元格 `1px solid var(--line)`、表头 `--surface`、外层 `overflow-x: auto` 防宽表撑破列宽。

原则：**内容的层级由内容决定，但尺子必须是同一把。**

**验收**：`html/` 断言行内样式；走查量到 `h ≤ --text-base`、`blockquote.borderLeftWidth > 0`、列表缩进等于某个 `--space-*`。

### P0-4 三条命令与改名入口完全不可发现

**症状**：`/name`、`/model`、`/skill:<name>` 在页面上**一次都没出现过**；会话没有重命名入口；**空状态是一片空白**，不教任何东西。

**证据**：页面上提示性元素 0 个（唯一文案是 placeholder `Ask something… (Cmd+Enter to send)`）；`html/`、`ui/` 里无 `datalist`、无 rename 入口；空 store 走查的首屏见截图 —— 顶栏 + 空侧栏 + 空正文 + 输入框，**没有任何一句告诉读者可以做什么**。

**为什么是 P0**：改名和 skill 显式调用是**做得到但没人知道做得到**。按定义就是「理解对」失败。README 写了，但**需要说明才能懂就是设计问题**。

**改法**（按收益）：
1. **空状态**（收益最大、最便宜）：没有消息时，正文区放 2–4 行可点的示例提示，顺带点出 `/` 与 `Cmd+Enter`。这是唯一一个读者**一定会经过**的教学位。
2. 输入框 `/` 触发：列出 `/name`、`/model` 与已知 skill 名。原计划用 `<datalist>`（零 JS），**实际不可行**：`list` 属性只在 `<input>` 上生效，`<textarea>` 忽略它，而编排器必须是 textarea（prompt 允许多行）。故用普通按钮 + 一点客户端脚本。
3. 会话行加一个小小的改名入口（仅当前会话）——`/name` 已经能改，这条只是让它看得见。

**验收**：一个没读过 README 的人，在不看文档的情况下能改名一个会话、能发现 skill 的存在。

### P1-1 正文行宽 121 字符

**证据**：1280 视口下段落实测 **920px @ 15.2px**；`#transcript` 没有任何 `max-width`。舒适阅读区间 45–90。

**改法**：给 `#transcript` 的内容列一个 `max-width: 68ch`（≈78 字符）并对齐到左侧（不要居中——左侧和侧栏对齐更稳）。**一处 CSS**。注意：只约束**正文块**，不要约束代码块/表格（它们要占满可用宽度，超出时横向滚动）。

**验收**：量到 chars/line 落在 60–80。

### P1-2 顶栏 6 个 chip，4 个在说「还没有」

**证据**：空会话实测 6 个 chip：`session 675c3ea0` / `model deepseek-v4-flash` / `tokens 0 in / 0 out` / `cache 0` / `cost $0.000000` / `context 2.8k / 1M`。

**问题**：刚打开的页面，最显眼的横条上**4 个 chip 在说「还没有」**；`session 675c3ea0` 是读者没选过也控制不了的随机 id；`model` 是默认值。真正的重点（空对话 + 输入框）反而没有视觉权重。

**改法**：没有用量的会话**不画用量 chip**（有数据才出现）；`session` 未命名时不显示，命名后显示名字。

**验收**：空会话顶栏 chip 数 ≤ 2。

### P1-3 同一串数字在一屏上出现三处

**证据**：顶栏 chip（累计 `cost`）、每个 exchange 下面的 footer（单轮 `1 model call, 0 tool calls · 10 in / 10 out · $0.000000 · 0% cached`）、以及状态行（同一句话）。长会话里 `$` 出现 **28 次**。

**细分**：footer 与 chip **分工是对的**（单轮 vs 累计），真正的重复是**状态行**；而**全零 footer**（`0 in / 0 out · $0.000000`）是纯噪声 —— 夹具会话只有一条极小回答，却照样打印一行。

**改法**：状态行**只说「正在发生什么」**（working… / failed: … / cannot change…），结果只留 footer；footer 在用量为 0 时不画。

**验收**：turn 结束后，同一串数字在屏上只出现一次；0 用量不产生 footer。

### P1-4 `Stop` 在没事可停的时候可以按

**证据**：夹具会话（空闲）实测 `#stop` 为 `disabled: false` 且可见。

**问题**：一个不撒谎的按钮应该在自己无用的时候是灰的。现在是**无害的谎言**（点了不会误杀），但仍是谎言。

**改法**：无 turn 时 `disabled`，随任务面板一起刷新（`#model-picker` 已经这么做了，照抄）。

**验收**：空闲态 `#stop[disabled]` 存在；turn 中消失。

### P1-5 会话的默认身份是随机 id

**证据**：顶栏 `session fx1` / `session 675c3ea0`；侧栏行显示第一句提问（可能是 `/bin/sleep 25` 这种机器话）。

**改法**：未命名时用「新会话」或首句的**截断可读版**；命名后显示名字（命名入口见 P0-4）。

**验收**：未命名会话在顶栏不再出现裸 id。

### P1-6 状态行把长路径当反馈

**证据**：打开会话后状态行是 `opened 2 messages in /var/folders/m4/…/fx-store-…/project`。

**问题**：读者关心的「2 messages」被一个临时目录路径淹了。

**改法**：`opened 2 messages`；路径进 tooltip。

**验收**：状态行长度不随 cwd 增长。

### P2-1 没有响应式：窄屏直接塌掉

**证据**（同一页面，逐档量）：

| 视口 | 侧栏 | 正文列 | 段落 | 输入框 |
|---|---|---|---|---|
| 1280 | 272 | 984 | 920 | 600 |
| 900 | 272 | 604 | 540 | 220 |
| 800 | 272 | 504 | 440 | **120** |
| 690 | 272 | 394 | 330 | **26** |
| 480 | 272 | 184 | 120 | **26** |

侧栏固定 272px 从不折叠；编排器子项（`Send` 70 + `Stop` 66 + picker 192）宽度固定且**永不换行**，导致输入框被压到 26px。**这个页面只在 ≥ ~900px 时可用。**

**改法**：
1. 一个断点（`@media (max-width: 60rem)`）把侧栏改为可折叠 / 抽屉。
2. `#composer` 用 `flex-wrap: wrap`，picker 在窄屏落到下一行（注释里已经写了「narrow window wraps it under the buttons」，但 CSS 没有实现这一点 —— **代码注释和现实不符**，顺手修正或删掉那句）。
3. `#model-picker` 的 `max-width: 12rem` 在窄屏收更紧。

**验收**：390px 视口下输入框 ≥ 200px、无横向滚动、侧栏不占 272px。

### P2-2 折叠行的点击目标只有 21px

**证据**：含内容的会话里 `#transcript summary`（thinking / 每次工具调用 / 工具结果的折叠行）共 94 个，高度分布只有 **43px 和 21px** 两种，其中 **88 个是 21px**，低于 24px 的最小点击目标。

**为什么在这个层级**：展开工具调用是这个界面上**最高频的交互之一**（每次想看「它到底跑了什么」都要点一次），触屏上 21px 会频繁点空。它不改变结果，所以不是 P0；但它是**量出来的硬伤**，不是主观感受。

**改法**：给 `#transcript summary` 加一点垂直 padding / `min-height: 24px`（`--space-*` 里取一档）。一处 CSS。

**验收**：走查量到 `#transcript summary` 的 `getBoundingClientRect().height >= 24`。

### P2-3 无障碍缺口

**证据**：地标只有 `<aside>`，无 `main`/`nav`/`header`；`#status` 无 `aria-live`（流式状态不播报）；无 `prefers-reduced-motion`（`.dot` 的 `pulse` 动画无开关）；无 `:focus-visible` 令牌（靠 UA 默认轮廓，能用但没纳入设计系统）；无 `meta theme-color`。

**改法**：给交谈区 `<main>`、侧栏 `<nav>`；`#status` 加 `aria-live="polite"`；`@media (prefers-reduced-motion: reduce)` 关掉动画；给 `:focus-visible` 一条 `outline: 2px solid var(--accent)`。都是几行。

**验收**：走查量到地标 ≥ 2、`#status[aria-live]` 存在、reduced-motion 下 `.dot` 无 animation。

---

### P2-4 长会话的代价随长度线性增长

**证据**：21 个 exchange / 2035 条消息的会话，整页 HTML **3.7MB**、DOM **23547 节点**、页高 **87k px**、首次内容绘制 **5.3s**。每次切换会话都是全量重渲染。

**判断**：这不是当前最痛的点（还能用），但它**封顶了会话能长到多长**，而且和 P0-2 的客户端后处理叠加。建议先记录、观察，不做提前优化。真要做，方向是：老 exchange 折叠为摘要、或只渲染最近 N 轮 + 「load earlier」。

---

### P2-5 仪器本身要干净退出

**证据**：`node harness/ux-walkthrough.mjs --fast` 写完 5 个观察后，在 `main()` 结束处对临时 Chrome profile 调 `rmSync` 抛 `ENOTEMPTY`，进程以非零码退出。

**为什么值得修**：这是**量尺**。一个会在成功路径上伪失败的仪器，会让人学会忽略它的退出码 —— 那么下次真失败也看不见了。加个 `rmSync(..., { recursive: true, force: true, maxRetries: 5 })` 或直接删掉清理。

## 三、建议执行顺序

按「越往后改越贵」和「先做能看到效果又不返工的」：

1. **P0-1 表格** + **P0-3 正文排版** —— **同一段工作**（`html/render.mbt` 一行 flag + `html/theme.mbt` 一组正文样式 + 测试）。加起来约 30 行，却决定「读起来对不对」。**先做这个。**
2. **P1-1 行宽** —— 一处 CSS，和上一条同文件、同一次走查验证。
3. **P0-2 复制代码** —— 客户端 + 一点 CSS，收益大、可单测（DOM 层面）。
4. **P0-4 发现性** —— 空状态 + datalist + 改名入口。

## 七、第四批：会话删除（已做完）

删除是这个界面里**唯一会丢东西**的动作。设计上的核心选择是：**做成可撤销的，而不是做成要确认的**。

### 三个决定

**1. 删除 = 改名移出 `.jsonl`，不是 unlink。**

`sessions_in` 本来就按 `.jsonl` 后缀过滤，所以把文件名改成 `<原名>.jsonl.deleted` 就足以让它从所有列表里消失——**不需要第二套「回收站」簿记**。字节留在原地，名字可预测，于是**即使撤销那一屏早就关了，也能在 shell 里手动改回来**。会话日志是这个程序唯一的产物，一次手滑不该能销毁它。

**2. 不弹确认框。**

确认框给每一次删除都加一道税，去拦一个小概率事件，而且拦得比看上去少：真正会发生的错误是**点错了行**，而等对话框把名字显示出来时读者已经不看了。改成：删完在列表**下方**给一行 `Deleted <名字>` + Undo——名字出现在读者**还能感到意外**的那一刻，修法只差一次点击。

**3. 可以删掉正在看的那个会话。**

不拦，而是把显示搬到另一个会话。拦下来会让读者必须学一条「这个不能删，先切走」的规则，而页面本来就有能力显示别的。

### 拒绝删除的两种情况

都是「有别的状态依附在文件上」：**有 turn 正在这个会话里跑**（它会继续往一个没人列出的名字写），**有后台 job 还活着**（job 会继续跑，而没有任何一行能找到它）。

### 写代码时又抓出两个 bug（都是我自己的）

**bug 1：替换会话会选到「正在被删的那一个」。**

`next_session_after` 在改名**之前**运行（故意的：registry 不能为空，否则 `shown()` 会 panic），此时去问「这个工作区最新的会话」——答案就是**它自己**，因为文件还在。于是页面继续渲染一个已经从列表里消失的会话，**并且刷新后仍然如此**（runner 还在内存里）。有第二个会话时它返回的是那个，所以普通测试碰不到。

修法：候选里显式排掉这个路径。加了精确复现这个场景的测试（工作区里只剩一个会话），并把修复合回退验证过——**确实会报 `the page must not still be showing the deleted session`**。

**bug 2：撤销提示里的标签宽度是 0。**

`.undo button`（第 83 行）打不过 `.sidebar button { width: 100% }`（第 97 行）——**同优先级下靠后的胜出**，按钮吃掉整行，旁边的标签被挤成 0 宽。而标签就是「删掉了什么」，没了它确认也就没了。修法是把选择器写成 `.sidebar .undo button`。

### 顺手修的一处：两个图标的对比度不达标

删除和改名两个按钮原来靠 `opacity` 淡出（0 / 0.5），量下来分别只有 **1:1 和 1.67:1**——低于非文字组件要求的 3:1，而且在触屏上根本够不到。改成**用颜色而不是透明度来「安静」**：`--muted` 在页面底色上是 **5.05:1**，可读但不抢戏；删除按钮只在指针悬停时变红，用来和旁边的改名区分。

## 八、帧的标签：一处沉默的、永久性的失联（已修）

### 现象

读者报的：一个 turn 早就结束了，页面**仍然显示它在跑**，按刷新才对。报告得很准：「服务端是对的，浏览器停在旧帧」。

### 根因

客户端判断一帧是不是给自己的，只做一次字符串比较：

```js
frame.session === document.getElementById('transcript').dataset.shownSession
```

transcript 公布的是 **short id**（8 位，`session_tag()`）。而三处 scoped 帧里有两处打的标签是**完整路径**：

| 位置 | 标签 | 后果 |
|---|---|---|
| `ui/turn.mbt:153` | `session`（short id）| ✓ 正常 |
| `ui/turn.mbt:132` | `visible.path` | ✗ **永久丢弃** |
| `ui/requests.mbt:168` | `shown.path` | ✗ **永久丢弃** |

于是两个后果：**「N other session(s) running」永远不消失**（那句提示来自 turn 开始/结束时的 sidebar 刷新），以及**排队提示 `queued behind the running turn` 从来不会显示**。

关键在「永久」：帧格式完全合法，只是**不是给这个页面的**，被丢在客户端。服务端每一帧都发对了，所以刷新就能看到正确的。

### 为什么测试没抓到

帧和页面是**分别**断言的，各自内部一致，**没有任何东西把两者互相对照**。这正是这类 bug 的形状：跨文件（服务端渲染 ↔ 客户端比较）、跨语言（MoonBit ↔ JS）的一条字符串契约，而两边各自都有测试。

补的测试就是把这个契约钉住：从 page 的 `data-shown-session` 里取出**客户端真的会比较的那个字符串**，再要求每一个 scoped 帧都带同样的标签。已把修复合回退验证——确实会报 `a scoped frame is tagged <path>, but the client compares against <id> — it would be dropped`。

（写这条测试时我自己先踩了个 off-by-one：`data-shown-session="` 是 20 个字符我切了 21，测试报出来的差异看起来像服务端标签不对。所以现在前缀长度是从前缀本身算的，不是写死的数字。）

### 顺手堵上的第二条路径

同一句症状还有一条独立路径：客户端只在 `apply(frame)` **之后**重新读 `shown`。只要 `apply` 中途抛异常（装饰、滚动、任何一点），`shown` 就停在旧 id，之后**所有** scoped 帧都被丢掉，页面彻底不再更新——**刷新就好**，所以极难报。

改成 `try { apply(frame) } finally { 重新读 shown }`：异常仍然会抛（浏览器的「uncaught exception」检查会抓到），但页面不会因此永久失联。

### 验证

- 单测 **526 全过**（新增 1 条契约测试）
- **端到端因果验证**：两个会话，A 在屏幕上、B 跑一个 ~6 秒的 turn。旧行为下 `1 other session(s) running` **轮询 60 秒都不消失**（而 B 的 turn 早已结束）；修复后 **4 秒内自己消失**，全程不刷新
- `ui-browser-check` 全过

## 九、侧栏：27MB 只为了找两个不存在的名字（已修）

### 现象与怀疑

读者报「有时候切换会话点了没反应」。我没能复现丢点击——**32 次点击零丢失**（快速连点、慢按、跨会话反复切、逐个切换）——但量出了另一个东西：**侧栏重建随会话数线性增长**，而它发生在每次切换和每次 turn 边界上。

### 根因

一个会话的 label 在日志**开头**，名字在**结尾**，中间没有索引。原来的做法是：

```moonbit
name: session_name_of(text)   // 读整个文件 + parse_session_file（全量 JSON 解析）
```

于是每个缓存失效的会话都要**读+解析整份日志**，只为找一个可能根本不存在的名字。侧栏上限是每工作区 10 个。用读者自己的 store（7 个会话、**27MB**）实测：

| | 耗时 |
|---|---|
| 启动到可服务 | **495ms** |
| 侧栏全部冷缓存的首屏（27MB 全读+全解析） | **+367ms** |
| 同上，但**只读不解析**（实验） | **+59ms** |

**80% 是解析，不是读。** 而对这份 store 来说，答案是：**7 个会话里一个重命名都没有**。

（顺带纠正一个容易搞错的点：`grep session_info` 会命中 5/7 个文件，但那些全是**对话正文里提到这个字段的散文**——agent 自己写文档时写到过。真正的重命名条目是 **0 个**。）

### 修法：先做一次便宜的预筛

只有 `session_info` 条目会写名字，所以先问一个便宜的问题：**这份日志里到底有没有重命名？**没有就完全不用解析。

预筛用的是**编码后的标记**，不是裸词：

```moonbit
pub fn name_entry_token() -> String { "\"type\":\"session_info\"" }
```

用编码形态的原因正是上面那条：`session_info` 会出现在对话正文里，匹配散文会让慢路径白跑一趟。

**正确性边界说清楚**：`false` 是**确定的**答案（没有重命名条目 = 没有名字可找）；`true` 只意味着「好好查一下」，仍然走原来的权威解析。所以这个改动**不改变任何语义**，只是跳过「确定没有」的那些。

### 结果

| | 修前 | 修后 |
|---|---|---|
| 侧栏冷缓存（7 会话 27MB） | 367ms | **130ms** |
| 启动到可服务 | 495ms | **214ms** |
| 热缓存 | 3.8ms | 3.8ms（不变） |

正确性三种情况都实测过：**有名字显示名字**（`deploy triage`）、**没名字显示首句**、**名字被清除退回首句**（符合「最后一次赢」）。

### 测试

两条：一条钉住**标记必须等于编码器实际输出的字节**（编码形态一变就报错——否则会出现「有名字却永远显示 id」这种查不出来的问题）；一条钉住**提到该字段的散文不算重命名**。

### 剩下的大会话切换延迟，不是这个

修完后最大的会话（14MB）切换仍需 **~1.0s**，24MB 的需 ~0.6s。那部分是**渲染整段对话**（11MB JSON → HTML），不是侧栏。这是另一件事，也是我先前建议**暂不做**的那件（分页/虚拟化会引入一堆新状态）。现在有了更准的数字，可以再决定。

## 十、连接安静地死掉：页面不知道自己收不到更新（已修）

### 现象

读者连续两次报同一件事：**任务其实早就完成了，页面还在显示「在跑」，按刷新才对**。这次的现场是一条跑了很久（`moon test` + 600s 超时）的命令。

### 根因：一条没有心跳的流

`/events` 只在**有帧的时候**才写。而一条安静 10 分钟的连接，**两端都无法察觉对端已经死了**：

- `EventSource` 只在**报错之后**才重连；半开连接（换网络、休眠、代理丢弃流）不会报错——可能几分钟，也可能永远不报。
- 服务端这边也没有心跳，所以它同样不知道。

于是页面冻结在最后一次收到的状态。**而刷新（= 重连，重连会收到全量快照）就把一切修好了**——这正是它难以报告的原因：服务端是对的、帧是对的，只是没人告诉浏览器「你已经断线了」。

### 修法

**服务端**：空闲时也发心跳，15 秒一次。

用**具名事件**而不是 SSE 注释（`: ping`）。注释更便宜，但 `EventSource` 会**直接丢弃注释、不触发任何回调**——那么唯一需要观察心跳的一方（浏览器）就永远看不到它。

心跳是**投递进订阅者自己的队列**，不是直接写 socket。两个原因，第二个是关键：
1. 保证**只有一个写入者**，心跳不会插进某一帧的字节中间；
2. **避免对 `queue.get()` 做超时包装**——那会**取消**挂起的读，而恰好在这一瞬间到达的帧会被丢掉。用「队列多一个生产者」换来读仍然是普通的阻塞读，不会为了治一个罕见的挂死而引入一个罕见的静默丢帧。

**客户端**：不信连接会自己报告死亡。

每一帧都自带活性信号——**有东西到达就说明管道通**。所以记录「最后一次听到声音」的时间，超过容忍期就**自己重建流**。

### 一个我写完才想到的坑（已修）

`connect()` 一开始**没有**刷新 `lastSeen`。后果：重连后如果仍然没帧（**服务端在忙，不是死了**），5 秒的检查会**每 5 秒重连一次**，而每次重连都要服务端渲染**整份快照**——慢服务器会被页面「帮忙」得更慢。

修法：**把重连本身当作一次活性事件**，这样重试被节流到每个容忍窗口一次。实测：17 秒内重建 **1 次**（修前会是 3–4 次）。

### 验证

- 服务端：裸 socket 实测，空闲 15.0s 收到 `event: ping`（chunked 帧格式正确）
- 客户端：`lastSeen` 在健康连接上保持新鲜（16 秒后仍远小于容忍期，证明心跳确实在到达并刷新它）
- 看门狗：人为把 `lastSeen` 置旧 → **7 秒内自动重建连接**；节流后 17 秒内只重建 1 次
- 单测 **536 全过**（新增：服务端心跳 1 条、客户端脚本守卫 1 条）
- `ui-browser-check` 全过、`ux-walkthrough` exit=0

### 还有一半没做

心跳管的是**连接**死了。但页面**在连接正常的情况下**也可能错过帧——那就是上一节那个「标签打错、帧被静默丢弃」的问题，已经单独修掉了。两条路合起来，才是「刷新就好」这个症状的完整解释。

## 十一、只渲染最近 N 轮 + 「载入更早」（已做）

### 先验证前提，再动手

你要求「前提是真的能提高切换流畅性」，所以我先量了三块成本（真实 14.5MB 会话，14 轮）：

| 环节 | 耗时 | 截断能省吗 |
|---|---|---|
| 服务端**解析日志** | ~300ms | **不能**（要先解析才知道 leaf/context）。而且只在**第一次打开**某会话时付，已打开的会话复用内存里的 Runner |
| 服务端**渲染 HTML** | ~141ms | 能 |
| **浏览器** parse+replace+layout | ~1084ms（其中 parse 284ms、replace 479ms、layout 121ms）|

后来发现还有第四块，见下。字节在 14 轮里**分布均匀**（无单点巨块），所以按轮数截断确实成比例省。

### 实现

- `render_transcript` 新增 `limit?`：**先收集、再取最后 N 个渲染**。不是先算「要跳过多少」——那个算术我写错过两次（最后一轮是循环结束后补推的，所以「数 user 消息」和「实际渲染轮数」差一）。收集很便宜（只是持有 session 已有的片段），而且不需要预测总数。
- **id 不重新编号**：`index` 照常前进，被渲染的 exchange 保留流式时的 id（`exchange-13-blocks`），否则针对它的 patch 会落空。
- 顶部一个 `N earlier turns` 的**显式按钮**，不是滚动触发。滚动加载需要「已加载到哪」这个状态在刷新、重连、切会话之间都成立——bug 就长在那里。这里 transcript 是「session + 一个数字」的函数，数字只在这一个地方变。
- 窗口是**每会话**的（在 Runner 上），默认 6 轮——所以普通会话完全看不到这个控件。
- 追加而不是只重渲染：一次 `refresh()`，滚动位置靠浏览器自身的 scroll anchoring（它就是为「视口上方插入内容」而存在的）。

### 结果（同一会话、同一机器 A/B）

### 结果（先更正上一版里被负载放大的数字）

上一版我写「4.8–6.0s → 1.3–1.7s，3–4 倍」。**那个 A/B 不干净**：当时机器上同时跑着多个服务端、headless Chrome 和编译，差值被放大了。机器空闲后重测，**同一个会话、交替点击、取中位**：

| | 全部 15 轮 | 6 轮窗口 |
|---|---|---|
| 页面 HTML | 3.35 MB | 0.98 MB |
| DOM 节点 | 30,619 | 10,013 |
| 整页加载 | 351–404ms | 166–203ms |
| 点击切换：服务端→首个 patch | ~260ms | **~118ms** |
| 点击切换：`replace:transcript`（浏览器） | 445–578ms，中位 **480ms** | 115–184ms，中位 **126ms** |

**能缩放的那部分约 3 倍**（浏览器替换 480→126ms，服务端往返 260→118ms）。不缩放的部分（侧栏、状态栏等固定区域）不受影响。前提**成立**，但幅度是 **~3 倍**，不是上一版写的 3–4 倍。

### 顺带更正：`decorateCode` **不是**瓶颈

上一版我怀疑 `decorateCode()` 是隐藏大头（一次测得 3391ms）。**干净测量推翻了它**：

| | 实测 |
|---|---|
| 窗口 6 轮下的 `<pre>` 数量 | 471 |
| 其中在**关闭的 `<details>`** 里（浏览器根本不渲染） | **469** |
| `decorateCode()` 耗时 | **12ms**（每块 0.02ms）|

那个 3391ms 是**我自己的测量假象**（在已包装的 DOM 上重复装饰，会嵌套放大）。

我据此加的「按语言缓存预留宽度」因此**量不出收益**。（它仍然是个正确的改动——原来每块读一次 `offsetWidth` 是 layout thrashing——但我不声称它带来了可测的改善。）

**另一个顺带发现**：`GET /?bust=...` 会 404，因为路由是精确匹配 `(Get, "/")`。我几次「页面是陈旧的」其实都是这个——我用 `?bust=` 想绕缓存，结果拿到了 404 页。不是 bug，但值得知道。

### 一个我自己功能里的 bug：点「载入更早」会丢失阅读位置（已修）

我原本声称「位置由浏览器自身的 scroll anchoring 保持」。**实测：锚点位移 4202px。**

原因：transcript 是**一个元素**，替换它是换掉整棵子树，而不是「视口上方插入内容」——scroll anchoring 不管这种情况，浏览器只是**保留 scrollTop**。而页面刚刚在读者**上方**长了高，于是读的东西**正好下移了增加的高度**。

修法：点按钮时标记「即将向上生长」，替换后用**高度差补偿** scrollTop。实测位移 **4202px → 0px**。

### 验证

- 单测 **550 全过**。新增 7 条：窗口精确渲染 N 轮（**对 1/2/3/6/13 逐个验证**，因为那个 off-by-one 不是常数）、id 不被重新编号、短于窗口时不动、`limit=0` 时渲染全部、scroll 补偿存在。
- 服务端逐字核对：`class="exchange"` 恰好 6 个、id 为 `exchange-9..14`、文案 `8 earlier turns`、963KB。
- 端到端 3 个 14.5MB 会话反复切换，每次 1.3–1.7s，均落到 6 轮 + 控件。

**`harness/ui-browser-check.mjs` 现在挂在一个 check 上**（等实时 tool 结果 `#transcript .result` 超时），**不是这个改动造成的**：我把窗口默认值临时设成 `0`（与改动前完全等价）后重跑，**照样失败**。那是并行编辑者进行中的「实时折叠」功能（同批新增了 `live_fold_test.mbt`，测试数 541→549），或实时 turn 的环境问题。我没有改那个功能，也没有改 harness。
