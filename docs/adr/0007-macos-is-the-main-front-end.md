# ADR-0007：macOS 是主线，Web UI 暂停；边界判据是「事实属于谁」

- **状态**：已采纳
- **日期**：2026-09-15
- **相关**：`macos/README.md`、`docs/macos-pitfalls.md`、`docs/adr/0001-no-vdom-framework.md`（路线一被否）、
  `README.mbt.md` 的「原生的第二个前端」、`macos/appffi/`、`ui/`

## 背景

`macos/` 最初是**为了验证边界**而存在的第二个前端：路线 B「界面重写，内核复用」要落地，就得有一个
真的界面来证明 `core/` / `platform/` / `agent/` 一行不改也能驱动。这个目标达成了 —— 那次交付里
`macos/appffi/` 是新的，下面三层没动过。

但接下来要决定的是另一件事：**以后往哪边投**。已经清楚的事实：

1. **两边都要维护的成本是真实的。** 同一个功能（设置面板、侧边栏、用量）要在 MoonBit 的 HTML DSL
   和 SwiftUI 里各实现一遍，而且两边会往不同方向漂。
2. **Web 版有一部分是不可替代的**：浏览器里能同时开多个会话、能贴链接、能分享；这些 macOS 端短期内
   做不到也不需要做。
3. **macOS 端拿到的是每天在用的那个**：它是 App、有菜单栏、有输入法、有系统材质、有平台控件。
   开发者自己的日常就在它里面。

## 决策

**1. macOS 端是主线；`ui/`（Web UI）暂停投入。**

不删、不重构、不为了它改下面的层。它的存在仍然有价值（第二个消费者、`html/` 那套 DSL 的验证），
但**不再作为 UI 基准**，也不再要求 macOS 端与它保持一致。删不删 `ui/` 是另一个决定，本 ADR 只记录
不再投入。

**2. 边界判据定为一句话：事实属于谁。**

这是这次开发花代价换来的，写下来因为它替代了原来那句含糊的「照着 web 版做」：

| 事实 | 归谁 | 例子 |
|---|---|---|
| 关于**对话/领域**的 | shell，一份 | 金额的小数位（`format_cost`）、图片是什么格式（`load_image`）、用量（`Session::usage`）、是否被压缩、上一轮是否中断 |
| 关于**这个窗口**的 | 客户端，不上线 | 滚动跟随、分组折叠、焦点、拖拽悬停、popover 开合 |
| 两个方向都依赖的**不变量** | 写在一处，**在坏了会丢数据的那一侧强制** | 流式行的 id 必须跨轮唯一 |

判据的形式化说法：**「谁能对这个事实负责？」** 不是「这个逻辑放哪边更方便」。

**3. 前端用平台写法，不再镜像 Web 版的布局与控件。**

备忘录式的列表+详情、`NavigationSplitView`、`.searchable`、`Section(isExpanded:)`、
`DisclosureGroup`、Liquid Glass、输入法 —— 这些在 Web 版里要手搓，在这里是白拿的。镜像 Web 版的
jQuery 式布局等于**两样都付**：既抄了一遍布局，又放弃了平台控件。

## 理由

**「照搬 Web 模式」的失败是具体的，不是抽象的。** 两个案例：

- **流式行的 id**：Web 版按轮命名（`stream-<turn>-<seq>`），macOS 侧把它抄成了每轮从 1 开始
  （`reply-1`）。形状抄了，**让这个形状安全的那个不变量没抄** —— 宿主是「按 id 找行再追加」的，
  于是第 2 轮的思考和工具行写进了第 1 轮的行里，转录看起来就是「上一轮的进度没了」。
- **输入框的状态**：dsh 的 composer 自己持有状态；macOS 第一版把 `draft` 提到 `RootView` 再用闭包
  传进去，正好是它避免的那种「第二份意见」结构，代价是**发送按钮/回车完全不工作**（详见
  `docs/macos-pitfalls.md` 第三组）。

**「什么都放客户端」的失败同样具体**：图片格式清单、大小上限、金额格式如果各写一份，就是两份规则，
而且一定会漂。所以它们留在 `load_image` / `format_cost` 里，和 `read` 工具、CLI 共用同一份判断。

**「平台写法」也不是免费**：每个平台控件都有自己的语义要去发现（⇧Return 在可增长的输入框里是
submit、`Group` 装不了 `Section`、嵌套 `Section` 会遮蔽平台类型）。所以要付的是**发现成本**，
而不是实现成本 —— 这笔账比手搓划算，但要在 `docs/macos-pitfalls.md` 里累积下来，否则每次重付。

## 后果

**变好的部分**

- 一个 UI 只有一处实现，不再是两处各漂一半。
- macOS 端可以按平台的方向演进（备忘录式的信息层级、系统材质、输入法、菜单栏、快捷键），
  不需要先回答「Web 版怎么办」。
- `ui/` 那 2400 行 HTML DSL 的维护压力消失。

**要付的代价**

- **「两个前端必须一致」这个验证机制变弱了。** 原来它是真的在干活：两侧各自钉住同一批 JSON 字面量
  （`macos/appffi/app_wbtest.mbt` ↔ `macos/PiShell/Tests/PiModelTests`），改一个字段名而只改一边，挂的是一个构建。
  这对**线格式**仍然成立（契约测试还在，`pi-shell-cli` 还是那股线上的第二个消费者），但「同一段
  markdown 两边画得一样」这类**观感**上的一致性检查没有了。以后 `md/` 或事件字段的改动，要靠契约
  测试和 `pi-shell-cli` 兜，不能靠「反正 Web 版也会发现」。
- `core/` 「不许碰 IO」这条硬约束的重要性上升了：它以前由两个后端（js/wasm-gc 的 `moon check`）
  守着，现在它是**唯一**那条把内核和界面分开的线。
- `html/`、`server/`、`ui/` 会慢慢腐烂。看到它们的代码时默认它可能已经过时。
- 新功能只需要一个前端，意味着**「这个功能该长什么样」不再有第二个答案来校准**。补偿办法是把设计
  理由写进 `macos/README.md`（现在就是这么做的），而不是靠对照 Web 版。
