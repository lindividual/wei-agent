# ADR-0001：不自己实现 VDOM / 组件框架

- **状态**：已采纳
- **日期**：2026-09-13
- **相关**：`README.mbt.md` 的「服务器渲染，不是单页应用」；提交 `baa4416`（删掉路线一）；
  ADR-0004（本 ADR 记的那件「正确的最小解法」后来做成了它）；ADR-0007（`html/` 已经删了，
  所以这条决定的现实分量变了：不再有第二个前端在验证它）

## 背景

有人（第二次）提出：要不要自己写一个类似 rabbita 的框架，把 UI 开发的效率提上去。

第一次是路线一：复用 pi 内核、用 rabbita 重写界面。它跑得起来，但和路线二并列意味着两边都停在
半成品，所以删掉了。删之前留下了一条可复现的结论。

## 决策

**不写。** UI 层继续用现在这套：一个 168 行的 HTML 树 + 序列化器（`html/node.mbt`）、一组渲染函数、
一个 4 种操作的 patch 协议，以及不到 100 行的客户端脚本。

## 理由

两个独立的理由，任一都足够。

### 1. 编译器层面：那层 DSL 在包外不可用

rabbita 的 `server_side_render` 在 `internal/` 包里，`Html::to_virtual_dom()` 的返回类型也来自
`internal/`，编译器强制 internal 可见性。唯一出口是整页 `App::render` —— 正是「流式输出」不需要的
形状。这不是偏好问题，是可见性规则，自己写一个也得重建这层 interface。

### 2. 架构层面：那类框架的本质与这个设计的性质互斥

VDOM 框架 = 客户端状态 + 一棵虚拟树 + 一次 diff。本设计的四条最有价值的性质，全部来自**没有**
这两样东西：

| 性质 | 为什么依赖「没有客户端状态/没有 diff」 |
|---|---|
| 服务器是文档唯一的写者，客户端和服务器不会「状态不一致」 | 客户端没有状态可分歧 |
| 客户端不到 100 行 JS，帧可以按字节验证 | 没有树要建、没有 diff 要跑 |
| 流式增量是 append，不是重渲染 | 没有 diff，所以不需要「哪里变了」 |
| 重连 = 重新拉一遍可变区域 | 服务器随时能重新渲染出全部状态 |

采用那个模型意味着把状态搬到客户端 —— 四条性质一起消失。效率提升买到的是「不用手写
`el("div", attrs=[...])`」，代价是一个新的失败模式类别，而这一类正是这个 UI 曾经踩过最贵的坑
（首帧发整页、客户端 `outerHTML` 替换 `#transcript`，结果是页面看起来正常、输入框和状态行却
永久失效，而所有字节层面的断言全部通过）。

## 后果

- 写 HTML 仍然是手写构造。**这部分可以改善，而且已经改善了**：`html/node.mbt` 的 `el`/`attr`/`cls`
  是一次调用的 interface，`html/theme.mbt` 里的 chip / panel / meter 是复用的组件。
- 若将来要治「标签是字符串、拼错编译不报错」这个问题，正确的最小解法是**给标签一个类型**
  （`div(...)` 而不是 `el("div", ...)`），只动 `html/`，不加客户端状态、不加 VDOM。这条当时被记为一次
  架构评审的「候选 B」，未被否决 —— **后来做成了 ADR-0004**。（那次评审本身不在仓库里，所以
  「候选 B」这三个字母在这里没有可点的去处；能点的去处是 ADR-0004。）
- 下一个 reviewer 不必重新推一遍理由 1，也不必重新提这个方案。
