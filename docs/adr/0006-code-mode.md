# ADR-0006：code mode —— 两个工具的模式，以及 `wait` 为什么必须存在

- **状态**：已采纳
- **日期**：2026-09-15
- **相关**：`core/code_mode.mbt`、`core/system_prompt.mbt`、`platform/tools.mbt`、`platform/jobs.mbt`、`platform/fs.mbt`、`core/settings.mbt`、`html/settings.mbt`

## 背景

`script` 工具上线后的第一次真实测量（`core/script.mbt` 的注释里也记着）：一个 604 次工具调用的
会话里，**507 次**走了它存在的理由那些形状 —— 266 次 `grep -rn`、99 次 `python3 - <<'PY'` 改文件、
66 次 `moon test`、52 次 `moon check` —— 而 `script` 被调用 **0 次**。工具在提示词里，手工调用时
能正常工作，缺的只是「被想起来的理由」。

结论不是「描述写得不够好」（那是上一个决定，也确实改了描述），而是**有八个动词可选的时候，
最省事的一步总是只动一个动词的那步**。只要 `read` 还在，读一个文件就没有理由写成命令；只要
`bash` 单独可用，一次 `grep -rn` 就比「写个程序一次问完」便宜。

因此要做的不是再加一个工具，而是一个**只给两个工具的模式**：`exec`（跑一件事）与 `wait`
（收一件已经跑出去的事打印的东西）。

## 决策

**1. 模式是设置，也是启动参数；下一轮生效。**

`ToolMode`（`Tools` / `Code`）与三个上限同构：flag > 设置面板 > 内置默认，且**读取点在每轮开头**。
工具集是请求的一部分（schema 在请求里，工具名在 system prompt 里），所以只能下一轮生效 ——
中途换工具等于让模型按旧 schema 的回答去用新工具。`App::tools()` 由设置派生而不是存字段：
一个存起来的数组漏刷新，就会和读者正在看的面板悄悄不一致。

**2. `exec` 一次一件事，两种方言写在一条 schema 上。**

- `bash`：shell 命令。
- `moonbit`：MoonBit 程序（`@builtin/NAME` 走内置脚本，否则当源码交给 `run_script`，与 `script`
  工具同一份实现、同一套预置库、同一个 staging 缓存）。

选哪一种由模型决定，而**一次调用只跑一种**。没有拆成两个工具，是因为拆开就又回到「两个动词」
了；「只能有一个」这条规则**写不进**这个项目实现的那套 JSON Schema 子集（`oneOf` 没实现），
所以它落在执行处，回一句模型能改的拒绝（`ExecDialect`）。同一个判定函数还被 driver 用：
`leaves_a_process(name, arguments)` 决定这次调用要不要开 job 记录 —— `bash` 要，`exec` 只在方言
是命令时要，`moonbit` 不要（它在调用内编译并跑完，`&` 起出去的进程不属于它）。

**3. `wait` 是唯一无法由 shell 表达的那块，所以必须自己提供。**

非交互 shell 里 `cmd &` 之后 shell 立刻退出：**没有任何东西会回到对话里告诉你那个进程后来打印了
什么**。现有设计里 `exec_managed` 恰恰总是把子进程的输出文件读走并删掉，所以「跑出去了」这件事
在 `script`/`bash` 时代是没有下半场的。做法：

- 命令返回且**留下了活进程**时，保留输出文件（`keep_output=true`），在 tool result 里点名 job id
  和 `wait` 用法，并把文件位置挂到 job 记录上（`JobOutput`：out/err 路径 + 已读偏移）。
- `wait` 从上一次读到的字节偏移继续读（`read_slice`，按字符边界切），所以等两次不会给两遍同一行。
- **有界**：默认等 120s、上限 900s、`timeout=0` 表示只取当前已有的输出；一次最多交回 32KB 并说明
  还有更多。后两条是为了「后台跑的是个只会写日志的服务器」这个真实形状：没有界，一次 `wait` 会
  把 turn 的时间预算花光、把对话撑爆。

**4. 输出文件的生命周期：本轮的活进程，跨轮即弃。**

文件路径**不持久化**（`Job.output` 在 `parse_job_store` 里读回 `None`）：它属于产出它的那次运行。
所以重启后 job 记录仍然有用（进程可能还活着、还能停），但 `wait` 会**明说读不到**，而不是去读现在
恰好叫这个名字的文件。命令返回后没留下活进程的，就地删掉。

**剩下的靠年龄收**（`clear_job_outputs(now)`，启动时跑一次）：超过 24 小时没被写过的 `job-*`
删掉。不能用「启动就清空整个目录」—— 那个目录是**机器的**临时目录，一台机器上跑两个服务器是
常态，先启动的那个没有资格删后启动那个正在等的输出。年龄是唯一能把两种情况分开的东西：还在被
等着的文件刚刚被写过，一天没人碰的文件属于一次真正结束了的运行。

**5. system prompt 跟着模式换。**

工具清单本来就是从声明生成的，所以不会列出没声明的工具；**「怎么干活」那段也必须换**：八个工具
那段里的「只读一个文件时 `read` 更便宜」在 code mode 下是在描述一个不存在的工具。turn 开头读一次
mode，同时喂给 prompt 和 schema，所以不会出现「提示词里有、请求里没有」。code mode 那段的重点是
它自己的难点：读文件是 `cat`/`sed -n`、搜是 `grep -rn`、输出要**在命令里**收窄（封顶保留的是末尾，
裸 dump 会正好丢掉要找的那段）、不能有交互式命令、`&` 留下的东西用 `wait` 收。

## 理由

- **喂给八个动词的对话，和喂给两个动词的对话，是两种工作方式**，不该由「这个 README 说优先用
  `script`」来调和。降低选择性比增加建议有效 —— 这一点有数字（507 vs 0）。
- **模式必须是可选的、可逆的、看得出来的**：它拿走的是读文件的唯一途径，所以 ① 不能是默认
  （默认不改变任何现有会话的行为），② 必须在面板里明说代价（「读文件要写成命令」），③ 必须一句
  话能切回去（`--mode tools`）。
- **`wait` 而不是 `kill`/`status`**：侧栏本来就能停进程，模型也能自己 `kill`；缺的只有「收集输出」
  这一件。加一个工具是加一个动词，而这里能省的都该省。
- **拒绝放在执行处而不是 schema 里**：这条 schema 子集没有 `oneOf`，而「两个都填」的拒绝文本能
  直接说出哪个错了 —— 这正是「先校验」比「信任形状」值钱的地方。
- **`settle_gone` 复用，但不能直接用**：

  1. `wait` 自己每 250ms 看一次进程表并落一次结算，因为服务端那个 2 秒的监督循环在 `pi`
     （一次性 CLI）里根本不存在，而 `wait` 需要「进程一没就返回」，不是「最多晚两秒」。
  2. **但「进程都没了」在内层窗口里是假的。** 后台命令的 shell 在命令返回前几毫秒就退出了，
     而记 pids 的正是那个还没返回的调用 —— 这一刻进程表看起来已经空了，而列表其实只有 shell。
     实测：`sh -c 'sleep 2; echo …' &` 三次里有一次在启动后 **20ms** 被记成「exited on its own」，
     记录连同它指向的活进程一起消失。所以 `Job` 多了一个 `call_open`，调用返回前（`note_execution`
     先调 `finish_call`）pids 不完整、一律不结算。它不持久化：重启后没有在飞的调用，表就是全部真相。

## 后果

- **`note` 在 code mode 下没有替代**：跨压缩的事实记录消失。不提供 `note` 的别名是刻意的 ——
  两个工具的模式里，第三个工具就是模式在漏。
- **图片读入退回占位**：`read` 是唯一能把图带回对话的工具。原本「没有图片」已是已知限制，但在
  code mode 下 `cat` 一个 png 会把末尾 50KB 变成乱码，模型要自己看出来不该这么干。
- **重启后 `wait` 读不到上次的输出**（设计如此，见 §4），文本里说明。job 记录本身仍然可读可停。
- **两处必须一起改**：`tools_for_mode` 与 `build_system_prompt(mode=)`。测试钉住了这件事 ——
  `core/code_mode_test.mbt` 断言 code mode 的提示词**不含**「For a single file, `read` is cheaper」，
  且不含 `- read:`。加工具时若只改一处，这个测试会红。
- `execute_tool` 多了一个 `jobs?` 标签参数：`wait` 要读会话的 job store，而它在 `agent/driver.mbt`
  里，不在工具层。省略它等于「这个调用方没有 job 记录」，`wait` 会说没有而不是崩。
- **`exec` 的 id 是 `<tool>-N`**（`exec-3`，不是 `bash-3`）。实测过：模型拿到「用 job id 去 wait」
  却不知道 id 是什么时，会先猜 pid 再猜 `bash-1`，白花两次调用 —— 所以结果里**直接写出 id**。
