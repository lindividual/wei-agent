# wei Agent 设计规范

**这份文档和代码是同一套数字。** token 在 `macos/WeiShell/Sources/WeiModel/Design.swift`（值，可测）和
`macos/WeiShell/Sources/WeiShell/Design.swift`（`Color` / `Font` / 图形 / 材质），`DesignTests` 把其中**能算**的
部分算出来 —— 对比度、比例顺序、栅格、logo 的对称与出檐。

为什么写成一套而不是继续手写：这份文档诞生前，窗口里有 **11 个字号**（5…22）和 **14 个间距值**。那不是尺度，
是一段历史 —— 每次改动都从「上次那个数看着还行」开始。

## 一、身份

| | |
|---|---|
| 名字 | **wei Agent** |
| 可执行文件 | `wei`（包内、`ps`、崩溃报告路径里用单字；文件名和 Finder 用全名） |
| bundle | `macos/dist/wei Agent.app` |
| bundle id | `io.github.lindividual.wei-agent` |
| 标志 | `wei-logo.svg` |
| 图标 | `macos/make-icon.swift` 画出来的，不是提交进来的 `.icns` |

**名字在三处必须一致**：Finder 显示的是 bundle 的**文件名**（只有 `CFBundleDisplayName` 会留下一个叫
`wei.app` 的文件配一个写着 "wei Agent" 的窗口）、Dock 和 app 切换器用显示名、`ps` 用可执行文件名。三处同源：
`make-app.sh` 里的 `NAME` 和 `EXECUTABLE`。

**应用内也出现名字**：最左栏左上角是标志 + 「wei Agent」（`Wei.MarkView(height: 18)` + `Font.control(.semibold)`）。这不是
装饰 —— 窗口标题改成「项目 + 会话数」之后，app 自己的名字在界面里**没有别的地方**出现了（只剩关于框和 Dock）。

### 标志的形状原样抄，不做「几何化」

`Wei.Mark` 是 logo 的**路径命令**，不是一组参数：

```
      ▟▙   ▟▙        ← 两条笔画：胶囊 + 一条向左下扫出的尾巴（尾巴就是 w 的暗示）
   ▁▁▁▁▁▁▁▁▁▁        ← 容器：顶边是一条中间下凹的曲线，底边平、底角圆
```

上一版把标志压缩成「圆角方里两条胶囊」，丢掉了**下凹的顶边**和**尾巴** —— 而那两样就是标志本身。所以这里是
路径：`move` / `line` / `curve(两个控制点)` / `close`。

三点实现上的事实，都踩过：

- **曲线是三次贝塞尔，不是二次。** SVG 的 `C` 带两个控制点；映射到 `addQuadCurve` 会把尾巴悄悄磨圆。
- **坐标系翻转只做一次。** SVG 是 y 向下、CoreGraphics 是 y 向上。手算翻转试了两次都错（先圆角跑到上面、
  再整个倒过来），最后是 `translate` + `scale(1, -1)` 翻上下文，**下面每个数字都还是 SVG 的**。SwiftUI
  那边**不需要翻** —— `Path` 和 SVG 一样是 y 向下。
- **两处绘制，一份数据。** 图标（CoreGraphics）在 app 编译**之前**就画好了，import 不到 `Wei`，所以常量在
  那里抄了一份；`DesignTests` 断言形状的三条性质（两笔画**互为镜像**、顶边**下凹**、笔画**有尾巴**），抄错
  任何一条都会挂。

**图标**：薄荷色瓦片（容器色即瓦片色，最干净）+ 标志占瓦片宽 78%。**验证到了什么程度**：用 WebKit 把
`wei-logo.svg` 渲染成 800px，和自己的绘制逐像素量边界框 —— pine 色区域的宽高比 **1.97 vs 1.98**，形状一致
（不是看出来的，是量出来的）。

## 二、颜色：**一个**色相，两个明度

| token | 值 | 角色 |
|---|---|---|
| `Wei.Brand.mint` | `#78E5A4` | 标志的容器色。浅色外观的**填充**，深色外观的 accent |
| `Wei.Brand.pine` | `#30714A` | 标志两条笔画的颜色。浅色外观的 accent，深色外观的填充 |
| `Wei.Brand.forest` | `#0E2A1B` | 深色外观里画在 mint 填充上的字 |

**一个色相的品牌，把「两种外观都读得出来」全部压在明度上。** 紫+黄那一版靠**换色相**；这一版靠**换明度**：
pine 够暗（白底 5.86:1）所以浅色外观用它当 accent，mint 够亮（暗底 10.75:1）所以深色外观用它。规则一样，轴
不一样。

代价明确，也写下来了：**mint 在白底上只有 1.55:1，所以它在浅色外观里只能是填充。** 这不是选色的缺陷，是
选色蕴含的约束 —— 有测试钉着（`testOneHueCoversBothAppearancesByLightness`，四条断言**包括两条「应该失败」
的**）：谁把 mint 拿去当浅色模式的 accent，失败的断言会解释为什么不行。

| 语义 token | 浅色 | 深色 | 用在 |
|---|---|---|---|
| `Palette.accent` | pine | mint | 交互：链接、焦点环、默认按钮、工作区绿点、工具的完成勾 |
| `Palette.onAccent` | 白 | forest | 画在 accent 填充上的字（**发送按钮**） |
| `Palette.highlight` | mint | mint | 品牌色当**背景**时（标志的容器） |
| `Palette.onHighlight` | pine | mint | 画在 highlight 上的字（**Running 胶囊**） |
| `Palette.highlightWash` | mint 15% over 白 | mint 22% over `#1E1E1E` | 胶囊的底、用户气泡的底 |
| `Palette.selection` | mint 30% over 白 | mint 30% over `#1E1E1E` | **列表里被选中的那一行**的底（会话行、工作区行） |
| `Palette.markFill` / `markInk` | mint / pine | mint / pine | 标志本身：容器用 mint、笔画用 pine，**两种外观同一组颜色** |

**选中那一行为什么不是 `highlightWash`**：胶囊和气泡是小东西、看一眼就过；选中的行是四十行里的一行，
读者要扫过去的 —— 15% 的洗色不构成「这一行被选中了」。30% 是那个分寸：看得出是品牌，不至于成为窗口里
最响的东西。两行的辅助文字（时间、项目名、工作区计数）在填充上用 `onHighlight`，因为灰字在品牌底上
只剩 1.86:1（`secondary` 3.84:1）—— 那不是「弱一点」，那是找不到。行的**名字**仍然是 `labelColor`。

**平台不给这个颜色，它是自己画的。** macOS 的 `List` 选中底色是**系统 accent**，`.tint` 到不了（详见
`docs/macos-pitfalls.md`），而且平台还会把选中行的默认色文字换成白色 —— 白字画在浅绿上，正是
`Wei.Ink.selection` 那条测试要拦的搭配。所以颜色是自己画的（`RowSelection`），平台的**画**被关掉、
**状态**留着（`selectionHighlightStyle = .none`，见 `macos/README.md`）。

**标志的两条笔画不再是 `accent`**：`accent` 在两种外观里换明度（浅色 pine、深色 mint），而标志是
`wei-logo.svg` 里一张固定的图 —— 深色外观下笔画被画成了和容器一样的 mint，标志变成一块纯绿。品牌色可以
随外观换哪个当 accent，标志不行。

**应用方式**：`.tint(Wei.Palette.accent)` 加在窗口根上，这是平台自己的机制。

**「用一点 logo 的颜色」落在四处**，都走 token：工作区那个「当前会话在这里」的绿点（原来是硬编码
`.green`）、用户气泡的底、Running 胶囊、工具完成的勾（原来也是硬编码 `.green`）。**错误仍然用系统的红** ——
那是平台传达「出错了」的方式，品牌色不该覆盖它。

### 对比度（`DesignTests` 实测）

| 前景 / 背景 | 比值 | |
|---|---|---|
| pine 字 / 白 | **5.86:1** | AA ✓ |
| 白字 / pine 填充（发送按钮） | **5.86:1** | AA ✓ |
| mint 字 / `#1E1E1E` | **10.75:1** | AA ✓ |
| forest 字 / mint 填充 | **9.92:1** | AA ✓ |
| pine 字 / 胶囊底（浅） | **5.47:1** | AA ✓ |
| mint 字 / 胶囊底（深） | **6.23:1** | AA ✓ |
| mint 字 / 白 | **1.55:1** | ✗ ← 所以它在浅色外观里只做填充 |
| pine 字 / `#1E1E1E` | **2.16:1** | ✗ ← 所以它在深色外观里只做填充 |
| mint / pine（标志的两色） | **3.48:1** | 形状可辨 ✓ |

### 中性色：一律**借**

灰阶全部用 macOS 语义色（`.labelColor` / `.secondaryLabelColor` / `.tertiaryLabelColor` / `.separatorColor` /
`.windowBackgroundColor` / `.controlBackgroundColor`），一个都不硬编码。理由不是省事：只有它们**回答**深色模式、
增强对比度、非活动窗口变暗。硬编码的 `Color.gray.opacity(0.2)` 在四个场景里错四个。

动态色用 `NSColor(name:dynamicProvider:)` —— 平台自己的机制，顺带白拿 increase contrast / reduce transparency 变体。

## 三、字体

五级。**比平台大一号，这是故意的。**

| token | 字号 | 职务 |
|---|---|---|
| `Size.title` | **20** | 对话栏标题（我们自己画的标题） |
| `Size.body` | **15** | 内容：转录、通知、要读的段落 |
| `Size.control` | **13** | 控件和列表行。**= `NSFont.systemFontSize`** |
| `Size.caption` | **12** | 计数、时间、状态行、胶囊。可读的下限 |
| `Size.micro` | **11** | 紧贴图标的数字，不用于正文 |

**三栏的层级**（「三栏字号看起来一样」就是这一条改的）：栏标题 20 / 会话行标题 15 / 行内时间与状态 12 /
控件 13。

**平台画的字不在这套 token 里，也改不了。** 窗口标题（中间栏那一行）是 `navigationTitle` /
`navigationSubtitle` 画的，而**它的字号没有 API 可设**：`NSWindow` 只有 `title`/`subtitle` 两个字符串，
AppKit 里没有任何 title font / attributed title，SwiftUI 的 `toolbarTitleDisplayMode` 文档明说
"This modifier has no effect on macOS"。量出来平台用的是 **13 semibold**（标题）和 **11**（计数）。

试过自己画（`toolbar(removing: .title)` + 自己的 item），**已回退**：那样画出来的是「窗口标题的照片」，
Window 菜单 / Mission Control / 辅助功能读到的仍是平台那份，两处会不一致 —— 而当初要自己画的理由
（把按钮放进这一栏）也不需要它：两个会话动作现在都在窗口尾端（见 `macos/README.md`）。

所以那张表要这样读：**`title`(20) 指的是我们画的标题**（现在只有对话栏那一个），平台画的窗口标题不在其中。

| 标题 | 谁画 | 字号 | 符合规范？ |
|---|---|---|---|
| 中间栏（列表栏）标题 + 计数 | 平台 | 13 semibold / 11 | **不适用**：不是我们的 token，也改不了 |
| 对话栏标题 | 我们 | `title` **20** semibold（实测宽 118.5pt，与标尺 20pt 的 118.5 一致） | ✅ |

会话行的**标题**取 `body`(15) 而不是 `control`(13) —— 行是读者**挑**的内容，不是他们**操作**的控件，
而且一个两行的行如果第一行和第二行一样大，就没有第一行。

**为什么 `body` 不是 13**：`NSFont.systemFontSize`（13）是**控件**的尺寸，而这个窗口是**读物** —— 转录是
读几分钟的散文，13 是控件的字号不是阅读的字号。所以「对齐平台」的锚点是 **`control` = 13**，`body` 比它
大一号。规则不是「抄平台」，是「知道自己画的是两件事里的哪一件」。有测试钉住这个锚点。

SwiftUI：`Wei.Font.title()` / `.body()` / `.control()` / `.caption()` / `.micro()` / `.code(size:)`。
等宽默认取 `control`；转录里的代码取 `body` —— 和周围正文字号一致，所以代码段和散文段在页面上重量相同。

## 四、间距：4pt 节奏，2pt 微调

| token | 值 | 用在 |
|---|---|---|
| `Space.tiny` | 2 | 同一行的两行文字之间（**唯一允许的奇数步**） |
| `Space.tight` | 4 | 控件内部：图标到文字、圆点到它的字 |
| `Space.cozy` | 8 | 卡片里堆叠项之间、胶囊内部 |
| `Space.regular` | 12 | 默认间隙、密集面的内缩 |
| `Space.loose` | 16 | 组之间、栏的内缩 |
| `Space.section` | 24 | 区块之间、面板内边距 |
| `Space.page` | 32 | 对话框、空状态四周 |

**「整体偏紧凑」就是这一条改的**：`regular` 从 8 到 12、`loose` 从 12 到 16、`section` 从 16 到 24、行高从
30 到 40、正文字号从 13 到 15。判断标准写在测试里（`testTheLayoutIsLoose`）：行高至少容得下两行正文，
控件高度至少比它的字大 16。

## 五、圆角与控件尺寸

| token | 值 | 用在 |
|---|---|---|
| `Radius.chip` | 8 | 胶囊、徽标、小的行内面 |
| `Radius.control` | 10 | 输入框、按钮（≈ 高度的 1/3，Apple 按钮的比例） |
| `Radius.panel` | 12 | 通知、内容里的分组块 |
| `Radius.row` | 14 | 行的选中高亮 |
| `Radius.surface` | 28 | 浮起来的输入卡片 |

| token | 值 | 用在 |
|---|---|---|
| `Control.regular` | 32 | 工具栏高度的控件（搜索框） |
| `Control.small` | 24 | 行内小控件 |
| `Control.row` | 40 | 两行文字的列表行 |
| `Control.hairline` | 0.5 | 分隔线、浮层描边 |

**间距在栅格上，圆角不在** —— 这个区别是有意的。间距是两个东西之间的距离，必须和别的间距同度量，否则一列
控件会一进一出；圆角是**一个角**的形状，是绝对量：32pt 的控件上给 12 会明显过圆，那里正确的值是 10，而它
不在 4 栅格上。**把圆角也塞进栅格是那种「让角落变错」的整齐规则** —— 这条规则我最初写在测试里，是测试失败
把它纠正过来的，注释留在那里。

## 六、浮层材质

**一个实现**：`weiSurface(in:)`。

- **macOS 26+**：`glassEffect(.regular, in: shape)` —— 系统材质，采样背后内容，自带发丝边和平台对「浮起来该
  多高」的意见。
- **macOS 14–15**：`.regularMaterial` + 0.5pt 发丝边 + 极淡阴影。

**26 上所有自己画的都刻意去掉**：玻璃上再叠自己的描边是第二道边，再叠自己的阴影是第二次抬升 —— 那正是
「像在模仿平台」。形状泛型，因为浮起来的不都是圆角矩形：搜索框是胶囊，它和输入卡片**同一种材质**。

## 七、组件

### 最左栏

```
🟡🟣 wei Agent          ← 标志（18）+ app 名字（control 13 semibold）
[🔍 Search all sessions] ← 搜索框（28 高，系统 NSSearchField）
Workspaces              ← 分组标题（caption 12 + secondary）
[+] Add Workspace…      ← 和项目行同一个 glyph 槽位
📁 wei-agent      ● 1   ← 文件夹图标 + 名字 + 会话数 + 绿点
📁 pi-web-shell    22
▸ Running sessions      ← 只在这两种东西存在时才出现，而且在项目**下面**
▸ Running tool calls
```

- **这三行是这一栏自己的话：标志/名字 → 搜索 → 列表。** 标志和搜索曾经都在**工具条**里，而工具条是
  52pt 高、整窗共用、**一行深**的一条带子：两个东西叠不进去（会去挤压旁边的按钮），而搜索是平台的
  accessory band（自己画的东西到不了它上面）。所以名字回到第一行，工具条只留给设置齿轮。
- **列表的顺序是**窗口的**，不是 store 的**（`WeiModel/Sidebar.swift` 的 `stableSidebarOrder`）。第一次列表用 store 的顺序
  当种子（所以打开 app 时看到的仍是「最近用过的在上面」），之后位置就固定下来：store 的顺序是「最新写入的在前」
  （`list_workspaces` 按组内最新会话的 mtime 排），而 turn 一直在写文件 —— 实测两个项目的最新会话相差 **0s / 2s**，
  于是每次 `sessions` 事件它们就换一次位，整个列表跟着上下走 32pt。只有**没见过**的行/组才动（走到最前：那是读者自己
  刚开的会话/刚加的项目），取值（`running`、标题、计数）永远取线上的。`RootView.workspaceLabel` 也读同一份数组，
  所以行和它的名字不会各说各话。
- **第一行标题上面的那 16pt 空气，是那一行自己的 `padding(.top:)`，不是列表的 `.contentMargins(.top:)`。**
  两者静止时长得一样，点击时不一样：滚动内容的边距属于**滚动视图**，重新套用是另一趟，中间那几帧这一栏就被画成
  没有它的样子（实测：整栏文字在那些帧高 16pt，稳定后复位）。规则：**边距要跟着行走的时候，就写在行上。**
- **列表里「不变的在上、会变的在下」。** 两个运行小节一度在最上面，而它们是条件出现的：一个 turn 开始
  或结束、一条 `bash` 开始或结束，它们就整块进出，把下面所有项目行连同鼠标目标一起推下去再拉回
  （实测：第一个项目行 `y=226`（无运行）↔ `378`（一个 turn + 一条命令），差 152 = 两个小节的
  33+41 和 33+45）。读者瞄的是项目，所以项目在上、寄存器在下。代价是**项目多到填满这一栏时寄存器
  掉到折线以下**，这是明知的取舍：读者要点的东西必须在原处；「有没有在跑」在会话栏那一行（`Running` 胶囊）
  和输入框的 Stop 上还有一份，而中栏那个正是最要紧的那个（屏幕上的这个 turn）。
- **搜索框是系统控件，换的是谁来摆它。** 用 `NSSearchField` 而不是自画的胶囊，是因为自画的 `.glassEffect`
  胶囊压在侧栏材质上会**发黑**（实测：填充 124–138，而侧栏本身 220–247）。

### 中栏

```
wei  7 sessions         ← 栏标题（平台画的：项目名 + 计数）
Today                   ← 分组标题（control 13 semibold + secondary）
macos 版还缺少…停止会话；切换会话。请实现
9月17日                  ← 名字（control.medium）+ 时间（caption 12 第三档色）
```

- **标题栏归中栏**：三栏 `NavigationSplitView` 里 content 栏赢得标题，detail 栏的 `navigationTitle` 被忽略。
- **搜索框在这一栏上面那道？不是。** 搜索在**最左栏**（查询跨所有项目，放这里会被读成「筛当前项目」）。
- **会话行的第三行只在「有话说」时出现**：搜索结果是项目名，有回合在跑时是 `Running` 胶囊。
  名字和「多久以前」是每行都有的；项目名曾经常驻，但它就是窗口标题里那个词，日常视图里每行再读一遍
  不值一行位置。代价：跑着的行比别的行高一行。
- **新建会话按钮在窗口尾端的工具条里**（`plus`）；`pencil` 在旁边。两者都是平台自己的工具条按钮。
- **搜索框的形状是明知故犯的偏离**：macOS 的标准搜索控件是 `NSSearchField`（`.searchable`）—— 圆角**矩形**、
  位置由修饰符决定。三栏里「这一栏」不在它支持的 placement 里，落到工具栏又像在搜对话。取标准控件的**行为**
  （前置放大镜、内联清除、Return 提交）+ 工具栏按钮的**形状和高度**。**胶囊在 macOS 上不是搜索框的标准形状**，
  那是 macOS 26 工具栏按钮的形状。

### 状态胶囊 `StatusChip`

`Font.caption` + `Space.tight`/`Space.tiny` + `Radius.chip` 的胶囊 + `highlightWash` 底 + `onHighlight` 字 +
一个 `Icon.mark` 的圆点。**它是两色系统在一个控件里的全部**：底取「在这个外观里当背景能读」的那个色相，字取
「在这个外观里能读」的那个。

**只画线上真有的状态**：每行传来的字段只有 `running`。

### 对话栏

```
会话名的标题（Font.title 20）+ 模型 · 目录（Font.caption 12，secondary）+ 发丝线
转录
```

- **对话栏有它自己的标题**，因为三栏 split 里窗口标题归中栏。这里画的是 web UI 钉在转录上方的东西：会话名，
  以及下面两件读者会在中途核对的事实 —— 哪个模型、工具在哪跑。这两件原来在窗口副标题里，三栏之后没有副标题了。
- **打开会话落在末尾。** 会话是从结尾读的；不加这条，切换过来的第一帧是九十轮日志的**顶部**，那是没人想从那里
  开始的地方。和「跟随」是**两条规则**：跟随是「跟上还在变长的转录」，必须尊重一个滚上去读东西的读者；这条是
  「我刚被交到另一段对话手里」，无条件落底。web UI 是同样的判断。
- **折叠长内容**：工具输出默认只显示两行（`lineLimit(2)`），点「Show all」展开；思考块**到达时画末尾 3 行**
  （固定高度、点击展开全部），**停止流式之后**折成一行「Reasoning」。一个打印 400 行的工具是常态不是例外，
  永远摊开的日志会把读者要看的下一件东西顶出屏幕。规则在 `WeiModel/LiveWork.swift`（3 行尾巴、`reasoningPeek`）
  和 `RootView.swift` 的 `ThinkingRow`，取舍写在 `macos/README.md`。
- **一个 turn 有两种折叠，看它跑没跑完**：跑完的按「轮」折（`Worked through …`，理由见 `WeiModel/Turns.swift`）；
  正在跑的只留**最新一个 tool call**，更早的折成一行 `N finished tool calls`。思考和中间那些正文不进这个折叠
  —— 把模型解释自己为什么调工具的话藏起来，屏幕就只剩一个转圈。

### 空状态

列表为空时说**为什么**（「这个项目里没有会话」/「没有匹配的结果」/「没有选中项目」），居中、`Font.control` +
`secondary`。没有消息的空列表和「还没加载完」在屏幕上一模一样。

同一条原则用在**转录**上：刚接手一段还没从 shell 读回来的会话时，那一栏画一行 `Opening…`
（`RootView` 的 `OpeningNotice`），因为「这个会话是空的」和「rows 还在路上」在屏幕上是同一个画面。
措辞是**读者的动作**（「打开中」）而不是机器的动作（「加载中」），而且**不用 spinner**：等待以毫秒计
（30MB 会话约 150ms），一闪而过的转圈看起来像闪屏而不是进度。

### 输入区的两个菜单：模型与档位

工具行里 `模型 ▾` 和它右边那个 `◠ High ▾`。**两个菜单是同一个判断的两半**：模型是*谁*答，档位是*花
多少力气*答 —— 都是关于「这条消息会被发成什么」的决定，所以都在写消息的地方，不在设置面板里。

| 元素 | 画的 | 按下去 |
|---|---|---|
| 模型 | 模型名（`Font.micro` 11，secondary）+ 8pt chevron | 换下一个 turn 用的模型 |
| 模型菜单表头 | `US dollars per million tokens — in · out · cached`（二级色，不可点的一行） | —— |
| 模型项 | `0.14  0.28  0.0028   DeepSeek V4 Flash`；不能看图的带 `· no images` | 换过去，并再说一次合规性 |
| 档位 | `brain`（`Icon.inline` 12）+ 档位名 + chevron | 换下一个 turn 的思考档位 |
| 档位项 | `Low — thinks briefly; a sooner first word` | 换档位；模型没有这档就不接受，并说一句为什么 |

- **档位用平台的 `Picker` 语义**（菜单里带勾），因为问题是「哪一个」而不是「还要不要做这件事」：
  勾就是读者在问一个贵问题之前唯一要核对的东西。
- **可选档位是 shell 给的，宿主不写表。** 档位是**每个模型**的事实（flash 有 `low`、pro 没有），
  菜单画的是 shell 说这个模型有的那几个 —— 宿主自己编一张表就会给出 API 会拒的档位。
  所以 `think` 事件和 `models` 事件是两个事件，各自的列表长度不同。
- **两种字号**：工具行里模型名和档位名都是 `Font.micro` 11（`⊕` 那一排是小图标 + 小字的尺寸），
  不是 `Font.caption` 12。这一行是**扫一眼**的东西，不是读的段落。
- **档位的字写在 shell 里**（`level_detail`），因为「`low` 意味着什么」是关于 provider effort 的事实；
  宿主只负责把它排成 `名字 — 那句话`。价格同理：**三个数按列对齐**（`Pricing::columns`），宽度取自整个
  catalog，所以行与行之间数字落在同一列 —— 这是「比较」这个动作的前提，而宿主自己编一遍就是第二份实现。
- **模型菜单里价钱在名字前面**，和「档位」相反。因为价是要**上下比**的那一列，而名字宽窄不齐；把名字放
  前面，它会把右边每个数字都推一下。这是排版规则被数据形状决定的一个例子：不是「哪个读起来更顺」，
  是「哪个能对齐」。
- **那句话写到刚好一个从句，单位是「点」不是「字」。** 菜单的宽度**等于它最长的那一项**（AF 实测：
  第一版把话写全，最长项 470pt / 整菜单 **511pt**），而菜单不能折行 —— 所以散文式的说明在这里是
  按宽度付费的。现在最长的一项是 330pt（`NSFont.menuFont` 量文本）。判断标准：一句话只保留
  **读者能拿去行动的那个后果**（`off` → 答案可能更浅；`max` → 最慢最贵）。
- **档位名不进标题栏、不进转录**：屏幕上的名字是 `High`，而发出去的是 `high`；两者是同一个概念的两个
  写法，出现在两个地方（给人看 / 给 API 看）。终端里对应 `/think <level>`（选）和 `/think`（问）。

### 麦克风按钮 `Composer` 里的听写入口

`⊕` 旁边那个，**形状跟 `⊕` 一样**：24×24 的圆、`Wei.Icon.inline` 的字（这是工具行里"小图标"的尺寸，
不是 `Control.small`）。两个控制做同一件事（往里加东西），长得一样是故意的。

| 状态 | 画的 | 按下去 |
|---|---|---|
| 空着 | `mic` 描边 | 开始听 |
| 正在准备 | `mic.fill` | 取消 |
| 在听 | `mic.fill` 加粗 + `highlightWash` 底 + **accent 描边环** + **脉冲** | 结束这句 |
| 定句中 | 同上 | —— |
| 下模型中 | 小 `ProgressView` | —— |
| 麦克风被拒 | `mic.slash` | 打开隐私设置 |
| 模型没装 | `arrow.down.circle` | 下载 |
| 其它失败 | `mic.slash` | 再试一次 |

- **「在听」用 `highlightWash` 而不是红点。** 这个 app 只有一个强调色和一个高亮色，而录制指示器是一个
  *背景* —— 那正是 highlight 那个色相被选来做的事。真正的反馈是字在输入框里一个个出现，那里本来就是读者在看的地方。
- **但底色不够，所以有第二个信号。** 只换底色被读成「这个按钮被选中了」，而不是「现在正在发生」：
  再加一圈 `accent` 描边（同一个圆、同一个尺寸，所以什么都不动，只有「多了一条边」在说话）和
  符号自己的脉冲（`symbolEffect(.pulse, options: .repeating, isActive:)`，只在 `isListening` 时跑）。
- **发送按钮在听写期间是可用的。** 按它 = 结束这句话 → 等它落进输入框 → 发送。禁用版本被读者
  当场否掉了：说完了、字在框里、箭头是灰的，而且没有任何东西解释为什么。
- **一个按钮，一个状态一件该做的事。** 没用弹出菜单、没有「出错才出现的第二个按钮」：上面每个状态都
  只有一件下一步，而一个**能做**这件事的按钮比一个列出这件事的菜单好找。按钮要做什么写在 tooltip 里，
  用词说 —— 一个图标说不出「这个语言在这台 Mac 上还没模型」。
- **tooltip 和 `accessibilityLabel` 是同一个字符串**（`dictateHelp`），两个不会描述出两个状态。
- **错误不弹窗。** 听写失败没有东西需要被打断（没有正在提交的东西、没有会丢的数据），所以就在按钮上
  就地说明（和「中断的回合」那条同一个判据）。

## 八、没抄备忘录的什么

| 备忘录有 | 我们没有 | 为什么 |
|---|---|---|
| 格式工具栏 | — | 我们发纯文本 + 附件，markdown 由模型生成，没有「格式」这个动作 |
| 附件浏览器 | — | 附件属于消息，不是独立对象 |
| 「无更多文本」摘要行 | — | 会话的第一句提问就是它自己的摘要 |
| 时间为纲组织笔记 | 项目**再**时间 | 笔记没有「工作目录」这个轴；会话有，而且工具在哪跑是一等事实 |
| 正文列搜索 | 搜**会话名和目录** | 搜正文要读每个文件 —— 那是这个 shell 处处在避免的成本 |

## 九、怎么用，怎么验

```swift
// 颜色
.foregroundStyle(Wei.Palette.secondary)
.background(Wei.Palette.highlightWash, in: Capsule())
.tint(Wei.Palette.accent)                    // 一次，加在窗口根上

// 字体
.font(Wei.Font.control(.medium))
.font(Wei.Font.code(Wei.Size.body))

// 间距与圆角
.padding(.horizontal, Wei.Space.loose)
RoundedRectangle(cornerRadius: Wei.Radius.control, style: .continuous)

// 浮层与标志
.weiSurface(in: Capsule())
Wei.MarkView(height: 18)
```

**规则**：这个文件里**不出现裸数字**。字号、间距、半径、颜色都走 token；真要新的一档，那是**改规范** ——
改在 `Design.swift` 并让 `DesignTests` 重新算对比度，不是在调用点写一个 7。

```bash
cd macos/WeiShell && swift test --filter DesignTests   # 对比度、比例顺序、栅格、标志几何
```

**这套规范没做到的**（老实说）：

1. **深色模式没有真机对照**。两个色相的对比度是**算**出来的，深色下的实际观感没有验证过。
2. **`List` 的选中底色：已经查清，但用的是平台外的办法。** `.tint` 确实到不了 `List(selection:)` 的选中底色
   （macOS 26 上四种 list style 全试过，都是系统的 `#0064E1`），而且列表聚焦时平台还会把选中行的默认色文字
   换成白色。现在是自己画（`RowSelection`）+ 把平台的画关掉（`selectionHighlightStyle = .none`）。
   代价写清楚了：这是一处 AppKit 逃生门，列表自己的箭头键选择、`AXSelected` 都还在（只关了「画」）。
3. **动效没有规范**（时长、曲线）：现在只有一处 `.animation(.default, value:)`。
4. **栏宽断点没有规范**：三栏的 min/ideal/max 各自为政，没有一条「窗口窄于 X 收起第一栏」的规则。
5. **没有「密度」这一维**：行高、内缩、字号绑在一起的整体档位（紧凑/宽松）还不存在，现在只有一套。
6. **两个菜单的「弹开之后」没量到**：闭合的控件是**量过**的 —— AX 读到 `AXMenuButton | Thinking: High
   [985,806 58x17]`，可访问性名字也在（`High` 单独出现时没有「这是思考档位」的意思，所以标签是
   `Thinking: High`）。但菜单弹开的宽度**只有算术**（`NSFont.menuFont` 量文本 + ~40pt 内边距 → 最长项
   330pt），没有实测：这台机器上有一个常驻探针进程占着 frontmost，菜单根本不弹（`docs/macos-pitfalls.md`
   第六组有这条）。按工具行的自查：`Thinking` 文字对得齐、58pt 宽，和模型菜单并排后没挤到别的控件
   （`AXTextField` 792pt 仍在原位）。**「算出来的宽度」不要写成「量出来的宽度」。**
