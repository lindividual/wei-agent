# Jev（System One）能用在哪些地方 —— 一份落到本仓库的评估

> 结论先行，然后是三条候选线的具体形状、成本、验收和**不建议做**的部分。
>
> 和 `docs/local-model-context.md` 是同一类文档、同一把尺子：那篇问「本地小模型放在哪」，
> 这篇问「一个 70–500ms、$0.042/MTok、**只输出结构化决策**的远程模型放在哪」。
> 两者在**同一个位置**上得出同一个否定结论（见 §3.3），值得先看一眼那篇的 §2。

## 0. 先说结论

| 候选 | 值得做吗 | 理由（一句话） | 成本 |
|---|---|---|---|
| **系统一/系统二路由**（推理档位、收尾判定、风险门） | **值得，而且先做这个** | 唯一能在**已有日志**上先把准确率量出来的方向；而且**推理档位今天是手动档**（读者能选 `off/low/high/max`，见 §5.5，但选哪个还靠人） | 一个新包 + 一个默认关的开关 |
| **上下文压缩优化** | **值得，但靶子要换** | Jev 写不了摘要（不能生成），但它能**判别**和**验收**；而 $4.61 那个杠杆根本不在模型手里 | 落盘格式要先定，改晚了很贵 |
| **computer use / web bridge** | **值 1 个 spike，不值一个项目** | 输入必须是无视觉的文本（AX/OCR/快照），这套东西我们已经为截图付过一次账了；但它是**全新表面**，失败模式最多 | Swift 侧 AX + OCR；web 那半可以零 Swift |
| 让 Jev 当主循环模型 | **不做** | 它不生成，而我们的主循环产出的是工具参数和文字 | — |

三条里**只有一条现在就该动手**（§8 的顺序），另两条的第一步都是「离线、零 UI 面、能回退」。

**要按接入点看行动顺序，直接翻 §11 的总表**（按「读者能感觉到 × 把握 ÷ 改动面」排，不是按省钱排）。

## 1. Jev 是什么，以及它的硬边界

一次请求，一次响应，没有对话：

```
POST https://api.typesafe.ai/v1/systemone     Authorization: Bearer <key>
{ "model": "jev-latest",
  "state": <string | object | array>,          // 要判断的东西，一次吃进去
  "questions": { "<你自己起的 id>": { "type": "noul" | "choice" | "score",
                                      "instructions": "...", "criteria": ... } } }
→ { "model": "jev-1.13.0",
    "answers": { "<同一个 id>": { "noul": 0.92 }
                              | { "choice": "technical", "probabilities": {...}, "confidence": 0.82 }
                              | { "score": 1.6, "legend": {...}, "probabilities": {...}, "confidence": 0.78 } },
    "usage": { "input_tokens": 312, "output_tokens": 48 } }
```

| 事实 | 数 | 对我们的意义 |
|---|---|---|
| 价格 | 输入 **$0.042/MTok**，输出免费 | 一次典型决策 ≈ **$0.0002**；**加问题几乎不要钱** |
| 延迟 | **70–500 ms** | 可以放进一轮的必经路径，而不会让读者等（对比 3–329 s） |
| 窗口 | **64k**/请求；state + 最长的问题 ≤ **32k** | **装不下我们任何一段真实历史**——见 §3.3 |
| 选项数 | Choice 最多 **255** | 工具清单、会话清单、屏幕 item 都在里面，但屏幕上 4000 个节点不在 |
| 输入 | 只有文本。**没有图像/音频/视频** | computer use 必须先把屏幕**读成文字**（AX 树 / OCR） |
| 频率 | 250k tokens/s、1200 rpm，429/529 退避 | 单机够用；但它是一条**远程依赖**，要有确定性回退 |
| 输出保证 | 结构绝对合法（不会 type error） | 换来的是：**它不会走形**，但**会给出一个合法的错答案** |

它**做不到**的四件事，每一条都关掉一个候选：

1. **不生成**：写不出摘要、写不出工具参数、写不出一个 URL（`type_text` 这种字段只能交给会写的模型）。
2. **不可靠地计数、比较日期、排序**：这些是算术，留给我们自己的代码。
3. **不做多步推理**：需要连推两跳的问题，拆成两次请求。
4. **不是视力**：截图理解今天在能力之外。

还有两条操作性的事实值得记下来，因为它们直接影响架构而不是调参：

- **扇出只收一次 state 的钱。** 同一个 state 上问 10 个问题是**一次** state 摄入。所以
  「拆成 10 次请求」不只是慢 10 倍，是贵 10 倍——**决策要按「一步一请求、多问题」来设计**。
- **上下文腐化是真的。** state 里塞进与问题无关的材料，准确率就掉。成本约束（state 越小越便宜）
  和准确率约束（state 越小越准）指向同一个方向，这很少见，要利用它。

## 2. 和本仓库现有设定的对账

`docs/local-model-context.md` 得出的三条结论，换成 Jev 之后要重新读一遍——因为**变的是动机，不是约束**：

| 那篇的结论 | 对 Jev 还成立吗 |
|---|---|
| 「**不要改写已发送的内容**」——前缀缓存按字节前缀命中，投影期重写会把后半段全部按新输入计价 | **完全成立**，而且更硬：Jev 的答案不是逐字可复现的，同一条工具输出问两次得到两个不同的 keep 集合。**决策必须落盘**，否则每一轮的投影都不同，缓存命中率归零 |
| 「用户本地模型的真实优势是**隐私**，不是更快更省」 | **不成立，反过来了**。Jev 把 tool 输出发到第三方，隐私是**新增的代价**；换来的是速度和成本。这也是它唯一比本地模型强的地方——**它不需要一台符合条件的机器**（本地路线在 Mac14,2 上死在 `deviceNotEligible`） |
| 「先做阶段 0，别先接模型」 | **仍然成立**。见 §8：$4.61 那个杠杆不在模型手里 |

另外两件本仓库已经付过账、这次可以直接用的事：

- **上下文占用是锚定出来的**（`core/context_pressure.mbt`：用 provider 实报的 `prompt_tokens` 做锚，
  相对误差 17% → 0.2%）。**任何 Jev 方案的收益都用这个数验收，不要用字符 ÷4 估**，
  也不要只看决策自己的花费——要量整个 turn 的账单（`core/session_usage.mbt`）。
- **精确事实已经有一条确定性的抽取链**（`core/facts.mbt`：路径、命令、错误行的正则；
  `assemble_summary` 把它们逐字附在摘要后面）。**规则能读出来的东西不要再问模型**，
  这是 TypeSafe 自己文档里的第一条元规则，也是这个仓库的既有品味。

## 3. 应用一：computer use / web bridge

### 3.1 参考实现已经给了答案，照抄它，不要照抄「大模型看截图」

[`awlevin/typesafe-computer-use`](https://github.com/awlevin/typesafe-computer-use)（MIT，macOS）
是一个把 Mac 朝一个自然语言目标驱动的 loop。它的核心决定是：**从不把截图发给大模型。**

```
screencapture ─► Vision OCR ─► 合并成文本块 ─► 丢掉与目标重复的行
accessibility ─► 可操作元素（role/label/frame），剪掉不在屏上的，被剪掉的带 label 的留着当离屏控件
                     └─► 一张**带编号的清单**，每项带着来源（ocr / ax / ax+ocr）
accessibility ─► 当前聚焦字段 · AppleScript ─► 前台 app / URL · 时钟 ─► 日期时间
                     │
                     ▼
        一次 TypeSafe 请求，三个 **互斥的 Choice**（有离屏控件时四个）
        kind: click_item | use_browser | type_text | scroll… | done | none
        item: 点哪一项（只给 click_item 用）
        site: 去哪个站（只给 use_browser 用）
                     │
                     ▼
        确定性执行 ─► 等待 ─► 下一步        会写的模型只在真的需要自由文本时被叫
```

它量出来的数（同一个截图、同一个目标、各一次决策）：

| | Jev | Opus 5 直接看截图 | 倍数 |
|---|---|---|---|
| 单次决策成本 | $0.0002 | $0.032 | **155× 便宜** |
| 模型延迟 | 0.13–0.38 s | 5.2 s | 14–40× 快 |
| 端到端一步（含抓屏 + OCR） | ≈1.5 s | ≈5.5 s | 3.7× 快 |
| 一个 12 步任务 | $0.003 | $0.40–0.90 | 130–300× 便宜 |

**它最诚实的一句话，也是我们要抄的那句话**：

> 「大模型在像素上免费做的那部分推理，这里必须重建为确定性的状态。」
> （作者的例子：日期。Jev 眼里日期是文本不是序数，所以 `dates.py` 自己解析、自己算「in 27 days」。）

三条可以直接搬过来的工程经验：

1. **把决策切成互斥的窄问题**。作者的原话：**每一个卡住都来自两个意思相同的选项**——
   置信度衡量的是概率的集中度，选项一重叠，读数永远是「不确定」。所以
   「下一步做什么」和「做在哪个元素上」要分成两个 Choice，而不是一个「大动作」。
2. **AX 有覆盖盲区，只能当加分项**。实测（同一台机器十个 app）：Finder 100% 有 label、
   Chrome 88%、Slack 85%、Notion 68%、**Spotify 0%**。终端把整个网格暴露成一个文本区。
   所以 OCR 是主源，AX 是「图标也能看见」的那一半。
3. **抓屏比决策贵**。一步里 OCR 占掉约三分之二。做 web 的时候这件事反过来——
   见 §3.4，网页快照是一次 JS 调用，比整屏 OCR 快一个数量级。

### 3.2 落到本仓库：哪一半在哪一边

本仓库已经有一条分界：**关于对话的事实归 MoonBit，关于窗口的事实归 Swift**。computer use 正好可以按这条线切，而且两边都有一半已经存在：

| 层 | 归属 | 今天的状态 |
|---|---|---|
| 抓屏 + 三种结局（拿到图 / 读者按了 Esc / 被拒） | Swift | **已有**：`WeiModel/Screenshot.swift`，规则带测试 |
| 录屏权限的申请与复查 | Swift | **已有**：`WeiShell/TCCProbe.swift`；`make-app.sh` 用稳定身份签名，所以权限能扛过重建——**这是最贵的前置条件，已经付过了** |
| OCR（Vision）、AX 树遍历、动作执行（`AXPress` / `CGEvent`） | Swift | **没有**，要新写；参考实现的剪枝规则（跳过不在屏上的子树、跳过 <4pt 的节点、跳过 `AXMenu`、4000 节点 / 0.6 s 上限）是现成的标准 |
| 状态组装 + 发一次请求 + 解析答案 + 落盘 | MoonBit | `platform/http.mbt::post_json` 已有；请求体构造应该是纯函数、可离线测 |
| 「能不能驱动这台机器」的策略、暂停、交还 | 两边 | **没有**，见 §3.5 |

### 3.3 不要做的事：让 Jev 帮你「看这一屏然后规划」

- 它没有视觉入口。走截图就要自己接 OCR + AX，那部分工作是**平台工作**，和选哪个模型无关。
- 单屏 item 数（AX 走完 172 个控件是常态）在 255 个 Choice 的边界之内，但**一张屏幕的
  OCR 文本轻松超过 32k state 预算**。参考实现的解法是「清单化 + 裁剪读区」，那就是
  「先确定性提取候选，再让模型挑」——**过滤在前，判断在后**。

### 3.4 web bridge 那半：先用已有的桥，零 Swift

这台机器上真的有一个可用的桥：`kimi-webbridge`，本地守护进程 `127.0.0.1:10086`，
它的 `snapshot` 返回的**就是可访问性树文本 + `@e` 引用**，`click` / `fill` / `evaluate` / `screenshot`
都是现成的动作。也就是说，**网页这一半需要的输入形状，今天就是对的**——不需要 OCR、不需要权限、
不需要新 Swift：

```jsonc
// 状态 = 目标 + 快照（文本），不是像素
{ "state": { "goal": "把最便宜那档票的结账页打开",
             "url": "...", "items": [ {"@e12": "link 'Tickets' (top-left)"}, ... ] },
  "questions": {
    "kind":   { "type": "choice", "instructions": "下一步做什么？",
                "criteria": { "click_item": "...", "navigate": "...", "scroll_down": "...",
                              "type_text": "...", "done": "...", "none": "..." } },
    "item":   { "type": "choice", "instructions": "点哪一项？（只有 kind=click_item 有意义）",
                "criteria": { "@e12": null, "@e31": null, ... } },
    "sane":   { "type": "noul",   "instructions": "上一步填进输入框的文本语义合理吗？" }
  } }
```

冻结成一句设计规则：**Jev 挑动作，会写的模型只在那个字段真的需要自由文本时才被叫**
（参考实现的 `type_text` 就是这个位置，还额外用一条 Noul 回读字段值、低于 0.5 就清空）。
我们的主循环是 DeepSeek，它本来就在写文本——所以在 web 这条线上，Jev 的收益是
**延迟和每步成本**，文本仍然由 DeepSeek 出。

这条线是**最便宜的第一次实验**：一个 spike 目录（`spikelocalsum/` 旁的兄弟），
`post_json` 直接打 `127.0.0.1:10086`，跑同一个目标，把每步的 payload 和答案按参考实现的
`step-NNN-payload.txt` / `step-NNN-answers.json` 落下来，能离线重放。**不动 Swift，不动 `core/`。**

### 3.5 computer use 的体验部分是真正的难点，不是技术部分

参考实现的已知边界值得抄进设计原则，因为它们是**体验**问题而不是能力问题：

- 「**跑的时候你用这台机器，就是在跟它抢焦点和光标**」。→ 设计上必须有一步是
  「**你来接管**」，而不是让它在你打字的时候替你点。
- 「只有主显示器被捕获」「两个一样 label 的按钮只能给一个粗区域并分摊投票」。
- 「密码从不输入」——靠浏览器密码管理器或 SSO 按钮。这条要留，它是 `Responsibility` 那条原则底线。

也就是说：这条线该给的默认值不是「自动化一切」，而是**逐动作可选、随时可停、看得见它在做什么**。

## 4. 应用二：上下文压缩优化

### 4.1 先把三层和三笔钱摆清楚

| 层 | 文件 | 今天做什么 | 账 |
|---|---|---|---|
| 截断 | `core/truncate.mbt` | 硬上限 2000 行 / 50KB / 单行 500 字符 | 免费 |
| 瘦身 | `core/trim.mbt` | >4KB 的旧工具输出留头 40 + 尾 20 行；清空旧 thinking；边界 `advance_step=8` 量化 | 净赚 **$0.35** |
| 压缩 | `core/compaction.mbt` + `agent/driver.mbt::compact_if_needed` | 超阈值让**云端模型**写摘要 | 一次调用，**不可逆** |
| 代码 digest | `core/script.mbt` | 程序产出 digest，只回打印的 | 已实测 10.5× |

语料（`spikelocalsum/README.md`）：37 个会话、27,882 条模型可见消息、13,370 次请求、
22.3 MB 工具输出（14,242 条）。已量出的四条结论里，有三条**决定了 Jev 该放在哪**：

1. 账单差异**几乎全来自裁剪边界放在哪**：同样的裁剪动作，只换 `recent_window` = $8.01 / $9.06 / $12.51 / **$13.67（现状）**，差 1.7 倍。
2. **`recent_window: 20 → 2` 值 $4.61（总账单 34%），一行不用模型。**
3. **「压缩」这个词能兑现的全部是 $0.86（6%）**：从 $6.77（确定性规则）到 $5.92（>1KB 全换标记的天花板）。
4. 完全重复的工具结果只有 **1.1%**——纯规则已无可拓。

**所以第一件事不是接模型，是把 $4.61 拿到手**（§8 阶段 0）。Jev 要站的位置是
第 3 条那 $0.86 里的**非结构化那一块**，而且它只能进去一次。

### 4.2 Jev 在这里能做的两件真事（都建立在它**不能写**上）

**A. 判别式折叠：把「留哪几块」变成一个可落盘的决策。**

它写不出摘要，但完全可以只回答「留/不留」：先把工具输出**确定性地切成带编号的块**
（`moon check` 的错误行、`grep` 的命中、diff 的 hunk），然后一次扇出：

```jsonc
{ "state": { "goal": "...", "tool": "bash", "blocks": ["1: …", "2: …", ...] },
  "questions": { "b1": { "type": "noul", "instructions": "第 1 块里有后续步骤需要的东西吗？", ... },
                 "b2": { ... }, ... } }
```

成本是**可控的**，而且可以现在就把账算出来：一个 50KB 的输出 ≈ 12k tokens，切成 200 块
（每块约 15 tokens）= 3k state + 200 个问题 × ~10 tokens ≈ **5k tokens ≈ $0.0002**。
输出免费，所以问题加得多一点不心疼。

**但这里有三条必须先认下来的代价：**

1. **state 不能是原始输出**（32k 预算 + 上下文腐化）。所以「确定性提取候选 → 模型挑」
   的顺序是硬的，不是优化。这条和 §3.3 是同一条规则。
2. **决策必须落盘，否则缓存必死。** 投影期问一次、下一轮再问一次会得到不同的 keep 集合，
   前缀从那里断掉，重发的那一段通常又正好是最新最贵的。落盘形态建议直接用日志已有的能力：
   `Custom(custom_type: "sysone-fold", data: {tool_call_id, model, keep: [...], confidence})`，
   **并且记 response 里的 versioned model id**（`jev-latest` 是会移动的别名）。
   落了盘，投影就是**同一输入的纯函数**，也让离线重放成为可能——这正是参考实现
   `step-NNN-payload.txt` 在解决同一个问题。
3. **验收不能靠美元。** 能省钱恰恰是因为模型看一条结果的时间变短了，
   「少留的部分里没有后面要用的东西」这一点在这个语料里**没有被量过**。
   `spikelocalsum/score.py` 的召回口径可以直接拿来用：**事实召回要接近 100%**
   （错一个路径就是丢掉一次工具调用）。

**B. 当收尾判定（Noul）。** 见 §5.4：它需要**换一个问题**问（不是「目标达成了吗」，而是「这一轮产出了新东西吗」），
而且要先离线量过「打转」的占比。这是本文档里唯一一条自我降级的判断。

### 4.3 压缩这条线上，Jev 帮不上的地方（说清楚，省得再试一遍）

- **它不能替我们做 compaction。** 窗口 **64k**，而 1M 窗口的压缩阈值是 **98 万**
  （`CompactionSettings::for_window`）。差 15 倍。这和 `docs/local-model-context.md` 对本地模型
  得出的否定结论**是同一个结论**：要压缩的输入本身就装不进压缩器的窗口。
- **它不能生成摘要。** 这条是硬的（不生成）。
- **拿它给摘要做「有没有幻觉」的打分，边界很模糊。** 摘要的每一句是否被日志支持，
  是判断题，但「日志里没有」和「日志里那段我没读到」在模型眼里是同一件事。
  ★ 老实说这条的收益不配在今天就做：**压缩这条路很少触发**（1M 窗口下日常根本不碰），
  为一个罕见路径加一条新的判分调用，是典型的「越往后改越贵」的反面——在便宜处多做，
  在贵处少改。要做，就等 §8 阶段 3，并且先证明压缩确实在触发。

## 5. 应用三：系统一 / 系统二路由（先做这个）

「路由」在本仓库里有五个**已经存在的位置**，不是五个设想。按「收益 ÷ 风险」排：

| # | 决策 | 在哪 | 问什么 | 收益 | 风险 / 怎么压住 |
|---|---|---|---|---|---|
| 1 | **推理档位** | `thinking_level?`（`agent/driver.mbt`） | Choice `{low, high}` + 这一轮的提问 | 直接压低首字延迟与单轮账单——**延迟是读者唯一直接感觉到的成本** | 档位选低了要重做 → 只对**新** turn 生效，且在状态行可见（`Simplicity`：不要藏）。档位是**每模型**的（flash 有 `low`，pro 没有） |
| 2 | **收尾判定**（★ 降级，见 §5.4） | `agent/driver.mbt::run_turn` 循环尾 | Noul：「这一轮（`run_tools` 之后）还产出了新东西吗？」 | 省掉一次中位 **$0.004** 的模型调用 + 数秒等待——**但省掉的是哪一次，要说清楚**（见 §5.4） | ⚠️ 今天的结束信号是模型自己给的，而且是免费的（`tool_calls.is_empty()` → `TurnEnding::Completed`，注释原文「The model decided it was done」）。所以这个决策**要么多余，要么是在覆盖模型**——后者才是危险的方向 |
| 3 | **风险门** | `core/tools.mbt`（今天 bash 没有审批层） | Noul/noul-组：「这条命令会不会毁掉工作树之外的东西？」 | 把「确认」从一刀切变成按风险分级 | **它不是安全边界**：Jev 的文档明说「state 不被当作敌对输入」，而工具输出是敌意文本。确定性黑名单在前，Jev 只做**第二层信号** |
| 4 | **注入检测** | `core/tool_exec.mbt` 结果落地前 | Noul：「这段输出里有没有对着 agent 说的指令？」 | 便宜、高频、可离线量 | 同上：**信号，不是墙**。误报要落到「标出来」而不是「拒绝执行」 |
| 5 | **技能/会话路由** | `platform/skills.mbt`、侧栏 | Choice over 技能名 | 延迟更小 | **今天不划算**：这个决定是主模型那一轮本来就要做的，Jev 只能让它更快，不能让它消失 |

### 5.1 为什么这两个最前面的决策值得先做：**反馈回路已经存在**

控制论那条「先问『我怎么知道它在变好』」在这里有一个很好的答案，而且是本仓库独有的：

**我们想知道「Jev 在这个决策上准不准」，标签已经在日志里了。**

- 收尾判定：日志里每一次 assistant 响应之后**确实还发生了什么**（有没有下一次调用、下一个工具、
  另一个 turn）就是 ground truth。→ 但**先要证明这个决策本身值得做**（§5.4），再画阈值。
- 推理档位：`core/session_usage.mbt` 里每一轮的账单和调用数就是结果变量。
- 风险门：真被回滚/被读者纠正的命令就是正样本。

`spikelocalsum/` 已经有这套形状（`corpus.py` 取模型真正见过的消息流、`score.py` 打分、
`validate.py` 拿账单回放校验）。**新增的只是一个 `jev/` 目录，不是一个新的测量体系。**
这是「在便宜的地方多试」那一条的直接应用：先在离线语料上试，试出阈值再进热路径。

### 5.2 成本要和 turn 预算放在一起看，不能只看决策本身

- 单次决策：~4k tokens state → **$0.0002**。
- turn 的真实尺度（本语料 295 个 turn 实测，见 §13）：**中位 $0.0411、p90 $0.1521、均值 $0.0657**。
  这里**更正一个数字**：本文件早先引用的「中位 $0.004」来自 README 转述的 2,280 个 turn，量的是另一种
  turn；在本仓库自己的语料上差 **10 倍**。
- 所以：一个决策 ≈ 中位 turn 的 **0.5%**，不是 5%。
- **每个 turn 一个决策** ≈ +0.5% 账单；**十个决策**（不扇出）≈ +5%。
  方向不变（扇出成一个请求），但绝对值比早先的说法小一个数量级。

推论：**决策要少而宽，不要多而窄**。宁可一次问五个问题（同一个 state），
不要五次各问一个问题。

### 5.4 自我修正：第一版把「收尾判定」排第一，那是夸大了

第一版的理由是「一次 $0.0002 换掉一次中位 $0.004 的调用」。读回 `agent/driver.mbt` 末尾之后，
这个理由站不住，两个具体原因：

**① 今天的结束信号是免费的，而且由模型自己给出。** 循环里推出结束的只有一行：

```moonbit
if tool_calls_of(message).is_empty() || stopping() {
  break
}
```

「模型不再要求工具」本身就是一次收尾判定，花了零次额外调用。它写进日志就是 `TurnEnding::Completed`，
那个枚举的注释原文是 **「The model decided it was done.」**。所以「问『目标达成了吗』」在大多数时候是
**重问一遍模型刚刚回答过的问题**，用的还是同一份对话。

**② 在它不冗余的地方，它是在覆盖模型，而那是最危险的方向。** 模型要求工具，就是它认为还没做完；
一个只知道「目标 + 对话」（同一份日志）的第二模型凭什么更知道？如果 Jev 判「达成了」而模型正要跑测试，
被砍掉的是真工作。**早停丢工作的代价，远大于多跑一轮 $0.004。**

**那还剩什么？** 剩的那一小块是真的，但要换个问题问：

| | 问什么 | 判据 |
|---|---|---|
| 不要问 | 「目标达成了吗」 | 和模型自己的停止信号重复 |
| 该问 | 「这一轮（`run_tools` 完成后）**产出了新东西吗**」 | 比较**相邻两轮之间新增的内容**——新文件、新错误、新信息，对上**换个参数重读同一个东西**。这才是「打转」的形状，而 `README` 里已经有「调用数看得见打转」这句话 |

而且**这一条必须先离线量出来**：对日志里每一个 `run_tools` 后的位置，看「从此往后这个 turn 还产出了什么」。
如果「什么都没新」的轮次只占几个百分点，这个想法就该从表里删掉。**这件事不用接 Jev，纯日志分析。**

如果做了，还有一个小的工程结论：**要新增一个 `TurnEnding` 变体**（例如 `Concluded`），因为
`is_interruption` 的现有语义是「除了 `Completed` 都要提示读者」，而被判定器停下的 turn 属于「有人叫停了它」
那一类，不能冒充 `Completed`。

**所以推理档位顶到第一**，三条理由：它在**读者唯一直接感觉得到的轴**上（延迟）；它的标签
（账单、调用数、读者要不要重说一遍）和结果变量都已经在 `core/session_usage.mbt` 里；
它也是**读日志就能先量一半的那一个**（见 §5.5）。

### 5.5 档位：手动那一半已经落地，自动那一半还缺数据

第一次评估这条时的理由是「macOS 侧 `thinking_level="high"` 是写死的，**连读者都没得选**」。
那一半**已经修了**：档位现在是读者在输入框里能改的设置（模型菜单旁边那个 ◠ 菜单，或终端里的
`/think <level>`），默认仍然是 `high` —— 和写死时行为一样，所以这次改动**没有改变任何已有会话的请求**。
选项由 shell 按**每个模型**给（flash 有 `low`、pro 没有），切到没有当前档位的模型时会夹到那个模型的默认值。
日志侧也补了：每一轮开始时 driver 都把实际用的档位写成 `thinking_level_change`，所以「没说过」和
「说过 `off`」现在是两个不同的状态。落点在 `macos/appffi/app.mbt`（`think_event` / `think_report`）、
`macos/appffi/settings.mbt`（`set_think_level`）、`core/model_catalog.mbt`
（`ThinkingLevels::offered` / `default_level` / `in_force`）。

**这恰好把 #1 的门槛降低了一格，但没把它拆掉。** 「拿 10 条真实 turn 手工标该 low 该 high」现在不用
先改代码就能做（菜单里就能切），而 §8 阶段 2 要的自动档位仍然缺两样东西：

1. **对照组**。今天全部 49 个会话日志里，`thinkingLevel` 只有 `high` 一个值（`grep -h thinkingLevel ~/.wei/sessions/*.jsonl | sort | uniq -c`
   → 全部 `high`）。也就是说，**在读者开始用这个菜单之前，本地没有任何 low/high 的质量对比**——
   「low 更快更便宜」是推论，不是量过的事实。菜单的第一个价值是**产出这份数据**，不是「已经知道 low 更好」。
2. **结果变量怎么对齐**。每轮 `usage.reasoning` 已经在日志里，但「这轮该不该 low」的标签要人来打。

所以顺序变成：**先让读者选（已做）→ 收一批带档位差异的日志 → 再谈自动判定**。自动档位的其它三条
判据（只对**新** turn 生效、状态行可见、档位是**每模型**的）都已经有落点了：`/think` 与菜单都只影响
下一轮、两次改档位都会往状态行写一句话、`ThinkingLevels::offered` 是那个「每模型」的事实来源。

### 5.6 工程落点（尽量少动结构）

- **一个纯包**（例如 `sysone/`）：请求体构造 + 答案解析 + 阈值判定。**纯函数、无网络**，
  和 `core/` 里的决策一样可以离线测。IO 走已有的 `platform/http.mbt::post_json`。
- **决策落盘**成 `Custom` entry（含 versioned model id）。理由是二阶的：**决策一旦进了回路，
  它就成了系统状态的一部分**；不落盘就无法回答「为什么当时这么判」，也无法重放。
- **密钥**沿用 `DEEPSEEK_API_KEY` > 设置面板那套（`core/settings.mbt::AppSettings`）。
  注意 `AppSettings` 加字段 = 一次设置迁移，这个成本是真实的，别顺手加两个开关。
- **开关默认关**，和 `docs/local-model-context.md` 对本地模型的处置一致。
- **它是热路径上新增的一条远程依赖**，不要只拿 $0.0002 跟它比价：还要跟「断网 / 429 / 超时」
  的退化成本比。退化的行为必须是确定的、默认的、静默的（见 §6 那条硬指标）。
- **确定性回退**是必须的：429/529、超时、或者关掉了，行为要退化成今天的样子，而不是报错。
  它是**远程依赖**，而我们的 turn 有 `max_seconds` 守卫——多一条在热路径上的远程调用，
  要给那条守卫留的量就变多了。
- ★ 一个结构性的取舍值得提前拍板：把 Jev 做成**第 8 个工具**（`sysone(state, questions)`），
  还是做成**驱动自己的决策**？前者零新控制流，但主模型得先花一次 DeepSeek 调用（几秒、几美分）
  才轮到这个 $0.0002 的决策——对 §5 那类「省钱省时」的动机基本等于白做；
  后者才是收益所在，但意味着 `agent/driver.mbt` 要认识**第二个 provider**，
  而 `core/model_catalog.mbt` + `AgentContext` 今天都假设「一个 base_url、一个 key、
  一种 OpenAI 兼容协议」（Jev 不是）。**这是这次评估里最贵的一处结构改动，值得单独一个 ADR。**

## 6. 怎么知道它在变好（每一行都要能落到一个已有的量尺）

| 问题 | 量什么 | 现成的工具 |
|---|---|---|
| 决策准不准 | 校准曲线（confidence vs 实际正确率）；同一状态重跑的稳定性 | 日志即标签；`spikelocalsum/score.py` |
| 省不省钱 | **整个 turn** 的账单，不是决策自己的 | `core/session_usage.mbt`；`validate.py` 拿实报账单回放 |
| 有没有伤到上下文 | **事实召回率**（路径/命令/错误行） | `core/facts.mbt` 的抽取口径 |
| 有没有打坏缓存 | cache 命中率不下降 | `context_pressure.mbt` 的锚定数 + 日志里的 `usage` |
| 体验有没有变差 | 读者要不要重说一遍（「继续」「不是这个」） | 会话日志里本来就有 |

**三条硬指标**（和本地模型那份一样，不因为是远程模型就放宽）：
缓存命中率不降、事实召回接近 100%、端到端任务不回归。

## 7. 不要做（Purpose 那条：选择不做什么，往往就是决定）

1. **不让它写摘要、写参数、写文案、看图。** 不生成、无视觉是硬边界，绕过去就要另配一个会写的模型——
   那时收益就只剩「挑动作」这一层，回到 §4.2A。
2. **不问它代码算得出来的东西**（计数、日期先后、排序）。TypeSafe 自己的元规则：
   「避免问模型任何代码能精确计算的东西」。
3. **不把 N 个问题拆成 N 次请求**（state 收 N 次钱）。
4. **不做成安全边界**（state 不被当作敌对输入）。
5. **不为了「新」而多加一次调用**：$0.0002 便宜，但它是远程的、有延迟的、有 429 的。
6. **不在 UI 上多一个默认开的开关。**

## 8. 建议的顺序（阶段 0 不用模型）

**阶段 0（先做，零模型）—— 已于 2026-09-19 量完，见 §12**
- `recent_window: 20 → 2`（`advance_step: 8 → 1`）：**省 $5.62（$16.30 → $10.67）**；
  逼出来的重读 ≤ $0.26（上界）→ **净 ≈ +$5.36**。仍然是投影、可逆性不动。
- 更狠的确定性阈值（$10.67 → $7.89，天花板 $6.86）。
- **放行条件只剩一个**：`w20` vs `w2` 的**端到端任务成功率**（需要真实调用）。
  召回口径用 `score.py`；经济账用 `rig`；暴露面用 `regret.py`——前两件都做完了。

**阶段 1（离线，零 UI 面，零热路径）——这一阶段本身就是验收**
- 建 `jev/` 离线目录，复用 `corpus.py` 的消息流。
- 量四个决策：推理档位、收尾判定、风险门、工具输出折叠。
- 产出：**校准曲线 + 阈值 + 每类的准确率**。跑不出比确定性规则更好的数，就到此为止，成本近乎为零。

**阶段 2（进热路径，默认关）**
- 先接**推理档位**（今天没人做的决定、在延迟这条轴上、回退便宜：档位选低了重跑一次即可）。
- 再接**收尾判定**——但要先过 §5.4 那道门：离线量出「打转」轮次的占比，量不出来就不做。
- 决策落盘成 `Custom` entry；开关默认关；429/超时退化成今天的行为。

**阶段 3（按需）**
- 判别式折叠（落盘格式要先定，这是「改晚了很贵」的那一段）。
- compaction 的验收门（只在压缩真的触发时才值得做）。

**阶段 4（独立项目，不是本方案的延续）**
- computer use：Swift 侧的 OCR + AX + 动作执行 + **接管/暂停的体验设计**。
- web bridge 那半可以在阶段 1 就顺手做掉（零 Swift），当作验证「动作集互斥」这条经验的地方。

## 9. 需要拍板的几个问题

1. **动机排序**：省钱、延迟、质量、还是能力边界（拿到 vision 拿不到的那部分）？四者导向不同方案——
   为省钱，阶段 0 那两行比接模型值钱得多；为延迟，推理档位最直接
   （收尾判定先过 §5.4 的门）；
   为能力，只有 computer use 是新的。
2. **能不能接受把工具输出发到第三方？** 这是相对本地模型**新增**的隐私代价，
   而且它恰好出现在「上下文压缩」这个本来最想留在本地的地方。
3. **能不能接受驱动层认识第二个 provider？**（`model_catalog.mbt` / `AgentContext` 今天假设单 provider。）
   不接受，就只能做成工具，那 #1/#2 的收益基本归零。
4. **computer use 的默认值**：逐动作确认，还是先跑再报？谁在什么时候可以接管？

## 10. 附：为什么不建议「让 Jev 每轮决定注入哪些 skill」

（这一节是评估之后单独追加的，因为它看起来最像 Jev 的形状——从 N 个选项里挑 K 个——但账算下来是反的。
数字都是本机实测。）

### 10.1 先纠正一个前提：主前端今天**根本没有注入 catalog**

`core/skill.mbt` 与 `macos/README.md` 的叙述是「catalog 进系统提示，模型按描述挑，`/skill:` 是读者自己点名」。
但在 macOS 这个主前端上只有后半句：

- `Shell::system_prompt`（`macos/appffi/app.mbt:1152`）与 `run_turn` 前的 `AgentContext::new`
  （`app.mbt:1512`）都只传 `sections=[instructions]`——`AGENTS.md` / 设置里的指令，**没有 `skill_catalog_prompt`**。
- 全仓库调用 `skill_catalog_prompt` 的只有两处：`ui/session.mbt:325`（暂停的 Web 版）和 `wei/main.mbt:95`（vim 形态）。
- `app.mbt:1763` 的注释仍写着「The catalog in the system prompt tells the model what exists」——那是 Web 版的行为，
  在 macOS 上这句已经不成立。**这是一处 drift，值得单独修（改注释或补上 catalog），和 Jev 无关。**

所以「每轮让 Jev 决定注入哪些」在 macOS 上实际要问的是**两个**问题：catalog 要不要进提示，以及谁来挑。

### 10.2 实测：catalog 比整个工具 schema 还大

用 `skill_catalog_prompt` 的格式把本机 `~/.agents/skills` 走了一遍（12 个技能，描述按 frontmatter 解析）：

| 量 | 值 |
|---|---|
| catalog 字节 | **6,705 B** |
| 折算 token（字节 ÷ 4，中文部分偏低） | **≈ 1.7k** |
| 整个固定开销（系统提示 + 7 个工具 schema，`request_overhead_tokens`） | **1,314 token** |
| 单条描述长度 | 245–567 字符，平均 ≈ 350 |

`core/skill.mbt` 的注释说 catalog 是「a few hundred tokens for a dozen skills」——**低估约 5 倍**。
原因很具体：`Skill` 的定义是「One line telling the model when this skill applies」，而真实文件的描述
往往是「一句话 + 一连串触发词」（`moonbit-orientation` 450 字符、`kimi-webbridge` 567 字符还带中文）。

### 10.3 三笔账，全部指向「不要每轮让模型挑」

**① 它要省的那笔钱，本来就是缓存价——Jev 贵 18 倍。**

catalog 是**固定前缀**（`dedup_skills` 排序、`skill_catalog_prompt` 在空时返回 `""`、三处注释都在说这件事），
所以它按 cache-read 计价（`deepseek_v4_flash_pricing`：0.0028/M，**新输入的 1/50**）：

| | 每请求 |
|---|---|
| catalog 走缓存读（现状的 Web 版） | **$0.0000047** |
| Jev 过滤一次（1,676 catalog + ~200 任务 + 12×10 问题 ≈ 2.0k token × $0.042/M） | **$0.000084** |
| 倍数 | **17.9×** |

1,000 个 turn：catalog 缓存 **$0.0047**，Jev **$0.084**。**省钱方向上它是纯亏。**

**② 每轮变，打掉的不是 catalog，是整段对话。**

catalog 在系统提示里，也就是请求的**第一个字节**。一次变化，从那一位到数组末尾全部按 fresh input 重算：

| 对话大小 | 一次前缀失效的重算成本 |
|---|---|
| 20k | $0.0027 |
| 100k | $0.0137 |
| 400k | $0.0549 |

比 Jev 调用本身贵 **33×–650×**。这就是 `core/trim.mbt` 那个 `advance_step` 量化、`dedup_skills` 的排序、
`skill_catalog_prompt` 的「内容不变则字节不变」三处设计共同的敌人；也是 `docs/local-model-context.md` §2
说的那条硬约束。**在系统提示里放一个每轮都不同的字段，是这个仓库里最贵的一种改动。**

**③ 这个判断今天有人免费在做。**

| 谁在挑 | 成本 | 延迟 |
|---|---|---|
| Web 版：主模型看着 catalog 顺手挑，然后 `read` 它 | **$0**（同一次 forward pass） | 0 |
| macOS：读者用 `/skill:` 点名 + 本地前缀补全（`WeiModel/SkillCompletion.swift`，纯函数、纯前缀匹配） | **$0** | 0 |
| Jev 每轮过滤 | $0.000084 + 断前缀 | 70–500 ms + 一次远程往返 |

用 Jev 取代第一行，是「花一次远程往返做一次主模型顺手就完成的判断」；取代第二行，是「把读者已经明确
表达过的意图再猜一遍」。

### 10.4 但这个想法照出了一个真问题，以及一个真正适合 Jev 的位置

真问题：**catalog 是全量注入，没有检索**，而它已经比工具集合还贵。三件确定性的事可以先做，都不需要模型：

- `<location>` 每条 60–75 B（12 条 ≈ 800 B，占 12%），而它可由名字 + 已知 root 推出来；
- 描述可以在**进 catalog 时**截断（`core/truncate.mbt` 已有），全文仍留在文件里给 `/skill:` 展开和 `read`；
- 12 选 3 的检索用本地 BM25/grep 就够——TypeSafe 自己的第一条元规则是
  「不要问模型任何代码能精确计算的东西」。

Jev 真正站得住的位置不在这里，而在**补全菜单**：今天的菜单是**前缀匹配整条拼写**（`SkillCompletion.matches`），
所以它只在读者已经开始敲 `/sk…` 时才出现。**「这个任务该用哪个 skill」这个判断，今天没有人回答**——

- 主模型不知道有 catalog（macOS），读者得先知道技能存在才敲得出来；
- 前缀匹配不懂语义（「把这个仓库的 C 绑定查一下」不会命中 `moonbit-c-binding`）。

这是一个标准的 Ranking 问题（TypeSafe 自己的用例表里就有），而且它**同时满足** Jev 的四个长处、
**避开了**它的三个短处：

| 为什么合适 | 为什么安全 |
|---|---|
| Choice ≤255 项、12 个技能正合适 | 输入 = 草稿文本 + catalog，**不碰对话前缀**（不进系统提示、不进日志） |
| 可一次扇出问「哪个相关 + 相关度分档」 | 可以 debounce（读者停下来才发），不在热路径 |
| 输出免费、$0.0002、70–500 ms | 结果是**给人看的一列**，读者按 Tab 才算数（Agency） |
| 天然带 confidence：**低置信就不显示**，这是 `confidence-gated routing` 的直接应用 | 失败只是菜单顺序难看，不会写错日志 |

验收也干净：不需要美元指标（钱这个方向它一定输），只用
**「推荐里点了的比率」**和**「读者要不要重说一遍」**——两个数都在日志和 `SkillCompletion` 的现有测试里。

**如果一定要在对话里做**（把 catalog 从提示里拿掉、按需给），cache-safe 的形状只有一个：
系统提示里留**一行常量**说明「有技能这回事」，把「这一轮相关的几个」挂在**最新一条用户消息**后面——
那一轮本来就是新输入，前缀零损失。但那时收益只能靠 attention 论证（1.7k 描述噪音值不值得），
并且要先量「带噪音 vs 不带，主模型挑对的比率差多少」。**不要**把它放进系统提示的 `sections` 里。

## 12. #0 已经量完，然后暂停（2026-09-19，本机 49–50 个会话 / 33,977 条消息 / 16,239 次请求）

脚本：`spikelocalsum/regret.py`（`python3 regret.py`，约 60 秒，**纯日志、无模型**）；
经济账：`spikelocalsum/rig`（复演每次请求并按前缀缓存计费）。完整表格在
`spikelocalsum/README.md` §5.5。这里只留结论和它改掉的一句话。

| | 值 | 出处 |
|---|---|---|
| 现状（`w20-s8`） | $16.296 | rig |
| **#0（`w2-s1`）** | **$10.673** | rig |
| **省** | **$5.62（34%）** | rig |
| 更狠一档（`w2-s1-5+5`）/ 天花板（`marker`） | $7.89 / $6.86 | rig |
| #0 额外提前裁掉的中间字节 | 172.6 M（占语料 0.6%），涉及 **1,482** 个结果 | regret.py A |

| `read` 里「读过、未改过、又读一遍」的比例 | **38.8%（801/2065）**，间隔中位数 48 条消息 | regret.py C |
| 其中落在 #0 这条带里的 | **185** 次，把整笔调用记在它头上共 **$0.259** | regret.py C |

**能动手了。** 净收益 ≈ **+$5.36**（省 $5.62，逼出来的重读 ≤ $0.26，而且那 185 次重读发生在字节
**还在窗口里**的时候——本来就会发生，所以真实成本更接近零）。改动是 `TrimPolicy::default()`
里的两个数字，可逆。

### 12.1 这一步改掉的一句话

`spikelocalsum/README.md`（以及基于它的 `docs/local-model-context.md`）原来是这么说的：

> **一条工具结果的「有用寿命」是一次请求，而现状买了十次。**

**实测不支持。** 不变重读的间隔中位数是 **48 条消息**，其中一半（399/801）发生在
**今天已经裁掉的位置之后**——模型的习惯是**回去拿窗口早就不给的字节**，不是「看过一次就够了」。

站得住的理由换成**价钱比**：留着的字节每个请求按 **cache read**（0.0028/M）重发一次，
回去重读一次按 **fresh input**（0.14/M）收一次，**差 50 倍**。
所以「20 条消息之后还想再看一眼」不构成保留的理由——**留 50 个请求的价钱才等于重读一次**。

这条修正比原来的说法有用，因为它给出了一个可迁移的规则：
**窗口该由「留 vs 重读」的价钱比决定，而不是由对「有用寿命」的猜测决定。**

### 12.2 决定：暂停，以及我们继承了哪些风险（2026-09-19）

**#0 暂停。** 不是因为账算错了（省 $5.62 是真的），而是因为**质量那一侧没有闸门**，
而它继承的恰好是这个仓库里最贵的一种风险：**静默变差**。下面六条按「伤得多重」排。

**R1 — 35% 的额外暴露连重读都救不回来。**（`spikelocalsum/recoverable.py`，本语料实测）
标记文案对所有工具都一样：「`re-read the file if you need them`」。对 `read` 是真的，
**对 `bash` 是假的**——那输出从来不在文件里。按 #0 新增遮蔽的字节拆：

| 来源 | 占新增暴露 | 怎么恢复 |
|---|---|---|
| `read` | **64.9%** | 再读一次，同字节 |
| `bash` | **33.9%** | 只能**重新执行**（可能不幂等 / 花钱 / 慢 / 不复现） |
| `exec`+`grep` | 1.2% | 同上 |

⚠️ 按字节算的比例**不等于**风险比例（1KB 的测试结果可能比 100KB 的目录清单重要得多）。
另有一条连 `read` 都不干净的证据：`read` 的重读里 **23% 发生在文件被 edit 之后**，
那时「再读一次」拿到的不是同样的字节。

**R2 — 最大的风险，日志量不出来。** 模型看到「894 行被省略」，合理地判断「我大概懂了」，
不再读、继续干活——**日志里没有任何痕迹说这次丢失造成了损失**。它表现为
「agent 今天不行」。这正是 pi 完全不做、openseek 明确拒绝的首要原因。

**R3 — 我们已经有的仪器，没对准最贵的那个事件。** `core/deepseek_request.mbt::RequestDrift`
的注释把这个机削写得很清楚（「一条被改写的中间消息会在那里终结共享前缀」），但它比的是
**同一个 turn 内**相邻两次请求，而一个 turn 的首次请求 `comparable: false`。
**跨 turn 的边界移动——真正最贵的那个——按构造不可见。** 我在 `trace.py` 里看到的那次
「一次吃掉 30% 的钱」，在 wei 自己的生产指标里不会显示。这是最便宜的一个修复（§13.5 候选 B）。

**R4 — 投影没有被钉住。** `TrimPolicy` 是 `(日志, 策略, 代码) → 字节` 的纯函数，**不冻结**：
改策略/升级代码，每个历史会话的投影都变了（有界，一次，但 `rig` 的数字不含它）；
而且「上周二模型到底看到了什么」变成不可回答的问题。dsh 花代价把 replace 落进日志就是为了这个。
wei 的裁不落账——好处是日志里每个字节都在，代价是上面这两条。

**R5 — 读者看到全文，模型看到 60 行。** 转录里是完整输出，所以读者会默认「它看过这个」。
答错时，日志里没有东西把「它没看过第 500 行」和「它答错了」连起来——R2 在实践中不可测量的原因。

**R6 — 语料是自家 dogfooding。** 50 个会话、一台机器、一个人、长会话为主。
经济账的方向大概率对，绝对值不可外推。

**放行条件（唯一一条）**：一个能跑 `w20` vs `w2` **端到端任务成功率**的评测。
在那之前不动 `TrimPolicy::default()`。

### 12.3 顺便记下：为什么 pi / dsh / openseek 都不做这件事

调研它们的源码之后，这个问题值得单独记一句，免得下一轮再花四轮重新发现：

| | 立场 |
|---|---|
| **pi**（pi-mono） | **完全不做**投影期改写，只在 `contextTokens > window - 16384` 时总结 |
| **openseek** | **明确拒绝**，理由写在源码里：这个 guard「是天花板守卫，不是成本优化」——改写模型可见的前缀会打掉缓存定价，**只能在「不改就是请求失败」时开火** |
| **dsh** | **有条件下做**：只在 `compactIfNeeded` 里裁剪，而且**落成一条 log 的 surface replace** |
| **wei** | **无条件做**：每次请求、每一条旧结果、不落账 |

三个他们不做的理由，按重要性：

1. **收益在账单上（可见、可归因、当场可量），代价在质量上（不可见、不可归因、延迟出现）。**
   没人会为「今天这个 agent 有点笨」提 issue，提了也会归因到模型。
2. **通用产品的处境不同。** 前缀缓存价钱比是**供应商的**：DeepSeek 是 read = 1/50 且
   `cache_write = 0`；Anthropic 是 write = 1.25×、TTL 5 分钟、缓存是**显式断点**。
   pi 面向多供应商，**它的投影策略不可能同时对两边最优**，所以只能选处处安全的默认值 = 不动。
   ⚠️ 这也意味着 **1/50 不是自然常数**：它变了，#0 这类策略的最优解就变了。
3. **它是对「自己用户会话多长」的下注。** 那个 14 请求的会话里，完全不裁（$0.0065）比现状
   （$0.0090）**还便宜**——短会话里裁打破前缀的钱超过它省下的字节。wei 的语料是长会话为主。
   （对 #0 有利的一点：同一个短会话里 #0 = $0.0052，比 raw 和现状都便宜——**#0 是在缩小赌注，
   不是在同一个赌注上加倍**。）

**所以 dsh 的答案是「门槛 + 落账」，openseek 的答案是「只在会失败时开火」。**
如果哪天重启 #0，这两条就是现成的设计模板。

`regret.py` 是纯日志，没有反事实：一个被提前裁掉、**之后再也没被拿回来**的行不留痕迹。

## 13. 其余候选的复查（2026-09-19，本语料 49 个会话 / 16,239 次请求）

#0 暂停之后，把剩下的候选按同一个尺子过了一遍：**先量得到的东西量掉，先把「零风险」和
「失败看得见」的挑出来。** 结果是**两个决定性的否定**、**一个新发现的零风险项**，以及
**一个被自己的语料推翻的数字**。

### 13.1 两个否定（省下的工作量比任何新增都值）

**① compaction 在这套配置下从不触发。** 49 个会话的日志里，`compaction` 类 entry **0 条**。
原因是 1M 窗口：阈值 = 窗口 × (1 − 0.16) ≈ 84 万 token，而这个语料最长的会话也只有 400k 出头。

→ **整个 §4 的「用 Jev 判摘要」就此作废**，§11 的 #10（compaction 验收门）也作废。
不是「收益/风险比不划算」，是**这条路径今天根本不存在**。要重启它，先得有一个会触发的配置
（小窗口模型，或者一个真的长到 84 万 token 的会话）。

**② 工具输出的硬上限从不生效。** 17,826 条工具结果里，带截断标记的只有 **38 条（0.2%）**
（头截约一半、尾截约一半）。`default_max_lines=2000 / max_bytes=50KB` 不是成本旋钮，它是一个
**从来没被碰到的安全阀**——而且它和 pi 的常量一模一样（继承来的，不是调出来的）。

→ **不要去调它。** 这是一个有价值的否定：它说明「工具输出本来就很大」这个直觉在这套管线里
不成立——**大的是累积，不是单条**（单条的中位远在 50KB 之下，而 22.3 MB 的累积来自 14,242 条）。

**③ 顺带一个：最简单的「打转检测」没有人口。** 同一 turn 内重复相同工具调用的：**0 个 turn**。
（跨 turn 的重复也只有 1.0%，见 `README.md` §5.5 C′。）所以「抓重复命令」这个确定性检测器
**无从下手**——打转如果存在，它是**语义上的**（不同命令、同样结果），而那正是需要判断力的地方。

### 13.2 一个被推翻的数字：turn 比文档里说的大 10 倍

| | 值 | 出处 |
|---|---|---|
| turn 数（`turn-start`…`turn-outcome` 配对） | 296 | 本语料 |
| **每 turn 的模型调用轮数** | 中位 **29**、p75 69、p90 135、p99 218、max 338 | 同上 |
| 轮数 ≥ 20 的 turn | **62%** | 同上 |
| **每 turn 花费** | 中位 **$0.0411**、p90 $0.1521、max $0.39、均值 $0.0657 | 同上 |
| 撞到 round/time 上限的 turn | 17（6%） | 同上 |

本文件 §5.2 早先引用的「中位 turn $0.004」转述自 README 的 2,280 个 turn——**量的是另一种 turn**，
在本仓库自己的语料上差 10 倍。**任何「占一次 turn 多少」的说法都要用这张表。**

而且它把成本结构说清楚了：

| 成分 | 费用 | 占比 |
|---|---|---|
| 新输入（fresh） | $9.18 | **43%** |
| 缓存读 | $8.91 | **42%** |
| 输出 | $3.02 | 14% |
| └ 其中 reasoning | $1.62 | **7.7%** |

（这台机器上有个 app 实例在实时写 `~/.wei/sessions`，所以重跑时计数会漂 ~1%：
turn 数 295↔296、工具结果 17,407↔17,826、占比 43↔44%。结论不受影响。）

**86% 的账单是「把对话反复重发」。** 这直接定了所有候选的天花板：能动的只有
**发送多少（body 大小）** 和 **发多少次（轮数）**——而 #0 动的是前者，`-34%` 已经把它吃掉大半；
后者（29 轮/turn）是整个候选表里最大的一块未动之地。

### 13.3 由此重排：思考档位（原 #1）的奖池只有 7.7%

上表最后一行就是它的天花板：**reasoning 占全部账单的 7.7%**，而且它和 #0 得同一个病——
降档之后「本来该想而没想」的损失，从日志里看不出来。
更关键的是实测分布（16,256 条响应）：**47.8% 的响应 reasoning 为 0**，中位 30，p90 969，
p99 3,932，max 40,507。也就是说 **`high` 是一个上限而不是下限，模型自己已经在调节**——
那 47.8% 的响应上根本无钱可省，钱全在长尾，而长尾正是**最不该降档**的地方。

另外：49 个会话**全部**跑在 `high`，没有一个天然实验组，所以它也**只能靠 A/B 定**。

**→ 原 #1 从第一格降到「不值得单独做」。** 真要碰，先做成读者可见的选项（现在连人都没得选），
而不是让模型猜。

## 14. A 和 B 的落地（2026-09-19）

两项都做了，选择都按**长期更优**而不是工作量最小。代码改动：`core/`（两处签名 + 三个测试）、
`agent/`（一个参数 + 一个返回字段 + 两个测试）、`ui/`、`wei/`、`macos/appffi/`（两处装配 + 一个落盘 sink）。
`moon test` **825 全绿**，`moon check` 0 错。

### 14.1 A：不是补一个 section，是让「漏掉 section」不可表达

**做了什么。** `build_system_prompt` 的 `sections : Array[String]` 换成三个具名参数：

```moonbit
pub fn build_system_prompt(
  cwd, tools, mode?,
  instructions? : String = "",          // 工作区自己的说明
  skills?      : Array[Skill] = [],     // 技能目录
  stale_tools? : Array[String] = [],    // 本轮没有的、之前用过的工具
) -> String
```

**为什么这样做，而不是「在 macOS 的 sections 数组里加一行」。** 因为漏掉一个 section
**不是一个错误**——它只是少了一段文本，模型就是不知道有技能这回事，没有任何东西会失败。
只用一次改动去修，下一次还是同一种错。而根因是**形状**：四个调用点各自手写数组、各自决定顺序、
各自决定放进什么。把**输入**交进去、由一处决定顺序，漏掉就变成了写不出来的代码。

还有一个当时没预料到的收益：修的过程中发现 macOS **少了两段**，不只是 catalog，还有
`tool_change_prompt`（工具档位换了之后，模型继续调用已经不存在的工具的提示）。
同一个 bug 的两个实例——这本身就是「形状不对」的证据。

**代价，要明说。** 静态 catalog 是固定前缀，每个请求按 cache read 计（$0.0000047），
所以**日常账单几乎不动**；但它是**第一次改动每个已有会话的系统提示**，所以升级后每个会话的
**第一次请求**要从头重算一次。和有意的行为一致（Web 版一直如此），一次性，但真实存在。

**这一处的教训值得单独记**：`macos/appffi/app.mbt` 里那句「The catalog in the system prompt
tells the model what exists」的注释，是**照着 Web 版写的、在 macOS 上从来没成立过**。
注释描述意图、代码决定行为，两者分叉时**没有编译器会拦**——除了把意图变成类型。

### 14.2 B：把「一个 turn 的第一次请求」从不可比变成可比

**做了什么。**

| 变更 | 位置 |
|---|---|
| `RequestDrift.within_turn : Bool` —— 区分「turn 内的前一次」和「上一个 turn 的最后一次」 | `core/deepseek_request.mbt` |
| `request_drift(previous, current, within_turn?)` | 同上 |
| `run_turn(previous_request? : Array[Json]?)` —— 调用方把上一 turn 的末次请求交回来 | `agent/driver.mbt` |
| `TurnResult.last_request : Array[Json]` —— 交出去，供下一个 turn 用 | 同上 |
| `Open.previous_request`（macOS）、`Runner.previous_request`（Web） | `macos/appffi/app.mbt`、`ui/session.mbt` |
| **`Shell::log_drift`** —— 每 turn 一行 JSON，写进 `WEI_DEBUG` 那个文件 | `macos/appffi/app.mbt` |

**为什么加 `within_turn` 而不是只让 `comparable` 变 true。** 两者回答不同的问题：turn **内**的
序列按构造应该是 append-only，那里出现改写是**这段代码自己干的**；turn **之间**是日志的两条
记录之间，那里的改写是**对话被投影成了不同的样子**（边界被刚追加的消息释放了，或者发生了压缩）。
分不清就会让读的人去错的地方找。

**为什么让它落盘，而不是只放个字段。** 一个没人读的字段就是死代码，而且**R3 的问题正是「没有
人能看见」**。`WEI_DEBUG` 已经存在（`WeiKit.WireLog` 用它记 host 侧的线上流量），所以这里写进
**同一个文件**：一个变量打开一次会话的两半证据，默认关闭。每 turn 一行 JSON，含
session / 时间 / 调用数 / 可比请求数 / **本轮最贵的改写** / 首个请求自己的读数（含 `within_turn`）。

⚠️ 老实说这个 sink 的分量：它有测试（写/不写、字段齐不齐），但**还没有接到任何画面或诊断面板上**。
它的价值现在等于「你跑 `WEI_DEBUG=…` 就能看见」——比之前「只有测试能看见」进了一步，
但离「平常就会看见」还有一步。**这一步值得做，但还没做。**

### 14.3 顺带确认的一件事

B 做完之后，可以回答一个之前只能猜的问题：**边界到底多久动一次、动一下多贵**。
`log_drift` 的输出就是答案的来源，而且它现在对**每一个真实会话**都在计（打开开关时），
而不是只在 `rig` 的复演里。这是「先修仪器，再改行为」那条原则的落实——
**在调 `TrimPolicy` 之前，先让它的代价可见。**
