# 原生 macOS 壳

一个原生窗口，驱动同一套 agent。它起先是路线 B「**界面重写，内核复用**」的验证物，现在**是主线**：
Web UI 已暂停投入，日常开发与使用都在这一端。

那条边界的判据因此定得更死：**事实属于谁**。关于对话的事实（金额格式、图片是否合法、用量、是否被
压缩、上一轮是否中断）在 shell 里，一份；关于**这个窗口**的事实（滚动位置、折叠、焦点、拖拽悬停）
在客户端，不上线；两个方向都依赖的不变量（流式行 id 跨轮唯一）写在一处，并在**坏了会丢数据的那
一侧**强制。

**动这里之前先扫一眼 `docs/macos-pitfalls.md`。** 里面是 `症状 → 原因 → 修法` 的表，六组：构建打包、
SwiftUI 编译期摩擦、输入法、平台 API 的发现、验证与自动化、调试手法。这张表存在的理由很直接：本
文件里已经写着的坑，开发者（我）照样踩了其中一条的变体。

窗口左边是会话列表，右边是对话，`⌘,` 是设置。它可以被打开成三种东西：

```bash
# 1. .app：给人用的那个（打包，见下）
macos/make-app.sh                   # → macos/dist/wei Agent.app
open "macos/dist/wei Agent.app"

# 2. 开发循环：改一次跑一次，不打包
macos/build-moonbit.sh release      # → macos/vendor/libwei.a
cd macos/WeiShell && swift run WeiShell

# 3. 终端：同一套 agent，打的是线上字节，没有窗口
cd macos/WeiShell && swift run wei-cli
cd macos/WeiShell && swift test       # 线格式（WeiModel）+ 边界本身（WeiShellTests，真 boot runtime）
```

```
macos/appffi/       MoonBit：agent + 会话 + 会话列表 + 设置 + 事件出口（这一层是新的）
macos/build-moonbit.sh  把上面那个包编译成 host 能链接的 libwei.a
macos/WeiShell/      Swift：窗口、三栏（Projects / Sessions / 对话）、设置面板、边界
macos/make-icon.swift   图标（画出来的，不是提交进来的）
macos/make-app.sh       打包成 .app（图标、Info.plist、签名）
```

MoonBit 侧的测试是 `moon test macos/appffi --target native`。

## 复用了什么

| 包 | 复用 | 说明 |
|---|---|---|
| `core/` `platform/` `agent/` | **原样** | 一行没改。它们本来就不认识 UI |
| `html/` `server/` | **不用** | HTML DSL、主题、patch、HTTP/SSE，全是 Web 的 |
| `ui/` | **不用** | 它的渲染函数与 `@html`/`@server` 绑在一起 |

`ui/` 的状态是重写的，不是搬过来的 —— 但也没有重新设计，`appffi/app.mbt` 里的
`Shell` 就是 `ui/session.mbt` 的 `Runner` 减掉「只有贴着文档才有意义」的那些字段
（transcript 深度、live patch id、订阅者）。会话列表同理是 `ui/sidebar.mbt` 减去属于页面的
那部分：折叠、显示上限、「load earlier」、撤销提示 —— 每一条都是关于一栏网页的决定，而这一栏
现在是宿主的。剩下的部分是会话有哪些、叫什么、描述一个会话要花多少读。

## 切会话：为什么线上跑的是行，不是事件

宿主手上有两样东西是 Web 版没有的：一份「我看到过的全部事件」的记忆，和一个**它没看过**的会话。

- 自己开的会话，逐步重放事件就对了 —— 它本来就是这么画出来的。
- 换过去的会话（以及 `WEI_SESSION` 恢复的那个），事件早就发生完了，宿主一条都没收到。
  所以 `history` 事件发的是**行**，不是 delta：整段对话一行 JSON，每行都是 `complete`。

行而不是事件，是因为历史没有时间：把一段已经结束的对话重放成一串 delta，是在编造一个所有事情
都同时发生的下午。id 带 `h-` 前缀，因为流里的 id 是 `reply-1`、`tool-2` —— 两者混在一份记录里
会让 delta 追加到错误的块上。

历史**只在第一次见一个会话时**发（见下面「同时跑多个会话」）：host 现在每会话存一份转录，重放
一份它正在看的会话，会用它自己那份更旧的状态覆盖掉已经收到的行。

## 分界线的判据

**`ui/` 和 `appffi/` 的差别只有一个：谁拥有视图。**

Web 版里服务器拥有文档，浏览器应用 patch —— 所以线上跑的是 HTML 片段，因为浏览器不知道
一段对话长什么样。这里 host 拥有视图，所以跑的是**事实**：这段文本来了、这个工具开始了、
这一轮结束了。`ffi.mbt` 的文件头写着这条。

副作用是这套事件只有在真的写了第二个前端之后才会证明自己，而它确实证明了 ——
`Conversation`（消费侧）与 `app_wbtest.mbt`（生产侧）断言的 JSON 字面量是**同一批**。
改一个字段名而不改另一边，会挂一个构建，而不是产出一个默默忽略事件的 host。

## 线程，和为什么必须这样

MoonBit 的 async 是单线程协作式的，它需要一个线程来跑事件循环，服务所有 socket 和定时器。
macOS 需要主线程跑自己的事件循环。**两者不能是同一个线程**，所以：

```
主线程                        wei-agent 线程
  NSApplication run loop         @async.run_async_main
  SwiftUI 渲染                     turn / HTTP / 工具进程
       │                                 │
       │  wei_post(文本)             │  wei_emit(JSON 行)
       └──────────► inbox.c 队列 ─────────┘
```

- 命令往一个方向走：C 里的队列 + pthread mutex。C 是因为它要跨线程加锁，而且 host 的字节
  不是 MoonBit 引用，不能当引用碰。
- 事件往另一个方向走：`wei_emit` 在 MoonBit 侧是 FFI、在 host 侧由你自己定义。
  这个方向没有锁，因为 `Emit` 在 Swift 里拿一把。
- 命令循环是**轮询**的（50ms），不是被唤醒的。唤醒需要一个 pipe 加一个注册到事件循环上的
  reader，那是第二个线程和第二种失败模式，换来的是一个已经足够快的按键。空队列时轮询是两个
  syscall。

## 这个 MVP 少了什么

不是遗漏，是用来换「先知道这条路通不通」的。Web UI 暂停之后，这张表要按**新的基准**读：缺的东西
不再和 Web 版对照，而是「一个每天在用的 App 该有而它还没有的」。

- **markdown 是宿主渲染的**，而 Web 版是 cmark 渲染成 HTML 的 —— 两者对同一段 markdown 会有
  细微差别（表格、脚注、raw HTML 的处理）。真要说谁对，得挑一个共享的实现，那是后面的事。
- **答案里的图有两条画不出的边界**：段落里的图单独占一行（文字不绕排），表格单元格里的图只剩
  alt 文字。两条都是取舍，理由写在「答案里的图」那一节。
- **附件只支持图片**（png/jpeg/gif/webp，和 `read` 工具同一份清单），没有文件预览侧栏；一次最多
  一条消息，没有对附件条数的上限。
- **事件在宿主侧不落盘**：一次运行里看到的就是全部。Web 版有 SSE 重连与「load earlier」窗口，
  这里没有 —— 会话已经长了的时候，重启就把上半段交给 `history` 一次性发过来，没有分批。
- **没有导出**、
  **没有 `/tree` 分支视图**（`core` 有 `path_to`，宿主没有界面）、**没有「load earlier」窗口**
  （长会话一次全发）、**没有 `@` 引用文件的补全**（`/skill:` 有了）。
- **会话列表不分组折叠到「最近 N 条」**：分组折叠有了，但一个目录下几百条会话仍然是几百行。
- **语音输入不自动发送，也没有唤醒词**。要开着麦克风听唤醒词，就得一直录、一直在转写，而换来的是
  一个说出来就能用的入口 —— 那个交易在这个 app 里不划算（见「语音输入」那一节）。

## markdown：为什么解析在 shell 而不是 host

原生的 `Text` 不能被喂 `<h2>`。宿主**有**自己的 markdown 解析器 —— `AttributedString(markdown:)` 认表格、
认每列对齐、也留得住围栏的语言标签（这几点与仓库里早期注释说的相反，实测于此）—— 问题不是能力而是
**一致**：它是另一套实现，行为跟着系统版本走而不是跟着这次构建走；而这里有两件事只能由一个地方决定，
一处是「哪个图片 target 允许被读」（`md/walk.mbt`），一处是「原始 HTML 当文本还是当标记」。所以解析在
`md/` 里做一次（cmark），结果当数据跨过去：

| 时机 | 线上跑什么 |
|---|---|
| 流式期间 | `reply`/`thinking` 的 delta；**回答**还多一条 `blocks`，每 ~150ms 或每 ~64 字符一次，只带**新完成的那部分**（`from` = 宿主已经有的块数），并带上这段解析覆盖到正文的哪个字符（`parsed`，UTF-16 code unit） |
| 块停止增长 | 一条 `blocks` 事件，`from` 由 shell 对整段做一次 `diff_prefix` 得出 —— 通常是「最后一块变了」，而不是整段重发 |
| 打开会话 | `history` 的每一行自带 `blocks`（整段历史一次解析，不是每行一问） |

### 实时渲染：空白行是边界，`from` 是差值

早期版本的理由是「每个 delta 重解析累积文本是 O(n²)」—— 这个数字是对的（实测 40KB 文本重解析
400 次 = 2.16s），但结论下得太早：**贵的是「解析次数 × 文本长度」，不是解析本身**（40KB 解析一次
只要 5.4ms）。所以规则改成「只解析还没定型的那一段」：

- **边界** = 最后一个顶层空白行（`md/live.mbt` 的 `safe_boundary`）。它前面的 markdown 已经不会再变，
  解析一次、永不重发 —— 这也是「读者已经读过的部分不会在眼皮底下变形」的保证。
- **围栏里的空白行不是边界**：那是代码块内部的空行，从这里切开会让一个代码块变成两个。开/闭围栏
  是两条不同的规则（开围栏允许 info string，闭围栏只允许那一串符号，且长度不得短于开围栏）。
- **`from` 让帧可叠加**：`diff_prefix` 给出「宿主已经有的前几块」，帧只带后面的。宿主做
  `held[:from] + blocks`（`WeiModel/Conversation.swift`）。**帧带的是尾巴而不是整段** —— 第一版
  带了整段，宿主就会变成 `head + head + tail`，而这种错在「只有一帧」的测试里完全看不出来。
  所以拥有一条**重放性质测试**（`macos/appffi/app_wbtest.mbt`：把一段回答按 delta 喂进去，
  再把所有帧重放一遍，应当逐块等于整段的一次解析）—— 它抓住了上面那个 bug。
- **边界也是协议字段**（`parsed`）：宿主画的是「`blocks` + `text` 从 `parsed` 起的那一段」。前半是定型
  markdown，后半就是正在写的那一块本身（纯文本，那些 delta）。少了它，一行一旦有了第一个完成的块，
  正在写的部分就不显示了 —— 要等下一次 `from` 前移才补上。**这条是读代码发现的**：shell 侧注释写着
  「正在写的那块已经在宿主屏幕上了」，而宿主的规则是「有 `blocks` 就只画 `blocks`」，两边各自都成立。
- **reasoning 不做实时解析**：宿主按设计就是把它当纯文本画的（到达时 3 行尾锚，结束折一行），
  解析了也没人画。实测里它是实时流量里的三分之一。
- **两道闸门**（时间 + 字符数），而且**先问闸门再建字符串**：`StringBuilder::to_string` 会拷贝
  到目前为止的全部内容，放在闸门之前就是那个 O(n²)。被拒的 delta 是常态（大多数 delta），
  所以它必须什么都不花。

实测（`--repeat 30` 的假模型，一段 30 倍长的回答，共 185 帧、最终解析 67KB）：线上 `blocks` 帧
**99KB ≈ 最终解析的 1.47 倍**；若每帧重发整段解析则是 6.1MB（91 倍），**省 62 倍**。验收标准就是
这条：帧的总字节数 ≲ 最终解析的 2 倍。

`md/` 是 cmark —— **和 Web 版渲染用的是同一个引擎**，这是它作为共享包存在的全部理由：两个前端
对同一段 markdown 要有同一个意见。Swift 侧只负责画：`Block`/`Span` 的 tagged JSON 在
`WeiModel/Sidebar.swift` 里解码，`RootView.swift` 里逐种块画（表格、围栏、列表、引用各自成视图），
「哪段已定型、哪段还在写」那条切分是 `WeiModel/Sidebar.swift` 的 `unparsedTail`（有测试，单位是
UTF-16 code unit，和 shell 的 `String::length` 同一把尺）。

## 答案里的图：范围由 shell 判，字节由宿主读

`![alt](/tmp/shot.png)` 现在**画出来**，不再是只留一句 alt 文字。这是从前那条注释（「宿主没有
loader，破图框比一句话更糟」）的正面回答：宿主**有** loader 了 —— 和附件缩略图同一套解码。

**能画什么，只在 `md/walk.mbt` 里判一次**（`drawable_image`），宿主只负责「这条目标该怎么读」
（`WeiModel/Picture.swift`，有单测）。判两次是这个仓库里已经写下来的失败形状（宿主一份格式清单、
shell 一份），所以不判第二次：

| 目标 | 画不画 | 为什么 |
|---|---|---|
| `/tmp/shot.png` | ✅ 读文件 | 模型刚存的图就是长这样，也是修之前唯一真正让人难受的场景 |
| `file:///tmp/shot.png` | ✅ 读文件 | 同一个文件。**这里故意不复用 `is_unsafe`**：那条规则是给「交给系统去打开」的链接用的，图是宿主自己读字节 |
| `file://host/x.png` | ❌ 只剩 alt | 带 host 的 file URL 是「读别人机器上的东西」，不读 |
| `data:image/png;base64,…` | ✅ 随身带字节 | 图片没有「加载失败」这一档。仍然过解析器自己的 `is_unsafe`，所以 `data:text/html` 不是图 |
| `http(s)://…` | ✅ 拉取 | 唯一需要网络的一档，也是唯一可能在宿主画的时候还没到的 |
| `chart.png`（相对路径） | ❌ 只剩 alt | 相对**谁**是读者的问题不是模型的问题，猜错不如给一句话 |
| 读不到 / 不是图 | ❌ 只剩 alt | 就是修之前所有图的行为，位置也不变：图该在哪儿，那句话就在哪儿 |

两条布局上的取舍，写下来是因为它们是取舍：

- **段落里的图单独占一行**。`Text` 吃的是 `AttributedString`，里面装不下图，所以含图的段落按
  「文字段 / 图 / 文字段」拆开画 —— 文字**不会绕着图排**。绝大多数答案是「图自己一行」，那就是
  一段文字，什么都不变；`before ![](…) after` 变成三行，这个形状没有答案会写。
- **表格单元格里的图是 alt 文字**。单元格是按文字量出来的宽度（`Table.swift`），图进不去，
  所以那里画的是 markdown 本来就给的那句话。

图按目标缓存（`Pictures`，滚动时行会重建，不缓存就是每次滚动重读一遍；远端那条就是每个来回一个
请求）。**失败不缓存**：文件可能只是还没写完，下一次重画就该再试一次。高度上限 420pt，且**不放大**
——`maxWidth` 是上限不是目标，否则一个 1×1 的 data URL 会铺满整栏。

## 打包

```bash
macos/make-app.sh release           # → macos/dist/wei Agent.app（约 3.7MB）
```

打包前会 `rm` 掉旧的宿主可执行文件再重建：SwiftPM 不知道 `vendor/libwei.a` 变了（那个归档不在
依赖图里），所以 MoonBit 侧改完之后它可能报「构建成功」而留下旧二进制 —— 症状是最坏的一种：App 的
行为和修复前一模一样。

脚本做四件事：跑 `build-moonbit.sh`，`swift build -c release`，组装 bundle（可执行文件改名叫
`wei`，写 `Info.plist`，生成图标），最后签名（默认 `wei-dev`，见下一条）。

几个决定：

- **不用 Xcode 工程。** 没有 nib、没有 asset catalog、没有 SwiftPM 做不了的构建阶段 —— 一个
  `.xcodeproj` 会是同一个程序的第二份描述，和第二件要同步维护的事。
- **图标是程序画出来的**（`make-icon.swift`）。提交一个 `.icns` 等于提交一个谁都不能 review、
  谁都不能改的二进制；写成几行 CoreGraphics，改个颜色就是改一行。
- **版本号读 `moon.mod`。** 打包脚本自带一个版本常量，就是一个没人记得改的数字。
- **签名用本机一张固定的自签身份**（`macos/make-identity.sh` → `wei-dev`），没有才退回 ad-hoc。
  这不是为了 Gatekeeper —— 两种签法下载来的副本都会被挡住。是为了 **TCC**：macOS 把权限绑在 App
  的 designated requirement 上，而 ad-hoc 的 requirement 里是 **cdhash**（每次构建都变），自签的
  里面是**证书**（不变）。于是 ad-hoc 下每次重打包都等于换了个 App、权限要重问一遍；固定身份之后，
  重建的 App 在 macOS 眼里还是同一个。机制与实测见 `docs/macos-pitfalls.md`。
  `WEI_SIGN_IDENTITY` 覆盖身份名，`WEI_SIGN_IDENTITY=-` 强制 ad-hoc；`WEI_BUNDLE_ID` 覆盖
  bundle id，因为 identifier 一旦变了，macOS 就会忘记哪个 App 对应哪个文档/窗口。
  真要发布仍然得换成 Developer ID 加公证。

**为什么必须打包，而不只是「方便」**：`.app` 是一个身份 —— 名字、图标、一个稳定不变的
identifier，以及 `LSApplicationCategoryType` 这类让系统知道它是什么的东西。裸可执行文件在
Dock 里是一个通用文档图标，名字取自文件名，`applicationShouldTerminateAfterLastWindowClosed`
之类的行为也没有立场。`WeiApp.swift` 里那句 `setActivationPolicy(.regular)` 就是给裸二进制
写的补丁，打包之后它是 no-op。

**Working directory 的坑**：双击启动的 `.app`，cwd 是 `/` —— Finder 不传目录，内核默认是根。
照单全收的话，从 Finder 起的每个会话都在商店里单独一格（`----`），工具会在卷的根目录上跑，
工作区叫「什么都不是」。所以 `start_dir`（`appffi/app.mbt`）把 `/` 读成「没选目录」，然后按顺序
问两个问题：**上次用过的那个工作区**（`last_workspace`，就是侧栏排在最上面的那个），没有就问
**home**。`/` 以外一律当真，因为那是有人选的（终端的 `cd`、launcher、"Open With"）。

**为什么要问 store**：只答 home 的时候（这次改动之前），每次从 Finder 启动都落在家目录——一个
读者从没打算在里面工作的地方，而第一条 prompt 就会把它变成一个真工作区，永久留在侧栏上
（`--Users-lucas--`，标签 `lucas`）。问 store 拿到的答案是读者自己选的目录，也就顺带把「启动默认
落在哪」从「猜」变成「上次的事实」。代价是启动时多一次 `list_workspaces`（readdir + 每个会话一次
stat + 每个工作区读 8KB 头），和侧栏过一会儿本来就要做的那次读是同一个。

**配套的一半在侧栏**：`say_sessions` 会把「还没落盘的当前会话」塞进它所属的那一组，而**只在那一组
已经存在时**（`carry_current`）。以前没有组就现造一个，于是从 Finder 启动的窗口里多出一个
`workspace_name(home)`（`/Users/lucas` → `lucas`）的行，读者一点就消失——见 `docs/macos-pitfalls.md`
那张表。现在没有组就没有行：刚装好的 store 是空的，侧栏也就是空的，这是实话。

**反过来的一课：读者亲手点名的目录要记账**（`note_workspace`）。上面那条规则有个必然的后果：一个
会话如果在「store 不知道的目录」里，它就没有组可以待，于是侧栏上会有一条**看得见、却列不出行**的
对话。能造成这件事的只有一种输入：读者在 `/new` 后面写了路径（`/new /somewhere/new`）。那正是
「我在这里工作」的声明，所以这个目录被记下来；而**继承来的**目录（⌘N 不带项目、启动时没有目录）
不记 —— 否则首次启动就会把 home 写进侧栏，又回到上面那个 bug。**工作区是有人选过的地方**，
这就是那条界线。`new_in`（文件夹选择器）走同一条路，它那句 `workspace added: …` 保留着：那是
一个关掉对话框之后屏幕上什么都没有的场合，需要一句话。

## 第一次打开：一个空的窗口，和一条能按的话

一台干净的机器上双击打开，读者看到的是：侧栏只有品牌和一行 `Add workspace`；中栏一句
`No project selected.`；对话栏是空的，输入卡片下面一行 `No API key` 加一个 **Open Settings**
按钮。**没有引导流程**，也不该有：这个 app 只有一件事是新的（项目 = 你机器上的一个目录），
其余都是 macOS 的常识。

之前这里有两个问题，都不是「缺了引导」，而是**说了不该说的话**：

1. **启动时那行 `error` 是重复的、还是错的**。shell 送完 `ready` 之后又送了一句
   `no API key: set DEEPSEEK_API_KEY and reopen` —— 让读者去重开一个他刚打开的窗口，去设一个
   他可能根本没有变量，而这件事 app 自己有面板。`ready` 里的 `key: missing` 已经把同一件事
   交给了宿主，宿主把它画成输入区下面那堵墙，所以那句 `error` 只是同一件事的第三个说法。
   删掉了。
2. **然后第一条 prompt 会花掉一次请求去学同一件事**。没有 key 时提问会真的发出去，
   回来的是一句 401 的协议话（`HTTP 401: Authentication Fails (auth header format should be
   Bearer sk-...)`），外面还包着 `Failure(...)`（见下一条）。于是**读者第一次尝试的代价是
   一次往返、一个会话文件、和一个永久留在侧栏上的项目行**。现在 `turn_refusal` 在
   **`start_turn` 的第一行**拦下来：没有 key 就只回一句、不置 busy、不写文件、不发请求。

那句「唯一入口就是这个面板」的推论到这里才完整：**门要画成门**。所以输入区下面那句不再是指令
（`no API key — open Settings`），而是事实（`No API key`）**加一个按钮**。`ShellClient.blocked`
负责前半句，`missingKeyIsFixableHere` 负责「这个墙有没有门」——shell 根本没起来（比如没有 `HOME`）
时没有门，给个按钮就是给个走不通的控件。

面板在哪个 tab 上打开，是跨**两个 scene** 传的：主窗在 `RootView` 的树里，设置窗在 `WeiApp` 的
`Settings` scene 里，两者除了 `ShellClient` 没有任何共享。所以按钮把「想开哪一页」放进 client
（`askForSettings`，一个**计数器**加一个 pane，不是 flag：第二次按也必须算一次事件），`SettingsView`
在 `.onChange(of: settingsAsk)` 里读它。见 `docs/macos-pitfalls.md` 第二组。

**错误消息的形状**：`\{err}` 打在一个 `Failure` 上是 `Failure(the model endpoint returned HTTP
401: ...)`——把一个内部类型的名字摆在读者脸上，而里面那句话本来就是写给人看的。现在所有
catch 点都走 `@core.error_text`（`core/script.mbt`）：`Failure` 剥掉包装，别的错误（`DecodeError`
这类子错误本来就只打印自己的话）原样。它同时给回 `core/script.mbt` 里那句注释一个实现——
之前那个 `unwrap_raise` 是同一个规则的**文本版**（给子进程 stderr 用的），两个版本现在是同一条规则。

## 输入区：为什么是浮在对话上的卡片

输入控件的形状来自一个判断：**凡是会改变「这条消息会被发成什么」的东西，都放在写这条消息的地方。**

```
        ┌───────────────────────────────────────────────┐
        │  [缩略图 ×]                                    │  ← 附件（有才出现）
        │  Ask something…                                │  ← 唯一的输入框，⌘↩ 发送
        │  ⊕  ✎  ●  模型 ▾  ◠ High ▾              ⏹  ↑   │  ← 工具行（✎ = 草图，● = 麦克风）
        └───────────────────────────────────────────────┘
          728 model calls · 2.5M in / 530.5k out · 290.8k thinking   ↻ 99% 186M   ◐ 49% 492k/1M   ＄1.0171
```

- **卡片是一块 Liquid Glass**（macOS 26 的 `glassEffect`，14/15 上退回 `.regularMaterial` + hairline），
  所以对话从底下滚过去时看得见它从底下滚过去：它是浮在对话上的一个面，不是「把窗口底部换掉了」。
  玻璃分支上**不再叠自画的描边和阴影** —— 系统材质自带边和高低，再叠一层就是两条边、两层影，
  那正是「像在模仿系统」的典型症状。转录在卡片后面渐隐，硬边会让浮起的卡片看起来像对话到此为止。
- **附件是缩略图行，有才出现**，悬停才显示删除按钮。缩略图是从**附件自己的字节**解出来的（不是
  再读一次文件），所以预览到的就是将要发出去的；文件事后被删掉，预览也还在。
- **模型是卡片里的菜单**，不是设置面板里的一项。模型决定这条消息多少钱、以及刚附上的截图能不能
  被看见 —— 两个都是关于「这条消息」的决定。选错的代价要当场说：不能看图的模型在菜单里就写着
  「· no images」，附上图片而当前模型不能看时，shell 会**在发送之前**回一条错误。

  **菜单里写的是价，不是 id。** 三列 `0.14  0.28  0.0028`（输入 / 输出 / 缓存读，USD 每百万 token），
  表头那行说一次单位，后面跟名字。理由有两个，都是量出来的（`docs/macos-pitfalls.md` 第六节）：
  ① **价格才是这个菜单存在的理由** —— pro 的输入价是 flash 的九倍，而这件事原来一个字都没写；
  ② **id 在菜单里是纯成本** —— `DeepSeek V4 Pro (deepseek-v4-pro)` 让每一行宽 ~110pt，而菜单的宽度
  等于最长那一行（整菜单从 338pt 变成 335pt：去掉 id、加进三个价和一个表头，宽度反而略降）。
  闭合状态因此从 269.5pt 变成 142pt（AX 实测），多出来的宽度还给了输入框。

  **对齐是算出来的，不是排出来的。** 菜单项只能是**一个** `Text`（`HStack` 会被压成第一段），所以三列
  靠空格 + `monospacedDigit`；而「同样位数的空格」要求每个数**字符数相同**，这件事由 shell 做
  （`Pricing::columns`：宽度取自整个 catalog，所以 `0.14` / `0.30` / `1.32` 都是四个字符）。数字在前、
  名字在后也是同一个理由：名字宽窄不一，放前面会把要比较的数字推来推去。

  **id 没有被丢掉，它搬到了它该在的地方**：`/model` 和设置面板里的 model 那一格（那里读者是要拿它去
  打字的），以及菜单按钮的 tooltip。`ModelSpec::label` 现在就是名字，`label_with_id` 是另一个答案 ——
  原来两者共用一个字符串，这正是 id 出现在菜单里的根因。
- **模型旁边是「想多久」**（◠ + 档位名），同一个判断的另一半：模型是**谁**答，档位是**花多少力气**答。
  默认 `high`（和这个仓库一直以来写死的那个值一样，所以不给读者多一个决定时行为不变），可以选到
  `low`（首字更快、账单更小）、`max`（想得最久最贵），或 `off`（不想）。

  **可选项是 shell 发的，不是宿主写死的表。** 档位是**每个模型**的事实（flash 有 `low`，pro 没有），
  菜单画的是 shell 说这个模型有的那几个；切到一个没有当前档位的模型，档位会被**夹到那个模型的默认值**
  —— 而不是留着 `low` 发出去被 API 拒掉。菜单上不显示的东西这里也管：发给模型的永远是 shell 记下的那个值。

  **这是个决定，不是偏好**：选错了重说一句就行，而且只对**下一轮**生效（历史消息不动，前缀缓存也不动），
  所以它在输入框里而不在设置面板里 —— 和模型同一条理由。终端里用 `/think <level>` 选、`/think` 问当前是哪个。

  **档位记在会话的日志里，而且「没说过」和「说过 off」是两个不同的状态。** 每一轮开始时 driver 都会
  把这一轮实际用的档位写成一条 `thinking_level_change`（没指定时也写，写的是 `off`），所以：重开一个
  会话得到的是它上次真正用的档位，而不是某个默认值；而 `SessionContext.thinking_level` 的 `None` 只
  剩「这份日志还没跑过任何一轮」这一个含义。
- **下面一行是账，而且只记一种账**：左边是正在发生的事（`thinking…` / `working… 3 model call(s)`），
  没有 turn 在跑时是**整个会话的累计** —— 多少次 model call、进了多少 / 出了多少 token、其中多少是思考。
  右边是缓存、上下文环和会话总花费，点价钱开出全部明细。两个都是「这段对话现在什么状况」，不是
  「这个窗口现在什么状况」，所以它们读的同一份数（会话总计）。

  **每个数都在屏幕上，不只是 tooltip 里。** 第一版把上下文来源、系统提示占比、缓存明细都放进
  tooltip 和弹层，读者的反馈是「没看到这些信息」—— 没露在屏幕上的数字等于不存在。tooltip 只负责
  把已经看见的那个数**解释清楚**（这个 49% 是量的还是估的、其中多少是系统提示），不负责藏信息。

  **左边为什么是会话而不是上一轮。** 上一轮的数字已经在它自己的结尾了：shell 给每个 turn 收尾都发一条
  note 行（`3 model calls · 2 tool calls · $0.01`），同一批数字写两处就是读者开始不信任何一处的那个地方。
  真正没有别处可看的是会话累计，而输入框下面这个问题本来就是「这段对话现在什么状况」——「刚才那轮多少
  钱」滚到那轮结尾就有；要精确到分类，面板里的 `Last turn` 那一节给的也是它。

### 语音输入：麦克风、句子、和平台自己的听写模型

工具行里 `⊕` 旁边那个麦克风。**它不是「另一个输入方式」，它是把字放进同一个输入框** ——
转录出来的字和键盘敲的没有区别，shell 完全不知道它们是说出来的还是打的。

用的是 macOS 26 的 `SpeechAnalyzer` + **`DictationTranscriber`**（不是 `SpeechTranscriber`）：
**全离线**（不出机器、不需要网络）、**无时长上限**、中文有标点、边说边出字。用 `DictationTranscriber`
不是随手选的——它才是系统听写用的那个模型，带 `.shortForm` 提示和 `.punctuation`/`.emoji` 选项；
本机上同样一段英文，`SpeechTranscriber` 要单独下载模型才能用，而中文两套模型都能跑。

**一句话是「composition」，不是一次插入。** 字以 marked text 进去——就是输入法打拼音时用的同一套机制。
这不是为了好看：它一次性换来四件事——字边说边出现（下划线也是系统画的）、改词直接替换而不是重复
追加、光标停在原处（可以在句子中间口述）、**一句话一次撤销**。最后一条是量出来的：一次 ⌘Z 干净地
把整句话收回去。

**一次听写什么时候结束、一段话什么时候算数**，是这套东西里唯一真正难的地方。规则一共四条，
按发生顺序：

| 读能看到的 | 什么时候发生 | 字怎么办 |
|---|---|---|
| 说了一半、还在改 | 任意时刻 | 标记文字直接替换（`setMarkedText` 的 `replacementRange`）—— 不是追加 |
| 句子定稿了 | **读者还在说**（句中的停顿就是边界） | 落成普通文本（`unmarkText`），**继续听下一句**；一次听写可以说好几段 |
| 读者按停 | ↩、再按一次麦克风、或按发送 | 关麦 → 等最后一个结果（最多 2 秒）→ 定稿。**一定是「关麦 + 有字」结束的**：没等到最终结果就用已经听到的定，所以不会丢字，也不会卡在「Finishing…」 |
| Escape | —— | 把**还没定稿的**拿回去；已经定稿的句子留在那里（那时它已经是普通文字，拿走叫意外，不叫撤销） |

**「谁按停」和「按停之后干什么」是两件事**，这是上面第三条容易读错的地方：

- **按停只结束听写，不发送。** 说完的话留在输入框里，读者看一眼再决定 —— 听错一个字很便宜，
  发出去很贵。
- **但按「发送」时会先把话说完再发。** 见下。

### 有话要说的时候点发送

**发送按钮在听写期间是能点的**（这一点改过：第一版是禁用的，读者的体验是「说完了、字在框里、
箭头是灰的、也不知道为什么」）。现在点它做的事是：

1. 停止听写（不是丢掉 —— 是**结束**这句话）；
2. 等它定稿落进输入框（`sendWhenSettled`，最多 2 秒）；
3. 再发**框里现在的东西**。

所以「说完 → 点发送」是一次操作，不需要先停一次再点一次。↩ 同理：**听写期间按 ↩ 和点箭头的
效果一样**（有字就发了；一个字都还没定稿时它只是结束听写，把这句话留在框里等下一次 ↩）。

箭头什么时候是灰的？只有**框里真没有字**的时候 —— 也就是第一段话还没定稿的那一两秒。
这是 `draft` 的真实状态，不是一条关于听写的规则。


**麦克风没开 / 模型没装 / 权限被拒，都不是「按住没反应」**：按钮自己变成 `mic.slash` 或一个
下载箭头，悬停/读屏说的是下一步能做什么（打开隐私设置 / 按一下下载，带进度）。错误不以弹窗形式
出现——这里没有东西会被打断。

**「在听」要看得出来**，而颜色不够：底色 + 一个描边环，加上符号自己**脉冲**（`symbolEffect(.pulse)`，
只在听的时候跑）。只换底色很容易被读成「这个按钮被选中了」，而不是「现在正在发生」。

**涉及隐私的两件事写在这里，而不是埋在代码里**：只有一个开关，开着时才开采，松开就关
（`removeTap` + `stop`，不等最终结果）；转写在本机做，**一个字节都不出机器**。

**不做的事**：不自动发送（听错一个字很便宜，发出去很贵）、不朗读回答（TTS 是另一件事）、
不做语音命令（「把 X 改成 Y」需要结构化，是第二期）。

代码分两边，边界和这个仓库其它地方一致：**关于「一句话该怎么做」的规则在 `WeiModel/Dictation.swift`**
（纯状态机，20 条测试不需要麦克风也不需要权限），**关于麦克风和字段编辑器的事实**在
`WeiShell/VoiceCapture.swift` 与 `WeiShell/DictationField.swift`。

### 附件为什么走 shell 而不是宿主自己拼

宿主只发路径（`/attach <path>`），读文件、判断格式、判大小都在 shell 里 —— 复用的是 `read` 工具
那一套 `load_image`：**同一份格式清单、同一个 4MB 上限**。宿主自己再判一次，就会有两份清单、两个
上限，而且一定会在某个时刻不一致。

图片字节跟着 prompt 一起进**同一条 user entry**（`agent/driver.mbt` 的 `prompt_images`）：图片是问题的
一部分，单独存成一条消息，会让恢复会话时图片排在它所回答的那个问题的答案后面。送出去的时候先文字
后图片，顺序就是读者看到的顺序。

用量那一行的数字来自**日志**（`Session::usage` / `Session::last_prompt_tokens`），不是进程里的累加器：
所以重启、换会话之后它们还对，而 `prompt` 是 provider 真正计费过的那次请求大小 —— 是量出来的，
不是估出来的。金额的位数由 `core` 决定（一轮常常是千分之几美分，四舍五入到分就全是 `$0.00`），
宿主不再算一遍。

## 界面：三栏，跟着备忘录走

布局上对齐 macOS 备忘录，因为它就是「一列来源 + 一列列表 + 一份文档」这个形状的标准答案：

| 备忘录 | 这里 |
|---|---|
| 来源栏：文件夹 + 计数 | **Projects 栏**：`folder` 图标 + 工作目录名 + 会话数；正在看的那个工作目录有一个绿点 |
| 列表栏：按时间分组（今天 / 昨天 / 过去 7 天 / 过去 30 天 / 六月…） | **Sessions 栏**：只列**当前浏览的**那个工作目录的会话，标题就是时间段；**读者置顶的会话在最上面的 `Pinned` 一栏里**（见下），并且**不再重复**出现在时间段下；每行**两行**：名字，然后是 `项目 · 时间 · 状态胶囊`（项目只在搜索时出现） |
| 内容栏 | 转录：**按「轮」组织**，见下 |
| 标题栏写着**列表**那栏是什么（文件夹名 + 笔记数） | 标题栏写着**工作目录名 + 会话数**（见下：这是三栏 split 的规则，不是选择） |
| 搜索在**它所筛的那一列**里，是悬浮控件 | 搜索**跨所有项目**，所以它在 **Projects 栏**里，是这一栏的**第一行**（标志/名字那行下面、列表上面）。控件仍是系统的 `NSSearchField`（见下：`.searchable` 只管到「在哪一栏」，管不到「在这一栏的哪一行」） |
| 右上角一个「新」按钮 | **两处**：窗口尾端的工具条按钮 `plus` 新建会话，以及 Sessions 栏**列表的第一行**（和 Projects 栏的「Add Workspace…」同一形状，见下）。窗口尾端还有两个会话动作：`pencil` 改名，`pin` / `pin.fill` 置顶（改成 `plus` 是因为 `square.and.pencil` 是「新建**文档**」的隐喻，和旁边那支铅笔打架）。设置是 **Projects 栏工具条最前面的齿轮** |
| 设置是**一排偏好标签** | `SettingsView` 是 `Settings` 场景里的一个 `TabView`，macOS 把它画成**系统自己的偏好工具条**（一个标签一个按钮，窗口标题跟着当前标签走）：API Key / Tools / Skills / Instructions / Turn Limits |

**没抄的，以及为什么**：备忘录的**格式工具栏**（我们发的是纯文本 + 附件，markdown 是模型生成的，
没有「格式」这个动作可做）、**附件浏览器**（附件属于消息，不是独立对象）、**「无更多文本」这种
摘要行**（会话的第一行提问就是它自己的摘要）。

### 为什么是**三**栏

一个会话有**三件**事：它属于哪个项目、它叫什么、里面是什么。两栏的版本只能把前两件塞进一列 ——
侧边栏是「工作目录，下面嵌着它的会话」—— 这在 16 条会话时读起来没问题，在几百条时不行：读者要
滚过一整个项目才够得到下一个，每个项目的标题都把下一个往下推。而且**会话列表没有地方「只关于一个
项目」**，而「按时间分组」恰恰要求它关于一个项目。

拆开之后每栏各有一件事，而且**中栏可以有一个自己的标题**（时间段），不用和项目名抢。

```
Projects               Sessions                 （对话）
● wei Agent          │ wei  7 sessions          1. macos 版还缺什么…
[Search all sessions]│                          wei-agent
Workspaces           │  + New Session           ← 列表的第一行，和 Add Workspace… 同一形状
[+] Add Workspace…   │
folder wei-agent  1  │ Today
folder pi-web    22  │   macos 版还缺少…
folder Madolumo   7  │   ● Running  9月17日   ← 状态和时间同一行
folder …          1  │
folder …      0      │
v Show 3 More        │  ← 只在前面的项目超过 5 个时出现；点开 → ^ Show Less
▸ Running sessions   │ Yesterday
▸ Running tool calls │   修一下分组
                     │ Previous 7 Days
                     │   优化一下 macos 端…
                     │ Previous 30 Days
                     │   8月12日
```

**两侧的项目行自己也不会换位。** store 的顺序是「组内最新一条会话的 mtime 在前」（`list_workspaces`），而 turn 一直在
写文件 —— 实测两个项目的最新会话相差 **0s 和 2s**，于是每次 `sessions` 事件它们换一次位，整个列表上下走一行。所以顺序
在**第一次列表**之后归窗口：`stableSidebarOrder`（`WeiModel/Sidebar.swift`）把到达的顺序按「读者已经看到的位置」重排，
只有**没见过**的行/组才动（走到最前，那是读者刚做的那件事）。这是「事实属于谁」那条边界的一个例子：「列表不许在读者手下
自己重排」是关于**这个窗口**的事实 —— 而读者自己把它挪过之后，同一条边界也管着那个位置（见下面两条）。

**两个运行小节（`Running sessions` / `Running tool calls`）在项目**下面**，不是上面。** 它们是条件出现
的：一个 turn 开始或结束、一条 `bash` 开始或结束，它们就整块进出；早先它们在这一栏最上面时，进出会把下面
每一个项目行连同鼠标目标一起推下去再拉回（实测：第一个项目行在 `y=226`（无运行）和 `y=378`（一个 turn +
一条命令在跑）之间跳，差 152 = 两个小节的 33+41 和 33+45）。读者瞄的是项目，所以不变的在上面、寄存器在下面。
代价：项目多到填满这一栏时这两个小节掉到折线以下；「有没有在跑」在会话栏那行（`Running` 胶囊）和输入框
的 Stop 上各有一份。见 `docs/design-system.md`。

**工作区那行的折叠箭头没有了，换来的是列表末尾的一个折。** 会话搬走之后，项目行底下没有东西可折了，而一个点了
没反应的控件比没有更糟；但**项目本身**会多到把下面那两个运行小节挤走。这不需要很久：把八个真 store 目录喂进
一个 760 点高的窗口，点开折之后两个小节就从 `y=434` 掉到 `y=530`（实测，整整 96 点）—— 再长一点它们就在折线
以下了。所以折在**列表末尾**：超过 **5 个**项目时只画前 5 行，第 6 行是 `Show 3 More`（数字是**折住几个**，
这才是这一行存在的理由 —— 读者数不过来的那一屏上，光写 `Show More` 是一行「点进去还有东西」而不是
「你要找的可能在里面」）；点开画全部 + `Show Less`。
阈值和标签都在 `WeiModel/WorkspaceColumn.swift`（`workspaceColumn` / `workspaceFoldLabel`），有测试；
**折住的状态是这个窗口的**（`WorkspaceList.showingAllWorkspaces`，`@State`，不上线）。

**顺序也是读者的，靠拖拽**（`List.onMove` → `ShellClient.moveWorkspace(from:to:)`）。整段交互是平台画的：跟着
指针的那一行、落点的横线、拖到边缘时的滚动，所以这里是一个修饰符，不是自己画的拖图加一条要和行高对齐的插入线。
一次**拖了两行**（指针从第 1 行拖到第 4 行）实测 `onMove [0] -> 3`，`proj-eight` 从第 1 行落到第 3 行。

拖拽的**算术语义**不靠猜：`destination` 是**被抬起之前**那张列表里的空隙下标（`count` = 末尾），所以「往下一格」
是 `from + 2`，不是 `from + 1`；`WorkspaceMoveTests`（`WeiShellTests`）把四行/五行的每一个 (source, destination)
同时喂给 `movingWorkspace` 和平台的 `move(fromOffsets:toOffset:)`，断言两者一致 —— 差一格这种错在 review 里看不出来，
在 app 里每次都是同一个方向的偏移。

**行上的右键菜单和拖拽不能共存，这是量出来的，不是猜的。** 判据是一轮对照实验：一个几十行的 SwiftUI app，
左右两栏、行一模一样，**只差右边有 `contextMenu`**，同一扇窗、同一段合成拖拽各拖一次 —— 有菜单那栏 `onMove`
一次都没触发（行留在原位），没菜单那栏立刻 `onMove [0] -> 3` 并换了位。不是时序问题：菜单自己的按下追踪把
「按下并移动」吃掉了。两个手势抢同一个按下，只能留一个 —— 留了拖拽（读者伸手要的那个、直接操作、别的 Mac
列表都是这个）。代价是**每行够不到自己的菜单**，于是原来菜单里那三项搬到**这一栏的工具条**上（⋯，`ellipsis.circle`）：
作用对象是**这一栏正在列的那个项目**（填色的那一行，一次点击之遥），`Move Up` / `Move Down` / `Remove Project…`，
可移时才可点（实测：列着第一行时 `Move Up` 灰、`Move Down` 亮）。换来的两件事：动作在工具条上**先说自己是谁**
（`Project actions`，`listed` 的名字进 tooltip —— 「Move Up」四个项目里没有主语），以及**折在后面的项目也能移**。
换掉的是鼠标手势的可达性（选中再按 ⋯，不是右键那一行）。工具条位置实测：齿轮 `x=120…164`、⋯ `x=164…208`、
平台自己的侧栏开关 `208…255` —— 三样都装得下，没有挤压（这比齿轮那条旧记录的 `117…157` 靠后，就是因为多了一个 item）。

**顺序不落盘。** 下次开窗仍然从「最近用过的在上」起头 —— 存下来就意味着那个种子**永远**不再生效，而启动时的顺序
是有用的。这是明知的上限，不是漏掉的。

**这一栏从上到下是自己的一句话：标志 + 应用名、搜索框、列表。** 三样都是这一栏的内容行，谁都不在
工具条里 —— 工具条上只有两样**动作**：设置齿轮（最前）和正在列的那个项目的 ⋯（见上）。

- **标志 + 名字**（画出来的 `Wei.MarkView` + `wei Agent`）是这一栏的**第一行**，用的是和图标同一份
  几何（`Wei.Mark`），不会各画一份。它一度只是标志、待在工具条里、名字只在悬停提示里；再往前是
  标志和名字都在工具条里，`VStack` 堆成两行 —— **那两版都不成立**：工具条那 52 点是整窗共用的
  一条带子，**一行深**，塞两行不会变成两行（实测：18 点的标志 + 折叠按钮两个 item 要 61 点，而这一
  栏只有 208 点，于是平台把折叠按钮从 47 宽压到 38），而**任何东西都放不到 accessory band 上面**
  ——那上面就是标题栏的拖动区（见坑表）。所以名字回到第一行，工具条只留给设置。
- **搜索框**：控件仍是系统那个 `NSSearchField`（`.searchable` 用的同一个），**换的是谁来摆它**。
  `.searchable(.sidebar)` 把它放在这一栏的 **accessory band** 里 —— 那是个**平台拥有的**槽位，位置
  在这一栏内容的上方、标题栏的下方，**这一栏自己画不出任何东西能落在它上面**（实测：搜索框
  `y=61…89`，这一栏的内容要到 `y=98` 才开始；想挤进去只能落在标题栏上）。要「名字在上、搜索在下、
  列表再下」这个顺序，就得自己摆那个控件；用 `NSSearchField` 而不是自画的胶囊，是因为自画的
  `.glassEffect` 胶囊压在侧栏材质上会**发黑**（实测填充 124–138，而侧栏本身 220–247）。
  尺寸和边距照抄原来那个槽位：高 28、离这一栏边缘 10（原来是 `x=18`，而这一栏从 `x=8` 起）。
- **列表**在最后，第一个标题上面那 16pt 空气写在**那一行自己的 `padding(.top:)`** 里，**不用**列表的
  `.contentMargins(.top:)`：两者静止时一样，而边距重新套用是另一趟 —— 点击引起的更新中间那几帧，这一栏
  会被画成没有它的样子（整栏高 16pt，然后复位）。这条是量出来的，见 `docs/macos-pitfalls.md`。

设置那个齿轮放在这一栏靠的是 `ToolbarItem(placement: .automatic)`：同一个 item 声明在这里，它就落在
**这一栏**的最前（实测 `x=117…157`，在平台自己的侧栏折叠按钮 `x=161…204` 前面）；写成 `.navigation`
会落到**中间栏**，写成 `.primaryAction` 则到窗口尾端（那里已经有会话的两个按钮）。

### 标题栏归**中间那栏**，而且这不是偏好

三栏 `NavigationSplitView` 里，**content 栏**（中间那栏）赢得窗口标题，detail 栏的 `navigationTitle`
**被忽略**。原来的写法是 detail 上挂 `title`/`subtitle`，于是标题栏一直显示 `pi` —— 那个名字来自
`WindowGroup("pi")`，也就是「没被赋值的标题」。

发现它的办法便宜到值得记下来：**从进程内部问窗口自己叫什么**（`NSApp.windows` 的 `title`/`subtitle`，
写进 stderr）。窗口标题从外部读需要屏幕录制或辅助功能权限，而从内部读什么都不需要 —— 加了六行临时
探针，一眼就看到了。

所以这一栏写「工作目录名 + 会话数」，和备忘录一样：**在列表上方**，说的是这个列表是什么。
它现在是平台自己画的那两行字（`navigationTitle` / `navigationSubtitle`），字号是系统的 13 semibold / 11 ——
自己画过一版，回退了，理由在下一节。

**这一栏的工具条是空的；三个会话动作都在窗口尾端。** 「分叉」「置顶」「重命名」都是由平台画的工具条
控件（`ToolbarItem(placement: .primaryAction)`，声明在会话栏那一侧），落在窗口最右（两个按钮时实测
`x=835…917`，窗口宽 921）—— 也就是**会话栏**的上方。（`New Session` 曾经在这里，现在它是中栏的第一行
和 File 菜单的 ⌘N。）
这样安排是因为量出来的两条：

| 写法 | 结果 |
|---|---|
| 按钮声明在中间栏、`.primaryAction` | 落在 `x=872…917` —— 窗口尾端，**根本不是中间栏**（`.primaryAction` 是窗口的，不是栏的） |
| 按钮声明在中间栏、`.navigation` | 按钮到了这一栏头上（`x=230…271`），但**平台把窗口标题挤走**：`x=230…864` → `x=397…557` |
| 两个 `.navigation` item | 平台重排整行：标题从自己的栏跑到中间栏上（`x=467…921` → `x=230…397`） |

`.secondaryAction` / `.confirmationAction` / `ToolbarSpacer(.flexible)` 都试过，同一个结果。中间栏加按钮
不是做不到，是**要先把平台的标题换成自己画的**；那条路试过（下一节），回退了 —— 理由见那里。
于是两个动作一起放窗口尾端：**两个工具按钮在一行上很正常**，而且它们都是关于「会话」的。

### 中间栏的名字：试过自己画，回退了

原来这一栏的标题和条数是平台的（`navigationTitle` / `navigationSubtitle`），字号也是平台的：量出来是
**13 semibold** 和 **11**，而规范说我们自己画的栏标题是 `title`(20)。**平台那个字号没有 API 可设** ——
`NSWindow` 只有 `title`/`subtitle` 两个字符串，AppKit 里没有 title font，SwiftUI 的
`toolbarTitleDisplayMode` 文档原话是 "This modifier has no effect on macOS"。所以「改字号」的唯一实现
是自己画，我做过一版：`toolbar(removing: .title)` 去掉平台那枚，在自己的 `ToolbarItem` 里画 20 的标题
＋12 的计数（那时为了让「新建会话」压在这一栏上）。

**回退的理由有两条**：

1. **自己画的不是窗口标题，是它的照片。** `navigationTitle` 留着的话，Window 菜单、Mission Control、
   辅助功能读到的仍是平台那份；去掉的话，窗口就真的没有标题了。两种都不好：一处有两个名字，或者
   一处没有名字。
2. **它要解决的问题消失了。** 当初要自己画，是为了把按钮放进这一栏；现在两个动作都在窗口尾端
   （上一节），不需要了。

所以这一栏回到平台的标题，字号是系统的；规范那张表描述的是**我们自己画的字**，平台画的不在其中
（`docs/design-system.md` 里写明了）。

### 对话栏左上角的名字：为什么重复，为什么不和标题栏抢

对话栏（最右）的左上角写这个会话的名字，用 `safeAreaBar(edge: .top, alignment: .leading)`。
字来自列表那一行自己的 `label`（读者改过的名字 > 第一句提问 > 文件 id，`SessionRow.label`），
**读的就是那同一份数据**，所以它和中间栏那一行不会说出两个不同的名字。

**和中间栏那一行重复是故意的**：一个是「一张列表里的一个东西的名字」，一个是「屏幕上这个东西的名字」。
当年删掉的是另一种重复 —— 窗口标题（那会儿被赋予了会话名）和转录里的标题说同一句话，
看起来像程序不知道自己显示的是什么。现在窗口标题说的是**列表**（哪个项目、几条会话），
两者是两个事实，所以不打架。

**这一栏的标题是 bar，不是工具条 item**，而**改名的按钮是工具条 item**（上一节）。分开的理由也是量出来的：
工具条 item 里放**两个**东西（标题 + 按钮）时，平台会重排整行、把标题挤出这一栏
（`x=467…921` → `x=230…397`）；放**一个**东西就没事。所以名字在 bar 里（顺带得到 inset 和模糊），
按钮在工具条里（顺带得到平台自己的按钮样式、间距和辅助功能）。

名字是**单行 + 末尾省略**（`truncationMode(.tail)`）：一句话可以很长，换成四行的标题就变成第一段了；
末尾省略是读者预期的位置，而且留下的正是他会用来在列表里认出这条会话的开头。悬停给整句（`.help`）。
项目那行同样单行省略（悬停给完整路径，因为两个项目可以重名）。
**改名的铅笔在窗口尾端的工具条里**（和「分叉」「置顶」并排），对话框只有一个（在 `RootView` 里，
列表那一行右键菜单调用的也是它：两份对话框就是两处会各说各话的措辞和按钮顺序）。

**为什么不是 `ToolbarItem`（试过，量过）。** 一个工具条 item 只干净地装一样东西；这一栏的区域里放
**第二个** item，平台会重排整行，而且结果不是「往右挪一点」（三个 x 都是 AX 读出来的）：

| 写法 | 会话标题 | 窗口标题 |
|---|---|---|
| 只有标题一个 item | `x=467…921`（自己的栏） | `x=230…864`（列表栏，正确） |
| 标题 item + 铅笔 item | `x=230…397` —— **跑到列表栏上了** | `x=397…557` —— 被挤到两栏交界 |
| 铅笔塞进标题 item（`HStack`） | `x=230…397` 同上 | 同上 |

所以现在是**自己画的 bar**：两个控件由 `HStack` 排，别的东西一律不动。

**抬到工具条那一行**用的是 `offset`，不是负 padding：`offset` 只改**画在哪**，不改 bar 的高度，
而 bar 的高度正是转录第一行要避开的量。抬起的量**是算出来的**（`titleLift = 工具条/2 + 块高/2`）：
工具条 52 高、平台把自己的 item 居中在 26，所以块的**中线**要落到 26 上。它原来是量出来的常数 41，
那是这一块只有一行时的同一个答案；名字下面加了项目那行之后，常数 41 会让名字留在工具条那一行、
而项目掉到它下面 18pt（`y=5..29` vs `y=31..46`，AX 读的），正好挂在转录上。
**一个「抬多少」的常数只在它量的那个形状上对。** 块高在 `ConversationTitleHeightKey` 里已经有实测值，
抬起的量就从它算，不再有第二个数字可以过期。

**副标题是项目名，在小字里**（`caption` 12 / secondary）。中间栏那一行也写着它，但那一栏是「接下来读什么」
的列表，会滚走；一个读了十分钟答案的读者，屏幕上就只剩「他正在读的这东西叫什么」—— 加上它所属的项目，
这一栏就完全说清楚了。（对象是同一批：窗口标题里的项目名说的是**中间那栏的列表**，这里的项目名说的是
**屏幕上这一条**。）store 还没列出这条会话时（刚建的那一秒）这一行不画，名字自己站着。

**模糊带的高度跟着块走**：`safeAreaBar` insets 安全区，所以顶部那条「内容压过来会被糊掉」的带子
= 工具条(52) + bar 的高度，而 bar 的高度是 `ConversationTitleHeightKey` 量出来的实测值（不是常数）。
两行块（24 + 2 + 15 + 4 的上下内边距）本来是 45，带子是 97 —— 转录滚动区的起点（AX 读的）
从一行的 80 变成 97。这也是「抬多少」要算而不是抄的原因：这两个数是一起变的。

**名字上面那点空，写 8 得到的是 4。** 块是按中线抬到工具条那一行的（`titleLift`），所以块里的
padding 会被算两次：一半把字推下去，另一半把块顶高、再把它整体拉回来 —— 推送和拉回等量。
`padding(.top, Wei.Space.cozy)` 因此只把名字的行盒从 `y=5` 挪到 `y=9`（`y=5` 是紧贴窗口顶沿的
那版，也就是读者说的「太贴着上沿」），而下面的项目那行落到 `y=35…50`，仍在带子（52）里。
写这个数的时候要想清楚它是两倍的意思。

### 会话行：第二行永远是同一条

每行先是名字（`control(.medium)`），然后是**一条** `项目 · 时间 · 状态胶囊`：

- **项目只在搜索时出现**（`caption` / 第二档色，和项目栏的写法一致）。查询跨所有项目，一条来自别的
  项目的结果必须自己说是哪来的 —— 这是那一行本来要解决的问题。平时它就是在重复：窗口标题就在这行
  上面写着同一个项目名，日常视图里等于每行多读一遍同一个词。
- **时间**（`caption` / 第三档色，今天给时刻、今年给日期、往年带年份，`sessionAgeText`）。
- **`Running` 胶囊**只在有回合在跑时出现。它是 wire 上每行真有的唯一状态字段，所以也是唯一画成胶囊的。

**第二行永远是同一条，这是一条硬约束而不是排版偏好。** `List` 的行高是**建行时**量的，之后不再量：
同一身份的行内容变了，SwiftUI 就地更新视图，多出来的那一行会被行的下边缘切掉。实测两次，症状一模一样
—— 行仍是 `300x52`（`123…175`），最后一行落在 `y=168…183`：一次是回合开始（胶囊让它长了一行），
一次是搜索（身份没变，只是内容里多了一行项目名）。两次都被读者看到了（「时间显示不全了」）。

所以「有话说才出现的第三行」这个设计是错的，代价不是「行高会变」而是「变出来的部分看不见」。现在什么都
排在第二行里；真要给某样东西一整行，就得给**所有**行都留出那一行的高度。

名字从 15 降到 13，字重 `medium`（标题 15 semibold 的话，它在这行里就是个**小标题**了 —— 而这一栏的
真标题是时间段那行）。层级改成和项目栏同一套：控制字号 + 控制字号的正交，再靠颜色分层次。

**左右留白加在行自己身上，不在列表上。** macOS 上 `.listRowInsets` 和 `.contentMargins(.horizontal,)`
对 `.inset` 列表的**行内边距完全无效** —— 实测四种写法（不设 / 设 / contentMargins / 两者都设），
`AXRow`、`AXCell`、`AXStaticText` 三层的 x 一模一样（行 290…610、单元格 300…600、文字 306…）。
真正动文字的是行**内容自己的** `padding`：`.padding(.horizontal, 8)` 把文字从 306 推到 314，
正好和转录那条的 24 对齐（列表样式给的 10 + 单元格 6 + 这里的 8）。上下的 `padding` 让高亮比字
高一点，不至于像照着字画的框。

**只在行内画 wire 上真有的东西**：每行传过来的状态字段只有 `running`，所以只有它被画成一个胶囊。
失败 / 停止 / 中断这些都是**关于会话的事实**，但不在这个事件里 —— 要画就得往线上加字段，那是另一件
事（写进「下一步」了）。时间戳早就在 `modified` 里，只是一直没被用起来。

行高下限是 `Wei.Control.row`（40）：两行的行不能是照着字画的紧框，而 40 也正好是个好点的点击目标。

### 设置：平台自己的偏好标签，一行路径收尾

`SettingsView` 从「左边一列、右边详情」的 `NavigationSplitView` 换成了 `Settings` 场景里的
**`TabView`** —— macOS 把它画成**系统自己的偏好工具条**：一个标签一个按钮，窗口标题跟着当前标签走
（实测：`AXToolbar` 里一个按钮一个标签，标题是 `API Key`，窗口标题也是 `API Key`）。终端和备忘录都
长这样，而这座窗口本来就是对着备忘录做的，设置面板不该是唯一一个不合群的。

原来那版不难看 —— 系统设置也是列表 —— 但**列要占地方**：几行的列要吃掉窗口的一块，而且每个
面板都要多点一下才看得到内容。每个面板各只有几个控件，一排标签装得下，一眼就知道这里有什么。

减小的是窗口本身：`640 × 460` → `520 × 360`。跟着变小的是文字：原来每个面板底部都有一段解释，
现在收进 `Section` 的 **footer**（`formStyle(.grouped)` 自己就把 footer 画成小组下面的小字），
每页底部重复了多遍的「设置文件路径」变成**窗口脚下的一行**（它是窗口的事实，不是某个面板的事实）。

**只有一行句子、却占着一个标题的分组，是这次删掉的东西**：一个标题下面什么都没有，读者还得读完
它才知道下面没东西。有资格当标题的是分组里真有几行。

### 打开一个会话：先把「里面有什么」发过去，再说「现在看的是它」

这条顺序是 **实测修过一个白屏** 之后定下来的，写在这里是因为它看起来像可以随手调换的两行。

一条会话的转发顺序是（`macos/appffi/sessions.mbt` 的 `say_open`）：

```
history  →  session  →  usage / models / images
```

**为什么 rows 必须在前面**：宿主是在收到 `session`（「现在看的是这个会话」）时**换转录**的
（`ShellClient.showSession`），不是在收到 rows 时。所以先发 `session` 的后果是：宿主换到一份**空的**
转录上，然后在 rows 到达之前一直画着它。实测这条空窗有多长（30MB 会话）：

| 阶段 | 谁 | release |
|---|---|---|
| 读 + 解析 30MB 日志 | shell | 54ms |
| 建 1353 行 | shell | 25ms |
| 编码成 JSON（3.7MB 一条事件） | shell | 16ms |
| UTF-8 解码 | 宿主 | 2ms |
| **`JSONDecoder` 解出 1353 行** | **宿主主线程** | **51ms** |

合计约 150ms 的空白栏 —— 这就是读者报的「先白屏」。把 rows 放在前面之后，宿主对「不是当前会话的
rows」的处理本来就是**归档到那个会话名下**（`ShellClient.receive` 的路由），于是 `session` 一到，
换过去的就是**已经有内容**的那份转录：**一次渲染，没有空帧**。而且这段等待里屏幕上还是**上一个**
会话的内容，比白屏好。

配套的两件事：

- **`Conversation.loaded`**：空栏和「还没加载」在屏幕上一模一样（同一条原则见 `docs/design-system.md`）。
  这个标志把「会话是空的」（`history` 无 rows，是真答案）和「rows 还在路上」分开，后者画一行
  `Opening…`（**不是转圈**：等待以毫秒计，一闪而过的 spinner 看起来像闪屏）。
- **行 id 每个会话都从 `h-1` 重来**（`history_rows` 的计数是每次调用各自数），所以两个会话的转录会给出
  **同一批身份** —— 而 SwiftUI 对「身份没变」的视图**保留 `@State`**：在一个会话里展开的思考块会
  在另一个会话里开着。修法是在视图侧把这一叠行**按会话作用域**（`.id(session)`，加在 `LazyVStack` 上
  而不是 `ScrollView` 上，见 `RootView.swift` 的注释：滚动位置属于这一栏，落位机制挂在它上面）。
  shell 侧那条事实有测试钉着（「history ids start over in every session」）。

**落位**（打开会话落在末尾）是同一件事的另一半，而且它在这次修复里是**顺带修好的**：
`.onChange(of: session)` 里那句 `guard let end = WeiModel.endOf(conversation.rows) else { return }`
在**空转录**上直接返回 —— 也就是说旧顺序下它只有**一次机会，而那次机会必然落空**。rows 在前之后，
同一句代码就有了可落的地方。这个配对在 `TranscriptRoutingTests` 里断言。

#### 第二次量：一条事件的两半，各自贵在哪（真机、release、1353 行会话）

白屏没有被第一次修复消掉 —— 顺序修掉的是**空帧**，而剩下的是**主线程被占住**（线程忙的时候什么都画不出来）。
这次把一条 `history` 事件按「谁花的钱」拆开（一个临时探针在 `ShellClient.receive` 里逐阶段计时，
跑完即删；探针本身要便宜，见下面的「量具的坑」）：

| 阶段 | 修之前 | 修之后 |
|---|---|---|
| `trimmingCharacters` + `WireLog.elided`（**日志没开**时也在跑） | **101.0ms** | **0.0ms** |
| `Envelope.decode`（1353 行，主 actor） | 58.3ms | **17.4ms** |
| `Conversation.apply`（纯模型） | 0.0ms | 0.0ms |
| 线上字节 | 4,050,741 | **2,330,593**（-42%） |

两处改动：

1. **`WireLog` 的两半都要进 `if WireLog.isOn`**（`ShellClient.receive`）。`WireLog.line` 自己有一道
   guard，但**参数在调用前就算好了**：`trimmingCharacters` 会拷贝整行，`elided` 会扫一遍（找到附件
   字段还会重写）。一条事件带整个会话时，这是**为一份没在写的日志付 101ms 主线程**。一个关掉的功能
   在最贵的那条事件上花掉十分之一秒，是最贵的一种「关掉的功能」。
2. **只给会被画成 markdown 的行发解析**（`draws_markdown`，`macos/appffi/sessions.mbt`）。宿主只在
   **一处**读 `row.blocks`（`RootView` 的 `case .reply`）：提问是 `Text(row.text)`、思考是三行尾巴、
   工具是输出、note 是一行。别的行带上解析 = 没人读的字节。同一条会话上量到：
   reasoning 占了 4.05MB 里的 **1.6MB**（按字节 68%），而 shell 为它每次开会话花 29ms。live 路径
   同一条规则（`close_piece`）。

#### 第三次：窗口化（transcript 分页）

上面那条结论（「贵的是文档高度」）指向的办法是**让文档别那么高**：一个会话的历史不再一次发完，而是
**一页一页从最新往回发**，读者往上滚就自动要下一页。

**规则在 `macos/appffi/sessions.mbt` 的 `page_of`（纯函数，8 条测试）**：

| 参数 | 值 | 为什么是这个值 |
|---|---|---|
| 每页最多几轮 | **6** | 实测那条 19 轮的会话：最新 6 轮 = 320KB（全会话的 15%），最新 5 轮 = 247KB |
| 每页最多多少字节 | **256KB** | 按这些会话约 4KB JSON/点的密度，一页落在几千点而不是几万点 |
| **永不少于一轮** | —— | 一页不能是空的：宿主收到空页就不再问了，读者会卡在顶上；边界也总是落在**提问**那一行，因为「一轮」是这个宿主分组的单位（`WeiModel.turns(of:)`） |

线上的形状：`history` 多了 `oldest` + `has_more`；**新增 `earlier` 事件**（同样两个字段），它和
`history` 的区别是宿主**前插**而不是替换 —— 这正是它不能复用 `history` 的原因（重发 `history` 会把
shell 还没落盘的 live 行丢掉）。宿主回话的方式是新命令 **`/earlier <id>`**，id 就是「我现在最老的那一行」，
所以游标不会因为期间有 turn 追加而行漂移。

宿主的触发与「盯住」：

- **触发**：`onScrollGeometryChange` 读 `contentOffset.y`，在 `offset < 600 && conversation.hasEarlier
  && !awaitingPage && ❗!following` 时发 `/earlier`。最后那条是**量出来的**：一开始只判断「接近顶部」，
  结果切换会话时**连发了三页**（212 → 628 行）—— 新会话的 rows 到达时，滚动位置还是**上一个会话的**
  接近顶部，于是触发；而每加一页又把偏移留在顶部，trigger 再响。同时它和「跟随」规则在抢同一个
  revision（一个要把读者放到底部，另一个在他上方加行）。改成「读者**自己**往上滚了才加载」之后，
  两边不再打架（跟随是「尊重一个滚上去读东西的读者」，而「滚上去读东西」正是这个条件）。
- **盯住**：前插让内容变高，而滚动视图保持偏移 —— 于是读者正在读的那段会**往下滑**正好一页的高度。
  补偿是算术：把高度差加回偏移，通过 `.scrollPosition($scrollTarget).scrollTo(y:)` 写入（这是唯一能
  直接写偏移的 API；`ScrollViewReader` 只能跳到某个 id）。只在「一个页请求在飞、且行数真的变多了」时做，
  否则会把「live turn 在底部追加」也当成前插去补偿。

**实测（3 次取中位数，同一个量具，release）**：

| 配置 | 行数 | 文档高度 | 视图数 | 切换时最长主线程阻塞 |
|---|---|---|---|---|
| 不分页 | 1353 | 32,562pt | 70 | **181.9ms** |
| 分页（带上面那个 bug，级联 3 页） | 628 | 15,480–19,330pt | 125–188 | 107.9ms |
| 分页（修好后，实际发布的样子） | **212** | **5,670pt** | 114 | **100.4ms** |

也就是切换时最长的那个阻塞 **181.9 → 100.4ms（-45%）**，文档高度 **32,562 → 5,670pt（-83%）**。
而且分页之后那三个数字在三次运行里**完全一致**（5670/114），不再有级联带来的抖动。

**还欠着的（这次量出来的）**：切换里还有一个**跟内容无关的固定成本** —— 在**两个很小的会话之间**
切换（都是 3 轮、708pt）实测 **66.5ms**。也就是说 100ms 里约三分之二不是转录的，而这次的改动碰不到它。
它是谁，我**没有**查出来（可能是窗口三栏里别的部分在重建；`jobs`/`sessions` 事件也在同一时刻到达）。
下一次要动这条路径，应该先量它，别再从转录下手。

#### 量具的坑（这次的，值得记）

- **`String(describing:)` 在这条路径上是 166ms**：探针一开始把 `"\(event)"` 当标签打进日志，
  而那个 `event` 有 1353 行 —— 测的是量具，不是被测物。现在打的是 `String(line.prefix(48))`。
- **`inkFraction` 那种「每 tick 把整个窗口渲进一张位图」的探针，自己就是 33ms/帧**：于是「切换之后
  每帧都 33ms」看起来像应用的病，其实是量具的病。改成只在一头一尾量。
- **debug 构建的 release 结论是不可信的**：上一轮 `parse_session_file(30MB)` 在 debug 下 320ms、
  release 下 54ms（5 倍）。这次的数字全部来自 `swift build -c release`。
- 这台机器**屏幕录制权限被拒**，所以「白屏」我仍然没有**看到像素**。这次的证据是「主线程被占住多长」
  及其分解 —— 那是白屏的成因，不是白屏本身。

**还欠着的**（按影响排序）：

1. ~~**history 不分页**~~ —— 这次做了（见上）：一页 6 轮 / 256KB，往上滚自动加载，前插时补偿偏移。
   切换时最长阻塞 181.9 → 100.4ms、文档 32,562 → 5,670pt。**还欠的**是那条与内容无关的固定成本（约 66ms）。
2. **解码最后那 17ms** 仍在主 actor 上。挪到 detached task 需要 `ShellEvent`/`Row`/`Block` 满足
   `Sendable`；窗口化之后这条大半会自然消失。
3. **`turns(of:)` 每次 body 都算**（release 0.14ms / 1353 行）和 **50ms 的命令轮询**：都量过，都小。

### 转录按「轮」折叠 —— 对齐 web UI

一条 turn 的形状是 web UI 的 *exchange*（`html/render.mbt` 的 `render_exchange`），**刻意抄它**而不是自己
定一套：同一条对话在两个前端里应该长得一样，不然两边对「一轮是什么」就不再一致。规则：

```
你问的                      ← 气泡
› Worked through 3 model calls, 2 tool calls   ← 思考、工具调用、中间那些回答，全折在这里
修好了。**581/581** 通过。   ← **最后**一段文本才是「回答」
📊 3 model calls · 2 tool calls · $0.0128      ← 这一轮的账
```

三件容易做错的事：

- **回答是最后一段文本，不是第一段。** 一轮不是「一个问题一个回答」的形状：模型会先说一句、调工具、再说一句。
  只有 `reply` 参与「谁是回答」，**工具调用会截断回答**（web UI 的规则，照抄）。
- **折叠标签数出来的，标钱的那部分丢掉**：`Worked through 3 model calls, 2 tool calls`。没数字时退回
  `What it did`（web UI 的兜底文案）。
- **正在跑的那一轮不折**：要展开才能看它在干什么的折叠，会在每一轮被开合一次。

规则在 `WeiModel/Turns.swift`（纯函数，13 条测试），视图只负责画。

#### 跑着的那一轮：只留最新一个 tool call

「不折」指的是**这一轮的折叠不开**，不是「里面所有行都摊开」。后者是实测里读不下去的那个形状：
二十次 tool call 的日志把答案顶出窗口，而读者正在等那个答案。所以跑着的那一轮另有一条规则
（`WeiModel/LiveWork.swift`，8 条测试）：

```
你问的
› 2 finished tool calls          ← 更早的，折成一行，位置在**第一个被折的** call 那里
▸ bash ls -la                    ← 最新那个：正在跑的，或刚跑完的
修好了。              ← 回答还是最后一段文本
```

- **只折 tool**。思考和中间那些正文**在折叠外面**，这条是从 web UI 抄的，而且有测试钉着：
  把「模型在解释自己」的东西藏起来，页面就只剩一个转圈。
- **没有结果的行永不折叠**，哪怕它不是最新的。今天 shell 不会并发跑两个工具，这是**预防那条路**的：
  哪天并发真有了，折叠不能把一个还在跑的命令藏起来。
- **折的位置是第一个被折的 call 那里**，不是这一轮末尾 —— 否则一段「在两次 call 之间说的话」会跑到
  两次 call 下面，转录就不再是「什么时候发生了什么」的记录。
- **这一轮结束之后又回到旧样子**：外层折叠一盖，里面每一次 call 都能单独展开。开这一轮的折叠是
  决定要读它的工作过程；看一个还在跑的 turn 不是。
- **web UI 的 `settle`（秒后自动折回去）这里没有，也不需要**：那边是把整块 `<details>` 替换了一版，
  所以要用一个定时器把它收回去；这里只**藏旧的**，最新的那个从「在跑」到「已完」位置不变。

#### 思考块：到达时看尾巴，结束后折成一行

同一个道理的另一半。reasoning 是一个 turn 里最长的那段东西（实测一段推理就几万字节），全摊开就是
读者的问题和答案之间夹一页草稿。所以 `ThinkingRow` 分两种形状：

| 状态 | 画什么 | 为什么 |
|---|---|---|
| 还在到达 | **末尾 3 行**，固定高度，点击展开全部 | 读者想看的是它**现在**在想什么；固定高度才能让下面正在跑的那个 call 留在屏幕上 |
| 已结束 | 一行 `Reasoning`，点击展开全部 | 一段想完了的思考，值得说的是「有过这么一段」 |

两个实现上的点：

- **高度是量出来的**（一个隐藏的三行探针 + `PeekHeightKey`），不是拿 `NSFont` 的 ascender+descender
  算出来的 —— 和 `ConversationTitleHeightKey` 是同一课：要的是**文本系统**认为一行有多高，不是字体。
- **盒子锚在底部**，所以给它的是一段**截断过的尾巴**（`reasoningPeek`）而不是全文：`lineLimit(3)` 保留的是
  **开头**三行，一个还没换行到三行的长段落会看起来像卡住了。尾巴截断同时省掉一件事：每帧排版的
  是几行，而不是到现在为止收到的全部。

> 样式**不对齐 web UI**（那是原话：「主要是从 1. 用户的阅读压力；2. 渲染的性能 考虑」）。web 的
> 3 行是 `--peek-lines: 3` 加 `calc()` 算高度，这里是量出来的高度；web 的结果到达时先展开、1 秒后
> 自动折回，这里没有那个定时器。两边抄的是**规则**，不是像素。

### 浏览 ≠ 打开 —— 这是三栏带来的**新**状态

点一个项目只是**看它的会话**，**不**切换对话。两者必须分开，因为「打开」不是没有代价的动作：它换掉
正在看的转录、换掉 agent 的工具在哪个目录里跑、而且可能横切一个还在跑的 turn。

所以它是**窗口的事实**（`RootView.browsing`，`@State`），不是 shell 的事实 —— shell 对「哪个会话
开着」的答案仍然是 `client.currentPath`，两者**允许不一致**，那正是「浏览另一个项目」的意思。

两条规则把它焊住：

- **点会话**：如果那一行不在正在浏览的项目里（搜索跨项目的结果），第一栏跟着过去 —— 否则前两栏会
  对「读者在哪」持不同意见。
- **会话变了**（点了、`⌃⇥`、新建、删除）：中栏跟到那个会话所在的项目。按**路径**触发，所以在同一个
  会话下浏览别的项目不会被立刻撤销。

### 时间分组的两副面孔

中栏的标题是**模式相关**的，而模式由左侧栏的搜索框决定，不是另一个控件：

| 状态 | 列什么 | 标题 |
|---|---|---|
| 搜索框是空的 | 正在浏览的那个项目的会话 | **时间段**（Today / Yesterday / Previous 7 Days / Previous 30 Days / 八月…） |
| 搜了东西 | **所有**项目里命中的会话 | **项目名** |

问法变了，标题就得变：一条**跨项目**的结果必须说清它从哪来，否则点开它是一次没有交代的跳转。

**搜索框在 Projects 栏，不在 Sessions 栏。** 它原来在 Sessions 栏里，理由写的是「在它所筛的那一列
里」—— 这条对**过滤**成立，对**搜索**不成立：它一次筛的是所有项目，而画在某一栏里，看起来就是在
筛那一栏。读者输入别的项目名，然后看着列表换成另一个项目，得到的解释只有一个「原来它跨项目」。
所以它的位置跟着它的范围走，而范围是「全部」，于是它去了 Projects 栏；中栏只负责画结果。

控件本身也换成了系统的 `.searchable(placement: .sidebar)`。自画那颗胶囊是 `.glassEffect`，
而**玻璃铺在侧边栏那种 vibrancy 材质上会渲染成深色**（实测填充 124–138，侧边栏本身 220–247）——
浅色侧边栏里一颗黑药丸。系统自己的搜索框在侧边栏上怎么画就怎么画，这是不该由我们维护的第二份实现。

边界**五条**，且**都是闭区间**（都在 `timeSections` 里，有测试钉住）：今天 = 今天零点之后；昨天、
过去 7 天、过去 30 天 = 各自那天的零点之后；更早按月分，**今年的月份不带年份、往年的带**（一个能回溯
两年的列表里只有一个「六月」是有歧义的）。`modified` 这个字段**本来就在线上**（毫秒时间戳，由宿主
格式化 —— 这正是「关于这个窗口的事实归客户端」），只是一直没被用起来。

**为什么是这五档，而不是原来的「今天 / 过去 30 天」。** 两档时，中间那条在替三条干活：一个每天都
在工作的项目，「Previous 30 Days」底下压着三十行，而那里恰好是读者待得最多的地方 —— 标题什么都
没说。补上昨天和这一周，把「会回去找的」（昨天、这几天）和「偶尔翻的」（这个月）分开了。
**不再往下切**：一个两天宽的桶盖两行，标题要读者先算一遍才看得懂，而标题必须比它盖住的那些行
更便宜。尺子是**日历天**而不是滚动 24 小时 ——「今天凌晨 00:05」属于今天，尽管那不过是十几个
小时前。

### 置顶：一个关于「读者的列表」的事实

置顶的会话在最上面一栏（`Pinned`，在 Today 之上），而一个被置顶的会话**只**出现在那里 —— 它不再
重复出现在自己原本的时间段下。两处都显示是显而易见的替代方案，而它更差：同一个会话在同一栏里会有
两行，读者为了在长列表里找到它而置顶，结果多了一份拷贝而不是少了一堆行。置顶要的是「最近的那几条随时
够得着」。

**它不在搜索视图里**：搜索问的是**所有项目**，它的分组方式是「从哪个项目来的」；一条结果要么在置顶栏
和项目标题下各出现一次，要么被提出那个标题之外 —— 而那个标题正是跨项目搜索的全部意义。

**为什么是 `~/.wei/pins.json`，而不是日志里的 `session_info`。** 名字是**对话的一部分**，所以它写在会话
文件里、跟着文件走；而「我把哪几条放在手边」是关于**读者窗口**的事实 —— 写进日志就等于让别的读者
（另一个前端、另一台机器、下一个打开这个文件的人）也看到同一个架子。所以它是一个自己的文件（和
`settings.json`、`jobs.json` 同一个目录、同一个理由：这是第二份实现自己的状态）。

**里面是路径的数组（集合，不是序列）**：路径而不用名字，因为名字读者能改，一个改名就掉下来的置顶是
靠不住的；顺序不定，因为**唯一排序规则就是列表自己那条**（最近使用的在前）—— 置顶栏拿到的就是中栏
已经排好的顺序，`pins.json` 只回答「在不在上面」。

**置顶栏是「当前项目」的，不是全库的。** 中栏本来就只列一个项目的会话，标题就是时间段；把别的项目的
会话提到这一栏里，就会让一栏只有一条标题的列表突然跨项目 —— 而一旦跨项目，每一行就得自己说清
「我是哪个项目的」（那是搜索视图的规则）。想跨项目碰到置顶的会话，就在搜索框里搜它。

**目前只有 macOS 前端读这个文件。** 网页版（`ui/`）不读，因为它已经暂停；而且它读的
也是自己那份 store，置顶不是会话文件的一部分，所以两个前端各有一个架子是成立的 —— 除非以后想两
边一致，那就得让这个文件成为约定，而不是某一端的实现细节。

**删掉的会话，pin 留在文件里。** 删除是个可撤销的改名（12 秒），pin 在按下那一刻就消失的话，Undo 回来
的会话就不在置顶栏了 —— 那是个没被要求、也没法分辨的副作用。代价是文件会一条删除留一行，所以每次改
置顶时顺手重写一遍（在内存里也重读一遍）：删掉的路径会在**下一次置顶**时被清掉。判断「还在不在」看的
是**文件在不在、或者它在这个进程的注册表里**——刚刚新建、还没写盘的会话不算「没了」。

**两个入口，两条命令的话都对。** 中栏每一行的右键菜单第一项（`Pin Session` / `Unpin Session`，在分隔线
之上、不和「改名」「删除」混在一起），以及右栏工具条的图钉菜单（`pin` / `pin.fill`，填充表示已置顶；
菜单而不是第四个按钮，因为它是三个会话动作里唯一一个**状态**，而状态要能看见）。两处都看 `SessionRow.pinned`
这一份数据，所以工具条和中栏不可能给出两个说法。命令是 `/pin <path> on|off` —— **两个词，不是切换**：
切换的话，一个旧窗口里的菜单就会反掉另一个窗口刚做的决定。

置顶不碰会话文件，所以它**不限于屏幕上的那一条**（改名就有限制：它要往日志里追加）。

### 内存和「读者到底翻了多少个会话」

**每一条打开过的会话，曾经在窗口活着的整个期间都留在内存里。** `Shell.opens` 是「进程正持有其日志
的那些会话」的注册表，而它的准入条件是「读者看过它」—— 于是随手翻五个长会话就要付五个的钱。实测
（5 个真实的 15MB 会话，依次打开）：

| | RSS |
|---|---|
| 启动 | 67 MB |
| 开第 1 个 | 128 MB（+61） |
| 开第 2 个 | 168 MB |
| 开第 3 个 | 200 MB |
| 开第 4 个 | 261 MB |
| 开第 5 个 | **291 MB** |

也就是**大约文件的 2.4 倍**，而且**切走不释放**：`Open.session` 是那份解析好的会话，宿主那边每个
看过的会话还有一份转录 rows（约 +10MB/个）。

**规矩改成按字节的预算，不是按个数**（`Shell::trim_opens` + `open_budget`=64MB）：因为花钱的是字节 ——
一万个*小*会话一共才 37MB（每行 ~3.7KB），按个数淘汰会把它们全踢掉、却留下那五个真正占地方的。
两个**永远不淘汰**的例外都是关于正确性，不是关于速度：

- **屏幕上那一个**：`Shell::shown` 没有它会 panic，这是注册表唯一的硬不变量；
- **任何有 turn 在跑的那一个**：turn **持有这个 `Open`** 并往里写日志，把它的会话抽走就是让一个正在
  运行的 turn 写到一个注册表里已经没有的会话上。（判断用的是 `busy`，和侧边栏画 spinner 的是同一个
  字段，也是**最新**的值，不是读进来时的快照。）

淘汰顺序是**最久没看过**的先走（`shown_at` 是一个只增的计数器，不是墙钟：它只被用来比大小，而一个会
往回走的钟要额外编一个平局规则）。被淘汰的会话**没有丢任何东西**：文件就是那段对话，切回去重读它
（48MB 会话实测 ~350ms）—— 而且**不会弹「你删了什么」**，因为只是让它落回磁盘。

顺带修掉的还有两处**每次刷新都在付的**线性以上开销，都是量出来的：

| 位置 | 原来是 | 现在 | 实测（10000 行 / 一条 48MB 会话） |
|---|---|---|---|
| `history_rows`（`sessions.mbt`） | 每次 `history`/`earlier` **把整条会话建成 JSON 再切一页** | 先走一遍得到 `History`，只对**这一页窗口内**的行建 JSON | 231ms / 91MB 的数组 → 页大小（0.2MB）；一条 48MB 会话打开 389ms → 193ms |
| `append_text`（同一文件） | `text: previous.text + text` —— 每次都整段重拷 | `StringBuilder` 追加 | 一个 turn 连续三万块的人造日志：**38 秒 → 917ms**（真实会话到不了这个形状，但那条边是真的） |
| `stableSidebarOrder`（`WeiModel/Sidebar.swift`） | 每个项目每行 `Array.contains` + `first(where:)`（平方） | 两个字典 | 10000 行 **23.1ms → 1.05ms**（每次 `sessions` 事件都跑：每轮开始/结束、改名、置顶） |

**窗口那一页是怎么算的**（`History::page`）：一页最多 `page_max_turns` 个 turn，所以**不可能**包含第
`max_turns` 个 turn 更早的行 —— 于是先把窗口回退到那个 turn 的边界（和 `page_of` 同一套用户行边界），
只建窗口里的行，再交给**没有改动的** `page_of` 去花预算。`more` 由「窗口里还有更多」或「窗口之前还有
历史」合成。正确性钉在一条测试上：把一条 40 轮的会话**逐页走完**，每一页都和
`page_of(history_rows(全部), …)` 的输出**逐字节相同**（页、cursor、has_more 都比）。

**为什么 `history_rows` 还在**：它是上面那条等价性测试的对照实现，住在 `app_wbtest.mbt`（测试和这个包
共享作用域），不在发布构建里 —— 发布构建里没有任何地方建「整条会话的行」了，编译器也这么说。

### 列表的第一行是一颗按钮

`New Session` 是 Sessions 栏的第一行，**和 Projects 栏的 `Add Workspace…` 同一个形状**（同一种加号槽、
同一个字号，两个加号在整窗同一条竖线上）。

**同一件事画两遍，是因为它被用在两个时刻**：工具条那颗 `plus` 是给「手已经在窗口顶上」的人；列表
这一行是给「列表告诉他那个会话不在」的人 —— 眼睛就在这一栏里。Projects 栏也是这么配的（它的
「Add Workspace…」行 + File 菜单项），不是新花样。

**标签不带省略号**，这是唯一一处和 `Add Workspace…` 的写法不同：那个开的是选择器、还要再问一次，
这个在读者已经在的地方直接开会话；省略号是「后面有个对话框」的承诺。

**搜索时它不出现**：这一栏这时是**跨项目的结果集**，而「新建会话」没有项目可点名，留着它就是
承诺往眼前这个列表里加东西 —— 而它会加到别的列表去。空态那句话也不再指向它（说的还是
「No sessions in this project」，但没有再加一句指路的文字）。

**搜索的两条规则不一样**，而且这个区别是故意的：

- **拷的目录**命中 → 那个项目的**所有**会话都留下（输入一个路径是在要那个项目，这也是记不清项目名时
  的用法）；
- 否则按**会话名**过滤，一个都没命中的项目不出现在结果里。

「项目的**名字**命中就留下全部」看着像个便利，实际是个意外：输入项目名会倒出那个项目里的所有对话，
不管它们和这次搜索有没有关系。目录规则覆盖了真实场景，因为项目名通常就是它路径的一段。

### 选中的那一行：颜色是自己画的

选中那一行的底色**不是平台给的**，是自己画的一层（`RowSelection`），因为 macOS 上 `List` 的选中底色
走**系统 accent**，`.tint` 到不了 —— 实测四种 list style、聚焦/不聚焦两种状态，聚焦时一律是系统的
`#0064E1`，窗口上明明设了品牌色。于是「这个 app 的强调色」在它自己的列表里一次都没出现过。

自己画就得连带把平台的**画**关掉（`UnpaintedSelection`，把列表自己的 `NSTableView` 的
`selectionHighlightStyle` 设成 `.none`）——**状态留着**：箭头键、`List(selection:)`、`AXSelected` 全都
照旧，停的只是绘制。不是为了上色才关的（那一层藏在我们的填充下面，看不见），而是因为平台还会把这一行里
**没自己声明颜色**的文字换成「选中内容的颜色」：浅色外观下那是白色，白字画在浅绿上，正是这一轮收到的
第二条抱怨。

**两栏用的是同一个填充**（会话说「你在读的就是这个」，项目说「你在看的就是这个」，是同一类事实）。
以前它们不一样：中栏是平台给的蓝/灰，左栏是平台的灰，而左栏那个灰又刚好和它自己的选中状态差不多亮 ——
「左栏为什么更浅」这件事一开始就是两个原因叠在一起。现在两栏都由 `RowSelection` 画，颜色同一个 token。

**填充多大是照平台量的**，不是估的：`listRowBackground` 的 frame 比行每边小 2 点，而行里的 **cell** 又
自己内缩 10 点 —— 所以形状整体内缩 **10**（不是 10+2），行内容原有的 8 点内边距叠在上面，文字和填充边
的距离就和平台画的时候一模一样。两行的辅助文字（时间/项目名/工作区计数）在填充上改用 `onHighlight`：
灰字在品牌底上只剩 1.86:1，那不是「弱一点」，那是找不到。

### 一块流式行的名字是「哪一轮 + 第几块」

`<kind>-<turn>-<seq>`。这条规则是**修过一个真 bug** 之后写下来的：之前每个 turn 都从 1 开始，
于是第二轮的 `thinking-1` 和第一轮的**同名**，而宿主是「按 id 找行再追加」的 —— 第二轮的思考和
工具行被写进了第一轮的行里，读起来就是「发第二条就看不到进度了」。Web 版一直这么命名
（`stream-<turn>-<seq>`），原生壳漏了这一步。

宿主现在**自己也按 turn 加一层前缀**：丢转录的代价在宿主这边，就算 shell 哪天又重名，最坏是多
一行，而不是把上一条吞掉。

### 一条命令字打错，不能变成一个问题

`command_of` 把认不出的东西一律当 prompt。这条规则对「裸文本」是对的，对**命令词少了参数**是灾难：
`/restore` 曾经落进最后那个分支，被当成问题**发给了模型** —— 计费、回答、进日志，而读者并没有问。
所以每个带路径的命令都有「光秃秃」的形式，`/restore` / `/attach` / `/open` / `/rename` / `/key` …
都走和「参数不合法」同一个处理分支，得到一句说明少了什么。`/dismiss` 这种词两种拼法都认，因为它
本来就既可以当命令也可以带斜杠。

## 中断的回合

进程死在一个 turn 里，日志里就留着一个「开了没结」的 turn。宿主会收到 `session.interrupted` 和
当时的问题，在转录上方画一张条目，给两条出路：**Continue** 拿日志里那句原话接着跑（已经做过的
工具结果还在模型眼前），**Start Fresh** 写一条 `abandoned` 把它关掉。两条路 Web 版都有，规则同一套。

Continue **不带 prompt**：问题是日志里最后那条 user 消息，让宿主再传一遍就是同一句话的两个副本，
而错的往往是传过去的那份。线上用 `user.continued=true` 告诉宿主「这是续跑，别画第二遍问题」。

## 设置面板：什么该有控件

判据是 Web 版那一句：**这个正在跑的进程能不能兑现？** key、工具模式、技能开关、fallback 指令、
回合上限都是每一轮开头读一次（`Shell::api_key` / `run_turn` / `choose_limits` /
`choose_instructions`），存下来就是「下一轮生效」，所以它们值得一个控件。store、endpoint、模型
都在启动时定了，给它们一个控件就等于说谎 —— 面板里只留一句它们是只读的，以及设置文件的路径，
方便想手改的人去改。

面板各有一次「说清楚」，都是 Web 版踩出来的：

- **Key**：`DEEPSEEK_API_KEY` 压过保存的 key 时，**明说**。读者从字段上看不出来，「我存了它还是
  用旧的」读起来就是个 bug。
- **Tools**：换模式对「已经用过另一种模式的会话」要说明代价 —— 模型还能看见它不认识的工具调用。
- **Skills**：**关掉的技能也要列出来**，包括文件已经不在的那种（只剩一个名字）。看不见的设置
  就是撤不回来的设置。每一行都带路径，读者才知道自己关的是什么。
- **MCP**：`Skills` 的两条规则照搬（关掉的也列出来，看不见的开关撤不回来），但**行更宽**，因为
  问题不一样：一个 skill 是「在不在」，一个 server 是「配置了、关掉了、起来了、还是坏了」四种
  状态，读者得能分开。所以每行还说**传输**、**几个工具**，以及**没起来的那个为什么没起来** ——
  这是面板唯一能拿到失败原因的地方（目录里只列连上的 server）。一个坏掉的 `command` 如果只表现为
  「什么都没发生」，是最难查的那种 bug。
- **Instructions**：文本框里显示的是**在生效的那份文本**，并说明来源（本仓库的 `AGENTS.md` /
  保存的 / 没有）。保存的文本被仓库文件压过时不说清楚，读者会再存一次然后发现什么都没变。
- **Turn Limits**：每个 limit 各自带来源 —— **一条 flag 可以只定其中一项**，所以「这一页显示的是
  默认值」不是对三项都成立的话。flag 定的那项只显示、不给编辑：一个看起来能改、进程却会忽略的
  输入框，比没有输入框更糟。

没有 key 的解法值得单独说：从 Finder 启动的 App **没有** login shell 的环境变量，所以在一台
「装了它」的机器上 `DEEPSEEK_API_KEY` 是空的 —— 这时唯一的入口就是这个面板。这也是面板要先做
的原因：没有它，没有 key 的机器根本进不去。

面板不持有「将要保存的设置」副本：每个控件都是**请求一次改动，然后等 shell 说现在是什么**。
所以保存失败或进程拒绝时，窗口不会留在一个从未存在过的状态上。

### 标题为什么在内容里，而不是在标题栏里

设置窗的标题（左栏那一项的名字）是**靠左画在 detail 列里的**，标题栏里那一行没有字。这不是喜好，
是「系统那枚标题挪不过去」的结论 —— macOS 26 看起来提供了这件事的 API，实测都不是：

| 写法 | 结果（macOS 26.5，640×460 的 Settings 窗，量的是 `NSToolbar.items` 的窗口坐标） |
|---|---|
| `DefaultToolbarItem(kind: .title, placement: .navigation)` | item **确实到了导航位**（x=409…419），但它是**一枚 10pt 的空胶囊**：标题文字没跟过来，系统那枚居中的标题也还在 |
| 先 `toolbar(removing: .title)` 再放导航位 | 更糟：标题哪儿都没有了，只剩那枚空胶囊 |

所以用的是：`.toolbar(removing: .title)` 把系统那枚拿掉（`navigationTitle` 留着，窗口仍然有名字，
Window 菜单和 ⌘, 不受影响），再 `safeAreaBar(edge: .top, alignment: .leading)` 自己在内容里画一条。

选 `safeAreaBar` 而不是 overlay 或一行 header，是因为文档里那句：它 insets safe area 并且
**把 scroll edge effect 一起延伸过去** —— 滚上去的内容会被**同一套机制**模糊掉，
这正是这个窗原来就有、想留住的那层渐变（Skills 那一页内容长，滚一下就能看见它）。

代价写在明处：标题栏那一行没有文字了，标题从「窗口的」变成「这一列的」。另外 `Form` 的左边距
是平台给的，bar 不是 form row，所以那个缩进是**量出来的常量**（`SettingsView.titleInset`，30pt）：
标题首字和行标签首字在截图里对到同一个点上（窗口左边 219pt）。平台要是改了行距，这里要重新量，
不是套公式。

## 一个会话跑不动了：两种「不能继续 turn」

这两件事在 app 上都出现得很频繁，而且看起来一样（提问被吞了），根因是两处，都修在**内核**里
而不是宿主里 —— 它们是协议和日志的问题，不是窗口的问题。

### 1. 一份「看起来完整」的对话，provider 每次都会拒

规则不是「每个 tool call 都要有结果」，而是**「结果必须紧跟要它的那条 assistant 消息」** ——
provider 检查的是**相邻**，不是存在。Stop 掐在模型调用中间、读者随后又打字，就会做出这样一份日志：

```
assistant(tool_calls: exec "")            ← 要工具
turn-outcome(stopped)                     ← turn 关了
user("继续吧")                             ← 读者又打字了
turn-start("继续吧")
tool("The tool call was interrupted…")    ← 结果在这儿，晚了三条
```

**这份日志看起来是完整的**（结果就在文件末尾），所以第一版修复（只找「没有结果的调用」）查不出
任何问题 —— 而每一次请求都被拒。这是我在修完第一版之后、拿真实会话文件复现时才发现的：症状没变，
因为我把规则理解成了「存在」而不是「相邻」。

驱动现在在发请求之前把对话**重排**成合法形状（`plan_repair` / `apply_repair`）：结果在但离得远就
**搬过去**（用原来的 id，不复制 —— 重复的 `tool_call_id` 也一样会被拒）；根本没有就补一条合成结果
（「结果被记录之前就中断了，只读或幂等的操作才重试」，因为那个工具到底有没有改过东西日志里没有
证据）；没碰到的条目原样保留，所以一份本来就合法的日志跑完这个函数一个字节都不变。

放在驱动而不是前端，是因为被违反的规则属于协议：Web 版发现中断的 turn 会给读者一个「继续 / 重新
开始」的选择，app 没有，第三个前端也不该再记一遍。

**失败信息要带上端点说的话。** 这个 400 一开始只知道是「HTTP 400」—— 因为响应体拿到就被扔了。
现在会带上端点的 `error.message`（解开 JSON 信封、裁到 600 字）。一句
「tool message must immediately follow the assistant message」能立刻定位，「HTTP 400」要一个小时。

顺带修掉一个隐藏的一致性 bug：driver 用**调用方那份 session** 判断「有没有 turn 开着」，而那份
只更新到它被告知的上一次 commit。开 turn 这个 commit 以前不上报，所以一次失败的 turn 之后，
调用方的副本停在「没有 turn」，下一次提问就又开一个 —— 日志里出现两个 `turn-start` 一个
`turn-outcome`。现在开 turn 也上报，测试断言 turns 收支平衡。

### 2. 宿主把新提问当成了「继续上一个 turn」

`continuing=self.session.turn_in_flight()` —— 从日志推断。推断不出的是**读者想不想继续**：一个
网络错误让 turn 死掉之后，日志里那个 turn 还开着，于是下一个提问被当成 resume，读者打的字**根本
没发出去**，模型对着旧问题答了一遍。实测：输入的文字在请求里一次都没出现。

现在 app 永远 `continuing=false`：读者打字就是要开一个新 turn，旧的按 `abandoned` 关掉 —— 这正是
Web 版在读者无视「中断提示」直接打字时的行为。要继续应该是读者点的一个按钮，不是宿主替他做的决定。

## 调试：看不见的线上到底有什么

GUI 什么都不打印，所以 app 出问题时（面板一直转、窗口一直 "starting…"）没法判断是「请求没发出」、
「回答没回来」，还是「回答回来了但视图没用它」—— 这三种症状长得一模一样。

```bash
WEI_DEBUG=/tmp/wei-wire.log open "macos/dist/wei Agent.app"
tail -f /tmp/wei-wire.log
```

两个方向各一行，`→` 是宿主发的，`←` 是 MoonBit 发的。`/key` 的内容会被替换成
`<42 characters>`，长度留着（「字段本不该是空的」正是看日志要找的那类事）。默认关闭：一个没被要求
就在旁边写日志的文件是意外，而且里面会有 user 的 prompt。

`wei-cli` 打的是同一条线（不脱敏，它本来就是干这个的），所以两者对照着看能分辨「MoonBit 没发」
和「Swift 没收到」。

## 还有一类高频失败：exec 的字段名

`exec` 的两个方言字段是 `bash` 和 `moonbit`，而 tools mode 的 `bash` 工具用的是 `command`。一个在
tools mode 跑了很久的会话切到 code mode 后，历史里全是 `bash` 调用，模型会一直写
`{"command": "…"}` —— 实测一个会话里 **28 次**，每次都白跑一个来回（模型看懂拒绝文案、改成
`bash`、重发）。

所以 `command` 现在**被当作 `bash` 的同义词接受**（`core/code_mode.mbt`）。这不是放宽 schema，是
承认 schema 的表达力不足：`command` 只能指 shell 命令，语义上没有歧义。schema 的 description 一个
字没改 —— 那句话是缓存前缀的一部分，改它等于让所有已存在的会话重付一次前缀的钱。

字段名真的写错时（`cmd`、`shell`），拒绝文案现在**把收到的键名列出来**，而不是只说「传这两个」：
「你发的是 cmd, timeout」是能照着改的，「请传 bash 或 moonbit」还要模型自己猜哪里错了。

## 设计规范

**`docs/design-system.md`** 是这一套的规格：颜色、字体、间距、圆角、材质、组件。它和代码是同一些数字 ——
token 在 `macos/WeiShell/Sources/WeiModel/Design.swift`（值，可测）和 `macos/WeiShell/Sources/WeiShell/Design.swift`
（`Color` / `Font` / 浮层），`DesignTests` 把能算的部分算出来。

它存在的原因是具体的：写之前窗口里有 **11 个字号**和 **14 个间距值**，那不是尺度是历史。

**一个色相、两个明度**：`#78E5A4` mint 和 `#30714A` pine 是标志自己的两色（同一绿的两端）。pine 够暗所以
浅色外观用它当 accent（白底 5.86:1），mint 够亮所以深色外观用它（暗底 10.75:1）—— **一个色相的品牌把「两种
外观都读得出来」全部压在明度上**。代价是明确的：mint 在白底只有 1.55:1，所以它在浅色外观里**只能是填充**。
有测试钉着（四条断言，**包括两条「应该失败的」**）。

三条最容易违反的规则：

- **中性色一律借**（`labelColor` / `secondaryLabelColor` / `separatorColor` …），不硬编码灰 —— 只有它们回答
  深色模式、增强对比度、非活动窗口变暗。
- **间距在 4pt 栅格上，圆角不在**。间距是两点之间的距离，必须同度量；圆角是一个角的形状，是绝对量 ——
  32pt 控件上给 12 会明显过圆，正确值是 10，而 10 不在栅格上。
- **调用点不出现裸数字**。需要新的一档就改规范，不在调用点写一个 7。

名字、标志和图标也是规范的一部分：**wei Agent**，`wei-logo.svg`，标志按**路径命令原样**绘制（**下凹的顶边**
和两条笔画的**尾巴**就是 w 的暗示，几何化会把它们弄丢），图标由 `macos/make-icon.swift` 画在薄荷瓦片上。

**但标志的颜色不跟着外观换**（`Palette.markFill` / `markInk`，两种外观同一组值）。标志原来用的是
`highlight`（容器）+ `accent`（笔画），而 `accent` 在两种外观里换明度 —— 深色外观下笔画被画成了和
容器一样的 mint，那个 w 直接消失，标志变成一块纯绿。`wei-logo.svg` 是一张**固定的图**：容器 mint、
笔画 pine，两种外观都是。accent 可以随外观换哪个色当重音，标志不行。

## 已知的坑

> 完整清单在 **`docs/macos-pitfalls.md`**（按 `症状 → 原因 → 修法` 分组，六组，带验证与自动化）。
> 下面这几条留在这里，是因为它们的理由比表里一行更长。



**发送按钮点了没反应：闭包捕获的是旧值。** 这是「输入内容后发送，但是没有反应」的真凶，而且它比
看上去更像框架问题而不是代码问题。原来的写法是宿主把发送动作当闭包传给输入卡片：

```swift
Composer(draft: $draft, onSend: { client.send(draft); draft = "" })
```

闭包是**捕获值**。键盘处理函数（`.onKeyPress`）是早先某次 body 装上去的，那时 `draft` 还是空串 ——
于是它读到一个空串、把清空写到已经不在链上的 binding 上，而**输入框里的字一个都没少**。实测日志：

```
key return, draft=[first]        ← 处理器确实被调用了
ShellClient.send text=[] trimmed=[] ← 传给 shell 的是一个空串
onSend returned, draft=[first]   ← 而且没清掉
```

按钮那条路看起来是好的，因为点击本身会触发一次 body 重算、拿到新的闭包 —— 所以「按钮能发、回车不
行」这个组合是可信的，不是错觉。

修法是让发送**在 Composer 内部完成**，用它自己的 `@Binding`（活的），不再经过上层闭包：

```swift
let text = draft
draft = ""
client.send(text)
```

规律记下来：传进子视图的闭包里只要读了 `@State`/`@Binding`，就可能是旧值；跨视图共享的应该是
**引用类型或 binding 本身**，不是读它们的闭包。

- `swift build` 会刷一屏 `was built for newer 'macOS' version` 的警告：MoonBit 用本机 SDK
  编译 `libwei.a`，而 Swift 包声明的最低版本更低。是警告，不是错误。
- 归档要手动重建：改了 `macos/appffi/` 得再跑一次 `build-moonbit.sh`，SwiftPM 不知道它。
  更阴的一点是 SwiftPM 也可能不重链：`touch` 一个 Swift 文件未必让可执行文件重链，于是新的
  `.a` 被写着旧二进制。症状是「MoonBit 侧明明改了，线上没变」。`rm` 掉可执行文件再 build 一定对。
  已经踩到两次的产品：`WeiShellPackageTests.xctest`（`touch` 测试文件也没用，得 `rm -rf` 那个
  `.xctest`）和 `wei-cli`。两者的症状一模一样：**旧的 shell 用旧的线格式回答，于是新加的字段
  在日志里根本不存在** —— 这比报错难查，因为一切看起来都在正常工作。`swift test` 里那条真启 runtime
  的测试就是为这一类事存在的。
- **`ShellClient` 和 `wei_set_emit` 是一件事**，写第二条就等于把 app 弄成聋子：宿主装了 reader
  却没在 C 侧注册回调时，`emit_sink` 是 NULL，每一行都被丢掉，而 `wei_emit` 不报错。症状是
  「窗口起来、什么都不发生」。现在 `Emit.install` 同时做这两件事，`WeiShellTests` 里有一条真启
  runtime 的测试守着它（把那段注册删掉，测试会以 `state=starting` 失败）。
- `swift run WeiShell` 是裸可执行文件，不是 .app。`AppDelegate` 里那句
  `setActivationPolicy(.regular)` 就是为它写的 —— 否则有窗口、没菜单栏、不聚焦，看起来像卡死。
  真正打包时它是个 no-op。

## 滚动跟随：为什么不是「在底部就跟着」

朴素写法是一致的：每帧量一次「我到底了吗」，是就跟。它**必然在第一个 token 上失效**，因为内容
自己会生长 —— 生长这件事本身就把底部推离了读者，于是那一量就是「不在底部」，跟随从此永久关闭。

所以规则里真正重要的部分不是动作，是**谁有权改变它**：只有读者自己的滚动。往上滚 = 立刻停
（无条件，没有别的意思）；往下滚 = 底边回到视野里才恢复（半途的惯性不该让流式内容开始拽人）；
发出提问 = 恢复（他刚问了问题，答案得在他眼前）。除此之外——delta 到达、工具结束、窗口缩放——
一律不动这个决定。

```
delta 到达 ──────────────► 不变（关键：内容生长不是「离开底部」的证据）
读者往上滚 ─────────────► 停止跟随
读者往下滚, 底边可见 ─────► 恢复跟随
读者往下滚, 底边不可见 ───► 不变
发出提问 ───────────────► 恢复跟随
```

规则本身在 `WeiModel/ScrollFollow.swift`，可测；视图只负责两件它该负责的事：量（几何）和听
（`NSEvent` 的本地滚动监视器 —— SwiftUI 14 上没有「用户滚了」的回调，而测量分不出「读者在动」
和「内容在长」，那正是这条规则的全部内容）。

### 「末尾」是一个轮的 id，不是最后一行的 id

滚到末尾这件事有一行代码，而它是错的，且错得无声：**`ScrollViewReader.scrollTo(id)` 对一个没有
任何视图注册的 id 就是空操作** —— 不报错、不警告、不滚动，看上去和「布局不对」「时序不对」一模一样。

视图注册的是**轮**的 id（`ForEach(turns, id: \.element.id)`），而轮的 id 是它那条提问的行 id；顺手
写的「最后一行」`rows.last.id` 因此几乎永远不存在 —— 一条回答之后，最后一行是那段回答里的一个**块**
（id 是 `"<轮>/<块>"`）。后果就是点一下会话栏，长会话停在**最顶上**。

所以「末尾在哪」是一条有名字、有测试的规则（`WeiModel.endOf`），而不是视图里的一行 `.last`。
`TranscriptEndTests` 里专门留了一条断言写着这个坑本身（`rows.last.id != endOf(rows)`），免得它被
当成等价替换改回去。

还有第二件事：`LazyVStack` 只建视口附近的行，所以刚到达的轮可能**还没被建出来**，滚动要
`DispatchQueue.main.async` 推迟一拍。实测（从进程内读 `NSScrollView` 的滚动位置）：

```
切换 A → B → A，旧写法   scroller=0.000   ← 停在 48911 点的最后一段之前，也就是最顶上
切换 A → B → A，现在     scroller=1.000
```

## 附件：拖进来、粘上来、画一张、拍一张

**一个出口**（`/attach-temp <path>` 或 `/attach <path>`），六个入口：卡片上的 `+` 菜单（**选择文件 /
截屏 / 隐去窗口截屏**）、它旁边那支**铅笔**（画画）、拖到卡片上、⌘V 粘剪贴板里的图、Edit 菜单里的
同一批命令，以及 `⌘⇧S`。

`+` 从一个按钮变成一个菜单，是因为**它那三项共的是什么**：一张**已经存在于某处**的图 —— 一份在
磁盘上，两份在屏幕上 —— 而区分它们的就是那几个名字。一排只有图形的按钮，每一个都要读者先学才
知道是什么。这是这个平台的做法（一个 `+` 列出它能加什么），而快捷键的字面则交给平台自己画（菜单项
的 key-equivalent 那一列）—— **把 `⌘⇧S` 写进标题里试过一版，不成立**：自定义 `label` 会被菜单
丢掉，于是两行截图项看起来一模一样。

**铅笔不跟着进菜单，而且它是故意留在外面的。** 它是这一行里唯一一个**造**图而不是**找**图的入口，
所以它不是「图从哪来」那张清单的第四行，而是 `+` 旁边**同样重量的一个按钮**。它的第二个理由是
可发现性：它摆在那里，一个想画点什么的人就看得见自己能画；折进菜单里，这一步就变成了「先知道
它在那儿」。

拖拽不按扩展名过滤，因为**判格式是 shell 的事**（`load_image` 嗅字节）—— 按扩展名过滤会拒绝
一张没有扩展名的截图，而那正是当初引入 sniffing 的理由。

粘贴和截屏都没有路径，只有字节，所以宿主先写一个临时文件，用 `/attach-temp` 告诉 shell「这文件是我造的，
读完删掉」。删除放在 shell 侧是必须的：读发生在收到命令之后（agent 线程），宿主这边删会**和读
抢**。名字带 UUID，同一张截图粘两次是两个文件，而不是读者没要求的合并。

## 截屏：借系统的工具，把画带回来

**拍不是这个 app 自己做的。** `/usr/sbin/screencapture` 是系统本来就有的那条路，也是读者从 `⌘⇧4`、
`⌘⇧5` 已经认识的那条路，走它才做得到**框选和选窗口**：十字光标、选区、窗口高亮、空格在两模式之间
切换，全是系统画的，一行都不用重写。这个 app 加的是工具不做的那一半 —— 图回到 composer 里，
**发出去之前能画**。

不快门声（`-x`）：静音是读者的选择（系统设置里有），不是这个 app 替他定的。图也**不往剪贴板里放**
（`-c`）：剪贴板是读者的，一个把里面东西吃掉的截图功能，得先想清楚才敢用。

**两个入口，一个隐藏。** `Take Screenshot`（`⌘⇧S`）把窗口留在图里，`Take Screenshot Without This
Window`（`⌘⇧S⌃`）先把 app 收起来、拍完再放回来 —— 后者是「不要在截图里看见自己」那件事，而这件
事必须由调用方来做（工具不知道谁是调用方）。写进 Edit 菜单而不只是 `+` 菜单里，是因为**菜单栏是
快捷键唯一能被发现的地方**，而一个从来不开 Edit 的人不该永远不知道有 `⌘⇧S`。

**那个隐藏是 `NSApp.hide`，不是把窗口 orderOut。** 窗口是屏幕上最前面的东西，只把它挪开会留下
菜单栏和 Dock 在那里宣布一个有窗口的 app —— 而这正是要拍的东西的一部分。

### 三种结局，和它们**量**出来的边界

截图是**另一个进程 + 读者在回路里**，所以它的回答是「字节、它说了什么、以什么状态退出」，而三种
结局（拍到了 / 读者改了主意 / 被拒绝）全靠这一组读数分开。这一组是**量出来的，不是猜的**：写一个
自己的 bundle（换个 bundle id，于是 TCC 认它是另一个 app）跑同一条命令，四种情况各跑一遍 ——

| 情况 | 退出码 | 它说了什么 | 文件 |
|---|---|---|---|
| 框选完，有屏幕录制权限 | `0` | —— | 写了 |
| 框选完，**没有权限** | `1` | `could not create image from rect` | 没有 |
| 按 Escape，有权限 | `0` | —— | 没有 |
| 按 Escape，**没有权限** | `0` | —— | 没有 |

三条规则直接从表里出来，**每一条都有一个不这么写就会坏的场景**：

- **字节是唯一的裁判。** 写出来一张图就是成功，它顺带说了什么不算第二种意见 —— 工具对它能恢复的
  事也会往 stderr 写一行，先读文本的实现会**把手里已经有的图拒掉**。
- **取消是「安静 + 退出 0」，拒绝是「说话 + 非零」。** 所以只看退出码会把取消当成功，只看有没有文件
  会把取消和拒绝混成一个 —— 只有取消能产生「一个字没说 + `0`」这一对，而它换来的是**改主意的人
  看不到任何对话框**。这是这个功能能不能用的分界。
- **先判取消，再判权限。** 表里最后两行：没权限的人按 Escape 拿到的也是「安静 + `0`」，所以先看权限
  就会告诉这个读者「你的 Escape 是权限问题」—— 在他决定不要这张图的那一刻，说一句错的、关于错的事的话。

权限**在失败之后**才问（`CGRequestScreenCaptureAccess()`），不在手势之前：它是「为什么没有图」的解释，
而不是「会不会有图」的预告。实测没有权限的进程**照样拿到十字光标、照样等读者框选**，只是画不出图 ——
所以手势之前问，等于在一件本来能成的事前面放一个对话框。（这一步还有第二个作用：它把 app 写进
「屏幕录制」那个列表，否则读者按「Open Settings」过去会发现**没有 wei 这一行可开**。）

### 截图和草图是**同一张纸**

进去的是同一个 `Sketchpad`，区别只有 `under`：一张图在下面。所以「框一块、在里面圈一行、再发出去」
是一步，不是两个功能；五个工具、撤销、清空、插入的位置也全都一样。

**清空只清笔画，不清纸** —— 在一张截图上那是「一个什么都不做的按钮」和「把刚拍的图扔掉」的
区别。**插入在拍来的纸上一开始就可按**：空纸插出去是一张 640×420 的空白 PNG，一张什么都不说的图。

**纸的尺寸和分辨率是两个数，而截图两个都带自己的。** 空白草图是固定的 640×420 点、2× 导出
（1280×840），而截图不是：工具把屏幕的 dpi 写进文件，于是 `NSImage.size` 是它自己的点、
representation 的像素是它自己的像素 —— 全屏 2× 那一张是 **1470×956 点 / 2940×1912 像素**。
`Sketch.Paper.fitting` 是让两个都成立的规则：**保持形状、不放大、超出就缩小**（一张 200 像素的截图被
放大去填满纸，就是读者在给一张模型永远看不到的模糊图做标注），**而导出是那张图自己的像素** ——
2940×1912，不是「680 点的纸 × 屏幕的 2×」那个 1360×880。

这件事**只有眼睛会骗人的那一半能验**：把纸上画的和导出的比特对起来要过一张真的位图，所以它在
`WeiShellTests/PictureExportTests`（`ImageRenderer` 那半边只有窗口那侧有）—— 文件多大、图在不在
墨下面、**墨落在它被画下的地方没有**（同一列下面那一块留白，和上下镜像那一块留白，是三个像素
各管一件事），以及**图有没有被上下颠倒**（笔迹活在左上原点的坐标系里，从字节读出来的图活在
`CGImage` 的左下原点里，两边都得回答「这是哪一头朝上」）。

### 发出去的图回到会话里：**缩略图一行，点开在原地**

发出去的那张图现在**在会话里看得见**了。这件事原来不成立，而且是那种最叫人恼火的不成立：图在
日志里、也发给了模型，而读者自己那条消息只显示字 —— 在唯一一个看不见日志的人眼里，那就是「没发出去」。

**一条消息的图是一行缩略图，不是一叠原图。** 第一版把每张都按原尺寸竖着画，一张截图时是对的，
四张时就把整条对话推下去了：三张窗口截图比整个转录还高，而读者对自己刚发的图里有什么再清楚不过。
缩略图让**无论几张都只占会话的一行**，而且它就是 composer 发之前显示的那个 44 点小图
（`AttachmentChip`）的同一种东西 —— 同一件事的两头长得一样。

缩略图说得出「这是哪一张」，说不出「里面是什么」。所以**点一下就原地展开** —— 和工具输出那个
「Show all」是同一个套路（见 `ToolRow`）：点开、再点收起，空间是读者在需要的那一刻自己花的，
不是整条会话替每个附件预付的。单独开一个窗口或全屏查看器是另一条路，在这个只有一个窗口的 app 里
更差：图属于这条消息，而消息就在屏幕上。

**摆行的那条规则是算术，所以它在 `WeiModel/PictureFlow.swift`，有测试。** 失败的样子很安静：**一行
排不下的不是换行而是被挤**，而一张被挤到零宽的缩略图是**一张凭空消失的图** —— 没有报错、没有
东西可点。另外 `Layout` 要把同一个问题问两遍（`sizeThatFits` 多高、`placeSubviews` 摆在哪），
**两遍要是各算各的，高度就会和实际画出来的对不上**，症状是内容压在下一行上或者空出一条缝：
所以是一个函数给两处用。测试里那两条边界都是真实输入：宽度还是 `0`（布局的第一轮），和一条
**刚好塞满**的行（间距是「之间」而不是「之后」，差一个 gap 就是溢出）。

**这里还有一个踩过的坑，写进 pitfall 了：`Group { if let … }` 里的 `.task` 不会被调用。**
图加载不出来、什么都不显示，就是这一条 —— `if` 为假时那个分支**没有视图**，于是挂在上面的
`.task` 没有东西可挂，`load()` 从来没跑过。（回答里的图不会撞上：`Picture` 在读取期间画一个 spinner，
所以它的分支永不为空。）

### 菜单里那一项是**窗口**的事，不是 composer 的事

`+` 菜单和 Edit 菜单都要开同一张 sheet、跑同一条命令，所以状态和命令都在 `WindowActions` 上
（`macos/WeiShell/Sources/WeiShell/Screenshot.swift`），调用它的 view 只有两个。这不是洁癖，是
`docs/macos-pitfalls.md` 里那条「一个消息永远没离开 app」的同一个形状：**一个把值捕获进闭包的
入口，写的是另一个入口看不到的状态。**

## 草图：一个画图的地方，和它刻意不是的东西

工具行里 `⊕` 旁边那支铅笔 —— **不在 `⊕` 的菜单里**（见上一节）。**它不是绘图应用，是「做一张图」的
一条路**：有些话画出来比写出来短 —— 一个框、一支箭头、三个圈 —— 而原来的替代方案是离开这个 app
（去别处画、截图、把截图拖回来），为了画一张三秒钟的图付出三分钟。

边界写在功能里，不是写在文档里：**没有图层、没有颜色、没有选中、没有填充、没有文字工具。**
每一条都够得上一次「顺便加上」，而每一条都要在画第一个框之前先学它。五个工具（自由笔、直线、箭头、
矩形、椭圆）、撤销、清空、插入。

**产出走的是和剪贴板同一条路**：`ImageRenderer` 出一张 PNG，写成临时文件，`/attach-temp` 交给
shell —— 它嗅字节、读完删掉。所以这个 sheet 完全不知道「附件」是什么，也没有第二处理解字节。

**画布是固定 640×420 点的只有空白那一张；有图的时候纸随图。** 不变的理由是笔迹就活在纸的坐标系里，
窗口大小不参与 —— 小窗口画的和大窗口画的是同一张图，也不用在导出时重新布局。**1× 的墨是 2.5 个
像素**，每条斜线都是阶梯，而看图的是一个没有屏幕的读者 —— 所以空白那张导出按 2× 渲染，得到
1280×840 像素；有图的那张按「那张图自己的像素」算出比例（见上一节）。**纸不会窄到比工具行还窄**：
框一个词出来是 90 点的图，纸跟上去会把五个工具的标签挤成几个点一个 —— 下面留 420 点的下限，纸居中。

**纸的圆角用转录画一张图的同一个半径**（`Wei.Radius.panel`，见 `Picture`）：读者画的形状，就是它
变成图片之后被画成的形状 —— 直角卡片装在圆角 sheet 里、发出去又变成圆角卡片，是这个流程里唯一一处
「画的」和「拿到的」不是一个东西。**笔迹不跟着这个形状裁**：发出去的是一张普通矩形，在屏幕上下刀会
把一条画在角上的笔迹从眼里删掉、却留在文件里。

**屏幕和 PNG 是同一个 `SketchCanvas` 的两次渲染**，不是两份画法：一份「箭头长什么样」的第二个实现，
只会在发出去之后才暴露两边不一致 —— 有图的那一层也是这个 view 画的，同理。

三件放在 `WeiModel/Sketch.swift`（`SketchTests` 断言的那一半，都是算术，都能在没有窗口的情况下
判对错）：

| 算术 | 不管它会怎样 |
|---|---|
| 拖拽的**矩形要归一化** | `CGRect` 不接受负的宽高 → 往左上、左下、右上三个方向拖出来的都是零矩形：读者画了，看不见 |
| **多小的拖拽不算一笔** | 笔点一下是一个点（那是画的），矩形画出 `40×1` 是把按钮压下去的副产品 —— 而记住的一笔想不起自己是意外，那是一个擦不掉的污点 |
| **箭头的两支落在哪里** | 反向的箭头**看起来还是箭头**。零长度的拖拽没有方向，所以两支收回箭头尖 —— 那里要是 `NaN`，它顺着画出来的路径往下传 |

清空**不弹确认**：⌘Z 能把它放回去（清空之前画的都算历史，撤销按画的顺序往回走，然后才是清空）。
一张草稿前面的对话框是给常见情况加摩擦 —— 而「原谅」这一条要求的本来就是**能撤**，不是**先问**。

## 后台任务面板

工具栏上一个按钮，只在真的有东西在跑的时候出现 —— 一个永远能打开空列表的按钮，是教读者忽略它
的按钮。

面板回答的是「现在还有什么在跑」，不是「跑过什么」：已结束的 job 留在 store 里（重启后靠它认出
上一个进程留下的孤儿、靠它让 kill 还能到达每个 pid），但不发给面板。pid 也过滤成**进程表里还活
着的那些**：一条命令登记时会带上自己的 shell 和报告它的那个 helper，而读者去 `ps` 里要找的不是
它们。

Kill 杀的是**记录过的每一个 pid**：`cmd &` 的 shell 会立刻退出，真正的活在子进程里，只杀最后
一个已知 pid 会留下一个没人知道的孤儿。杀完状态是 `stopping` 而不是直接消失 —— 信号发出和进程
消失是两个时刻，一个忽略 SIGTERM 的进程会一直停在那里，读者看得见这个区别。

进程表每两秒读一次（和 Web 版同一个节奏）：一次读同时服务两个问题 —— 面板该显示哪些 pid，以及
某个 job 的进程是不是都没了。读两次会是两个可能互相矛盾的答案。store 写盘时**内容没变就不写**，
否则一个每两秒被 touch 的文件会让备份工具永远不得安宁。

### 顺带修掉的一个真 bug：幽灵 job

一个「会留下进程」的调用一旦在**执行之前**就失败（空命令、方言不对、解析失败），`note_execution`
永远不会被调用，那条记录就永远停在 `running`：面板里一行没有进程的行、一个杀不掉任何东西的
Kill、以及本会话十个槽位里少一个。`call_open` 正是「这次调用还没汇报过」的意思 —— 调用已经返回
而它还是 true，就是「永远不会汇报了」。修复在 `agent/driver.mbt`，两个前端都受益。

## 同时跑多个会话

**一个进程可以同时跑多个 turn**，每个会话一份状态。这是这版里最大的一次结构改动，也是 Web 版一直有而这一端没有的能力：那边的 `Runner` 是「一个打开的会话」，`App` 是「全部共享的东西」，这里原来是**一个**扁平 `Shell` 装着唯一那个会话的 `session` / `path` / `turn` / `busy` / `aborting` —— 于是「两个会话同时在跑」不是没实现，是**表达不出来**。

**改了什么。** 那些字段搬进 `Open`（`appffi/app.mbt`）：

| 留在 `Shell`（进程一份） | 搬进 `Open`（会话一份） |
|---|---|
| `settings` / `home` / `root` / `base_url` / `jobs` | `session` / `path` / `cwd` / `model_id` |
| `live_pids` / `saved_jobs` / `sent_jobs` / `labels` | `turn` / `busy` / `turns`（每会话一把锁） / `aborting` |
| `skills`（按 cwd 缓存，本来就是项目的） | `attached`（草稿属于写它的那个会话） / `last_turn` |

`opens : Array[Open]` 是「这个进程持有的会话」，`current : String` 是「屏幕上那个」。**「打开」不等于「在看」** —— 读者切走的会话留在 registry 里继续跑，这正是它存在的理由。`run_turn` 收一个 `Open` 而不是读 `self`，所以一轮 turn 只写自己的会话，**对屏幕上是谁毫不知情**。

**线上多了 `session`。** 每条属于某个会话的事件都带上它（`session_event`），因为主人必须知道一条 delta 该写进哪份转录。空 = 「屏幕上这个」：绝大多数事件是读者刚对自己看的会话做了点什么（路径不对、模型不认识、设置面板），那些不需要点名；**需要点名的是正在跑的 turn**，因为那是唯一一件可能发生在没人看的会话里的事。

行 id 也因此变成**每会话**的：两个会话都可能把自己的第一块叫 `reply-1-1`。这在「一次只看一份」的时候完全没事，一旦某份的重放能落进另一份就出事了 —— 所以 `session` 不是可选的。

**host 侧**（`ShellClient`）从「一份转录」变成「**每会话一份转录** `transcripts`」：事件按 `session` 分派，屏幕上那份进 `conversation`，其余进各自的。切过去是**换一份**，不是重新开始 —— 所以一个正在流式输出的 turn，切走再切回来，**半截答案还在**，接着长。

**历史只发一次。** `show` 对一个**没见过**的会话发 `history`，对一个**见过**的只发 `say_show`（会话 + 用量 + 模型 + 附件）。原因是硬的：跑着的 turn 的行在 host 上、还没进 shell 那份 `session`，重放日志会**用更少的覆盖掉更多的** —— 读者看到的就是「切回来那一轮的回答没了」。

**停止按会话。** `abort` 只设屏幕上那个会话的 `aborting`（每会话一个 `Ref`，因为 turn 要读到最新值），所以停 B 不会碰到 A。实测过：B 停下的同时 A 正常跑完。

**删掉的会话要挡住。** 多会话带来一个新数据风险：切走一个长 turn，然后在侧边栏把那个会话删了。`discard` 因此多一条拒绝 —— 有 turn 在跑的会话不能删。

几个仍然刻意保留的拒绝（`idle()`，按**屏幕上**的会话判断，不是按进程）：新建、dismiss、Continue。它们是「对**这个**会话做点什么」，另一个会话忙不是理由。

**而删除不再是其中之一。** 它原来也走 `idle()`，但那个判断问的是**屏幕上**那个会话 —— 而 `/delete` 自带路径，于是「切走一个长 turn 后回来清掉另一个安静会话」会被一句「a turn is running here」挡住，而真正的守则是“**被删的那个**”不能有活：`discard` 自己检查它的 turn 和它的 job。现在删除与 purge 都不经过 `idle()`，与 `NewSession` 当初的同一处修正同源。

### 怎么验的

假模型（本地 SSE，`SLOW` 就慢速流）+ `wei-cli`，一份 `cp` 出来的 scratch store，**永远不碰 `~/.wei/sessions/`**（见 `docs/macos-pitfalls.md` 里那条纪律）。三种场景各跑一遍：

```
concurrent    A 跑着 → 切 B → B 也跑 → 两条流按 session 交替到达 → 切回 A
abort-one     停 B 的同时 A 继续跑完（A 的 end 是 ""，B 的 end 是 "stopped"）
switch-back   离开 A 半截 → B 问一句 → 切回 A：A 的 delta 一直在到，名字都对
```

侧边栏那一行也确实据此打点：切到 B 时侧边栏是 `['AAAA!', 'BBBB*']` —— A 在后台跑。

host 侧的分派有单元测试（`WeiShellTests/TranscriptRoutingTests.swift`）：拿 wire 字面量直接驱动 `ShellClient.receive`，断言「B 的回答没落进 A」「切回来半截答案还在」「不在看的那份被留着而不是丢掉」。

## 停止，和换一个会话

两件每天都会用、而原来各只有一条路的事：**停止**只有浮层卡片里那个「Stop」按钮，**换会话**只有侧边栏那一行。两条路都是「你得先知道它在那儿」的东西，所以两边各补上了菜单与快捷键：

| 动作 | 菜单 | 快捷键 | 另一条路 |
|---|---|---|---|
| 停止这一轮 | Session ▸ Stop Turn | `⌘.` | 卡片里的 Stop |
| 下一个 / 上一个会话 | Session ▸ Next / Previous Session | `⌃⇥` / `⌃⇧⇥` | 侧边栏点那一行 |
| 收起 / 展开侧边栏 | View ▸ 系统那两项 | 平台自己的 `⌃⌘S` | 工具栏按钮 |

三条判断值得写下来。

**`⌘.` 是这个平台上「停」的意思**（Xcode 停编译、Terminal 中断），所以停止键就是它。停止后那一轮记的是 `Stopped`，转录上写「stopped」，而**花费照常报**：停下来的那一轮确实花了钱，不报就是把账抹掉。菜单项在没事可停时**变灰而不是消失**：会消失的命令没人学得会。

**但「请求」不等于「等工具自己跑完」，这一点原来写错了**，代价是每天都能撞上。`aborting` 是一个标志，
由回合在**两步之间**读 —— 而正在进行的那一步**就是**工具。于是按 Stop 之后状态变成「stopping…」，
那个 `bash: sleep 60` 却一直跑到自己结束。标志管得了「不要再进下一步」，管不了「把手里这一步停下」。

驱动侧其实早就准备好了：`@agent.ToolHandle` 带着一个 `stop`，调它就是 `task.cancel()`，再经运行时的
取消路径把命令行里的进程按 pid 杀掉（`SIGTERM` 起，必要时升级到 kill）。**宿主以前只拿它画那一行，
没存下来。** 现在 `Open.running_tool` 存着它，`Abort` 时**取出并调用** —— 取出而不是读取，是因为
第二次 Stop、或者工具已经报完之后的 Stop，不能去取消别的东西；回合结束时 `defer` 清掉，免得它活到
读者下一条提问上。

这条改不动单元测试能盖：它要一个真的子进程。验法是起一个**假模型**（几十行 python SSE，回答里塞一个
`bash: sleep 60` 的 tool call，`DEEPSEEK_BASE_URL` 指过去 —— 零 token、确定、形状随便造），发一句、
等 `sleep 60` 出现、发 `abort`，然后 `pgrep -f '^sleep 60$'`：实测从「还在跑」变成「已经没了」。
`stop_running_tool` 本身有单元测试（调用一次、只调用一次、回合结束就忘掉）。

**换会话这件事本身不需要排队。** 它一度被拒绝（「a turn is running — stop it first」），然后一度被改成「记住这个点击、turn 结束再执行」—— 两次都是在给一个只有一份会话状态的 shell 打补丁。现在 turn 写自己的会话，切走只是换屏幕上画哪一份，**中途切走不打断任何人**，所以上面那套「待执行 / 撤回 / pending 字段」全都删掉了。一个会话里同时开两个 turn 仍然被一把锁挡住（那会 fork 它的日志），但那是**每个会话**一把。

## 选一个文件夹开新会话

`⇧⌘N`（File 菜单和工具栏的「New Session」菜单各有一个入口）打开系统文件夹选择器，在里面开一个会话。
原来只有 `⌘N`：一个会话的目录**永远等于启动目录**，想换个项目就得重开一次 App。

**路径必须解析（canonicalize），这是这个功能唯一的坑。** `getcwd` 交回来的路径已经把软链接解掉了
（`/private/tmp/...`），而选择器交回来的是读者脑子里那个路径（`/tmp/...`）。按后者建会话，同一个目录
会在 store 里出现两次 —— 侧边栏两个分组、每个装着这个目录一半的会话 —— 看起来就像 App 把会话弄丢了。
所以路径进 shell 第一件事就是 `canonical_dir`，`/tmp/x` 和 `/private/tmp/x` 是同一个 `--private-tmp-···`
切片。`platform/picker.mbt` 在 Web 侧挡的是同一个坑的另一半（选择器打印的路径带结尾斜杠）。

实测（`/tmp` → `/private/tmp`）：

```
/new-in /tmp/wei-ws/target
→ session cwd = /private/tmp/wei-ws/target
→ status    = workspace added: /private/tmp/wei-ws/target
→ store 里只有一个 --private-tmp-wei-ws-target-- 切片
```

另外三件事：

- **marker 在会话之前写。** 会话开失败（目录没了、权限不对）时，这个 workspace 仍然是一个
  workspace —— 侧边栏那一行就是让这个目录还能被找到的东西。
- **已有的标题要保住。** marker 文件是 workspace 名字唯一存在的地方，而 `write_workspace` 是整体覆盖。
  所以先读、再带着读到的 `title` 写回去。Web 版这里写的是 `title: None`（会抹掉标题），现在没有东西
  设标题所以是潜伏的 —— 不跟着抄。
- **`canonical_dir` 返回 `None` 要说话。** 这不是理论情况：选择器给的是路径，对话框关掉到这一行之间，
  目录是可能被删掉的。三种失败各有一句话：不是目录 / 没选 / 是文件不是目录。

## 删除一个会话

删除这条路原来是走不通的：**点正在看的那个会话的「Delete」，shell 回「cannot delete the session
that is open」**；而且不管点哪一行，**撤销提示根本不出现**。两个 bug 一个根：宿主与 shell 对「删除」
这件事的所有权搞错了。

**一、看得见的那个会话也要能删。** 拒绝的理由是「窗口不能留在一个已经不在列表里的文件上」，这个
理由是真的，但它不是「拒绝」的理由，是**先决定谁来接班**的理由：同项目里这个进程已经持有的下一个
会话、否则那个目录里最新的一个、否则新开一个。决定好、**装到屏幕上**之后文件才动 —— 中间那一刻
`Shell::shown` 不会拿到空注册表（它 panic 的那条路）。Web 版一直是这个顺序（`ui/requests.mbt` 的
`delete` / `next_session_after`，那里的注释就是把顺序写错会出什么的记录：页面会一直画着一个列表
已经丢掉的会话，刷新也还在）。

顺带两件必要的事：**注册表也要减掉它**（`opens.extract_if`，这是唯一一处变小的路），否则那个
`busy` 标记会被 `say_sessions` 读到一个没人列得出的会话上；以及**替换要通过 `show` 而不是自己拼**
—— 接班的是宿主可能从没见过的会话，历史该不该发、快照发哪些，只有那一处知道。

**二、撤销提示是 shell 说的，不是点击猜的。** 宿主原来在点的一瞬间就把 `deleted = (path, label)`
放到自己状态里，再画那行 Undo：于是**删一个正在跑的会话（被拒绝）也会出现 Undo**，点它还会去
`/restore` 一个从没被删过的文件。现在的因果是反过来的：shell 做完事发一条 `deleted` 事件
（`path` + `label` + `restorable`），宿主**只**从这个事件画提示 —— 答应了就是答应了，拒绝了那条
`error` 里没有 Undo 可言。

这也是为什么提示里的 `label` 由 shell 读：那是文件还在、缓存还记得它长什么样的时候，宿主手里那份
行数据可能已经过期了。宿主侧的逻辑落在一处：`ShellClient.deleted`（一个 `DeletedSession`），一行不落
进转录（`Conversation` 对它直接 `return`）—— 删除是关于列表的事实，不是对话说过的话。**倒计时留在
宿主**（十二秒），因为「一行字值得画多久」是关于窗口的决定；但过期的动作是 `undoOfferExpired()`
交回给 `ShellClient`，窗口不自己保管那份 offer。

**三、确认框里多一个勾选框：「连文件一起删掉」。** 不勾（默认）就是上面那套 —— 文件改名成
`.deleted`，能从列表里撤销。勾了则是 `/purge`：**这是整个程序里唯一不可撤销的事**，所以它落在
**已经要问的那个对话框里**，而不是第二个确认框（同一个决定问两次）或第二个按钮（`Delete and
Remove` 让读者去对两个标签找差别）。

控件上有个真实约束：`confirmationDialog` 的 builders 虽然收 `ViewBuilder`，但对话框最终就是一组
按钮，别的控件不会到，而 `dialogSuppressionToggle` 问的是另一个问题（「别再问我」）。所以这里用的是
**`NSAlert` + `accessoryView`**（`RootView.swift` 的 `DeleteConfirmation`）—— macOS 上唯一能在按钮
旁边再放控件的对话框，而 SwiftUI 自己的 alert 底下就是它。它是**平台的对话框**，不是平台视图：
整框（标题、按钮、勾选框）平台画，`Wei` 的 token 不参与，所以「两套 token 会漂」那条不适用；
这条边界值得写清楚：「系统里只有这一个对话框带 accessoryView」不等于
「以后用 AppKit 画界面也行」。

**不可撤销的那一半也是 shell 的。** 勾选框在窗口上，但 `restorable` 由 shell 发：`/purge` 先改名、
再删文件（改名是原子的，删除不是；顺序反过来的话窗口可能看到一个删到一半的会话），失败就退回成
一次普通删除 —— 也就是那个可恢复的状态。宿主拿到 `restorable: false` 就**不画那行 Undo**：
一个指向已经不存在文件的恢复按钮，是个会撒谎的按钮。

拒绝的三条一条没少，只是都变成「关于状态」而不是「关于文件」：**有 turn 在写它**（切走一个长 turn
再回来删，是真实的一条路）、**有它起的后台 job 还在跑**、以及**文件已经不在了**。顺序按 Web 版：
先状态、后文件 —— 一个刚开跑的 turn 可能还没写出第一行，而**正在写的那个**才是不能删的那个。
（Web 版没有 purge 那一半：它只有那条可恢复的路，而这条路两边是同一套状态。）

**怎么验的。** 单元测试钉住两头：`macos/appffi/app_wbtest.mbt` 钉 `deleted` 事件的字段名（含
`restorable` 的两种取值），`WeiShellTests/TranscriptRoutingTests.swift` 钉「拒绝不发 offer、
`deleted` 才发、purge 的 offer 不可恢复、offer 不进转录」。端到端用 `wei-cli` 打一份 scratch store：

```
WEI_STORE=/tmp/… WEI_SESSION=<S2> wei-cli
> /purge <S1>
→ deleted {"path":"…/<S1>","label":"question number 1","restorable":false}
← 磁盘上只剩 <S3>.jsonl 与 <S2>.jsonl（<S1> 连 .deleted 都没有）
> /delete <S2>            # 正在看的那个
→ deleted {"path":"…/<S2>","label":"question number 2","restorable":true}
→ session  …/<S3>.jsonl  # 接班的是同项目最新的那个
→ history  …/<S3>.jsonl  # 而且走的是 say_open 的顺序：行在前，换屏在后
← <S2>.jsonl.deleted 还在，`/restore` 能把它拿回来
```

（这一条 Web 版修过同一个坑，`macos` 侧是照它的顺序抄的 —— 两个前端一套状态，一处想错了另一处
迟早会。）

## 技能：`/skill:<name>`、`/skill`、和补全

技能在 macOS 侧原来只有一半：设置面板能开关它们，但**调用那条路根本没有** —— 输入 `/skill:demo`
会被当成普通消息原样发给模型（`/skill:demo …` 的原文），而 `/skill` 那个「这里有什么」的问题，答案
是弹出一个设置面板。技能的语法、展开、framing 都在 `core`（`skill_command_parts` /
`skill_expansion`）和 `platform`（`expand_skill_command`）里，Web 版一直在用 —— 缺的只是「谁决定
调用它们」。

现在三条路都通了：

| 输入 | 结果 |
|---|---|
| `/skill:demo 做那件事` | 展开成技能自己的文本（带 `location`，所以技能内部的相对路径还能用）+ 读者原话跟在后面，**作为 user 消息**写入日志 |
| `/skill` 或 `/skill:` | 就地回答：一行一个 `/skill:<名字> — 描述`，**不开 turn**、不花钱 |
| `/skill:不存在` | 原样发给模型（其他前端的行为）。三种情况共用一个 `None`：不是技能命令、没有这个名字、文件已被删 |

两点值得记下来：

- **展开发生在回声和写日志之前。** 模型收到的文本和日志里记的文本必须是同一份，否则重启后转录
  会显示一条读者没发过的消息。所以 `run_turn` 里先展开、再 `say_user`、再写 entry。续跑的 turn
  不展开：它的 prompt 是从日志里读回来的，早在第一次发送时就展开过了。
- **`/skill` 的回答不开 turn。** 它是关于这台机器的问题，不是关于对话的问题 —— 没有东西要问模型，
  也没有东西要花。它以一条带标签的 note 落在转录里（标签 `skills`），因为读者的眼睛在那儿，也因为
  不带标签的正文会被当成谁写的回答。

`/mcp` 和 `/skill` 是**同一个形状的两个实例**，所以规则只写一遍：光秃秃的那个词回答「这里有什么」
（一份带标签的 note，不开 turn、不花钱），带名字的那个改设置（落盘、回一句状态、重发面板）。区别只有
一处，而且是故意的：`/mcp` **先重读配置**，因为读者打它通常就在刚写完一个 `.mcp.json` 之后 —— 从缓存
里回答会告诉他一个已经不存在的文件。技能不需要这一步，因为发现是每目录缓存的扫描、文件本来就在那儿。

补全在 Composer 里，**不新增线上字段**：shell 已经在 `settings` 里发了每个技能的名字、描述和开关
状态，所以 `contentView` 拿它过滤就够了 —— 也就不会出现「面板说有、展开说不认识」的两份答案。只
列**开着的**：关掉的技能展开会失败、模型也不知道它存在，列出来就是列一个按了没反应的命令。

四条规则在这条路上值得记下来，它们都是**时机**问题而不是列表问题，所以规则本身在
`WeiModel.SkillCompletion`（一个纯函数），Composer 只是把设置里的技能递给它：

- **触发是一个斜杠，后面还没有空格**（第一版只认 `/skill:`）。`/` 本身就是问题「这里有什么可
  用」，读者不该先猜出 `skill:` 这个前缀才看得到菜单。`/usr/local/bin`、`2 / 3` 仍然什么都不弹，
  因为那个空格 —— 和 Web 版同一条测试（`COMMAND_RE`），两个前端的菜单在同一个时刻开。
- **匹配的是整条拼写**，不是名字。`/sk` 列出所有技能（`/skill:moonbit` 以它开头），`/skill:mo`
  剩下 `moonbit`，`/x` 一个都不匹配、菜单不开。拼写只有一处（`SkillCompletion.spelling`），行的
  文字和点下去插入的文字是同一个函数 —— 否则菜单可能显示一条命令、插入另一条。
- **完全打出来的那一条不算建议**：`/skill:demo` 已经打完，再列一行把它还给读者就是挡住 Return 的
  噪音。
- **大小写按不敏感匹配、按原样插入**：`/skill:MO` 找得到 `MoonBit`，插入的仍是技能自己的名字，
  因为 shell 展开的就是它。

**键盘：↑/↓ 移动高亮、Tab 选中**（点击仍然可用，两条路都走 `Composer.insert`，所以不会给出两份不同的
文字）。三个决定写在这里：

- **默认第一行就是高亮行，而且它是画出来的**。Tab 会插入的那一行必须在按下去之前就看得见 —— 一个
  按下去才知道后果的快捷键，比没有快捷键更坏。
- **Tab 而不是 Return**。Return 在这个框里已经是「发送」，而且它后面跟着一长串判断（输入法合成中、
  听写没落地……）；让 Return 有时变成「选中」就是给一个键两个意思。Tab 原来在这个字段里什么都不做。
- **到头就停，不循环**（`SkillCompletion.move`）。菜单很短、两头都在屏幕上，循环只会把“按住 ↓ 到底”
  变成绕圈；**空菜单时返回第 0 行**，因为它和菜单是由同一个状态算出来的，最后一个匹配被窄掉的那一下
  也会问到它。

方向键只在**菜单开着时**才被收下（`Composer.step` 没菜单就 `.ignored`）—— 这个框会长到十几行，那时
↑/↓ 是移光标的。

## 一次技能调用在转录里长什么样

第一版把展开后的整段文本当问题画出来了 —— 那是**读者没写过的五万字**，五行的 bubble 里前三行是技能的
目录。展开是**有损**的：日志里只有一段文本，`<skill …>` 那层壳和读者自己的话在同一个字符串里，所以
想要回读者的话，就得把壳拆掉。

拆的地方只有一个：`core.skill_expansion_parts`，它是 `skill_expansion` 的反函数（名字、body、读者原话
三个部分）。**拆在写它的那一侧** —— 活的事件（`say_user` → `user_fields`）和历史行（`history_rows`）
各调一次同一个函数，所以实时的和重放的不会各拆一套。旧的宿主收不到这个新字段，退化成原来的显示，
不会解不开。

画出来是这样：

| 那一行 | 画成 |
|---|---|
| 读者有自己的话 | 话本身（bubble），下面是折起来的技能文档 |
| 只有命令 | `/skill:demo` 一条等宽 bubble，不让它读成一个句子 |
| 折起来的 | `skill demo · 57k characters` —— **数量是那个折叠唯一的问题的答案**（`SkillFrame.foldLabel`，
数字用 composer 同一套缩写规则） |
| 不是框架的普通消息 | 一个 bubble，原样 |
| 只是**提到**技能的句子 | 也是一个 bubble：整段前言必须在开头逐字对上才算框架，猜是不行的 |

同一条规则还修了两处同一来源的毛病：**侧边栏的会话名**（原来取那段文档的前 80 字）现在取读者自己的话，
没有话就取命令本身；**被中断那一轮的提示条**（原来是三段技能正文被引在「this turn was interrupted」下面）
现在引读者打过的命令 —— 只说显示，Continue 重放的仍然是日志里的原文。

## 压缩：一行，带标签

压缩是读者自己的话被一段摘要取代 —— 上下文满了，前面那些请求不再原样送出去了。Web 版会在转录里插
一条，这里原来是**什么都不说**。

现在两端都有一条 `note`：

- **在它发生的地方**，不是状态行。它是关于对话的事实，不是关于这一轮的数字。
- **`note` 带 `name`（标签）**，因为不带的 note 就是「一段被当成回答读的正文」—— 而这正是压缩摘要
  在 1500 条会话里读起来的样子。两边都有：实时那条走 `note` 事件，历史那条在 `history_rows` 里也
  贴上了标签。
- **数出来的，不是布尔**：一轮里可以压缩两次，布尔只会报第一次、吞掉第二次（所以 `on_commit` 里比
  的是数量而不是「有没有变过」）。
- 面板里画成 `DisclosureGroup`：摘要可以折起来。它是转录里最长的文本、被读得最少的一段，摊开就是
  把一页别人的散文塞进对话中间。

## 下一步

1. **一个目录下几百条会话**：分组折叠有了，还需要「最近 N 条 + 展开」。现在最多的工作目录是
   16 条，所以这条不急 —— 等到某天要滚很久再做。
2. **给 workspace 起名**：`write_workspace` 的 `title` 一直是 `None`，`core` 里有名字可读。Projects
   那一行现在显示目录最后一段，一个名字是读者唯一能改变它的方式。**这也是这一行菜单的另一半**：
   移除有了（见上），改名的位置已经空在那里。
3. **发布**：Developer ID 签名 + 公证，以及一个真的 bundle id。
4. **关掉 App 时把那几个 turn 停干净**：现在 `quit` 会给每个打开的会话设 `aborting`，但进程不等
   它们收尾 —— 一个正在写日志的 turn 是被硬切掉的，靠 `repair_session` 在下次打开时补。想让它
   体面，得让 `serve` 等到 `opens` 都没有 `busy` 再返回。

## 移除一个项目

Projects 栏那一行原来**只能进不能出**：加进来一个目录，唯一能把它拿掉的办法是在 shell 里知道
`~/.wei/sessions/--Users-me-src--` 这个名字、然后 `rm -rf`。行的右键菜单现在有一个
**`Remove Project…`**，问的框和删会话那个是同一个（`DeleteConfirmation`），连勾选框都是同一个。

**先分清移掉的是什么。** 读者右键的是一个**目录名**，而「移除」听起来像要把他的代码删掉——所以框里
必须说清楚：**工作目录一个字节都不动**，动的是 store 自己那一片 `~/.wei/sessions/--…--`。这一句话是
这个功能里最值钱的部分，界面上它就在正文里（`The project is a folder on disk and is not touched.`）。

**不勾（默认）：改名，会话全留着。** store 目录被改成 `--…--.removed`，**`list_workspaces` 按这个
后缀过滤**——和会话那边的 `.deleted` 是同一个机制：不是登记表里划掉一行，而是让名字离开每个 listing
都认的那个形态，于是「忘了」和「还原」都只是一次改名（`mv` 回去就回来了，手也能做）。`find_session`
一起过滤，否则 `--resume <id>` 会伸进一个读者已经从侧栏里移掉的项目。

**勾了：「连里面的 N 条会话一起删掉」——这是整个程序里唯一不可撤销的事，比 `/purge` 还大一号**
（那个是一个文件，这里是一整个目录）。顺序所以和 `/purge` 一样讲道理：**先改名，再清空**
（改名是原子的，`rmdir` 不是）——所以 store 侧是**两个函数**，`remove_workspace` 交回它改名后的路径，
`purge_workspace` 拿那个路径去清空。两次失败于是能说得不一样：改名失败是 **`could not remove X`**
（什么都没发生），清空失败是 **`X removed, but its N sessions could not be deleted — they are at <路径>`**
——**把路径报出来**，因为读者要的是那些会话消失，而这堆字节在哪儿只有这个名字知道。合成一步的写法
报不出后一种，而后者恰恰是「已经不可撤销了却只做了一半」的那一种。

**没有勾选框的情况：项目里一条会话都没有**。会话那边加勾选框，是因为「本来要说的损失」可以被它改掉；
空的框写着「也删掉它的 0 条会话」是个什么也做不了的控件。所以 `askAboutProject` 收 `sessions`，
0 就不放 accessoryView——**数是从行自己拿的**（`SessionGroup.sessions.count`），也就是读者在中间栏
数得出来的那个数，两边不可能对不上。

**窗口不能留在一个已经离开列表的项目里。** 这不是先决定后动文件的问题，而是一个更硬的事实：
`say_sessions` **永远会把屏幕上的那个会话列出来**（塞进它自己项目那一组的最上面），所以留在被移除
项目里的会话会让那一行立刻长回来。
于是接班要在**改名之前**决定（`rehome_after`，那时 listing 还认得出这个项目）三个答案按成本排：

1. 这个进程已经持有的、**另一个项目**的会话（最便宜，而且是读者会点的那一行）；
2. 都没有的话，store 里**最靠上的那个项目的最新一条会话**——也就是侧栏将会画出的第一行，
   代价是一次文件读，换来的是一个满的窗口而不是空窗口；
3. 都到不了（store 里只有这一个项目）就新开一个，目录是 `home`——`start_dir` 早就把「这个进程
   没有特别要待的地方、store 也没有话说」定义成它了。**不能**开在被移除的项目里：那会留下一个空行，它存在多久取决于
   读者多久不去用它。

**两条命令，两个词**（`/workspace-remove` 和 `/workspace-delete`），和 `/delete` 与 `/purge` 一个
道理：不勾和勾是两件事，读 wire 日志的人不该靠一个布尔去猜。两个都**不经过 `idle()`**——那个判断问的
是**屏幕上**那个会话，而这条命令说的是**整个项目**；真正的守则由 `project_idle` 自己查：这个项目里
任何一条会话有 turn 在写、或者有它起的 job 还在跑，就拒绝并说明是哪一条。第三条拒绝是「列表里没有
这个项目」（已经移除过、或者路径不对），它回一句话而不是当作成功——点了没反应和「已经没了」必须分得开。

**这个动作没有 Undo 行。** 删会话有一行十二秒的撤销（文件改名成 `.deleted`，是本进程刚做的事）；
移除项目不做那一行：项目是**读者自己的资源**不是这个进程刚造的东西，而且勾了之后根本没有可还原的东西。
不勾那一半的退路仍然在（改名回去），但那是一条 shell 命令，和 `.deleted` 一样——**报告是那一行消失**。
能查到的证据在状态行（`project removed: proj-a · 2 sessions kept` /
`project and 2 sessions removed: proj-a`），说在这里是因为正在报告的那一行已经没有了。

**怎么验的。** `platform/session_test.mbt` 钉两头：不勾的那次**会话文件一个不少**（在新名字下）、
listing 里没了、`find_session` 找不到、再移除一次是 `None` 而不是炸、**另一个项目仍然移得掉**（证明
`None` 是「这个项目不在列表里」而不是「store 坏了」）；勾了的那次走的就是那两步（`remove_workspace`
→ `purge_workspace`），store 目录整个不在（`.removed` 也没有），再清一次是 `false`。命令解析和路径
完整（空格）在 `macos/appffi/app_wbtest.mbt`。端到端用 `wei-cli` 打一份 scratch store，两种各走一遍
——**注意列表里的数和真删掉的数会对不上**，而这**是对的**：侧栏把「刚开、还没落盘」的那个会话也列出
来（`say_sessions` 总会列出屏幕上的那个），而磁盘上没有它的文件，所以勾选框中删掉的是 2 而不是 3。

```
# 勾了：当前会话就在被移除的项目里（proj-a 有 2 条真会话 + 1 条还没落盘的）
/new-in /tmp/wei-ws/proj-b
/sessions                       → proj-b(1)  proj-a(3)
/workspace-delete /private/tmp/wei-ws/proj-a
→ status   project and 2 sessions removed: proj-a
→ session  {"cwd":"/private/tmp/wei-ws/proj-b"}   # 接班：进程里另一个项目已持有的会话
← store 里连 --private-tmp-wei-ws-proj-a-- 都没有了
```

```
# 不勾：改名，会话全留着，那条退路是手也能走的
/workspace-remove /private/tmp/wei-ws/proj-a
→ status   project removed: proj-a · 2 sessions kept
→ sessions 只剩 proj-b
← store 里是 --private-tmp-wei-ws-proj-a--.removed/，两条 .jsonl 一个字没动   # mv 回去 = 还原

/workspace-remove /private/tmp/wei-ws/never
→ error    that project is not in the list
```
