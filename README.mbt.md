# pi-web-shell

[pi](https://github.com/earendil-works/pi-mono) 的独立复刻：一个 MoonBit 实现的
agent 内核，加一个服务器渲染的 Web UI，交付形态是单个 native 二进制。

```
core/      纯逻辑：消息模型、DeepSeek 编解码、agent 状态机、会话树、工具、压缩
platform/  native 实现：HTTP/SSE、文件系统、进程
agent/     驱动：把状态机接到模型与工具
html/      HTML DSL、转义、渲染、Patch
server/    HTTP 路由 + SSE 广播
ui/        可执行：agent + server + Web UI 合一（交付形态）
           ├ main.mbt      进程：命令行、端口、task group、生命周期
           ├ session.mbt   Runner / App 两个类型及其访问器（谁开着、在干什么）
           ├ cli.mbt       启动期：命令行、凭据、打开第一个会话
           ├ commands.mbt  输入框里那句话是什么意思（/name、/model、/skill:）
           ├ model.mbt     一个会话跑在哪个模型上
           ├ settings.mbt  设置面板：显示什么、提交改了什么
           ├ sidebar.mbt   会话列表：标签从哪来、为什么不用重读整个 store
           ├ turn.mbt      跑一轮 turn，以及说清这一轮发生了什么
           ├ panels.mbt    各个区域：信息条、用量数字、模型下拉框、两个侧栏、对话
           └ requests.mbt  每条路由"意味着什么"
pi/        可执行：命令行跑一次完整 turn
cli/       可执行：打一次真实 API，最小链路验证
verify/    可执行：拿真实会话全量跑往返验证
harness/   Node 脚本：用 pi 当 oracle 生成 fixture
docs/adr/  架构决策记录：被否决过的方案与理由是承重的，不该被重新讨论
```

**一条硬约束**：`core/` 不许碰 IO，必须能编译到**每一个**后端。
`.githooks/pre-commit` 会跑 `moon check -p core --target js` 和 `--target wasm-gc`；
这两条失败就说明有平台代码渗进了核心逻辑。约束靠编译器执行，不靠自觉。

## 运行

```bash
moon run ui                          # → http://127.0.0.1:8790
moon run ui -- --continue            # 继续本目录最近写入的会话
moon run ui -- --resume <id|path>    # 打开指定会话
moon run ui -- --port 9000 --model deepseek-v4-flash --store ~/.pi-mb/sessions
moon run ui -- --no-picker               # 侧边栏不放「Choose…」，只留路径输入
moon run ui -- --max-cost 0.10           # 这一轮的硬帽（优先于设置面板里存的）
moon run ui -- --max-rounds 30           # 每轮最多多少次模型调用
moon run ui -- --model deepseek-v4-pro   # 新会话默认用哪个模型（每个会话可在输入框右下角改）
moon run pi -- "prompt"              # 命令行跑一次完整 turn
moon run verify                      # 全量会话往返验证
```

API key 的取法有优先级：`DEEPSEEK_API_KEY` > 设置面板存下来的 key > pi 的凭据库
（`~/.pi/agent/auth.json`）。都没有也能启动 —— 页面照常起来，顶栏的设置面板让人现场填一个。

每轮的上限（模型调用次数、花费）同样是三层：flag > 设置面板 > 内置默认（200 次 / $1）。
两项都取自 2280 个真实 turn 的实测（中位花费 $0.004、第 90 百分位 $0.036、最贵 $0.295、
最长 165 次调用），所以默认值拦的是「一个不该发生的 turn」，不是「一个大 turn」。

## 设置面板

顶栏右侧的 `settings` 是一个原生 `<details>`。它装的是什么，由一个问题决定：
**运行中的进程能不能兑现它？** 能兑现的才可改，不能兑现的只展示 —— 一个看起来能改的表单
只是在撒谎。（模型是可改的，但它属于会话而不属于进程，所以入口在输入框右下角，见下。）

可改：

- **turn limits**：每轮最多多少次模型调用、最多花多少钱。留空 = 没有意见（用 flag 或内置默认
  200 次 / $1），填 `0` = 明确不设上限。有 flag 时那一项显示为只读并标注是哪个 flag 钉住的
  （见下面的取舍）。
- **api key**：当前用的是哪一个（环境变量 / 面板存的 / pi 的），以及它的**指纹**
  （`sk-4…2e36`）。**key 本身永远不回传浏览器** —— 只回指纹，面板能回答「我刚粘的 key 生效了
  吗」，但页面缓存、截图、扩展都拿不到凭据。
- **skills**：这个工作区发现到的每个 skill（含全局的、项目级的），逐条勾选，整份提交。
  关掉的按**名字**记，所以同一个名字的全局/项目两份一起生效，重装到别处也不会失效；
  「已经不在磁盘上但还关着」的名字仍然列出来并标注 `no file found`，否则一个读者关掉、
  然后又删掉的 skill 就再也开不回来了。
- **instructions**：工作区根目录那个 `AGENTS.md` 的**预览**，加上一份存在设置里的**后备文本**。
  规则只有两条：工作区有 `AGENTS.md` 就用它，没有就用这份后备。

关于 instructions 这块的取舍：

- **后备是「二选一」而不是「追加」**。仓库自己的文件才是「在这个仓库里怎么干活」的更具体的
  权威，两份拼在一起只会让读者去猜哪句话赢了。这份后备存在 `~/.pi-mb/settings.json`，是
  **跟着人而不是跟着仓库**的，所以「我一贯的偏好」放在这里是诚实的，不用提交进别人的 checkout。
- **只读工作区根目录那一个文件，不向上走**。往上遍历是这个设计开始变贵的地方：哪些目录算数、
  两个目录都有怎么办、仓库外面的文件算不算数。一个文件、放在工作区顶上，就是全部规则 ——
  需要按目录区分指令的读者，可以写在一个文件里然后说明哪段是关于哪个目录的。向上走还会让
  prompt 的内容取决于 checkout 恰好躺在哪里（`/Users/me/AGENTS.md` 是别人对自己机器的笔记）。
- **面板同时显示「谁在生效」和「生效的是哪段文字」**。只显示来源，读者分不清「我的文件被忽略
  了」和「我存的文本被忽略了」；只显示预览，读者不知道自己刚写进框里的那页东西到底有没有
  被发出去。来源那一行就是在回答这个。
- **每轮重读，不缓存**。一次 stat、有内容时一次小读，换来的是一边看着 agent 一边改 `AGENTS.md`
  的人，下一轮就生效 —— 缓存恰好会让这件事不发生，而这是这个功能唯一会被骂的失败方式。
- **工作区文件按磁盘上的原样发送**，只用首尾空白判断它到底说没说话（一个只有空行的文件等于没
  有）。把仓库里的文件改写一遍再塞进 prompt，是那种会让读者从此不信任每一个 diff 的悄悄编辑。
- **instructions 表单和 skills 一样永远带隐藏字段 `agents=1`**。清空 textarea 后浏览器提交的就是
  个空 body，和「这不是本面板发的请求」无法区分 —— 没有它，「不要后备指令了」就成了面板唯一
  表达不了的编辑。这条同样是浏览器验收抓出来的：路由 `/settings/agents` 一开始忘了加进
  `server/http.mbt`，提交后状态行纹丝不动、textarea 里还留着字，看起来完全正常。

只展示（每个都带 tooltip 说明用哪个 flag 改）：

- **model**：模型、endpoint、上下文窗口。
- **where things are**：监听地址、当前工作区、store 路径。

都存在 `~/.pi-mb/settings.json`（和 session store 同一层，不写进 pi 的文件）。

几处刻意的取舍：

- **环境变量优先于面板存的 key**，并且在面板里明说。反过来（面板优先）才是「UI 的 key」的
  字面读法，但会静默压掉读者**明明看着的 shell 里**设的 `DEEPSEEK_API_KEY`。
- **skills 表单永远带一个隐藏字段 `skills=1`**。全不勾时浏览器会提交空 body，而空 body 与
  「这不是本面板发的请求」无法区分 —— 关掉最后一个 skill 就成了面板唯一做不到的编辑。
  这条是浏览器验收第一次跑就抓出来的（状态行一直不动）。
- **提交后只替换 `settings-body`，不替换整个 `<details>`**：展开状态是浏览器自己的，替换外层
  节点会把读者正开着的面板关掉。请求体用 form-encoded（勾选框本来就是 form），服务端解码后
  **用实际生效的状态重渲染**再广播给所有标签页，而不是回显提交的内容。
- **只读的事实和可改的状态分得很清**。真正能在运行中兑现的只有「换 key」「改 skill 集」
  「改 instructions」「改 turn 上限」，所以面板只做这四件。上限之所以算数，是因为它们在
  **每一轮开头**重新读，而最需要改上限的时刻恰恰是「上一轮刚被上限拦下来」—— 要重启才能改就
  太蠢了。instructions 同理：它在每轮组装 system prompt 时读，改完下一轮就生效。
- **上限的优先级和 key 相反：flag > 面板 > 内置默认**。key 那边环境变量优先，是因为
  `DEEPSEEK_API_KEY` 是读者正看着的 shell 里设的，一个几个月前在浏览器里存过一次的值不该
  悄悄压过它。而上限里 flag *本身就是*那个慎重的动作：`--max-cost 0.10` 是这次运行敲下的硬
  帽，让面板里存过的五美元覆盖它就等于把安全边界变成建议。两种顺序的共同点是：意外的那一
  种要**说出来**而不是藏起来 —— flag 钉住的那一项在面板里是只读的，保存时会明确回一句
  「已保存，但 `--max-cost` 仍然生效」。
- **默认值是 placeholder，不是 value**。空 = 没有意见，如果把 200 填进框里，第一次按 Apply
  就把它固化成了「读者设的 200」，以后改默认值再也不会生效。
- **「清除 key」是它自己的表单，带一个隐藏字段**，而不是同一个 key 表单里的第二个提交按钮：
  提交按钮的 name 只在它是 submitter 时才进表单数据，而 `new FormData(form)` 根本不含提交按钮 ——
  共用一个表单的话，清除会发一个空的 `key`，被当成「什么都没存」，而且把「现在用的其实是哪个」
  那句话悄悄吞掉。这两条（隐藏字段 + 只替换 body）都是浏览器验收抓不到的类别里最贵的那种：
  页面看起来正常、按钮也有反应。

顶部信息条右侧的数字（token / cache / cost / context）现在是一个独立的 `usage` 区域：
一轮 turn 会刷新它好几次，而设置面板就挨着它，重建整条 bar 会把读者正在输入的面板清掉。

## 工作区指令：`AGENTS.md`

每轮组装 system prompt 时，除了工具列表和 skill catalog，还有一段工作区指令。来源只有两个，
顺序固定：

1. **工作区根目录的 `AGENTS.md`**（就是 session 的 cwd，`platform/agents.mbt`）。有就用它。
2. **设置面板里存的后备文本**（`~/.pi-mb/settings.json` 的 `agents_md`）。工作区没有文件时用它。

两个都没有，就不追加任何东西 —— prompt 和这个功能存在之前逐字节相同（`core/instructions`
的 `Absent`，专门和「有个空文件」区分开）。

这一段在 prompt 里的位置是**工具列表之后、skill catalog 之前**，`build_system_prompt`
的 `sections` 参数按给定顺序拼，并且跳过空串。两个调用者（发 turn 的、算 context 数字的）
走的是同一个 `App::system_prompt`，所以「发出去的 prompt」和「面板里那一句话在描述的东西」
不可能不一致。

和 pi、dsh 的差别是刻意压掉的复杂度。pi 从 cwd 一路 `dirname` 走到 `/`，每个目录按
`AGENTS.override.md` → `AGENTS.md` → `CLAUDE.md` 取第一个命中，全文拼进 system prompt，没有预算；
dsh 额外向上找 `.git` 当项目根、每目录所有候选都加载、按 trim 后内容 SHA-1 去重、按 64KB 预算
先丢宽的再截最具体的那个，而且不放进 system prompt，而是当一条持久化到 session 里的
`<system-reminder>` 消息，并在每次成功的 `read`/`write`/`edit` 之后增量对账。两边都有各自的
理由，但都是「多个目录 + 多层覆盖 + 预算分配」这一整类问题的解法。这里只回答一个问题：
**这个工作区有没有自己的指令？** 一个文件，一个位置，一条规则。

代价是写下来要诚实的：**没有按目录细分、没有祖先继承、没有总字节预算**。单个文件的读量有上限
（256 KiB，超出截断），而两个来源相加的总量没有 —— 一份巨大的 `AGENTS.md` 会实打实地吃掉
context。面板里那个预览就是给读者看这个的。

## 引用 skill：`/skill:<name>`

skill 有两条入口，取决于**谁来做决定**：

1. **模型自己决定**（默认）：每轮开头把 catalog（名字 + 一行 description + 文件路径）拼进
   system prompt，模型判断当前任务是否匹配，匹配就调普通的 `read` 工具去读正文。好处是
   按需加载 —— 不匹配的 skill 一个 token 都不花。
2. **读者自己决定**：在输入框里打 `/skill:<名字>`，服务器直接把那份 skill 的正文读进这一轮。

第二条是有意绕过模型判断的：你觉得相关的 skill，不应该取决于一行 description 有没有说服模型。
语法和展开都照 pi 做的，所以在那边养成的习惯在这里一样：

```
/skill:pdf-report
/skill:pdf-report 用 data.csv 里的数字    ← 后面的文字是附加请求，不参与匹配
/skill                                    ← 单独打（或 /skill:）报出目录里有什么
```

展开的形状是 pi 的（`<skill name location>` + 一行「相对路径以哪为基准」 + 正文），
frontmatter 去掉（那是 catalog 读过的，再送一遍等于让模型读一遍已经告诉过它含义的 YAML），
CRLF / CR / BOM 先规范化再找闭合的 `---` —— 这三条都是照 pi 的 `stripFrontmatter` 抄的，
因为「差不多的实现」会在 Windows 换行的文件上悄悄切错位置。

两处刻意偏离 pi：

- **属性值做了 XML 转义**。pi 不转义；名字是文件里的任意文本，含引号的名字会把属性提前闭合，
  剩下的名字就变成模型会当成结构的标记。普通名字下输出与 pi 逐字节相同。
- **未知名字原样穿透**（这条和 pi 一致，但值得写下来）：`/skill:` 开头但不是已知 skill 的
  消息，会当普通消息发给模型。这保证了打错的 skill 名不会吞掉一条消息。

只拦截 `/skill:` 和 `/model`（以及已有的 `/name`），其它 `/x` 一律当散文 —— 路径、除法、正则
都可能是真的消息。`/skill:` 这个命名空间是它们撞不上的。

## 每个会话用不同模型

`--model` 现在只决定**新会话**的起点。已经打开的会话用哪个模型，记在它自己的日志里：
切一次模型就往会话里追加一条 `model_change`（pi 的格式），所以它跟日志走，重启后还在，
而 pi 自己读同一份日志也会得到同样答案。

入口是**输入框右下角的下拉框**（照 dsh 的位置：模型选择就在 composer 的尾部），
外加 `/model` 命令（不带参数列出可选项）。下拉框是一个原生 `<select>`：键盘可达、
按平台的方式打开和关闭、选一下就提交（`onchange`），没有第二个 Apply 按钮可忘。
它自己是 `#model-picker` 一个区域，所以切换会话时只替换它，不会重建输入框 ——
重建 composer 会把读者正在打的字一起换掉。

**turn 运行时下拉框是 disabled 的**，而不是隐藏：模型切换是往日志里追加一条 entry，而正在跑的
turn 是按它自己的 leaf 往后接的，这条 entry 会挂到没人走的分支上（和 `/name` 拒绝改名的
是同一条理由）。disabled 而不是隐藏，是为了控制不跑到别处去。

`/model` 打错名字会被**当场拒绝并列出可选项**，而不是原样发出去：那个 id 会作为模型名进请求，
等一轮之后才由 provider 报错，读者根本分不清是自己名字打错还是别的问题。

### 模型目录

`core/model_catalog.mbt`，一张表而不是三个散落的常量 —— 因为「一个模型」其实是同一件事的
三部分：wire id、每 token 多少钱、能装多少对话。分开放就是「A 的窗口配 B 的价格」这类错误的
温床，而且它**不可见**：花费还是一个数字，context chip 还是有分母。

**一处定义**：`--model` 的默认值、新会话的起点、`AgentContext::new` 的默认 pricing/window、
CLI 验证二进制的模型，全都取自这张表，而不是各自写一遍字面量。之前有四处写着
`"deepseek-v4-flash"` 和它的费率，散落的第二份数字就是最先过时的那一份。

数字取自 pi 自己的目录（`~/.pi/agent/models-store.json`）。两件事值得先知道：

- **同一个模型有两个 id**。`deepseek-v4-flash` 是本仓库录制 fixture 时用的 id，它的费率
  （0.14 / 0.28 / 0.0028）就是那些 fixture 记账的数字；上游后来把它改名成 `deepseek-flash`
  并涨价（0.3 / 1.2 / 0.006）。两个都列出来：从旧日志恢复的会话记的是旧 id，必须保持它的
  历史成本不变，而新会话应该用当前的。改掉旧数字会让 `harness/fixtures/live.json` 变错，
  而对不上自己钉住的东西的 fixture 比一个过时的 id 更糟。
- **thinking 档位是每个模型的，不是每个 provider 的**：`deepseek-v4-pro` 没有 `low`。
  给它一张和 flash 相同的表，就会把 `reasoning_effort: low` 发给一个会拒绝它的模型。
  所以表里写成「存在但为 null」，让请求构造器里那套「不可用的档位退回 off」的规则生效。

日志里出现本 build 不认识的模型时，会话**照样能打开**，回退到默认模型继续跑 —— 拒绝回答比
用错模型回答更糟。但回退是**说出来的**：bar 上的 chip 报日志里的 id，`/model` 会写
`(unknown to this build; running on …)`，下拉框把那个 id 也列成一个选项。悄悄换掉它意味着
下一次点某个无关按钮就会把会话移到另一个模型上。

## 请求处理是一个能测的 interface

每条路由**决定什么**都在 `ui/requests.mbt`，`main` 只做三件属于进程的事：命令行、端口、生命周期。
界线是「这事属于进程还是属于模块」—— 起一个 turn 需要一个 task group（泛型、带 source location），
所以它是**作为回调传进去的参数**，而不是被 `Requests` 知道的东西。

抽出来不是洁癖，是因为摩擦已经产生过缺陷。读者见到的六条拒绝信息里，**五条只出现在 `ui/main.mbt`
这一个文件里，而它是唯一没有测试的文件**；模型下拉框「turn 结束后不解锁」那个 bug **没有任何测试
失败**，因为那个状态迁移没有 interface 可以断言。

**测试跨的 seam 是 `@server.Hub`。** 一条拒绝*就是*一帧：断言广播出去的内容，就是断言浏览器被告知
了什么，而这正是那个行为的全部。所以 handler 直接广播，而不是返回「该广播什么」的描述 —— 后者会
让「决定」和「发送」分成两处，正是当初遗漏模型下拉框的那种分工。测试像标签页一样 subscribe，
拿帧来断言。

抽出来立刻抓到的一处**已经漂移的重复**：`/model` 的守卫写了两遍（命令分支和下拉框路由），而且
**已经不一致** —— 下拉框在拒绝后会把控件放回原位，命令路径不会，所以打错一次 `/model` 会给下一次
点击留下一个和实际不符的下拉框。现在两条路径是同一个 `change_model`，各自都有测试。

一次副作用，值得记下来（见 `docs/adr/0002`）：把路由搬进有测试的文件后，`ui` 的测试开始以
`SIGABRT` 崩 —— 崩点在 `log` 的 stderr 写，因为 `moon test` 并发跑同一个包的测试，多个测试同时写
stderr 就 abort。所以 **`log` 只能待在 `main` 里**：它本来也是进程的事，而不是模块的事。

## Web UI：服务器渲染，不是单页应用

服务器是文档唯一的写者。浏览器端只有 **不到 100 行 JS**，它知道五件事：怎么应用一个
patch、怎么发一条 prompt、`data-session` 被点击时打开那个会话、带另一个会话标签的帧
不属于本页、以及设置面板的两个表单是发出去而不是跳转。对话长什么样完全
由服务器决定，所以客户端和服务器之间没有「状态不一致」这种失败模式。

```
GET  /         整页（含已有对话与侧边栏）
GET  /events   SSE，推 HTML 片段
POST /prompt   用户输入，立即返回
POST /session  切换会话（空体=新建），立即返回
POST /abort    停掉正在跑的 turn
POST /workspace  添加一个目录为工作区
POST /workspace/pick  打开宿主机的文件夹选择框，把选中的目录加成工作区
POST /new        在工作区里新建一个会话
POST /more       把某个工作区的会话列表展开到全部
POST /job/kill   停掉一个后台 job
POST /settings/key     保存/清除面板存的 key
POST /settings/skills  应用整份 skill 启用集
POST /settings/limits  设置/清除每轮的调用与花费上限
POST /model            切换当前会话的模型
```

**首帧是「可变区域的快照」。** 每个连接先收到 `transcript` / `sessions` / 状态行三个
区域的 patch，而不是整页。这条曾经写错过 —— 首帧发整页、客户端又用 `outerHTML` 直接
替换 `#transcript`，结果是浏览器把整个文档的片段塞进 body：输入框和状态行都被换成新
节点，而 JS 里捕获的还是旧节点，于是**页面看起来正常、输入框和状态行却永久失效**，
而所有字节层面的断言全部通过。

这个 bug 决定了验证方式：`server/http_test.mbt` 断言首帧里不能出现 `<html`，
`harness/ui-browser-check.mjs` 则用**真实的 headless Chrome**（不是用户的浏览器）
再确认一遍 DOM 真的没被嵌套、输入框的监听真的挂在屏上的那个节点上。后者是唯一能看见
这类问题的地方。

**流式期间不渲染 markdown。** 每个 delta 只更新累积文本（`SetText`），turn 结束时
一次性替换成渲染好的 markdown。半截的 `**bo` 渲染出来是错的，而且每来一个 delta
重渲染一遍累积文本是 O(n²)。

**折叠交给原生 `<details>`。** 客户端版为此维护了一个展开状态数组并写进 Model；
服务器渲染后这一项直接删掉，浏览器自己就记得 —— 工作区的折叠也是同一套：当前工作区
是 `<details open>`，其余折起来，展开状态由浏览器记着。

两处例外，都是因为 `<details>` 的表现力不够，而不是因为它的状态管理不好：

- **流式中的思考**要三个状态（最新几行、全部、收起），`<details>` 只有两个。它默认只露
  最后三行，样式表把正文盒子锚到末端把溢出的部分从*上面*裁掉（这个组合在真实 Chrome 里
  量过，不是推测）。而且这里「记住展开状态」恰恰是**不想要**的行为：turn 结束时会换成
  收起的成品，读者中途展开的块本来就该合上。
- **一轮 turn 的花费行**在答案下面。它要长得像一行数字而不是一个带框的可展开项，
  `summary` 改不成那样；而且它要的东西在下方、不在旁边。

这两处共用一套约定，客户端也只有**一个**处理器：按钮用 `data-expands` 说出它控制谁，
目标用 `data-expanded` 表明自己开着 —— 凡是需要开合、又不该把状态送回服务器的界面，
都并进这一对里，而不是各写一个一次性监听器。

**会话可以命名**：在输入框里打 `/name <文字>`（`/name` 单独打是查看当前名字，不会清空）。
名字写成 session 格式里本来就有的 `session_info` 条目，所以它跟着日志走 —— 重启后还在，
pi 自己也读得到（`Session::name()` 取路径上最新的一条，重命名是覆盖而不是追加历史）。
**turn 运行中拒绝改名**：那时 turn 正在按自己的 leaf 追加条目，此时再塞一条会挂在过期的
parent 上，最后落到没人走的分支里 —— 和当初写坏日志是同一类问题，这次靠拒绝而不是靠运气。

命令只拦截 `/name` 一个：把每个 `/x` 都当命令会悄悄吞掉真正的消息（路径、除法、正则），
所以不认识的一律原样交给模型。

**侧边栏列出所有工作区**，不只是当前目录。一个会话一行：**标签在左、时间在右**；指针停在
一行上时，右边的时间让位给改名和删除两个入口（键盘 Tab 到这一行时同样出现，触屏上没有
悬停则常驻）—— 不悬停时一整列只有名字，扫一眼不会先看到二十个 ✕。会话行因此正好一行高，
工作区折起来时它占的位置也随之为零。**当前会话**用三样东西同时标出：左侧一根 accent 竖条、
一层很淡的强调色底、加粗的名字。底不能单独承担这件事：任何「一眼看得见」的底色都会把行里
那个小字号的时间压到 4.5:1 以下（实测 `.06` 的底是 4.67，`.12` 的底是 4.33），所以底色取
`.12` 而时间改用深一档的 `--muted-strong`（4.66 → 5.02）。每个工作区在自己那段列表的**上面**
有一行「+ new session」，并随工作区一起折起来 —— 位置本身就是它属于哪个项目的说明，
指针停上去（`title`）和读屏（`aria-label`）拿到的是「new session in <工作区>」。
每个工作区最多列 10 个会话，多出来的折成一行「**Show N more**」按钮 —— 点它就把这个工作区
展开到全部（`POST /more`，进程内记住，按工作区各记一份）。**上限是为了「打开页面不重放整个
store」**：所以它落在渲染那一层，不在 store 那一层，`platform.list_workspaces` 现在把每个
工作区的会话都列出来（一次 readdir + 每文件一次 stat，排序本来就要），而**读会话头部**这件事
仍然只对真正要显示的那些做。点开一个别的目录里的会话会**把 agent 搬过去**：之后的工具都在
那个目录里跑，新轮次也写进那个工作区的会话目录。侧边栏底部一行可以**添加工作区**，两种方式：
「Choose a folder…」打开**宿主机自己的文件夹选择框**（macOS 的 `choose folder`，由服务器进程
调起；浏览器给不了绝对路径，只有 host 能给），或者直接填一个路径回车。两条路都走同一个
队列任务：路径被规范化、写进 store 里该工作区自己的 `workspace.json`、在那里开一个会话，
所以 `~/src/app` 和 `/Users/x/src/app` 是同一个工作区，而且**一个还没有任何会话的目录也是
工作区**（此前工作区由「store 里有会话」推断，于是刚添加、还没用过的项目会消失）。
写在工作区自己的目录里而不是一个全局注册表：删掉目录就忘记了这个工作区，也不会出现
「注册表和磁盘不一致」这种状态。这条不是靠类型保证的，所以验收脚本里有一条
端到端的证明 —— 切过去之后让模型 `read` 一个只存在于那个工作区的文件。

工作区的身份（cwd）**从会话文件的 header 读，而不是从目录名反解**：编码把所有分隔符
都换成 `-`，`--a-b--` 既可能是 `a/b` 也可能是单个目录 `a-b`，猜错就会把 agent 搬到一个
不存在的地方。会话自己记着答案。

**流式块会被定时冲刷。** 批处理只能按大小，就会出现这样的事：容器在**第一个 delta 到达时**就
插进 DOM，而里面的文本要攒够阈值才发第一帧 —— 于是流式期间点开是**空白**（对思考尤其明显，它的
阈值是 256 个字符）。所以除了按大小批处理，还有一个 250ms 的冲刷节拍：上限是「最多滞后 250ms」，
而不是「最多滞后若干字符」，同时也不会把每个 delta 都变成一帧。

**两个属性名不能混。** 侧边栏的点击委托把 `[data-session]` 当成「打开这个会话」；transcript
一度也用同一个属性名记录「我是哪个会话」（给帧过滤用），于是**在对话里点任何地方** —— 点开一个
块、选中一段文字 —— 都会被当成一次切换请求，而且它带的是短 id（不是路径），服务器找不到这个
文件就**新建一个空会话**：读者刚点开的那个块连同整个对话一起消失。现在 transcript 用
`data-shown-session`，并且「点击 = 打开会话」被限定在 `#sessions` 之内。浏览器验收里有 4 项盯着
它（点开有内容、会话没变、没有多出新会话）。

**打开会话默认落在最新处。** 长对话是从结尾读的，落在开头等于让人先滚过全部内容 —— 而且
初次加载时页面就在 `scrollY = 0`，原来的「贴底才跟随」判断在那一刻必然为假，所以长会话一定
停在最老的内容上。现在的规则分三种情况：**加载或切换会话**（读者自己点了某一行、或加了一个
工作区）就无条件落到最底；**流式追加**只在读者本来就在底部附近时跟随，往上翻着读不会被拽走；
**重连**替换的是同一份内容，因此保留读者的位置。

**状态行说清一轮发生了什么**：模型调用数、工具调用数、token 进出、花费。花费保留
6 位小数，因为一轮对话的成本是「零点几毫厘美元」，四舍五入到分就永远是 $0.00。

**每轮回答的结尾带一行本轮用量。** 同一批数字（调用数、工具数、压缩次数、token 进出、
花费、**缓存命中率**），但按「轮」给，而不是按会话累计。会话累计会把冷启动和压缩摊平，
看不出某一轮是不是把前缀缓存打掉了；本轮命中率才是读者能据以行动的数字。这一行来自
`turn_stats`：正在跑的那轮用 turn 结果（压缩调用自身的花费也在里面），重载的会话从日志
里的 assistant 消息重新算出（每条消息带自己那次调用的 usage，所以两边一致）。

**进入死循环的门槛是 200 次模型调用**（原来 40）。工具密集的一轮动辄几十次调用，40 会在
任务做到一半时把它砍掉；到这里还不停，才是真的在打转。到限时状态行会明说
`gave up after N model calls without a final answer`。

**三个上限，三个维度**：调用数（`--max-rounds`，默认 200）、钱（`--max-cost`，默认 $1）、
时间（`--max-seconds`，默认 1800）。默认值都是量出来的（2,280 个真实 turn：中位花费 $0.004、
p90 $0.036、最贵 $0.295、最长 165 次调用）——都在「从未发生过的 turn」之外一个数量级，
拦的是 runaway，不是大任务。状态行会说明是哪个守卫触发的。

**被守卫停下的 turn，会在日志里写下来为什么。** 这是重载后唯一看不到的东西：对话被成本
上限停掉、和被模型正常跑完，在消息里长得一模一样（都停在一条消息上）。所以终点会追加一条
`custom` 条目：

```json
{"type":"custom","customType":"turn-outcome","data":{"ending":"round_limit","turns":1,"cost":0.0000546}}
```

选 `custom` 而不是往 assistant 消息上加字段，是因为消息格式是 pi 的、有别的读者；而
「这一轮是怎么结束的」是**本 agent 怎么跑的**这一事实。`custom` 不会回放给模型，所以写下它
不会改变模型看到的东西（`context_messages_of` 对它是 `_ => []`）。
重复打开会话时，状态行会直接说 `opened N messages in <cwd> · the last turn stopped at the cost limit`。
输出被截断（`finish_reason: length`）也记 —— 那是最容易被误导的一种：turn 是正常结束的，
别的任何地方都看不出回答没写完。**正常跑完的 turn 不写任何东西**，所以「这轮是不是被停的」
永远有个廉价的答案。

**顶部信息条说清整个会话**（口径照 pi 的 footer）：会话 id、模型、token 进出、
cache 读、总花费、上下文占用。cache chip 同时给出**缓存命中率**（`cache 12.3k · 87% hit`）：
命中率 = `cache_read / (input + cache_read + cache_write)`，分母是服务端计费的 prompt 总量
（DeepSeek 把命中算在 `prompt_tokens` 里，`input` 是扣掉后的未缓存部分）。部分命中**绝不
四舍五入成 100%**：整数位会读成满命中时自动补小数（`99.9`、`99.95`、`99.998`……），这是 dsh
的口径（`formatCacheHitPercent`），用整数运算移植，保证平局各后端一致。数字来自日志
（`Session::usage`：assistant 消息 +
压缩调用），所以重启之后和重启之前一致 —— 而且**已经被压缩替代的那些调用仍然计入**
（钱已经花了；一个会因为压缩而变小的总额没人能信）。

**上下文占用是锚定出来的，不是估出来的。** 唯一会影响「接下来发生什么」的数字 —— 它和
压缩阈值比较，接近时整个 chip 变红，鼠标悬停说明「下一轮会压缩旧历史」。

纯启发式（字符数 ÷ 4）在两个地方是错的，都是拿真实会话量出来的：

| | 实测 |
|---|---|
| 平均值 | 只有 provider 真实计费的 **83%**（23,280 个响应） |
| 最大上下文 | 从未高估过，p99 是 0.93 |
| 固定开销 | **完全没算** —— 系统提示词 + 7 个工具 schema ≈ **1,314 token**，每个请求都有 |

第三条最直观：一句 `hi` 的对话，chip 显示 `~10 tokens`，而真实请求是 ~1,300。

所以改成锚定（dsh 的口径）：**provider 报的 prompt 大小是已知事实**（就存在 assistant 消息的
usage 里），只有锚点之后新增的部分才需要估：

```
next ≈ 上次真实 prompt_tokens + estimate(此后新增内容)
```

同一批会话上：**平均相对误差 17% → 0.2%**（7,510 个样本）。压缩阈值也换成了这个数 ——
阈值是硬边界，拿低 20% 的数去比会**压缩得太晚**，而太晚的代价是请求直接超窗被拒。
tooltip 会说明这一眼是 `measured` 还是 `estimated`（还没有任何响应报过尺寸时）。

每项都带 tooltip 给明细（input/output/reasoning、cache 读与写、花费拆分）。

**turn 进行中必须一直有东西在动。** 这条是用户实测出来的：一次提问可能让模型跑
19 次模型调用、25 次工具调用，而页面当时只推流「正文」——模型大部分时间在思考，于是
几分钟里屏幕上一片空白，看起来就是卡死。现在推的是三样东西：正文（`SetText`）、
**思考**（默认只露最后三行，读者不必读但能看到它在长）、以及**每个工具**——从它
*开始跑*的那一刻就出现，默认展开，`running…` 那一行后面跟着它自己的计时
（`data-since` + 客户端 `tick()`，不靠服务器每秒发帧）。计时放在那一行而不是标题里：
「在跑」和「跑了多久」是同一个问题的两半，而且这样标题就只剩工具名——和跑完后的标题
一模一样。

运行中的块和它跑完后**展开的样子逐字节相同**（`tool_body` 一处渲染、三处使用）：参数就
写在里面，不是一句概述，body 形状也一样。理由是「同一个东西不该在读者眼前换形状」——
读者盯着的块，在工具结束时变成另一种元素，他就得重新找自己在看什么。唯二的区别是
body 末位从 `running… · 6s` 变成结果、以及块上多了个 `open`。

收尾分两步：结果到达时块**展开着交出去**（`settling` 那一帧带 `open` 和
`data-settle="1000"`，客户端一秒钟后折起），而不是到达时就折好——结果正是读者在等的东西，
折好再给等于把它藏在一个没人知道要去点的点击后面。这一秒是**瞬时值而不是状态**：属性只
在那一帧上，所以稍后刷新出来的块是折起的，服务器也永远不需要知道哪些块读者看过。
计时的取舍则是明确的：时长不在日志里，所以重新载入的会话不可能显示它，与其让同一轮
「刚读完一种样子、刷新后另一种样子」，不如让它只活在运行期间。
**一个工具自始至终只有一块**——早先的写法是结果 append 在运行块旁边，于是那个带计时的
运行块会一直留在页面上。状态行同步给计数（`working… 3 model call(s), 2 tool call(s)`），
这是最便宜的「还活着」信号。这些节点都是临时的：turn 结束时会**整个 exchange** 换成
配对渲染好的版本（一次 `render_exchange`，和重新载入时走的是同一个），所以流式路径
永远不需要决定最终长什么样。

**运行中的 turn 必须能被「加入」。** 中途连上、或刷新、或切回来的人，拿到的是一份
「到目前为止」的快照，而它用的 id 必须是流还在写的那些——否则后续帧打在一个不存在的
目标上。这条对一个**已开始、未报告**的工具曾是破的：`Tool` 这一支的 result 不是可选的，
表示不了它，于是快照里没有这块，工具结束时那条 replace 被客户端静默丢弃
（`if (!node) return`）——结果永远不出现，而每个字节级断言都还是过的。现在它是
独立的 `RunningTool` 分支（带 `since`），并且**验收钉住了它**：在 `/bin/sleep 20` 跑到
4 秒时刷新页面，断言运行块仍在、`since` 未变、且结果最终落进同一个块。
（这条断言的写法有个坑：`readyState === 'complete'` 在新文档开始加载前就已经为真，
只等它会读到刷新*前*的 DOM，于是整段验证变成一场空——所以刷新前先打一个只有旧文档才有的标记。）

**一轮结束后只留答案。** 中间过程——推理、工具调用与结果、模型在动手前说的那些话——
收进答案上方一个 `<details class="work">`，标签上写着这一轮调了几次模型、几次工具。
所谓「最终输出」的判据是**最后一个 `Plain(Text)`**：一轮里模型会写很多次，它最后写的
那个才是要读的。会失真的情况写在了代码注释里：以工具调用收尾的一轮（撞上限、或被停）
没有答案可指，于是露出工具前的最后一句话——总比什么都不显好，但这不是「这一轮完成了」的声明。
答案下面那行数字是**按钮**，点开是明细：input / cached input / cache writes / output /
reasoning / 总 token，以及按 input / cache / cache writes / output 拆开的**花费**——
四项相加等于总额，因为 fresh input 和 cached input 是同样的 token、完全不同的价钱，
只给总额等于说了花多少钱、没说花在哪。

**会话之间是并行的，切换只是换看的那个。** 每个打开的会话有自己的 turn 槽位，所以两个
会话可以同时干活；切走不会打断任何人。切回来时，进行中的那一轮按服务器记住的实时输出
重新渲染（提问、已到的正文、思考、每个工具），而且**容器用的就是流式帧要写的那几个 id**，
所以后续增量会继续落到同一批节点上，而不是另起一份。侧边栏给正在跑的会话打一个点，
状态行在看别的会话时补一句 `· N other session(s) running` —— 否则后台的活儿是完全不可见的。

**转义是唯一真正的风险**，因为输入是模型输出和文件内容：`Text` 节点永远转义，
`Raw` 是唯一逃生口且只用于 markdown 渲染器的输出。`html/escape_test.mbt` 有四个
专门的注入测试（script 标签、事件处理器属性、属性逃逸、提前闭合标签）。

**标签是一个类型，不是字符串**（`el(Div, …)`，`html/node.mbt` 的 `Tag`）。这是为了堵住
`html/` 这层 interface 上唯一编译期查不到的东西：`el("dvi", …)` 曾经编译通过、测试全过，而
客户端对找不到目标的 patch 是**静默丢弃**的 —— 于是拼错一个外层标签 = 一个再也不会更新的区域，
所有字节断言照旧通过。这正是这个 UI 最贵的那类失败。

为什么不是「每个标签一个函数」（`div(...)`、`i(...)`，读起来最好）：标签名是普通小写标识符，
**局部变量会遮蔽它**。`for i in 0..<n` 在渲染 `<i>` 的文件里直接编译失败（`has type : Int,
wanted : function type`），而树里已经有 10 处这种命名（`i`、`label`、`body`、`head`、`html`、
`input`、`meta`、`style`、`summary`、`title`）。枚举构造器住在类型命名空间里，遮蔽不到。最小复现
留在 `html/node_test.mbt`，理由记在 ADR-0004。

代价与边界：`Tag::name` 是穷尽的（新增标签不给名字编译不过），`Tag::is_void` **不是**（`_ => false`
是刻意的，33 个里 30 个答 false）。属性仍是字符串 —— 属性拼错是可见的，标签拼错不是，所以只治了后者。

## 后台任务：调用结束之后还在跑的东西

一个命令可以在**工具调用结束时仍然活着**：`npm run dev &`、`sleep 300 &`、`some-server &`。
工具调用结束了，turn 结束了，侧边栏那个「正在跑什么」的面板里什么都没有 —— 只有一个没人在看
的进程。这正是「怕忘记关」的来源，所以它需要自己的记录。

这部分是照 [dsh](https://github.com/deepseek-ai/deepseek-harness) 的 background task runtime
做的（`docs/subsystems/jobs.md`），它的模型是：

| dsh 的做法 | 我们是否采用 |
|---|---|
| job 有 id（`<kind>-N`）、kind、label（命令）、status（running/stopping/completed/killed/failed）、startedAt/finishedAt | ✅ 同一个状态机与同一行格式（`<id> [<kind>] <status> — <label>`） |
| **job 属于会话**，访问按 owner session 划界 | ✅ 按会话记录；面板跨会话一起列出（"还剩什么在跑"是跨会话的问题） |
| 每个 owner 上限 10 个（默认），超了报错让调用方先清理 | ✅ 同一个数字与同一句话：**拒绝发生在启动之前** |
| 给模型三个工具：`job_list` / `job_output` / `job_kill` | ⏳ 未做（下一步）；目前是给**人**看的面板 |
| 完成时给 owner 注入通知（busy 下一步注入，idle 可能唤醒，唤醒有次数上限） | ⏳ 未做；我们的等价物是面板里那一行从 running 变成 completed |
| owner 销毁时 cancel 并 await；teardown 的 cancel 把记录标成 reported | 部分：进程退出时 `kill 全部 live job`；我们没有 session 关闭这个动作 |
| **job 记录是纯内存的，进程死了就没了**（`jobs-local`："jobs die with the harness process and are not durable across restarts"） | ❌ **我们不采用**：记录写进 `~/.pi-mb/jobs.json`，见下 |
| 杀进程用 **managed process group**：Linux 临时 user-systemd scope（连 `setsid`/被重新父化的后代都收），Windows Job 对象，macOS 退化为 detached 进程组并**明确承认逃出进程组的后代可能管不住** | 见下 |

**机制上我们和 dsh 不同，原因是运行时不同，而且我先做了实测**：MoonBit 的 async 运行时没有
`setsid`，也没有「给任意 pid 发信号」的接口；实测子进程**继承我们自己的进程组**（没有新 session），
所以整组杀会把服务器自己杀掉。于是改成两件可移植的事：

1. **让 shell 在退出前自报进程表**：命令后面追加 `ps -eo pid=,ppid=` 写进临时文件。这是后台子进程
   仍然挂在 shell 上的最后时刻；此后它被重新父化，但**我们记住了 pid**（重新父化不改 pid）。
2. **一个退避采样器**（0.3s/1s/3s/10s/30s，最多 5 次）覆盖 shell 自己来不及上报的情况：命令被
   超时杀掉，或者命令自己 `exit` 了。超时那一刻最后采到的进程树就是要去清理的东西。

杀进程走 `/bin/kill`（`-TERM` → 3 秒宽限 → `-KILL`），存活检查走 `kill -0` —— 都是进程，不需要 FFI。
**已知边界**（和 dsh 在 macOS 上承认的是同一类）：在最后一次采样之后才启动、并且父进程已被杀掉的
后代可能查不到。要根治得像 dsh 那样有一个真正的会话/进程组所有者（Linux 上 systemd scope）。

还有一个陷阱值得记下来：**输出不能走管道**。后台子进程会继承 stdout 管道，于是「读到 EOF」要等到
那个后台进程结束 —— `sleep 60 &` 会把工具调用阻塞一分钟，正好抵消了背景化。所以输出重定向到临时
文件，子进程可以继续往里写而不阻塞任何人（这也是 `npm run dev > log 2>&1 &` 之所以是常规写法的原因）。

模型也会被告知：工具结果里追加一行「this command left N process(es) running (pid …)」，因为决定
背景化的是它，而它看不到侧边栏。

### job 记录落盘（这一条我们做得比 dsh 多）

后台任务能活过工具调用，也就能活过**服务器**——而且它是真的活着，只有那份内存记录死了。记录一没，
它就成了没人认识、也没法 `pkill` 的孤儿。所以记录写在 `~/.pi-mb/jobs.json`（和 settings、sessions
同一层，不写进 pi 的目录），启动时读回来。

dsh 明确不做这件事：`jobs-local` 的文档写着「jobs die with the harness process and are not durable
across restarts」，要做持久化得换一个实现同一个 contract 的后端。我们选了做，因为代价很小（一份
JSON + 一次 rename）而收益很具体。

启动时做一次**对账**（`JobStore::reconcile`），用进程表回答一个只有它答得了的问题：

| 记录说 running，但 | 结论 |
|---|---|
| 还有任一 pid 在 | 仍然 live —— 这正是写记录的目的：读者能据此找到并 kill 掉服务器已经不管的进程 |
| 一个 pid 都不在 | 标成 `failed · lost: the server exited while this was running` |

第二种是诚实的做法：没人看见那个进程怎么结束的，让它永远显示 running 更糟。`nextId` 也一起存——
否则重启会重新发出 `bash-1`，而上一轮的 `bash-1` 可能还在跑。

写盘只在记录**发生变化**时发生（和上次写入的字符串比），因为面板是定时刷新的，否则每几秒白写一次。

> 实测（真进程，非模拟）：让它起 `sleep 240 &` → `jobs.json` 记下真 pid → `kill -9` 服务器 →
> 重启，页面照常列出那条任务（说明记录真的被读回来了）→ 杀掉进程再 `kill -9` 服务器 → 重启日志
> 说 `jobs 1 from a previous run are gone; recorded as lost`。

## 同一会话内一次只跑一个 turn

会话之间并行，但**同一个会话内的 turn 严格串行**（每个会话一个 turn 槽位）。这条是
承重的，而且不是推演出来的：

这不是推演出来的结论，是压测出来的。同时 POST 两个 prompt，日志变成这样：

```
entries 22, orphan parents [('e502f650','9b8d05ce')]     ← 有一条 entry 被写掉了
两条交错分支: 31e253f6→4a1d4897→… 和 571903ea→21616903→…
```

两个原因，都得修：

1. **没有串行化**：两个 turn 同时跑，共用同一个 `session`，各自从自己那份快照往后接。
2. **`append_entry` 是「读-改-写整个文件」**：两个写者必然丢更新 —— 这就是
   `9b8d05ce` 消失的原因。它还是 O(n²)：一条会话有 1000 个 entry 时，每次 append
   都重写整个文件。

现在 append 走真正的 `O_APPEND` 写入（一行一次 `write`，读者要么看到整行要么看不到），
同一会话内的顺序由该会话的槽位保证 —— 不是由 HTTP 层保证，也不是由一个全局队列保证：
后者会把所有会话也一起串起来，那样就没法并行了。

**不同会话的 patch 不会串台。** 每个在 turn 里产生的 patch 都带一个会话标签（帧级别的
字段，不是 patch 的一部分 —— 它说的是「这条给谁」，不是「做什么」），浏览器只应用当前
显示会话的。没有这一条，后台会话流式出来的文字会追加到读者正在看的那份对话里。
同一条保护也解释了为什么快照帧不带标签：它是给所有人的。

## 会话与恢复

会话格式与 pi 一致，而且是**可验证的一致**：`moon run verify` 把本机 160 个真实会话、
46,399 条 entry 全部解出来、再编回去，逐字节比对，当前 **0 失败**。

恢复有三条路径，都走同一个打开函数：

```bash
moon run ui -- --continue        # 本目录最近写入的会话
moon run ui -- --resume <id>     # 按 id 前缀或路径
# 或者直接在侧边栏点一个
```

打开时会先跑一次**崩溃修复**：进程在工具结果落盘前死掉会留下无应答的 `toolCall`，
provider 会拒绝这样的记录。修复时合成的错误文本明确告诉模型「不要盲目重试可能有
副作用的操作」，而且它是**追加到日志里**的 —— 只存在于内存里的修复不算修复。

### turn 是有身份的：中断是事实，不是推断

上面那个修复只能看到**一种**中断：assistant 消息要了工具、却没结果回答（`needs_repair`）。
它看不到另一种 —— **在两个工具之间被杀掉**，那种中断留下的对话是完全平衡的，没有任何缺口。

所以 turn 现在有开始和结束两条记录（都是 `custom`，不进模型请求）：

```json
{"customType":"turn-start",  "data":{"prompt":"build the thing"}}
{"customType":"turn-outcome","data":{"ending":"completed","turns":7,"cost":0.031}}
```

**两者之间就是「durably open」**（dsh 的说法：turn 在 turn 边界 durably open）。于是：

- 日志里**没有 outcome** ⇒ 这个 turn 从未完成 ⇒ 就是被中断了。这是从日志读出来的事实，
  重启前后一致，而且它在被写下的**那一刻之前什么都没发生**，所以在任何时刻被杀都会留下它。
- 打开会话时状态行直接说：`opened 12 messages in … · the last turn was interrupted while working on: build the thing`
  —— 把当时在做的那句话拿出来，因为那是读者最想知道的东西。
- **成功也写 `completed`**。这和直觉相反（上一版是成功不写），但只有这样才能让「没有 outcome」
  意味着「没完成」：不写成功的话，这句话就描述每一个正常结束的 turn。

`run_turn(continuing=true)` 是**续跑档**（不是重放）：不追加 user 消息、不重复开 turn（两处都
已经在日志里了），只把循环跑到完结并把 turn 关上。因为已完成的工具结果就写在日志里，
**已经做过的工作不会被再做一次** —— 这正是 DBOS 用 checkpoint 换到的东西（「已完成的 step
不重跑」），我们白拿，因为我们的 append-only 日志本来就是那张 checkpoint 表。

它不自动触发，而是转写末尾的一个选择：

```
┌ the last turn was interrupted while working on: build the thing
│ [ Continue ]  [ Start fresh ]
└
```

为什么是选择而不是自动：唯一不能安全跳过的是**崩溃那一刻正在跑的那个工具** —— 它可能已经
写了文件，也可能没开始，而日志里没有它的结果。所以这个判断交给知道那一轮在干什么的人。
实测（真 SIGKILL）：中途杀掉服务器 → 日志停在 `turn-start` 没有 outcome → 重开，状态行和
通知都指向那一轮 → `/continue` 跑完并写 `completed`，且 **user 消息仍然只有 1 条**
（这一条最初是坏的：prompt 被追加了第二遍，端到端测出来的）→ `/dismiss` 则写 `abandoned`，
通知消失。

> **两家都没有这个。** dsh 的崩溃处理和我们旧版一样：`interruptedTurnClosers` 补上无应答的
> toolCall，然后把控制权交回用户；`resume` 恢复的是**持久历史**，不是「把中断的 turn 跑到完」。
> mini-swe-agent 连 resume 都没有（只有 trajectory 导出）。所以这不是追赶，是没有参照，
> 这也是为什么第一步只做到「中断可检测 + 续跑档可用」，而不是自动续跑（见「已知限制」）。

侧边栏按最后写入时间排序：文件名里的时间戳是会话的 *开始* 时间，今天恢复的会话会被
后来居上的一次性会话压到后面。标签取第一条用户消息，只读每个文件开头 64KB —— 为了画
一个列表把每个会话整份读一遍，等于让「打开 UI」的代价和「回放所有会话」一样大。

**侧边栏总会显示当前会话所在的工作区**，哪怕 store 里还没有它：一个还没有写过的会话
不在 store 里，它的工作区也不在（store 要等到有对话才认识它）。不补这一行的后果不只是
「看着不放心」——「+ new session」按钮在工作区的 `<details>` 里，于是空 store 里根本没有
这个按钮，而第一个 prompt 恰恰要在这个状态下输入。

**会话文件在写入第一条 entry 时才建立**，启动本身不落盘。之前每次启动都写一个只有
header 的文件，用一周之后 store 里全是没人用过的「空会话」，选择器里全是点了没内容的
行。启动时还会清理这类遗留文件（只清小于 4KB、且早于 10 分钟的，所以正在被写入的会话
不会被误删），并在日志里报数量。

**每条 entry 带自己发生的时间**，而不是整个 turn 共用一个时间戳。turn 的时间都花在
entry 之间（模型、工具），四十条 entry 共用一个时间戳的日志，事后没法看出时间去了哪。

存储放在 `~/.pi-mb/sessions/`，**不是** pi 的 `~/.pi/agent/sessions/`。格式兼容是
刻意的（能读、能对拍），共用一份日志不是：两个进程同时 append 一份文件，就又回到上面
那个丢更新的问题了。

## 压缩

顺序是固定的：**先瘦身，再压缩**。

| | 瘦身（`core/trim.mbt`） | 压缩（`core/compaction.mbt`） |
|---|---|---|
| 做什么 | 裁掉旧工具输出的中段、清空旧思考 | 把旧历史交给模型总结 |
| 代价 | 免费 | 一次 API 调用 |
| 可逆 | **是**（原始内容还在，重读即可） | 否（信息已被摘要取代） |
| 何时用 | 每次请求前 | 瘦身后仍超过阈值时 |

因为瘦身免费且可逆，它先跑；如果瘦身后已在阈值以下，压缩就不必发生。

阈值由模型窗口推导（`CompactionSettings::for_window`）。`deepseek-v4-flash` 的窗口是
1M token，阈值因此是 98 万 token —— 日常几乎不会触发，但换个窗口小的模型就会。
所以这条链路是用 40k 窗口在测试里验证的，而不是靠等到线上触发。

压缩写成一个 `compaction` entry，带 `first_kept_entry_id`：它之前的历史被摘要取代，
之后原样保留。**被替换的内容仍然在文件里** —— 压缩不是删除，只是让后续请求不再携带。

**摘要回放必须带 `<summary>` 包装。** 这个字符串是 pi 的 `convertToLlm` 产生的，而且
有一个不显眼的前提：**pi-ai 根本不认识 `compactionSummary` 这种消息，喂给它会被静默
丢掉**（实测：喂进去，请求体里那条消息直接消失，不报错）。所以这个转换必须发生在请求
构造之前 —— 我们放在 `ContextMessage::to_message`。包装字符串本身由
`harness/gen-llm-message-fixtures.mjs` 从 `convertToLlm` 捕获，不是手写的：这正是那种
会被人「顺手改整齐」的字符串。

浏览器验收要先把 ui 构建出来（`moon build --target native`），它会自己挑空闲端口、
起服务器、跑完再收摊。它检查的东西：区域节点各只有一个、文档没有被嵌套、表单提交真的
到达服务器、流式容器在最终替换后消失、状态行报出花费、侧边栏新建与会话切换、**跨工作区
切换后工具确实在新目录里执行**、**服务器重启后页面自愈**（EventSource 重连 + 首帧快照）、
以及全程没有任何未捕获异常。

### 对拍是主要手段

pi 是 oracle。所有期望值都是从它那里跑出来的，不是手写的常量：

| fixture | 捕获方式 | 保护什么 |
|---|---|---|
| `core/deepseek_fixtures.mbt` | 把 SSE 喂给 pi-ai 的解析器，取它产出的消息 | 流式解析的每条规则 |
| `core/deepseek_request_fixtures.mbt` | `stream` 支持注入 `fetch`，直接抓 pi 实际发出的请求体 | `buildParams` + `convertMessages` |
| `core/tool_fixtures.mbt` | 从 pi 的工具注册表导出 | 工具描述与 schema 逐字一致 |
| `core/llm_message_fixtures.mbt` | 调 pi 的 `convertToLlm` | 摘要与扩展消息怎么变成模型消息 |

对拍已经抓到七个靠读源码不易发现的规则：`responseModel` 只在模型名与请求不同时记录、
`thinkingSignature` 是实际命中的字段名而非固定值、有工具历史但没传工具时要发
`tools: []`、工具定义必须带 `strict: false`、图片在不支持视觉的模型上要降级为占位
文本、工具声明的描述与参数形状必须与 pi 逐字一致、以及 compression 摘要的 `<summary>`
包装。

还有一个只有全量数据才能看出的坑：`usage.reasoning` 是 pi 版本演进中新增的字段
（6-7 月的会话没有，8 月之后才有）。所以读取旧 session 时必须保留可选性，而解析 SSE
时又必须总是产出它 —— 这是两条不同的代码路径，混用会一边损坏旧数据、一边与当前 pi
不一致。

### 端到端

```bash
moon run pi -- "Run 'ls' and tell me how many files are in this directory."
# prompt   Run 'ls' and tell me how many files are in this directory.
# model calls 2, tool calls 1, 1922ms
```

`moon run pi` 跑的是完整链路：派生上下文 → 调模型 → 执行工具 → 写回 session，循环直到
模型不再请求工具。写出的 session 文件能被 pi 自己读回来，这是最硬的兼容性证据。

### 静默的模型连接

模型流有两处会无限等待：等响应头、以及等每一块数据。没有超时的话，一个被接受然后被
遗忘的连接会让这个 turn 永远等下去 —— 而 turn 是单 worker 串行执行的，于是后面所有
请求一起排队到进程结束，页面表现为彻底卡死。所以两处都有 120 秒的空闲超时（按「每次
等待」而不是「整个请求」计时，慢但有进展的响应永远不会被掐断）。

### 端口冲突

第二个实例会拿到 `cannot listen on 127.0.0.1:8790 … pass --port` 并以 1 退出，而不是
留下一个不服务任何东西的僵尸进程。这条也值得说一句：原来的实现在这里会把启动日志和
运行时的错误输出写乱（同一时刻两个写者往同一个流里写，连 `cwd` 前缀都被吃掉），
所以现在错误只由运行时输出一行。

## 实测过的性能账

优化都从测量开始，否则很容易在不是瓶颈的地方花力气。当前数字与结论：

| 路径 | 实测 | 结论 |
|---|---|---|
| 会话数据路径（append / 派生上下文 / 瘦身） | 5000 条 entry：20 次 append **12ms**、派生+瘦身 **2ms** | **不需要优化**。每次 append 重建索引确实是 O(n)，但现实范围离拐点很远（要 5 万条） |
| 流式推流 | 一条 700 字回答曾经产生 **13.2MB** SSE | 已修：**13.2MB → 78KB（170×）**，见下 |
| 侧边栏刷新 | 20 工作区 × 10 会话 × 64KB：**88-150ms / 次**，而一个 turn 刷新两次 | 已修：按 `(路径, mtime)` 缓存标签（mtime 本来就有，不必额外 stat）+ 前缀 64KB→16KB：**冷 82ms、之后 17-22ms** |
| 大会话的整页与切换 | 最大的真实会话（92 条、257KB）：`GET /` **13ms / 242KB**，一次切换发 **236KB** | 暂不修。它随会话线性增长（投影：5MB 会话 → 每次切换约 5MB HTML）。触发条件是「单个会话超过一两 MB 或几百轮」，那时的修法是「只渲染最近 N 轮 + 加载更早」 |
| turn 中途刷新顶条 | 一轮 turn 会重建 bar 好几次；设置面板就在同一条 bar 里 | 已修：数字收进独立的 `usage` 区域，turn 只替换它，不会把读者正在输入的面板清掉（也不会重建整条 bar 的 HTML） |

流式那条值得展开，因为它的形状是**平方**而不是「慢」：`SetText` 每帧重发**整段累积文本**，
阈值又是 8/64 个字符，于是 39KB 的思考变成 599 帧 × 平均 20KB = **12.2MB**，客户端还要把一个
不断变长的字符串赋值 600 次。改成发**增量**（`AppendText`，每帧只带没发过的那一段）：

- 协议上更简单：不再需要「上次发到哪」的书签，每个 delta 恰好发一次；
- 字节变成线性：一条回答的流量 ≈ 文本长度 + 帧头 × 帧数；
- 另外两处收紧：帧里的会话标签从**完整路径**（每帧约 80 字节）换成**短 id**（8 字节），
  阈值 8→24（正文）、64→256（思考，反正折叠着）。

`html/patch_test.mbt` 有一条属性测试钉住它：把 4 万字符按小块喂进去，所有帧携带的文本量
**恰好等于**全文长度，帧数不超过 `长度 / 阈值 + 1` —— 平方行为会立刻让它失败。

## 已知限制

- **续跑是手动的**，不是自动的。崩溃后重开会话，转写末尾会出现一条带两个按钮的通知
  （**Continue** / **Start fresh**），而不是服务器自作主张地接着跑。这是刻意的：turn 被
  中断时，**正在执行的那个工具的结果是未知的** —— 它可能已经改了文件，也可能还没开始。
  已完成的 call 可以安全跳过（结果就在日志里），但「结果未知」的那个不能当成成功，也不能
  当成失败。DBOS 的保证建立在 step 是原子的之上，我们没有这个原子性。所以这个决定交给
  知道那一轮在干什么的人（读者），而不是替他们做。
  - **Continue** 走 `run_turn(continuing=true)`：不发新 prompt（那条已经在日志里，再发一次
    模型会看到两遍）、不重复开 turn，只把循环跑到完结。已记录的工具结果不会重跑；
    **只有崩溃那一刻正在跑的那个工具需要读者自己判断**。
  - **Start fresh** 往日志里写一条 `abandoned`，把那个 turn 关掉。不写的话它永远开着，
    通知会一直回来。
  - 两个按钮都会先检查 turn 是否还开着：通知是一段 HTML，另一个标签页可能已经答过它，
    或者读者已经直接输入新消息（那也等于放弃）—— 这种情况给一句话，而不是让 turn 失败。
  - 「最多一个 turn 开着」是不变式：直接输入新消息会自动把上一个未完成的 turn 关成 `abandoned`，
    否则日志会声称两个 turn 都在飞行中。
- **工具执行没有审批**：`bash`、`write`、`edit` 直接执行。pi 有审批流程，这里没有。
  自己机器上的本地工具，但值得知道。
- **工作区不是沙箱**（dsh 的文档也这么提醒）：把一个目录加为工作区，只是让 agent
  在那个 cwd 里跑工具；它仍然能用绝对路径读写任何它有权访问的地方。审批层不在这一版里。
- **文件夹选择框只在宿主机有桌面会话时出现**：由服务器进程调起系统对话框（目前只写了
  macOS 的 `osascript`），所以 SSH 登录、容器、非 mac 上侧边栏只有路径输入框。图省事可以用
  `--no-picker` 主动关掉它。放在 host 侧而不是浏览器里，不是因为实现偏好 ——
  `showDirectoryPicker` 只给不透明的 handle，`webkitdirectory` 只管相对名，而 agent 要的是
  绝对路径；两者都拿不到，所以这条路必须由 host 走。
- **工作区还不能改名或排序**：标题字段已经在了（`workspace.json` 的 `title`），但还没有
  入口；dsh 的 rename / reorder 是下一步。会话行有改名（只在当前会话那一行），因为 `/name`
  本来就只作用于「正在看的那个」。
- **会话列表没有搜索，也不排序**：顺序就是 mtime 倒序，工作区也是。dsh 有一套折叠成图标的
  搜索框 + Host 端内容检索（250ms 防抖、取 20 条），那是这个列表还没有的东西 —— 会话一多，
  「记得名字、找不到」就是下一条该修的。
- **「Show more」记在进程里，不落盘**：重启回到 10 个。两个标签页共享同一份（状态在服务器上，
  不在这张页面里），按工作区各记一份。理由是没有「关闭这个工作区」这个手势 —— 折回去这件事
  没有一个自然的触发点；真要做，该存的地方是浏览器的 localStorage，不是 store。
- **设置面板里只读的还是只读**：endpoint、端口、store 是启动参数，面板只展示它们和「用哪个
  flag 改」。**模型不在这一列** —— 它每个会话可改，入口在输入框右下角，不在设置面板里：
  面板是关于进程的，模型是关于会话的。
- **面板不写 pi 的凭据库**：key 存在 `~/.pi-mb/settings.json`（与 store 同一层，不是 `~/.pi/`），
  所以 pi 看不到它，两个进程也不会同时改一份文件。
- **模型目录是手写的**：`core/model_catalog.mbt` 里那三个 entry 是从 pi 的
  `~/.pi/agent/models-store.json` 抄来的，不会自动跟着上游变；pi 加一个新模型，这里得手动加一行。
  加一个模型要改的是「id + 费率 + 窗口 + thinking 档位」四件事，`model_catalog_test.mbt` 里的
  「每个 entry 都完整」那条会拦住漏掉的字段。
- **每个会话可以有不同的模型，但 thinking 档位还是进程级的**：`thinking_level="high"` 写死在
  turn 调用处，而 pro 模型没有 `low`（有 `high`）。想做 `/think:<level>` 是下一步。
- **没有图片**：`Image` 内容会被降级成占位文本（与 pi 在不支持视觉的模型上一致）。
- **工作区指令不向上查找、也不按目录细分**：只有 session 自己那个 cwd 里的 `AGENTS.md` 算数，
  上级目录的文件一律不读（理由见「工作区指令」一节）。也没有总字节预算。
- **不做流式渲染 thinking**：思考默认只露最后三行，把它实时渲染成 markdown 等于把读者
  不该读的文本按「已经在读了」的规格排版。
- 单会话广播：所有标签页看同一个会话（这是设计，不是缺陷 —— 切换是全局的）。

## 曾经存在过的路线一

最初有第二条路线：复用 pi 内核，只重写界面（pi 扩展 + rabbita 前端）。它跑得起来，
但和路线二并列意味着两边都停在半成品状态，所以删掉了（见 `baa4416`）。被验证过、
值得留下的两条结论：

1. **rabbita 的 HTML DSL 在包外不可用**：`server_side_render` 在 `internal/` 包里，
   `Html::to_virtual_dom()` 的返回类型也来自那里，编译器强制 internal 可见性。
   唯一出口是整页 `App::render`，那正是「流式输出」不需要的形状。
2. **SSE 逐块到达是可依赖的**：预期间隔 120ms，实测 120/121/121/121/121ms。
