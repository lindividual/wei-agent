# wei

一个 agent 内核，加一个原生 macOS 壳。交付形态是单个 native 二进制；界面只有一处实现。

它起先是 [pi](https://github.com/earendil-works/pi-mono) 的独立复刻 —— 消息格式、会话格式和
工具定义都照那份实现写，好两边对拍。现在它读自己的凭据、认自己的 skills 目录、生成自己的
fixture，那份依赖已经断干净了；留下的是几个格式，和注释里写明的出处。

```
core/      纯逻辑：消息模型、DeepSeek 编解码、agent 状态机、会话树、工具、压缩
platform/  native 实现：HTTP/SSE、文件系统、进程、script
agent/     驱动：把状态机接到模型与工具
md/        markdown → 块/span 树（cmark）。线上只有一个前端用，但它仍是共享层：原生 Text 不能被
           喂 `<h2>`，而且解析结果必须只有一个来源，所以在这里做一次、结果当数据跨过去
wei/ cli/   可执行：命令行跑一次完整 turn / 打一次真实 API
verify/    可执行：拿真实会话全量跑往返验证
scriptcheck/ 可执行：编译并运行内置的 script 程序
macos/     原生 macOS 壳：MoonBit 事件出口 + SwiftUI 宿主（**唯一前端**，界面细节见
           macos/README.md，踩坑清单见 docs/macos-pitfalls.md）
```

**一条硬约束**：`core/` 不许碰 IO，必须能编译到**每一个**后端。
`.githooks/pre-commit` 会跑 `moon check -p core --target js` 和 `--target wasm-gc`；
这两条失败就说明有平台代码渗进了核心逻辑。约束靠编译器执行，不靠自觉。

## 运行

```bash
moon run wei -- "prompt"            # 命令行跑一次完整 turn
moon run verify                      # 全量会话往返验证
moon run scriptcheck                 # 编译并运行内置 script

macos/make-app.sh && open "macos/dist/wei Agent.app"   # 原生 macOS 壳：打包成 .app
# 开发循环（不打包）和终端形态见 macos/README.md
```

API key 只有两个来源：`DEEPSEEK_API_KEY` > 设置面板存的 key。都没有也能启动 —— 窗口照常起来，
设置里能现场填。

每轮的上限同样是三层：flag > 设置面板 > 内置默认（200 次调用 / $1 / 1800s）。默认值取自
2,280 个真实 turn（中位花费 $0.004、p90 $0.036、最贵 $0.295、最长 165 次调用），拦的是
「一个不该发生的 turn」，不是「一个大 turn」。三个上限是三个维度：调用数看得见打转，
钱看得见一次昂贵调用，时间看得见两者都看不见的那种卡住 —— 状态行会说明是哪个守卫触发的。
时间那一条单独量过 50,000 个真实 assistant turn：一半在 2s 内结束、99% 在 50s 内，最长的一次
跑了 34 分钟；半小时超过所有量到的值，又仍然框得住一次卡住的下午。

## 验证

```bash
moon test                    # 全仓
moon test -p core            # 消息模型、编解码、会话树、工具、瘦身
moon test -p platform        # 工具执行、存储、工作区注册表、后台进程、设置文件
moon test -p agent           # 假模型端到端跑 turn（含停止时杀命令、前缀只增不减）
moon test -p macos/appffi    # 壳的决定：事件形状、命令的判定、fork 的失败路径
moon run verify              # 全量会话往返（当前 172 个文件、55,931 条 entry，0 失败）
moon run scriptcheck         # 编译并运行内置 script
moon run cli -- "hello"      # 打一次真实 DeepSeek，端到端
cd macos/WeiShell && swift test    # 宿主侧：解码、路由、转录、线格式 fixture
```

**两端读同一份线格式 fixture。** `macos/wire-fixtures.jsonl` 由壳自己的发射器生成
（22 个 kind，一行一个），`macos/appffi/wire_fixture_wbtest.mbt` 生成并校对它，
`WeiShell/Tests/WeiModelTests/WireFixtureTests.swift` 解码它。所以改名一个字段、只改一边，
**两边都会挂** —— 在这之前两侧各自钉自己的 JSON 字面量，而两个手写的字面量不会互相矛盾，
所以只改一边时两个构建都还是绿的。

**fixture 是一份记录，不是一条活的依赖。** SSE 期望值来自真的 `openai-completions` 解析器跑同样
的字节，请求体来自 upstream 自己的 builder，没有一个是手写的；生成它们的脚本已经删了，字节和
期望值都留了下来，所以不一致意味着**我们的实现跟那份记录分叉了**，而不是某个常量漂了。

## 一轮 turn 在屏幕上长什么样

**必须一直有东西在动。** 这是实测出来的：一次提问可能跑 19 次模型调用、25 次工具调用，
而只推流正文的话，模型大部分时间在思考，几分钟里屏幕一片空白，看起来就是卡死。所以推
三样：正文、**思考**（默认只露最后三行）、**每个工具**（从开始跑的那一刻出现，带自己的计时，
不靠每秒发帧）。

- **流式期间照样排版，但只排版已经定型的那一段**：每个 delta 只更新累积文本，shell 把「最后一个
  顶层空白行之前」的部分解析一次（`md/live.mbt` 的 `safe_boundary`），宿主画「解析好的块 + 边界之后
  的纯文本」。半截的 `**bo`、没有分隔行的表格、开着的围栏渲染出来都是错的，而每来一个 delta 重解析
  累积文本是 O(n²)（实测 40KB 重解析 400 次 = 2.16s），所以**正在写的那一块始终是纯文本**，它结束的
  那一刻才被解析一次。

  这条规则是**线格式**的一部分：`blocks` 事件在块停止增长时发一次，流式期间每 ~150ms 或每 ~64 字符
  一条（只带新完成的块，`from`），边界作为 `parsed` 一起发过去，`history` 的每一行自带解析结果。
  为什么解析在 shell 而不是 host：宿主用 `AttributedString(markdown:)` 也能解析（表格、对齐、围栏
  语言它都认），但那是**另一套**实现、行为跟着系统版本走；而「哪个图片 target 允许被读」「原始 HTML
  当文本还是当标记」这两件事只能由一个地方决定（`md/walk.mbt`）。
- **按大小批处理之外还有一个 250ms 冲刷节拍**：文本要攒够阈值才发第一帧，于是刚打开时是**空白**。
  节拍把「最多滞后」从若干字符改成 250ms。
- **跑完的工具随手收进折叠**，规则只有一条：最新完成的那个留在外面。一轮的高度否则随工具数
  线性增长。
- **一轮结束后只留答案**：中间过程（推理、工具、模型动手前说的话）收进答案上方。所谓
  「最终输出」是**最后一个 `Plain(Text)`**。
- **运行中的 turn 必须能被加入**：中途连上的人拿到的快照，id 必须是流还在写的那些。
  这条对「已开始、未报告」的工具曾经是破的（result 不是可选的，表示不了它），于是工具结束时
  那条替换被静默丢弃，结果永远不出现而字节断言全过。现在它是独立的 `RunningTool`
  分支，验收里有一条：在 `/bin/sleep 20` 跑到 4 秒时打开，断言运行块仍在、`since` 未变、
  结果落进同一个块。
- **会话之间的切换只是换看的那个**：每个打开的会话有自己的 turn 槽位，切走不打断任何人。
  侧边栏给正在跑的会话打点，看别的会话时状态行补一句 `· N other session(s) running`。

**打开会话默认落在最新处。** 长对话是从结尾读的，而初次加载时滚动在顶部，所以原来的
「贴底才跟随」判断在那一刻必然为假，长会话一定停在最老的内容上。现在：**加载或切换**无条件
落到底；**流式追加**只在读者本来就在底部附近时跟随；**重连**保留读者的位置。

**会话标题钉在顶部**，和侧边栏那一行用**同一个文案规则**（`session_label` + `display_label`：
读者起的名字 → 第一条提问 → 「New session」）。两处对同一个会话给两个名字，会让人怀疑哪个
才对。

## 工具

八个工具：`bash`、`read`、`write`、`edit`、`glob`、`grep`、`note`、`script`。描述与参数名
照抄 upstream 的定义 —— 那是调过的提示文本，照抄既让模型看到同一个工具，也让两边可对拍。

另有一个**只有两个工具的 code mode**（`exec`、`wait`），见下一节。

**`script`：跑一段 MoonBit 程序，只拿回它打印的东西。** 另外两条「一步做很多事」的路子
（`bash`、一长串 `read`/`grep`）都受同一件事限制：每一步都要回到对话里。script 把循环放进
程序 —— 一次调用里搜索、过滤、聚合、编辑，交回一份 digest 而不是它为了产出 digest 读过的
原始输出。两种用法：`name` 跑内置脚本，`source` 跑自己的程序。

内置四个（模型只传参数，不必写代码）：

| | 做什么 | 实测 |
|---|---|---|
| `@builtin/check` `[pkg]` | 跑 `moon check --output-json`，按文件聚合错误，只留首行消息 | 40 个错误 **21,336B → 2,028B（10.5×）**；干净时一行 |
| `@builtin/test` `[pkg\|file]` | 跑 `moon test`，只报失败，长值截断 | 失败输出里同一段 400 字符的值会打印三遍（断言、diff 的 `-`、`+`） |
| `@builtin/search` `pattern [dir]` | 正则扫工作区（`moonbitlang/regexp`，VM 引擎，**没有回溯爆炸**） | 跳 `_build`/`.git`/`.mooncakes`；封顶条数 |
| `@builtin/read` `path[:a:b]…` | 批量按行区间读 | 带 `total_lines`/`truncated` 页脚 |

预置库（六个函数，内置脚本与模型自己的程序共用同一份，所以没有两份实现）：
`list`、`read`、`read_lines`、`search`、`read_json`、`edit_text`（另有语言自带的 `fail`）。
`edit_text` 要求 `old` **恰好出现一次**，不是首个匹配 —— 一次含糊的编辑是调用方在猜。

**怎么跑**：staging 在会话级临时目录（工作区之外），`--target-dir` 指向同一个目录 —— **复用
同一个目录就是编译缓存**（实测冷 0.27–0.35s、热 0.03s），不需要另写 build cache 逻辑。
stdout 封顶 **32KB**，`moon` 自己的构建警告不进 digest（它们是说构建的，不是说明结果的 ——
合并进过一次，模型把它当成结果的一部分报回来）。超时走 `exec_managed`，默认 120s。

**描述本身就是验收对象。** 这个工具上线后的第一次真实测量：一个 604 次工具调用的会话里它被
调用 **0 次**，而其中 **507 次**走了它存在的理由那些形状 —— 266 次 `grep -rn`、99 次
`python3 - <<'PY'` 改文件、66 次 `moon test`、52 次 `moon check`。工具在提示词里、被调用时能
正常工作（同一次会话里手工调用过两次），缺的只是**被想起来的理由**。

于是描述不是「它做什么」而是「**它替掉什么**」：内置脚本逐条写上 `instead of \`grep -rn\``，
触发条件补上「**你要写个程序来改文件**」这一面（原来只说了「读」，而 99 次是写），并给出
两段**可抄的**例子 —— 只说函数名等于说「有这些东西」，写调用仍然要发明一次，实测的失败正是
这一点。`core/script_test.mbt` 把这几条钉住：每个脚本必须写「instead of」，描述必须含两种用法
各一个例子，且例子必须真的调用了预置库。

**安全边界，说清楚不粉饰**：native 的 `script` **与 `bash` 同级信任** —— 能读、能起进程、能改
工作区内的文件。它不是安全改进，**是效率改进**。真沙箱的两条路（wasm + moonrun policy 要
652 行 policy 且 `@fs` 在 wasm 上不可用；JS + `node --permission` 白送沙箱但多一个运行时依赖）
都还没走，理由见「已知限制」。

**内置脚本是字符串里的 MoonBit 源码，没有类型检查器看着它们** —— 一个拼写错误能编译整个项目，
只在模型调用那个脚本时才失败。所以 `moon run scriptcheck` 会编译并运行全部四个，pre-commit
跑它。**它是独立可执行而不是测试**，因为运行它意味着运行 `moon`，而 `moon run` 从 `moon test`
里跑会在构建锁上死锁 —— 实测两次。这条约束决定了它的形状，别把它搬回测试里。

## code mode：只有两个工具

八个工具换成两个：`exec` 与 `wait`。切换在设置面板里（下一轮生效），或者启动时用
`--mode code` 钉住这次运行。

**`exec` 一次跑一件事，两种方言**：`bash` 跑 shell 命令，`moonbit` 跑 MoonBit 程序（
`@builtin/NAME` 走内置脚本，否则当源码编译、预置库照旧）。两者共用一个工具而不是拆成两个，
是因为**选哪一种由模型决定，而一次调用只跑一种** —— 一条 schema 两个字段，调用时判「只能有
一个」，两条都填时回一句可以让模型改的拒绝（这条规则写不进这个项目实现的那套 JSON Schema 子集，
所以只能落在执行处）。

为什么会有这个模式。上一节的实测（604 次调用里 507 次是 `grep -rn`、`python3` 改文件、
`moon test`、`moon check` 这些形状，而 `script` 被调用 **0** 次）说明的不是工具不好用，而是：
**有八个动词可选的时候，最省事的一步总是只动一个动词的那步。** code mode 把选择拿掉 ——
读文件、搜仓库、改文件全都要写成命令，一次调用里塞进循环、管道和过滤不是「更好的写法」而是
唯一划算的写法。这是效率取向的取舍，不是能力增强，代价就写在下面。

| 没有 | 因此 | 替代 |
|---|---|---|
| `read` / `glob` / `grep` | 命令替掉它们 | `cat`、`sed -n 'a,bp'`、`ls`、`grep -rn` |
| `write` / `edit` | 同上 | `moonbit` 程序里的 `edit_text`（要求唯一匹配），或 shell 重定向 |
| `note` | 只有两个工具 | **没有替代**：跨压缩的事实记录在 code mode 下不存在 |
| 图片读入 | `read` 是唯一能把图带回对话的工具 | 「没有图片」本来就是已知限制；但 `cat` 一个 png 会让末尾 50KB 变成乱码 |

**`wait` 是唯一无法由 shell 表达的那块。** 后台进程打印的东西没有别的地方能报到对话里：非
交互 shell 里 `cmd &` 之后 shell 立刻退出，谁也不知道那个进程后来打印了什么。所以 `exec` 在
命令留下活进程时**保留它的输出文件**（`exec_managed(keep_output=true)`），在 tool result 里
说明「还在跑、用 `wait` 收」，并把文件位置挂到那条 job 记录上；`wait <id>` 从上一次读过的地方
接着读，所以等两次不会把同一行给两遍。侧栏背景面板看到的、模型 `&` 起而没管的、`wait` 收的，
是同一份记录。三条边界值得单独说：

- **没有 `kill` / `status` 工具**。侧栏本来就能停进程，模型也可以自己 `kill`；缺的只有「收集
  输出」这一件，所以只有一个 `wait`。
- **等待必须有界**。`timeout` 默认 120s、上限 900s，`0` 表示不等待、只取当前已有的输出。等
  一个永不退出的服务器必须能返回，否则它会一直占着这个 turn（turn 自己的时间上限是最后一道）。
- **一次 `wait` 最多 32KB，并说明还有更多**，因为后台进程可能是个只会写日志的服务器。读的位置
  按「实际交回了多少」前进，所以等两次不会把同一行给两遍。
- **`wait` 自己看进程表落结算，但只看「调用返回之后」的表**。服务端那个 2 秒的监督循环在一次性
  CLI 里不存在，而 `wait` 需要「进程一没就返回」。可是后台命令的 shell 在调用返回前
  几毫秒就退出了，那一刻进程表看着已经空了，而记录里的 pid 只有 shell —— 实测三次里有一次把还
  在跑的作业记成「已退出」，记录连同它指向的进程一起消失。所以调用返回前一律不结算
  （`Job.call_open`）。
- **重启后 job 记录还在，输出不在**。进程可能还活着、还能停，但输出文件属于上一次运行，`wait`
  明说读不到，而不是去读现在恰好叫这个名字的文件。留下的文件按**年龄**收：超过一天没写过的
  删掉，而不是启动时清空目录 —— 那个临时目录是全机器共用的，两个服务器同时跑是常态，先起来的
  没资格删后起来那个正在等的输出。

**模式是「声明」，不是「执行」—— 这两件事必须分开做。** 第一次实测就撞上了：一个在 tools mode 下
跑了半天的会话被切成 code mode，模型**连着调了 165 次 `bash`**，而每一次都跑成功了 —— 因为
`execute_tool` 以前只看消息里写的名字，从不检查这个名字是不是本轮声明的。provider 不会替你挡：
schema 里没有的名字，它照样会让模型发出来。所以判定落在**唯一会真的去执行的地方**
（`agent/driver.mbt`）：本轮工具集里没有这个名字，就直接回一条可以被模型改的拒绝，**什么也不跑**
（也因此在它之后才有 job 记录、`tool_calls` 计数也不涨）。

拒绝的措辞是提示文本，不是错误消息 —— 它同时回答「这轮有什么」和「这事该怎么做」：

```
Refused: this turn has no tool named `bash`, so nothing ran. This turn's tools are `exec`, `wait`.
A shell command goes in `exec`'s `bash` field.
```

**同一个工具，两种叫法，是工具的错不是模型的错。** code mode 的 `exec` 用 `bash` 字段，tools mode
的 `bash` 工具用 `command` 字段。一个在 tools mode 跑了很久的会话切到 code mode，历史里全是 `bash`
调用，模型就会一直写 `{"command": "…"}` —— 实测一个会话 28 次，每次白跑一个来回（看懂拒绝文案、
改成 `bash`、重发）。所以 `command` 现在作为 `bash` 的同义词被接受：`command` 只能指 shell 命令，
没有歧义，拒绝它不教任何东西。schema 的 description 一个字没动 —— 那是缓存前缀，改它等于让所有已
存在的会话重付一次前缀的代价。字段名真写错时（`cmd`），拒绝会把收到的键名念出来。

**为什么会有模型去调一个没声明的工具？** 因为它自己的历史。那次 165 次 `bash` 的会话是**被恢复**
的：上一轮的对话里全是 `bash` 的调用和结果（模式是逐轮生效的）。对照实验：同样 code mode 下
**新建**会话，模型第一次就用了 `exec`。所以除了拒绝，还提前说一句：system prompt 里多一段
`## Tools changed`，只在「对话里出现过的工具 ≠ 本轮的工具」时非空 ——

- 只从**模型看得见的对话**（`Session::context`）里找，所以一次压缩把旧调用抹掉之后，这段话也跟着
  消失，不会一直挂着；
- 没有任何陈旧工具时它是**空串**，这一点是承重的：prompt 就是缓存前缀，一段无条件出现的文本会让
  每个已存在的会话在升级后重新付一次前缀的价钱；
- 它排在最后一段，因为那是刚变成真的事实。

实测这段提示起作用的证据：在同一个被恢复的会话上，模型这次**第一次调用就是 `exec`**；再让它
「用名叫 bash 的工具跑一条命令」，它用 `exec` 的 `bash` 字段跑了，并回了一段说明 —— **「`bash` 是
字段名，不是工具」**。

System prompt 跟着模式换。「工具」那一节是从声明生成的，所以不会列出没有声明的工具；「怎么
干活」那段也换 —— 八个工具那段里的「只读一个文件时 `read` 更便宜」，在 code mode 下是在描述
一个不存在的工具。两处由同一个 `ToolMode` 决定，turn 开头读一次、同时喂给 prompt 和 schema，
所以不会出现「提示词说有一个工具、请求里没有」的错位。

## 会话、工作区、侧边栏

**会话可以命名**：输入框里打 `/name <文字>`（单独打是查看，不会清空）。名字写成 session 格式
里本来就有的 `session_info` 条目，所以跟着日志走，重启后还在，别的读者也读得到。**turn 运行中
拒绝改名** —— 那时 turn 正按自己的 leaf 追加条目，再塞一条会挂在过期的 parent 上，落到没人走
的分支里。命令只拦截 `/name` 一个：把每个 `/x` 都当命令会悄悄吞掉真正的消息（路径、除法、正则）。

**侧边栏列出所有工作区**，不只是当前目录。点开别的目录里的会话会**把 agent 搬过去**。
每个工作区最多列 10 个会话，多出来的折成「Show N more」，**上限是为了不重放整个 store**，
所以它落在渲染那层而不是 store 那层。

侧边栏最上面一行可以**添加工作区**，只有一种方式：能弹选择框的宿主机上是一个按钮（macOS 的
`choose folder`），弹不出的宿主机上是一个路径输入框。**按能力二选一，不是两个入口并排**：
知道路径的人在选择框旁边多看到一个框，只会想「这两个有什么区别」。一个还没有任何会话的目录也是
工作区（此前由「store 里有会话」推断，于是刚添加、还没用过的项目会消失）；工作区记在自己的
`workspace.json` 里，删掉目录就忘记了它，不会出现「注册表和磁盘不一致」。

工作区的身份（cwd）**从会话 header 读，而不是从目录名反解**：编码把分隔符都换成 `-`，
`--a-b--` 既可能是 `a/b` 也可能是单个目录 `a-b`，猜错就把 agent 搬到一个不存在的地方。

**删掉会话后的「Undo」过一会儿自己消失**（macOS 上是 12 秒）—— 那是善意而不是控件，读者
已经做完决定。实现的规矩是「新鲜度是状态的一部分」：删除时把时间戳记下来，渲染和**执行**都问
同一个 `still_undoable`，所以一个挂着很久的窗口重放这个请求不会凭空恢复一份被有意删掉的会话。
名字、时间、指针位置这些布局细节见 `macos/README.md`。

## 设置、工作区指令、skill

设置面板装什么由一个问题决定：**运行中的进程能不能兑现它？** 能兑现的才可改 —— 一个看起来能改
的表单只是在撒谎。可改四件：**turn limits**（每轮调用数、花费上限与时长上限）、**api key**
（只回指纹 `sk-4…2e36`，key 本身从不跨过那条边界）、**skills**（整份提交）、**instructions**
（工作区 `AGENTS.md` 的预览 + 一份后备文本）。其余（模型、store 路径）只展示，因为它们在启动时
就定了。

两种优先级的**方向是相反的，而且都是刻意的**：key 是**环境变量 > 面板**，因为 `DEEPSEEK_API_KEY`
是读者正看着的 shell 里设的，几个月前存过一次的值不该悄悄压过它；上限是
**flag > 面板 > 默认**，因为 `--max-cost 0.10` 本身就是这次运行敲下的硬帽，让存过的五美元覆盖
它等于把安全边界变成建议。共同点是：意外的那一种要**说出来** —— flag 钉住的那一项在面板里只读，
保存时明确回一句「已保存，但 `--max-cost` 仍然生效」。默认值是 placeholder 不是 value：空 =
没有意见，把 200 填进框里就把它固化成了「读者设的 200」。

**工作区指令**（`AGENTS.md`）只有两条规则：工作区有就用它，没有就用设置里那份**后备**。
后备是**二选一而不是追加** —— 仓库自己的文件才是「在这个仓库里怎么干活」的更具体的权威，两份
拼在一起只会让读者去猜哪句话赢了；后备存在 `~/.wei/settings.json`，**跟着人而不是跟着仓库**，
所以「我一贯的偏好」放在那里是诚实的，不用提交进别人的 checkout。**只读工作区根目录那一个文件，
不向上走**：往上遍历是这个设计开始变贵的地方（哪些目录算数、两个都有怎么办、仓库外面的算不算），
而且会让 prompt 的内容取决于 checkout 恰好躺在哪里。**每轮重读，不缓存** —— 换来的是改完下一轮
就生效，而缓存恰好会让这件事不发生。**按磁盘上的原样发送**，只用首尾空白判断它说没说话：把仓库
里的文件改写一遍再塞进 prompt，是那种会让读者从此不信任每一个 diff 的悄悄编辑。

**skill** 从工作区与全局发现，按名字记账，所以同名两份一起生效、重装到别处也不失效；已经不在
磁盘上但仍处于关闭状态的名字照样列出来并标注 `no file found`，否则关掉又删掉的 skill 就再也
开不回来。

## 用量与上下文

**输入框下方那排数字说清整个会话**：token 进出、cache 读、总花费、上下文占用；模型下拉框在这一
行上。cache chip 同时给出**缓存命中率**（`cache 12.3k · 87% hit` =
`cache_read / (input + cache_read + cache_write)`）。部分命中**绝不四舍五入成 100%**：整数位会读成
满命中时自动补小数（`99.9`、`99.95`、`99.998`…），用整数运算移植 dsh 的 `formatCacheHitPercent`，
保证各后端一致。数字来自日志，所以重启前后一致，而且**已被压缩替代的那些调用仍然计入** ——
钱已经花了。

**每一轮的回答结尾带一行本轮用量**：同一批数字，但按「轮」给。会话累计会把冷启动和压缩摊平，
看不出某一轮是不是把前缀缓存打掉了；本轮命中率才是读者能据以行动的数字。

**上下文占用是锚定出来的，不是估出来的。** 它是唯一会影响「接下来发生什么」的数字 —— 和压缩
阈值比较，接近时 chip 变红。纯启发式（字符数 ÷ 4）在两处是错的，都是拿真实会话量出来的：
平均只有 provider 真实计费的 **83%**，而且**完全没算固定开销**（系统提示 + 7 个工具 schema
≈ **1,314 token**，每个请求都有）—— 一句 `hi` 的对话因此显示 `~10 tokens` 而真实请求是
~1,300。所以改成锚定：**provider 报的 prompt 大小是已知事实**，只有锚点之后新增的部分才估：

```
next ≈ 上次真实 prompt_tokens + estimate(此后新增内容)
```

同一批会话上 **平均相对误差 17% → 0.2%**（7,510 个样本）。压缩阈值也用这个数：阈值是硬边界，
拿低 20% 的数去比会**压缩得太晚**，而太晚的代价是请求直接超窗被拒。tooltip 会说明这一眼是
`measured` 还是 `estimated`。

**这排数字按「每次模型调用」更新，不是按「每轮」。** 一次 19 次调用的轮次里，读者否则一直盯着
上一轮的旧数字直到整轮结束 —— 而那正是他最想知道「这轮花了多少、窗口还剩多少」的时候。
driver 每写一次日志就报一次（`on_commit`），把**日志当时的样子**交出去。代价是每次提交都重算
chips，而 context chip 要算固定开销，于是顺带重读一次 `AGENTS.md`（一轮几次，每次毫秒级）。
事件只发给**正在显示这个会话**的宿主（每条事件带 `session`，见「宿主边界」）。

## 压缩与瘦身

顺序是固定的：**先瘦身，再压缩**。

| | 瘦身（`core/trim.mbt`） | 压缩（`core/compaction.mbt`） |
|---|---|---|
| 做什么 | 裁掉旧工具输出的中段、清空旧思考 | 把旧历史交给模型总结 |
| 代价 | 免费 | 一次 API 调用 |
| 可逆 | **是**（原始内容还在，重读即可） | 否 |

阈值由模型窗口推导。`deepseek-v4-flash` 的窗口是 1M token，阈值因此是 98 万 —— 日常几乎不会
触发，所以这条链路是用 40k 窗口在测试里验证的，而不是等线上触发。压缩写成一个 `compaction`
entry 带 `first_kept_entry_id`：**被替换的内容仍在文件里**。

**摘要回放必须带 `<summary>` 包装**，而且有个不显眼的前提：**请求构造器根本不认识
`compactionSummary` 这种消息，喂给它会被静默丢掉**（实测：请求体里那条消息直接消失，不报错）。
所以转换必须发生在请求构造之前（`ContextMessage::to_message`）。包装字符串是从 upstream 的
`convertToLlm` 捕获的，不是手写的 —— 这正是那种会被人「顺手改整齐」的字符串。

**瘦身对前缀缓存的净收益只量出来一次，结论是「维持现状」**（数字见「实测过的性能账」）：裁剪省下约
$0.95 的 cache-read，而它改写已发送内容造成的重发约 $0.60，净赚 $0.35。试过「没超过压缩阈值
就不裁剪」的版本，算完是**亏的**，回退了。

## 后台任务与停止

`bash` 可以留下还在跑的东西（`npm run dev &`），侧栏的 Background 面板让它可见、可停：每行是
一个进程组，带自己的输出尾巴。进程按**会话**记账，超过每会话上限就拒绝新的后台命令并让模型
先清理 —— 「再起一个后台任务」不能变成积累没人数的进程的方式。

一个 turn 是单 worker 串行执行的，所以一个卡住的 turn 会让后面所有请求排队到进程结束。三处
防护：模型两条流（等响应头、等每块数据）各有 **120 秒空闲超时**（按「每次等待」而不是「整个
请求」计时，慢但有进展的响应永远不会被掐断）；turn 自己有三个上限；按停止会把正在跑的工具
一起杀掉（进程组，`subtree` + `kill_pids`）。

**被守卫停下的 turn 会在日志里写下来为什么。** 这是重载后唯一看不到的东西：被成本上限停掉和
正常跑完，在消息里长得一模一样。所以终点追加一条 `custom` 条目
（`{"customType":"turn-outcome","data":{"ending":"round_limit",…}}`）。选 `custom` 而不是往
assistant 消息加字段，是因为消息格式是 upstream 的、有别的读者，而「这一轮怎么结束的」是**本 agent
怎么跑的**这一事实；`custom` 也不回放给模型。输出被截断（`finish_reason: length`）同样记 ——
那是最容易被误导的一种：turn 正常结束，别处看不出回答没写完。**正常跑完不写任何东西**。

## 宿主边界：事实，不是标记

`macos/` 是原生 macOS 壳（SwiftUI + AppKit），驱动同一套 `core` / `platform` / `agent`。它的意义
不只是一个新界面，而是**把「谁拥有视图」这条边界换了一种切法**：

```
macos/appffi/  host 拥有视图 → 线上跑事实（这段文本来了、这个工具开始了、这一轮结束了）
```

跨过 C 边界的是**事实**而不是标记：宿主知道一行对话长什么样，壳只告诉它发生了什么。这一刀就是
「事实属于谁」那条判据 —— 关于对话的事实（金额格式、图片是否合法、用量、是否被压缩、上一轮是否
中断）在壳里，一份；关于**这个窗口**的事实（滚动位置、折叠、焦点、拖拽悬停）在宿主里，不上线；
两个方向都依赖的不变量（流式行 id 跨轮唯一）写在一处，并在**坏了会丢数据的那一侧**强制。

`appffi/ffi.mbt` 导出的是一份不长的事件表：`ready` / `sessions` / `session` / `history` / `settings` /
`models` / `images` / `usage` / `user` / `reply` / `thinking` / `tool` / `status` / `end` / `error` /
`jobs` / `note`。它们是事实而不是绘制指令 —— 说发生了什么，不说该怎么画。**每条属于某个会话的
事件都带一个 `session`**（空 = 屏幕上那个），因为一个进程里可以同时有几轮 turn 在跑，主人得知道
一条 delta 该写进哪份转录。

`models` / `images` / `usage` 是输入区带来的，形状都是「整份事实」：模型清单（含能不能看图）、
待发附件（含缩略图要用的 base64）、本会话用量与上一轮的花费。`settings` 是面板真正需要的东西：
技能清单（含已被关掉、文件已不在的那些）、在生效的 fallback 指令及其来源、三个回合上限各自的
值与来源。附件只传**路径**，读文件、判格式、判大小都在壳里，和 `read` 工具共用同一套判断。

`jobs` 是后台任务面板那条：还在跑的 job（id、标签、状态、活了多久、仍活着的 pid、属于哪个
会话），壳每两秒读一次进程表，一次读同时服务「面板显示什么」和「哪个 job 的进程都没了」。

`note` 是压缩那一行：一个 `Compaction` 条目替换掉读者自己说过的话，而线上别的东西都不会说这件
事，所以它是一行（发生在对话里的那个位置），不是一个状态行。`name` 是它的标签（「context
compacted」）—— 没有标签的 note 就是一段被当成回答读的正文；历史上（`history`）的压缩也补上了
同一个标签。

命令方向是 `/model` / `/attach` / `/attach-temp` / `/detach` / `/attach-clear` / `/usage` /
`/jobs` / `/job-kill` / `/rename` / `/restore` / `/skill` / `/instructions` / `/limits`，加上两个
裸词 `continue` / `dismiss` —— 中断的回合的两条出路。`attach-temp` 是粘贴板那条：剪贴板里只有
字节没有路径，宿主写一个临时文件，壳读完删掉（宿主删会和读抢，读发生在 agent 线程上）。这里有
一条硬规则：**认不出的命令词一律当 prompt，但「命令词少了参数」不行**。`/restore`
曾经落进最后那个分支被当成问题发给模型，所以每个带路径的命令都有一个「光秃秃」的形式，走和参数
不合法同一个分支。技能那条路（`/skill:<name>` 展开、裸 `/skill` 列清单）在壳里闭环，用的是
`core` / `platform` 里的同一份实现，没有新增线上字段。

**线程上有一条硬约束**：`moonbitlang/async` 需要一个线程跑它的事件循环（所有 socket 和定时器），
macOS 需要主线程跑自己的。两者不能是同一个，所以 MoonBit 跑在自己的线程上，事件经 JSON 行回到
主线程。想省掉这个线程的话，`moonbitlang/async` 提供了 `ExternalEventLoop`（GUI 程序接自己的
事件循环，MoonBit 在另一个线程上等）—— 但那是为 SDK 级的宿主准备的，链路更长，这条留作以后。

## 已经拆掉的做法：为什么，和留下的判据

这里的东西**已经试过、也已经拆掉了**。记下来是因为推理的代价很高，删掉等于把学费白交；
照着重做一遍则更贵。其中几条是**否决过的路**，几条是从那条路上剩下来的**判据** ——
按「还值不值得用」区分。

**不写 VDOM / 单页应用。** 曾经的服务器渲染版本里，服务器是文档**唯一**的写者，浏览器端只有不到
100 行 JS，所以客户端和服务器之间**没有**「状态不一致」这种失败模式 —— 这是整套设计里最值钱的
性质。VDOM = 客户端状态 + 一棵虚拟树 + 一次 diff，而上面那条性质正是来自**没有**这两样东西。
现在的原生壳换了切法（宿主拥有视图、线上跑事实），但同一条判据还在：事实属于谁。

**首帧是「可变区域的快照」，不是整页。** 这条写错过一次，代价很高：首帧发整页、客户端又用
`outerHTML` 替换正文容器，浏览器把整个文档的片段塞进 body —— **页面看起来正常、输入框却永久
失效**，而所有字节断言照旧通过。只有真实浏览器能看见这一类问题。

**转义是唯一真正的风险**（输入是模型输出和文件内容）：`Text` 节点永远转义，`Raw` 是唯一逃生口，
且只用于 markdown 渲染器的输出。

**标签是一个类型，不是字符串。** 在旧的 HTML 层里，interface 上唯一编译期查不到的东西是标签名，
而拼错的后果是**静默**的：客户端对找不到目标的 patch 直接丢弃，于是「拼错一个外层标签 = 一个再也
不会更新的区域」。不用「每个标签一个函数」是因为标签名是普通小写标识符，**局部变量会遮蔽它** ——
`for i in 0..<n` 在渲染 `<i>` 的文件里直接编译失败。

最后一条是这里唯一值得抄到别处去的判据：**一类错误会不会静默消失，决定了它值不值得用一个类型
去换。** 标签拼错会静默失效，所以值得；属性拼错是可见的，所以当时就明确只治了前者。

**并行开发两条复刻路线是个错误。** 最早的一条是「复用 pi 内核、只重写界面」（pi 扩展 +
rabbita 前端），它跑得起来，但和服务器渲染那条并列意味着两边都停在半成品，所以删掉了一条。
从它身上留下两条结论：**rabbita 的 HTML DSL 在包外不可用**（`server_side_render` 在
`internal/` 里），**SSE 逐块到达是可依赖的**（预期间隔 120ms，实测 120/121/121/121/121ms）。

## 实测过的性能账

优化都从测量开始，否则很容易在不是瓶颈的地方花力气。

| 路径 | 实测 | 结论 |
|---|---|---|
| 会话数据路径 | 5000 条 entry：20 次 append **12ms**、派生+瘦身 **2ms** | 不需要优化。每次 append 重建索引是 O(n)，但要 5 万条才到拐点 |
| 流式推流 | 一条 700 字回答曾经产生 **13.2MB** SSE | 已修：**13.2MB → 78KB（170×）**。形状是平方而不是「慢」：`SetText` 每帧重发整段累积文本，39KB 的思考 = 599 帧 × 平均 20KB。改成发**增量**后字节线性 |
| 侧边栏刷新 | 20 工作区 × 10 会话 × 64KB：**88–150ms/次**，一轮刷新两次 | 已修：按 `(路径, mtime)` 缓存标签 + 前缀 64KB→16KB：**冷 82ms、之后 17–22ms**。根因是**读+解析整份日志只为找一个可能不存在的名字**：27MB 的 store 里 80% 的耗时是解析而不是读 |
| **瘦身的前缀缓存账** | 3,500 次调用：不裁剪 prompt 总量是现在的 **1.45×**（省约 339M cache-read = **$0.95**）；被改写的调用 **7%**，多付约 **$0.60** | **净赚 $0.35，维持现状**。「没超阈值就不裁剪」的版本算完净亏 $0.36，回退了 |
| **请求前缀（`request_drift`）** | 每轮报告每次请求与上次的共同前缀、从哪条消息开始不同 | 修的是**量尺**：账单里唯一能靠读日志发现、又确实属于我们的浪费是「把已发过的内容改写一遍再发」，而此前日志只有 `usage`（记了什么）没有「为什么」。`moon run wei` 会把它打出来 |

**瘦身那条的教训值得单记**：裁剪的动机是省 token，而 cache read 也是 token —— 省掉的要跟
改写的代价比过才算数。「不要改写已发送的内容」这条设计意图本身**不是结论**。

**`moon build` 默认是 debug**：同一个 `verify.exe`，debug 5.65s vs release 1.17s（4.8×）。
拿 debug 构建比性能会得出反向结论。

**错误信息要带上端点说的话。** 上面那个 400 一开始只知道是「HTTP 400」—— 因为响应体拿到就被扔了。
现在失败信息会带上端点的 `error.message`（解开 JSON 信封、裁到 600 字）：一句
「tool message must immediately follow the assistant message」是能立刻定位的，「HTTP 400」是一个
小时。这不是顺手加的：**可观测性决定排查成本**，而这条线上唯一能说清「哪里不合法」的就是那个字段。

## 已知限制

- **续跑是手动的**，但**断口会被补上**。崩溃后重开会话，转写末尾出现一条带两个按钮的通知
  （Continue / Start fresh），而不是自作主张接着跑：turn 被中断时**正在执行的那个工具的
  结果是未知的** —— 它可能已经改了文件，也可能还没开始。已完成的 call 可以安全跳过（结果就在
  日志里），「结果未知」的那个不能当成成功也不能当成失败。DBOS 的保证建立在 step 是原子的之上，
  我们没有。

  但**「要不要继续」和「能不能发出去」是两件事**。规则不是「每个 tool call 都要有结果」，而是
  **「结果必须紧跟在要它的那条 assistant 消息后面」** —— provider 检查的是**相邻**，不是存在。
  所以驱动在每次请求之前把对话重排成合法的形状（`agent/driver.mbt` 的 `plan_repair`）：

  - 结果在，但离得远（Stop 掐在模型调用中间，读者随后又打了字，于是结果落到了新提问后面）→
    **搬过去**，用原来的 id，不复制（重复的 `tool_call_id` 同样会被拒）；
  - 结果根本不存在 → 补一条合成结果，写明「结果被记录之前就中断了，只读或幂等的操作才重试」；
  - 没碰到的条目原样保留，所以一份本来就合法的日志跑完这个函数一个字节都不变。

  实测的坏形状长这样，而它在日志里**看起来是完整的**（结果就在末尾，`needs_repair()` 会说「没事」）：

  ```
  assistant(tool_calls: exec "")            ← 要工具
  turn-outcome(stopped)                     ← turn 关了
  user("继续吧")                             ← 读者又打字了
  turn-start("继续吧")
  tool("The tool call was interrupted…")    ← 结果在这儿，晚了三条
  ```

  一份这样的日志，**每一次请求都会被拒**（HTTP 400），而且拒在第一个条目写下去之前，所以日志里
  连「失败了」都看不出来。补的是**协议**要求的那一块，不是替读者决定要不要重跑那个工具。
- **工具执行没有审批**，也**不是沙箱**：`bash`、`write`、`edit`、`script` 直接执行。把一个
  目录加为工作区只是让 agent 在那个 cwd 里跑工具，它仍然能用绝对路径读写任何它有权访问的
  地方。`script` 的 native 执行与 `bash` 同级信任（见「工具」一节）。
- **内置 script 是四个**，且只有 `check`/`test`/`search`/`read`。常用的命令（`git`、`npm`）
  仍是原始文本进对话。
- **code mode 是取舍不是增强**：`note` 没有替代（跨压缩的事实记录消失），图片读入
  只剩 `cat` 一个 png 的结果，`wait` 也读不到上一次运行留下的输出文件。见「code mode」一节。
- **切模式会让「旧工具名」在历史里留一段时间**：模式逐轮生效，所以刚切换后的对话里还躺着上一个
  模式的调用，模型有概率照抄（实测：被恢复的会话里 165 次 `bash`）。现在会拒绝 + 提前提醒，但
  真正的解法是**新会话**；旧会话越干净地切换，代价越小。
- **工作区指令不向上查找**：只有会话自己那个 cwd 里的 `AGENTS.md` 算数，上级目录一律不读，
  也没有总字节预算。
- **文件夹选择框只在宿主机有桌面会话时出现**（目前只写了 macOS 的 `osascript`）。SSH、容器里
  只有路径输入框。放在宿主侧是必须的而不是偏好：进程需要**绝对路径**，而选择器给的是不透明
  的 handle。
- **工作区不能改名或排序**；**会话列表没有搜索**，顺序就是 mtime 倒序 —— 会话一多，「记得
  名字、找不到」就是下一条该修的。
- **「Show more」记在进程里，不落盘**：重启回到 10 个。真要做，该存的地方是宿主的偏好，
  不是 store —— store 记的是对话，不是窗口的样子。
- **没有图片**：`Image` 内容会被降级成占位文本；**不做流式渲染 thinking**（思考默认只露最后
  三行，实时渲染成 markdown 等于把读者不该读的文本按「已经在读了」的规格排版）。
- **thinking 档位是进程级的**，会话级模型已经是每个会话独立的。
- **两个实例可以同时写同一份会话文件**：`Open.turns` 那把锁只管**本进程内**，交错写在磁盘上
  是会发生的（`docs/macos-pitfalls.md` 记了这条）。
